# ADR 架构决策记录 — 格式与规则

## 三条件过滤

仅当以下三项条件**全部满足**时，才创建 ADR：

| 条件 | 说明 | 不满足时的做法 |
|------|------|--------------|
| 难以逆转 | 改变决策的成本有意义，改主意代价高 | 记录在 detailed-design.md 即可 |
| 缺上下文会奇怪 | 未来读者会问"为什么这么做？" | 记录在 detailed-design.md 即可 |
| 真正做了权衡 | 存在真实的替代方案，选了其中一个有具体理由 | 记录在 detailed-design.md 即可 |

## 每变更 ADR 上限

| 变更类型 | ADR 上限 | 说明 |
|---------|---------|------|
| 功能需求级变更 | ≤ 2 个 | 常规功能变更 |
| 产品级变更 | ≤ 5 个 | 大型产品变更 |
| 功能缺陷级变更 | 0 个 | 通常不创建 ADR |

超出上限时 SHALL 提示用户变更粒度过大，建议拆分为多个变更。

## ADR 序号管理

1. 读取 `docs/adr/` 目录现有 ADR 文件
2. 取现有最大序号 +1 作为新序号
3. 文件名格式：`{4位递增序号}-{kebab-case标题}.md`（如 `0003-choose-redis-cluster.md`）

## ADR 文件格式

```markdown
# ADR-{序号}: {标题}

**日期**: YYYY-MM-DD
**状态**: 提议 | 接受 | 废弃 | 取代
**过期条件**: {何时应重新评估此决策}

## 背景
{当前场景描述和需要决策的技术问题}

## 决策
{选定的方案和具体理由}

## 后果
{决策带来的正面、负面和中立影响}

## 替代方案
{考虑过但未采用的其他方案及原因}
```

## 过期条件

每个 ADR SHALL 标注何时重新审视：

| 过期条件类型 | 示例 |
|-------------|------|
| 数据量阈值 | 数据量 < 10GB 持续 6 个月 → 重新评估 |
| 团队规模 | 团队规模 > 20 人 → 重新评估微服务拆分 |
| 技术里程碑 | 数据库升级到 v14 → 重新评估分区策略 |
| 时间期限 | 2026 Q3 → 重新评估当前消息队列方案 |

## ADR 索引更新

创建 ADR 后更新 `docs/adr/index.md`：

```markdown
# ADR 索引

| ADR 序号 | 标题 | 创建日期 | 状态 | 涉及变更 |
|----------|------|---------|------|---------|
| 0001 | 选择 Kafka 作为消息队列 | 2026-05-09 | 接受 | add-user-auth |
```
