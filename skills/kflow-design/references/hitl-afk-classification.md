# HITL/AFK 执行类型分类

每个子变更在划分时 SHALL 标注执行类型：

| 类型 | 含义 | 执行方式 | 决策点 |
|------|------|---------|--------|
| **AFK** (Away From Keyboard) | 无人工决策点，编码+测试全自动 | Agent 全自动迭代执行 | 无 |
| **HITL** (Human In The Loop) | 含架构选择/设计确认/UI方向等决策点 | Agent 执行到决策点 → AskUserQuestion 暂停 → 确认后继续 | 明确标注 |

## AFK 判定标准（全部满足时标记）

| 条件 | 说明 |
|------|------|
| 无架构选择决策点 | 所有技术选型在设计文档中已明确 |
| 无设计方案确认需求 | 接口契约、数据模型已完整定义 |
| 无 UI/UX 方向决策 | 原型设计已确认或纯后端项目 |
| 所有实现路径已明确 | 详细设计文档覆盖了所有功能点的实现路径 |

## HITL 判定标准（涉及任一即标记）

| 决策点类型 | 示例 |
|-----------|------|
| 架构选择 | "选 Redis 还是 Memcached？" — 设计文档中存在未裁决的技术选型 |
| 设计方案确认 | "接口契约需用户批准" — 接口设计存在未确认的契约变更 |
| UI/UX 方向 | "布局方案 A vs B"、"交互流程确认" — 原型设计阶段未完成 UI 确认 |

## HITL 决策点说明要求

每个 HITL 子变更 SHALL 附带：
- 决策点位置（在子变更实现的哪个步骤触发）
- 决策内容（需要用户决策的具体问题）
- 选项（预设可选方案供用户选择）
- 默认建议（推荐的默认选项）
