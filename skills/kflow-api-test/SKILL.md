# 角色

子变更级接口单元测试执行器。使用 curl/HTTP 请求对 api-tests/ 中定义的接口逐条测试。所有项目类型的必须阶段；轻量档下按阶段适用性声明条件适用。服务生命周期由变更级 agent 独占管理，本 agent 为纯消费者。

> ⚠ **子代理强制规则**（参见 skills/kflow-api-test/references/repetition.md §12）:
> 1. 本阶段主工作 MUST 通过 Agent 子代理执行，主 Agent 仅负责调度和验收
> 2. 主 Agent SHALL NOT 直接执行本阶段主工作，无例外
> 3. 子代理 SHOULD 前台运行（推荐 `run_in_background=false`），后台模式仅在权限已预配置时使用
> 4. 适用场景：直接触发 + triage 路由 + 其他 Skill 调用
> 5. 后台子代理权限失败时 SHALL 创建新的前台子代理重新执行，主 Agent SHALL NOT 直接接管（参见 §12.7）

# 任务

门控检查 → 确认项目类型 → 等待变更级服务就绪 → 执行 API 测试用例 → 健康评分数据采集 → 缺陷修复路由 → 输出测试报告 → 更新状态 → 下一子变更 → 前后端项目进入 E2E 测试 / 纯后端项目进入集成测试。

# 门控检查

进入接口单元测试阶段前检查：
- `.status.md` 存在
- 编码状态 = ✅ 完成（含代码审查通过）
- 代码审查状态 = ✅ 完成（kflow-code-review 通过）
- 子变更代码审查报告存在 (`test-reports/review/code-review.md`)
- `api-tests/` 测试用例文档存在
- `docs/service-guide.md` 存在（服务启动配置可用）

# 阶段适用性入口门控

> **机制说明**：四态判定矩阵参见 `skills/kflow-api-test/references/gates.md` §1.2，声明字段参见 `skills/kflow-api-test/references/state-values.md` §5，钩子豁免参见 `skills/kflow-api-test/references/hooks.md` §1。

> **适用范围**：仅 `变更档位 = 轻量` 适用；`标准` 档 SHALL NOT 应用，阶段集合维持既有规则。纯后端项目跳过 E2E 的既有规则与档位无关，按项目类型优先判定。

本门控 SHALL 在执行流程入口（PRE_HOOK 之前）读取变更级 `.status.md` 的「阶段适用性声明」区中的「接口单元测试」条目，并按「声明 × `api-tests/` 产物存在性」四态判定：

| 声明 | `api-tests/` 产物 | 判定 |
|------|------------------|------|
| `⏭️ 不适用` | 不存在 | 合法跳过，放行 |
| `⏭️ 不适用` | 存在 | ❌ 阻塞，提示声明与产物不一致 |
| `✅ 适用` | 不存在 | ❌ 阻塞，输出缺失产物清单 |
| `✅ 适用`（或声明区缺失） | 存在 | 通过，继续本阶段 |

- 声明 `⏭️` 但无判定依据 → ❌ 阻塞，提示缺失裁剪依据；`⏭️` SHALL NOT 由产物存在性或缺省值推断
- 声明区缺失（历史变更、非轻量档）→ 按 `✅ 适用` 处理

**裁准时**（声明 = `⏭️ 不适用` 且 `api-tests/` 不存在）：本阶段 SHALL NOT 执行——SHALL NOT 启动测试子代理、SHALL NOT 执行 PRE_HOOK/POST_HOOK（不启动服务、不做服务刷新、不清理浏览器）、SHALL NOT 产出阶段产物；直接放行至下一阶段（前后端项目 → `kflow-e2e-test`；纯后端项目 → `kflow-integration-test`）。阶段状态由 `kflow-design` 在写入声明时一次性标记为 `⏭️ 不适用`，`traceability.md`「接口测试」列整列填 `⏭️`、不计入覆盖率分母。

# 项目类型判断

| 项目类型 | 阶段处理 |
|---------|---------|
| 前后端项目 | 必须执行接口单元测试阶段（作为 E2E 测试前置）；轻量档下条件适用 |
| 纯后端项目 | 必须执行接口单元测试阶段（作为最终验收标准）；轻量档下条件适用 |

纯后端项目不再跳过接口单元测试。`kflow-api-test` 对所有项目类型必须执行；轻量档下按阶段适用性声明条件执行（判为 `⏭️ 不适用` 时跳过并直接放行至下一阶段）。

## 状态双写规则

阶段完成、回退与重执行时，主 Agent SHALL 同时执行两处写入：

1. **追加历史**：向 `docs/changes/{change}/status-log.md` 追加本次事件——阶段名、轮次、完成时间、耗时、终止结果；回退时另记回退原因与目标阶段
2. **刷新当前**：刷新变更级 `.status.md` 的当前状态字段——当前阶段、阶段状态表对应行、执行轮次、终止结果、未决事项

`.status.md` SHALL 保持在 100 行以内，超出部分改为写入 `status-log.md`。变更目录中不存在 `status-log.md`（历史变更未分层）时按既有单文件口径处理，SHALL NOT 强制回填。

> 读取边界：常规阶段推进与门控判定 SHALL 仅读取 `.status.md`；`status-log.md` 仅在中断恢复与审计场景读取。权威定义见 `status-file-layering` 能力。

# 执行流程

```
API 测试阶段流程 (curl/HTTP 驱动):

┌─────────────────────────────────────────────────────────────┐
│                   API TEST WORKFLOW                           │
├─────────────────────────────────────────────────────────────┤
│  0. GATE      → 阶段适用性门控（仅轻量档）                    │
│  │   └── 裁准（声明 ⏭️ 且 api-tests/ 不存在）→ 跳过本阶段     │
│  │       不启动子代理、不执行钩子，直接放行至下一阶段         │
│  1. PRE_HOOK  → CHECK_STATE → RELOAD → 引用                     │
│  │              skills/kflow-api-test/references/hooks.md api-test PRE_HOOK   │
│  2. CHECK     → 门控检查（前置阶段完成检查）                  │
│  3. TYPECHECK → 确认项目类型（前后端/纯后端，均须执行）       │
│  4. WAIT_SYNC → 等待变更级 agent 编译重启完成                 │
│  │   └── 变更级 agent 执行: 停止→编译→迁移→启动→健康检查     │
│  │   └── 收到「服务就绪，开始执行」信号后继续                │
│  5. EXECUTE   → 单轮遍历全部接口用例（curl/HTTP 请求）        │
│  │   ├── 按 api-tests/ 逐条执行接口测试                      │
│  │   ├── 记录 HTTP 状态码、响应体、响应时间                  │
│  │   ├── 验证响应结构与 api-tests/ 定义一致性                │
│  │   └── 记录执行结果（含全量遍历证明）                      │
│  6. EVALUATE  → 评估测试结果 + 健康评分                       │
│  │   ├── 全部通过 → 输出 summary.md                           │
│  │   │   ├── 其他子变更未完成 → 标记 ⏸️ 等待同步             │
│  │   │   └── 所有子变更完成 → 标记完成                        │
│  │   └── 有失败 → 提示进入缺陷修复阶段                        │
│  7. FIX       → (缺陷修复阶段处理，含根因分类路由)            │
│  8. RECHECK   → 定向重验：修复后仅重跑失败用例（不重跑全量）  │
│  9. SUMMARY   → 输出测试总结文档 + 健康评分                   │
│  10. NEXT     → 选择下一个子变更测试（按依赖顺序）             │
│  │   └────────────────────────────────────────────────────── │
│  │   所有子变更测试完成后                                     │
│  │   └────────────────────────────────────────────────────── │
│  11. NEXT_STAGE → 前后端项目 → kflow-e2e-test                │
│  │               纯后端项目 → kflow-integration-test          │
│  12. POST_HOOK → 引用 skills/kflow-api-test/references/hooks.md                  │
│                  api-test 阶段 POST_HOOK                             │
└─────────────────────────────────────────────────────────────┘
```

## 子变更 agent 服务使用约束

> **核心原则**：子变更 agent 为纯消费者，不管理服务生命周期。

- ✅ 子变更 agent 连接已知端口使用服务
- ✅ 子变更 agent 通过 curl 检测服务是否就绪
- ❌ 子变更 agent 不启动、停止或重启服务
- ❌ 子变更 agent 不执行编译或迁移操作

## 服务不可用上报

当子变更 agent 检测到服务端口无响应时：

1. 执行 `curl localhost:{port}` 确认端口状态
2. 如返回 Connection Refused → 立即上报变更级 agent
3. 标记当前测试用例为「阻塞等待服务恢复」
4. 等待变更级 agent 恢复服务后继续

# 健康评分数据采集

健康评分各维度通过 curl 命令采集原始数据：

| 评分维度 | 数据源 | 采集方式 | 评分规则 |
|---------|--------|---------|---------|
| 功能完整性 | 测试用例执行结果 | 统计 ✅/❌ 用例数 | 通过数/总数 × 100 |
| 响应时间 | curl 计时 | `curl -w "@curl-format.txt"` 或 `time curl` | < 200ms 满分，每超 100ms 扣 10 分 |
| HTTP 状态码 | curl 返回码 | `curl -s -o /dev/null -w "%{http_code}"` | 非 2xx/3xx 扣分 |
| 错误处理 | 异常输入响应 | 发送异常参数/缺失必填字段 | 正确错误码+消息体格式 |
| 契约一致性 | 与 api-tests/ 定义对比 | diff 响应结构与预期 schema | 响应结构匹配度 |

# 崩溃恢复

当 API 测试过程中服务崩溃时：

```
崩溃恢复流程:

1. DETECT    → 子变更 agent 检测到 curl localhost:{port} 返回 Connection Refused
2. REPORT    → 立即上报变更级 agent
3. MARK      → 标记当前测试用例为「阻塞等待服务恢复」
4. RESTART   → 变更级 agent 执行编译重启流程
              (停止→编译后端→编译前端→迁移→启动后端→启动前端→健康检查)
5. RESUME    → 健康检查通过后变更级 agent 通知子变更 agent 继续
6. CONTINUE  → 子变更 agent 从断点测试用例继续执行
```

# 单轮全面执行（执行类阶段）

接口单元测试阶段属于**单轮类执行阶段**，采用**单轮全面执行 + 定向重验**模式（参见 `skills/kflow-api-test/references/repetition.md` §14.2）：

- **单轮全量执行**：子代理在一轮内遍历 api-tests/ 全部接口用例执行完整流程，SHALL NOT 执行第二轮全量审查。
- **定向重验**：发现失败项时，仅在修复后**重跑失败用例**，不重跑全量；属**有界重试**，SHALL NOT 使用轮次循环判据或预设轮数。定向重验与已移除的 `recheck-round`（审查循环到达终止点后追加的复核轮）语义不同，命名 SHALL NOT 混用。
- **档位来源**：读取变更级 `.status.md` 基本信息的「变更档位」字段（缺失或读取到历史遗留的 `完整` 取值时按 `标准` 档处理）。变更档位 SHALL 只决定**审查形态与产出深度**，SHALL NOT 决定执行轮数。
- **审查范围冻结**：主 Agent 从阶段产物既有内容生成审查对象集合并冻结，审查维度限于本阶段枚举；冻结范围之外的发现降级为「范围外观察」——不改产物、不计入执行发现数，记入执行报告的「范围外观察」小节（为空时记「（空）」）。
- **回退重执行**：SHALL NOT 预置或提高执行轮数；「最近修订信息」的受影响项清单仅供验证门控的「受影响项 100% 覆盖」使用。

> **权威定义**：单轮类阶段的执行模型、定向重验与审查范围冻结唯一定义于 `agent-iteration-execution` 能力，本 Skill 仅引用，SHALL NOT 自行定义轮次数值或终止条件。接口单元测试/E2E 测试/集成测试三阶段 SHALL NOT 使用重复制类阶段的跨轮摘要注入机制（`repetition.md` §13 对该三阶段不适用）。

## 单轮工作内容

**遍历项**：api-tests/ 全部接口用例

**单轮流程**：
1. 遍历全部接口用例，逐条 curl/HTTP 执行：
   - 发送 HTTP 请求
   - 记录 HTTP 状态码、响应体、响应时间
   - 验证响应结构与 api-tests/ 定义一致性
2. 失败的用例记录后进入修复流程（定向重验仅重跑失败用例，已通过用例不重跑）
3. 采集健康评分数据（功能完整性/响应时间/HTTP状态码/错误处理/契约一致性）

**执行报告**：`test-reports/api/round-{n}.md`（N 为执行轮次：首次全量执行为 `round-1.md`，每次定向重验递增；含全量遍历证明、失败用例清单、范围外观察）

**定向重验后**：更新 .status.md `执行轮次` 字段为当前轮次号

## 复杂度评估

复杂度评估仅信息展示，不驱动执行行为：

```
复杂度分 = 接口数 × 1.5 + 场景数 × 2

低复杂度 (< 20 分) / 中复杂度 (20-50 分) / 高复杂度 (> 50 分)
```

分级阈值保留但仅用于信息分类，复杂度分写入 .status.md 备注列标注「仅供参考，不驱动执行行为」。复杂度不参与执行决策——单轮类阶段的执行轮数为 1（定向重验次数另计），迭代终止由定向重验全部通过或连续 3 次定向重验未通过决定。

## 执行流程

```
1. 复杂度评估 → 写入 .status.md 备注列（仅信息展示，不驱动执行行为）

1.5 INIT → 主 Agent 写入 .status.md 执行轮次为 1 轮（单轮全量；参见 references/repetition.md §14.2）
    └── 判定流程: 单轮类阶段执行轮数为 1——读取变更级 .status.md「变更档位」字段仅用于确定审查形态与产出深度；回退重执行时读取「最近修订信息」的受影响项清单供验证门控使用，SHALL NOT 用于推轮次

2. 构建阶段专属提示词
   ├── 分层加载（基础层 + 执行层 + 服务层）:

   │   ├── skills/kflow-api-test/references/state-values.md（摘要）
   │   ├── skills/kflow-api-test/references/gates.md（当前阶段相关门控）
   │   ├── skills/kflow-api-test/references/repetition.md
   │   ├── skills/kflow-api-test/references/service-lifecycle.md
   │   └── skills/kflow-api-test/references/hooks.md（服务相关章节）
   ├── 输入: api-tests/ + detailed-design.md + service-guide.md
   ├── 本子代理承担的测试范围: {api-tests/ 用例区间}（单个子代理 ≤ 3 个功能点对应的接口用例；超出时先分片再构建 prompt，前一片落盘后启动后一片承接）
   ├── 测试执行要求 (curl/HTTP 驱动)
   ├── traceability.md 待填充列: 接口测试(ID)
   ├── 覆盖率目标: 100%
   ├── 单轮执行指令: 「在一轮内遍历全部接口用例执行完整流程，完成后返回执行报告。发现失败项时按定向重验处理——仅重跑失败用例，不重跑全量。审查对象集合已冻结，SHALL NOT 审查清单之外的文件或内容、SHALL NOT 新增审查维度、SHALL NOT 借审查之名新增功能点/字段/章节/分支。冻结范围之外发现的问题 SHALL 记为『范围外观察』，不改产物、不计入执行发现数、不触发重跑。」
   └── 完成承诺: COMPLETED

3. 启动 Agent 子代理 (Agent(description, prompt, run_in_background))
   └── 子代理内维持现有 curl/HTTP 驱动测试流程

4. 定向重验（发现失败项时）
   └── 修复失败项后仅重跑失败用例（不重跑全量）；每次定向重验后更新 .status.md `执行轮次` 为当前轮次号；连续 3 次定向重验未通过 → 终止结果 `定向重验失败`

5. 主 Agent 验收
   ├── 执行报告: test-reports/api/round-{n}.md 完整（含全量遍历证明）
   ├── 审查范围: 未引入冻结审查对象集合之外的新内容；越界 → 拒收并要求在冻结范围内重审
   ├── 产物: round-{n}.md + summary.md
   ├── 覆盖率: traceability.md「接口测试」列覆盖率 = 100%
   ├── 定向重验: 全部通过（无失败项视为满足）
   ├── 健康评分: 各维度评分已采集
   └── 无占位符: 无 TODO/TBD/{待填写}
```

## 验收结果处理

- **通过** → 更新 .status.md（写入终止结果 `执行完成` 并更新「阶段耗时与轮次统计」区）+ 填写 traceability.md「接口测试」列 → 释放下一阶段门控
- **执行报告缺失/不完整或覆盖率未达标** → 拒收，直接重新启动 Agent 子代理执行剩余工作，不进入 AskUserQuestion
- **引入范围外新内容（越界）** → 拒收，要求子代理在冻结范围内重新执行，不进入 AskUserQuestion
- **定向重验连续 3 次未通过；或产物不合格** → 进入升级分支：记录 skill-suggestion.md（含阶段、轮次、失败用例清单、建议）→ AskUserQuestion 询问「定向重验连续失败，是否调整修复方案后重试？」；用户选「否」→ 标记 ⚠️ 阻塞并终止当前阶段

> **终止结果**：阶段终止时 SHALL 在 .status.md 写入终止结果，取值 `执行完成` / `定向重验失败`；`执行轮次` 字段格式为 `{N} 轮`（无分母；单轮全量为 1，定向重验后累计）；`定向重验失败` 须在 `docs/skill-suggestion.md` 留有对应的升级记录。

## 阶段衔接

验收通过并更新 `.status.md`（终止结果 `执行完成`）与 traceability.md「接口测试」列之后，SHALL 执行**阶段衔接决策**并直接调度目标阶段 Skill：按 `skills/kflow-api-test/references/phase-transition.md` 的决策表判定目标阶段状态，按调度映射表定位目标 Skill。系统 SHALL NOT 提示用户输入推进指令（如「继续 {change-name}」）作为进入下一阶段的条件；决策表、调度映射与停止条件的唯一真源为该文件，本 Skill SHALL NOT 内联其内容。

本阶段为**子变更级**，衔接分两层（参见 `skills/kflow-api-test/references/phase-transition.md` §4）：

- **子变更内推进**：先在当前子变更内按决策表推进至下一子变更级阶段。
- **跨子变更遍历推进**：当前子变更的全部子变更级阶段完成后，按 `auto-subchange-traversal` 顺序遍历状态为 `🔄 进行中` / `⏳ 待开始` 的子变更，推进至下一个子变更的首个未完成阶段；仅遍历依赖已满足的子变更——被依赖子变更未完成编码与接口单元测试前，依赖子变更保持 `⏳ 待开始` 不参与遍历；轻量档单子变更时退化为直接进入变更级衔接。
- **交回变更级**：最后一个子变更的全部子变更级阶段完成后，衔接决策交回变更级，对下一变更级阶段（集成测试）执行决策表。

阶段自身的人工门控 SHALL 照常执行，SHALL NOT 被衔接决策跳过；自动衔接免除的仅为「提示用户输入推进指令」这一步。

# 常见陷阱

| 序号 | 陷阱 | 错误做法 | 正确做法 |
|------|------|---------|---------|
| 1 | 忽略服务就绪检查 | 门控检查后直接发送请求 | 测试前先 curl 确认服务端口可连接 |
| 2 | 不验证响应体结构 | 仅检查 HTTP 状态码 | 同时验证响应体结构与 api-tests/ 定义一致 |
| 3 | 遗漏异常输入测试 | 仅测试 Happy Path | 按 api-tests/ 逐条覆盖 Error Path 和 Edge Case |
| 4 | 不记录响应时间 | 仅记录通过/失败 | 使用 curl -w 记录各接口响应时间用于健康评分 |
| 5 | 执行报告缺少全量遍历证明 | 仅记录失败用例，未证明全部用例已遍历 | 报告须列出全部接口用例的遍历结果，证明已完成全量遍历 |

# 上下文管理

- **curl 优先于浏览器**：接口测试使用 curl/HTTP 请求，轻量高效，无需浏览器环境
- **单轮执行报告**：一次全量记录全部接口用例的遍历结果与成败状态（含全量遍历证明），不按轮次增量
- **选择性读取**：读取 detailed-design.md 时仅提取当前子变更相关的接口设计章节

# 与其他 Skill 的关系

- **输入来自**：代码审查（`kflow-code-review`，子变更级）
- **输出给**：`kflow-e2e-test`（前后端项目，子变更级）、`kflow-bug-fix`（测试失败时）、`kflow-integration-test`（纯后端项目所有子变更通过时）

- **项目类型**：所有项目类型必须执行
- **执行模式**：单轮全面执行 + 定向重验（一轮内遍历全部接口用例，失败项仅重跑失败用例；参见 references/repetition.md §14.2），终止结果取值 `执行完成` / `定向重验失败`；审查范围冻结 + 范围外观察降级 + 定向重验失败升级；复杂度评估仅信息展示，主 Agent 验收闭环

# 核心提醒

- 所有项目类型必须执行本阶段（前后端+纯后端），纯后端项目不再跳过
- 子变更 agent 为纯消费者，不管理服务生命周期
- 使用 curl/HTTP 请求进行接口测试，轻量高效
- 单轮全面执行（执行轮次为 1）：一轮内遍历全部接口用例执行完整流程，SHALL NOT 执行第二轮全量审查；发现失败项时走定向重验——仅重跑失败用例，属有界重试
- 定向重验全部通过 → 终止结果 `执行完成`；连续 3 次定向重验未通过 → 终止结果 `定向重验失败` 并升级用户（记录 skill-suggestion.md + AskUserQuestion，用户选「否」时可标记 ⚠️ 阻塞）
- 冻结范围之外的发现降级为「范围外观察」——不改产物、不计入执行发现数，记入执行报告的「范围外观察」小节（为空时记「（空）」）
- 执行报告缺失/不完整或覆盖率未达标时拒收并直接重新启动 Agent 子代理；引入范围外新内容时拒收并要求在冻结范围内重新执行
- 覆盖率目标：traceability.md「接口测试(ID)」列 = 100%
