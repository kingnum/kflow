## 1. 概述

> **分层加载说明**：本文件属于「执行层」，仅在执行类阶段（plan/code/code-review/api-test/e2e-test/integration-test/bug-fix）的子代理 prompt 中加载。设计类和归档类阶段不加载本文件。详见 `07-agent-model.md` §17。**例外**：本文件 §13（轮间摘要传递机制）的适用范围已扩展到设计自审 SELFREV，设计类阶段按其 `references/self-review.md` 的引用采信 §13。

执行类阶段的主执行工作统一采用**重复制**模式：子代理每轮遍历全部工作项独立执行完整流程，禁止按轮次分段分配工作重点，通过每轮全量遍历实现自然收敛。创造性阶段（设计探索/原型设计/详细设计/归档/审计）主 Agent 直连执行主要流程，但自审（SELFREV）环节通过子代理串行执行，与 VERIFY 子代理验证机制对齐。

## 2. 重复制核心特征

- **每轮全量遍历**：每轮遍历全部工作项（全部功能点/全部测试用例/全部代码变更/全部子变更任务），不跳过已通过项
- **独立完整流程**：每轮对每个工作项独立执行完整流程（TDD/测试/审查），不跨轮分工
- **子变更自动遍历**：编码和代码审查阶段采用双层遍历——外层遍历全部未完成编码/待审查的子变更，内层对每个子变更遍历其全部功能点/代码变更。禁止仅处理单个子变更后等待用户确认
- **禁止节奏指引**：禁止「前 N 轮重点执行/中间 N 轮细节优化/后 N 轮验证」等分段分配指令
- **收敛驱动终止**：以**见证轮**（零新发现 + 零修改 + 报告证明全维全量遍历）为终止判据，达成即止；未达成则继续至轮次上限
- **终止点复检轮**：到达终止点时，累积未复核修复清单非空则追加 1 轮复检轮（§14.5.1）——不消耗档位轮次预算、全局最多 1 轮，确保任何被记入审查报告的修复都经过独立复核后才允许阶段终止
- **保留强制子代理 + 档位轮次上限（回退取 `max(档位上限, 影响范围分数映射)`）+ 主 Agent 验收闭环**

## 3. 阶段分类

| 类别 | 阶段 | 执行模式 | 说明 |
|------|------|---------|------|
| 创造性阶段 | 设计探索、原型设计、详细设计、归档、审计 | 主 Agent 直连（自审环节除外） | 需要创造性思维和深度上下文理解，主要流程由主 Agent 执行；自审（SELFREV）环节通过子代理串行执行 |
| 执行类阶段 | 计划、编码、代码审查、接口单元测试、E2E测试、集成测试、缺陷修复 | 重复制 | 任务明确可量化，每轮全量遍历全部工作项，独立执行完整流程，收敛驱动终止 |

## 4. 重复制执行流程

```
重复制执行流程:

┌─────────────────────────────────────────────────────────────┐
│              REPETITION MODE WORKFLOW                         │
├─────────────────────────────────────────────────────────────┤
│  1. ASSESS     → 复杂度评估（仅信息展示，写入 .status.md）    │
│  1.5 CHECK_HISTORY → 读取变更档位 + 检查阶段执行历史           │
│  │   ├── 读取变更级 .status.md 基本信息「变更档位」字段        │
│  │   │   └── 缺失 → 按 完整 档处理                            │
│  │   ├── 读取 .status.md「阶段执行历史」表                    │
│  │   ├── 判定执行类型：本阶段本轮 / 回退重执行                 │
│  │   ├── 回退重执行 → 读取「最近修订信息」中的影响范围分数     │
│  │   └── 按档位轮次上限规则（§14）确定轮次上限                 │
│  1.6 INIT      → 主 Agent 写入 .status.md 执行轮次为 1 / {上限}│
│  2. PROMPT     → 构建阶段专属 prompt（含收敛驱动遍历指令）    │
│  3. DISPATCH   → 启动 Agent 迭代子代理                       │
│  4. ITERATE    → 子代理每轮遍历全部工作项独立执行完整流程      │
│  │              每轮递增计数器，直至见证轮收敛或达轮次上限     │
│  5. ACCEPT     → 主 Agent 验收:                               │
│  │   ├── 执行轮次 >= 1 且（最近一轮为见证轮 ∨ 执行轮次 = 上限   │
│  │   │   ∨ 存在通过的复检轮）                                 │
│  │   ├── 终止点判定：累积未复核修复清单是否为空（§14.5.1）     │
│  │   │   └── 非空且未追加复检轮 → 拒收 → 追加 1 轮复检轮       │
│  │   ├── 产物文件是否齐全                                    │
│  │   ├── traceability.md 对应列覆盖率 = 100%                  │
│  │   ├── 无 TODO/TBD 占位符                                  │
│  │   └── 验证门控（收敛提前终止或使用复检轮时）§15             │
│  6. RESULT     → 验收结果处理:                                │
│  │   ├── 通过 → 更新状态 → 释放门控                          │
│  │   ├── 无见证轮且未达上限 → 拒收 → 直接重新启动 Agent 子代理 │
│  │   └── 达上限仍无见证轮且无通过的复检轮 / 产物不合格        │
│  │       → 非收敛分支（§14.6）                               │
│  │       ├── 用户选「是」→ 调整 prompt → 重新启动 Agent 子代理 │
│  │       └── 用户选「否」→ 标记 ⚠️ 需修订 → 阻塞当前阶段     │
└─────────────────────────────────────────────────────────────┘
```

## 5. 复杂度评估机制

基于可量化指标计算复杂度，**仅作为信息展示**写入 .status.md 备注列，不驱动子代理执行行为：

```
复杂度分 = 功能点数 × 1 + 接口数 × 1.5 + 场景数 × 2
```

| 复杂度 | 分数范围 | 说明 |
|--------|---------|------|
| 低 | < 20 分 | 简单任务，少量功能点/接口 |
| 中 | 20-50 分 | 常规任务，适中复杂度 |
| 高 | > 50 分 | 复杂任务，多接口/多场景 |

**权重说明**：场景数权重最高（E2E/集成测试场景复杂度高于单接口），接口数次之，功能点基准权重为 1。

**用途说明**：复杂度评估结果计算后写入 .status.md 备注列，标注为「仅供参考，不驱动执行行为」。**禁止**将分级转化为节奏指引（前 N 轮重点执行/中间 N 轮细节优化/后 N 轮验证等）传递给子代理。复杂度不参与轮次决策——轮次上限仅由变更档位（与回退时的影响范围分数）决定（§14）；迭代终止由见证轮收敛或达上限决定（§14.5）。

## 6. Agent 提前返回处理

当 Agent 子代理返回但主 Agent 验收发现产物不完整时：

1. 主 Agent 记录当前进度到 skill-suggestion.md
2. 使用 AskUserQuestion 询问用户是否调整 prompt 重新执行

## 7. Agent 完成判断

- Agent 迭代子代理 SHALL 在**达成收敛终止条件**（最近一轮为见证轮）或**达到轮次上限**后返回验收报告；收敛驱动意味着**提前于上限终止是合法的正常路径**，无须凑满轮次
- **见证轮判定**：某轮同时满足 (a) 零新发现问题、(b) 零修改、(c) 审查报告证明全部工作项已完成全量遍历时，该轮构成见证轮
- **反空转**：仅当报告证明全量遍历已完成时，该轮的「零新发现」才可采信；无实际工作但未证明全量遍历的轮次 SHALL NOT 被判定为见证轮
- Agent SHALL NOT 为凑满轮次上限而执行无增量价值的轮次
- **终止点复检轮判定**：到达终止点（最近一轮为见证轮，或 `执行轮次` = 轮次上限）时，主 Agent SHALL 判定累积未复核修复清单是否为空（清单维护见 §13）；非空时 SHALL 追加 1 轮复检轮（§14.5.1），SHALL NOT 在此时终止，SHALL NOT 因 `执行轮次` = 轮次上限而跳过
- **复检轮不改变完成判据**：复检轮构成见证轮即为通过，阶段终止并写入终止原因 `收敛（复检轮）`；未构成则按 `达上限` 终止并进入非收敛分支（§14.6）。复检轮 SHALL NOT 追加第二轮
- 收敛终止时豁免 §15 验证门控的「全量至少 1 轮」以外的常规判定；未达上限即终止（收敛提前终止）或使用复检轮时须满足 §15 验证门控
- 主 Agent 验收发现产物不合格时，按验收不通过流程处理（§9）
- Agent 的 prompt 中内嵌收敛驱动终止指令与轮次上限数值（由变更档位确定，SHALL NOT 硬编码为 10）

## 8. 主 Agent 验收标准

| 验收项 | 检查方式 | 判定条件 |
|--------|---------|---------|
| 执行轮次达标 | 检查 .status.md 中 `执行轮次` 字段 | `执行轮次` >= 1 且（最近一轮为见证轮 或 `执行轮次` = 轮次上限 或 存在通过的复检轮）。无见证轮且未达上限时直接拒收，不进入 AskUserQuestion |
| 终止点复检轮判定 | 检查轮间摘要的「累积未复核修复清单」与复检轮报告 | 清单为空，或已执行复检轮并据其结论写入终止原因；清单非空却未追加复检轮 → 拒收并追加 1 轮复检轮（§9 类型 A′） |
| 产物文件齐全 | 检查阶段定义的所有输出产物是否存在 | 全部存在则通过 |
| 覆盖率达标 | 检查 traceability.md 对应列覆盖率 | 覆盖率 = 100% |
| 无占位符 | 搜索 TODO/TBD/{待填写}/... | 无匹配项 |
| 验证门控（收敛提前终止或使用复检轮） | 当 `执行轮次` < 轮次上限 或终止原因为 `收敛（复检轮）` 时检查 §15 验证门控 | 受影响项 100% + 全量 ≥1 轮 + 产物完整 |
| 终止原因 | 检查 .status.md 中 `终止原因` 字段 | 取值 `收敛` / `收敛（复检轮）` / `达上限`，与实际终止路径一致（判读链见 §14.5） |

## 9. 验收失败记录与处理

验收不通过时按失败类型分流：

**类型 A —— 无见证轮且未达轮次上限**（子代理无理由提前返回）：

1. 记录到 `docs/skill-suggestion.md`（触发场景标注：无见证轮且未达上限）
2. **直接重新启动 Agent 子代理继续执行剩余轮次，不询问用户**

**类型 A′ —— 终止点清单非空却未追加复检轮**（终止点漏判）：

1. 记录到 `docs/skill-suggestion.md`（触发场景标注：终止点未追加复检轮，附清单条目数）
2. **SHALL 追加 1 轮复检轮（§14.5.1）后重新验收，不询问用户**；SHALL NOT 因 `执行轮次` = 轮次上限而跳过复检轮
3. 该拒收 SHALL NOT 计入 §14 的档位轮次预算——复检轮本身不消耗该预算

**类型 B —— 达上限仍无见证轮且无通过的复检轮，或产物条件不满足**（非收敛分支，§14.6）：

1. 记录到 `docs/skill-suggestion.md`，包含以下字段：
   - 发现时间、发现阶段（Agent 验收）、触发场景
   - 覆盖缺口详情（缺失的功能点清单）
   - 轮次信息（当前轮次 / 轮次上限）
   - 终止原因（`收敛` / `收敛（复检轮）` / `达上限`）
   - 复检轮的复核失败详情（如复检轮已执行且未通过）
   - 改进建议
   - 状态（待重跑）、优先级

2. 使用 AskUserQuestion 询问用户：「验收不通过，是否重新启动 Agent 迭代子代理？」
   - 用户选「是」→ 调整 prompt 后重新启动 Agent 子代理
   - 用户选「否」→ 标记 .status.md 为 ⚠️ 需修订，阻塞当前阶段

## 10. 重复制子代理 prompt 规范

构建执行类阶段子代理 prompt 时 MUST 包含：

| 内容 | 说明 |
|------|------|
| 当前阶段目标与产物要求 | 明确子代理需要产出什么 |
| 输入文档引用 | functional-designs/、detailed-design.md 等（使用文件路径引用，非复制内容） |
| traceability.md 中待填充的列和覆盖率目标 | 告知子代理需要达到的覆盖标准 |
| 轮间摘要注入（第 2 轮起） | 前轮摘要（已发现问题/未解决问题/覆盖率变化/本轮建议关注），仅在主 Agent 已提取摘要时注入；第 1 轮不注入 |
| 重复制遍历指令 | 「每轮遍历全部工作项独立执行完整流程。更新 .status.md 中执行轮次计数器为当前轮次号。禁止按轮次分段分配工作重点——每轮均须对全部工作项执行完整检查。执行轮次 SHALL 不少于 1 轮且不超过轮次上限 {上限}；当某轮零新发现且零修改、且报告证明全部工作项已完成全量遍历时，该轮构成见证轮，SHALL 提前返回验收报告。达成收敛或达到轮次上限之前 SHALL NOT 无理由返回。」（`{上限}` 由变更档位确定，SHALL NOT 硬编码为 10） |
| 每轮工作内容定义 | 明确本阶段每轮全量执行的具体工作项、流程和产物 |
| 复杂度评估（仅信息展示） | 可出现在 prompt 中但必须附带标注「仅供参考，不驱动执行行为」，标注后不得跟随任何按轮次分配工作的指令 |

**禁止项**：prompt SHALL NOT 包含：
- 「前 N 轮重点执行/中间 N 轮细节优化/后 N 轮验证」等分段分配指令
- 「这部分留给后面轮次」等暗示
- 任何按轮次分段分配工作重点的节奏指引
- 强制走满轮次上限的指令（例如要求做满全部上限轮次才允许返回，或禁止在达到上限之前返回）

## 11. skill-suggestion.md 触发条件扩展

原有 skill-suggestion.md 触发条件（用户指出指引方向错误、纠正意图识别结果、执行结果与预期不符）基础上新增：

- 子代理返回但主 Agent 验收不通过
- 复杂度评估不准确（首轮实践后反馈调整，仅影响信息展示的准确性）
- 子代理产物覆盖率不达标（traceability.md 对应列覆盖率 < 100%）
- 达轮次上限仍无见证轮（非收敛，§14.6）

## 12. 子代理隔离规则

### 12.1 主 Agent 职责边界硬线声明

执行类阶段中，主 Agent 职责严格限定为**调度**（构建 prompt、启动子代理）和**验收**（检查产物、决定通过/拒收）。主 Agent **SHALL NOT** 直接执行任何阶段主工作（编码/修复/测试/审查/计划等），**无例外**——即使子代理多次失败，主 Agent 也不得接管执行。

允许的主 Agent 工作：构建子代理 prompt、启动 Agent 子代理、读取产物文件检查验收标准、更新 .status.md 状态、使用 AskUserQuestion 与用户交互。

### 12.2 强制规则

| 规则 | 说明 |
|------|------|
| **子代理异常时 MUST 重新创建** | 子代理意外停止、报错、返回不完整结果或要求重做时，主代理 MUST 重新创建子代理（新 Agent 调用），SHALL NOT 接管子代理的执行工作 |
| **主 Agent SHALL NOT 接管** | 主代理不得在子代理失败后自行完成子代理的产出（如直接编写代码、设计文档、测试报告等），此规则无例外 |
| **重试粒度为轮次级** | 某轮子代理崩溃时，主 Agent 新建 Agent 重跑**该轮**（从当前轮次号继续，而非重启整个阶段）；新子代理的 prompt 包含前 N-1 轮的轮间摘要（如有） |
| **轮次级重试上限** | 同一轮次最多重试 3 次（即最多创建 4 个子代理：1 次初始 + 3 次重试）；3 次重试均失败后，主代理 MUST 标记该阶段为 ⚠️ 阻塞并提示用户 |
| **重新创建非恢复** | 重新创建的子代理是全新 Agent，不依赖前一个子代理的上下文或状态 |

### 12.3 适用阶段清单

| 阶段 | 使用子代理的步骤 | 隔离规则 | 子代理强制规则 |
|------|-----------------|---------|--------------|
| explore | SELFREV（按变更档位上限：轻量 1 轮 / 标准 2 轮 / 完整 5 轮，下限 1） | ✅ 子代理异常时 MUST 重新创建 | — |
| prototype-design | DESIGN（子代理委托，按有效工具链 execution_order 执行）；「子代理自动审查验证」路径下 VERIFY 9.1（导航验证）、VERIFY 9.2（Playwright 验证）、VERIFY 9.3（UX 规则审查）、SELFREV（按变更档位上限，人工审查方式下完全跳过） | ✅ 子代理异常时 MUST 重新创建 | — |
| design | SELFREV（按变更档位上限：轻量 1 轮 / 标准 2 轮 / 完整 5 轮，下限 1）、REVIEW（按变更档位：轻量单 Agent / 标准两视角 / 完整四视角） | ✅ 子代理异常时 MUST 重新创建 | — |
| plan | 重复制（计划审查）、SELFREV（按变更档位上限：轻量 1 轮 / 标准 2 轮 / 完整 5 轮，下限 1） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行计划主工作 |
| code | 重复制（TDD 编码） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行编码主工作 |
| code-review | 重复制（代码审查） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行审查主工作 |
| api-test | 重复制（接口测试） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行测试主工作 |
| e2e-test | 重复制（E2E 测试） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行测试主工作 |
| integration-test | 重复制（集成测试） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行测试主工作 |
| bug-fix | 重复制（缺陷修复） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行修复主工作 |

### 12.4 执行模式推荐

| 模式 | 适用场景 | 说明 |
|------|---------|------|
| 前台模式（推荐） | 默认 | `run_in_background=false`，主 Agent 可实时验收、提取轮间摘要 |
| 后台模式 | 权限已预配置 | `run_in_background=true`，适用于长时间执行且无需轮间交互的场景 |

**无后台模式硬限制**：后台运行本身不是问题根源，权限未配置才是。项目 `.claude/settings.json` SHALL 由 kflow-init 根据 `skills/kflow-init/references/permission-model.md` 自动配置权限（参见 §12.5），确保子代理不会因权限不足而降级执行。即使权限未完美配置，§12.7 后台权限失败回退前台子代理机制提供韧性保障。

### 12.5 权限预配置

项目 `.claude/settings.json` 中的权限声明由 kflow-init 根据 `skills/kflow-init/references/permission-model.md` 自动配置（参见 `kflow-permission-model` capability）。kflow-init SHALL 在目标项目中读取 `skills/kflow-init/references/permission-model.md` §1 全局必需权限清单，通过幂等合并策略配置 `.claude/settings.json`，确保子代理执行过程中无权限请求中断。

子代理 SHALL 继承 settings.json 中的预配置权限。

### 12.6 设计理由

- **独立性保障**：子代理独立上下文是其核心价值（避免"作者盲点"），主代理接管会丧失这一优势
- **职责清晰**：主代理的职责是编排（orchestrate），子代理的职责是执行（execute），两者不可混淆
- **质量保证**：主代理通常已在该阶段投入大量上下文（撰写产物、分析需求），接管执行会有"完成偏差"——倾向于走捷径或忽略细节
- **Token 成本换正确性**：重新创建子代理的 Token 成本高于主代理接管，但正确性和独立性更重要

### 12.7 后台权限失败回退前台子代理机制

即使 kflow-init 正确配置了权限，仍可能出现后台子代理因权限问题失败的情况（用户手动修改 settings.json、工具版本差异、新增未覆盖的工具调用）。本节定义韧性机制，确保后台失败时自动回退前台子代理重新执行。

#### 12.7.1 权限错误模式检测

主 Agent 从后台子代理（run_in_background=true）错误输出中匹配以下权限相关错误模式：

- "permission denied" / "权限不足"
- "not allowed" / "不允许"
- "requires approval" / "需要批准"
- "blocked" / "被阻止"
- 错误信息包含工具名 + 拒绝语义（如 "Bash command blocked"）

匹配至少一种模式即判定为权限问题，非权限错误按原有轮次级重试机制处理（参见 §12）。

#### 12.7.2 回退执行规则

检测到后台子代理因权限问题失败后：

1. 主 Agent 输出提示："检测到子代理因权限问题失败，创建前台子代理重新执行"
2. 构建与原后台子代理相同的 prompt（相同任务内容、轮次上下文）
3. 调用 Agent 工具：`run_in_background=false`
4. 前台子代理成功 → 正常继续，更新 .status.md 记录回退事件
5. 前台子代理也失败 → 标记 ⚠️ 阻塞，输出提示："子代理前台/后台均失败，请检查权限配置或手动处理"

#### 12.7.3 主 Agent 禁止接管硬线

主 Agent SHALL NOT 在任何情况下直接接管执行——即使后台子代理和前台子代理均失败，主 Agent 也不得在主 Agent 上下文中执行阶段主工作。此规则与 §12.1 主 Agent 职责边界硬线一致，无例外。

#### 12.7.4 不计入重试上限

后台权限失败回退前台子代理的执行 SHALL NOT 计入 §12.2 定义的轮次级重试 3 次上限——因为是不同执行模式的切换（后台 → 前台），而非同一模式的重试。回退后的前台子代理执行失败时标记阻塞，后续恢复操作（如用户触发恢复）从轮次级重试计数器的当前值继续。

## 13. 轮间摘要传递机制

> **版本**: 2.6.0 新增（变更 token-opt-inter-round-summary）
> **适用范围**: 全部多轮审查机制——执行类重复制**与**设计自审 SELFREV（kflow-explore / kflow-prototype-design / kflow-design / kflow-plan）。设计自审 SHALL NOT 被排除在轮间摘要注入之外（变更 converge-review-rounds）。

### 13.1 概述

重复制模式下，每轮子代理完全独立启动，零上下文继承。轮间摘要机制在每轮子代理返回后，由主 Agent 从自审报告/产物差异中提取摘要，注入到下一轮子代理 prompt 中，使后期轮次可以优化注意力分配——已修复项快速回归、未解决项重点分析、未涉及项全量检查（兜底）。

**核心原则**：摘要仅用于优化注意力分配，不跳过任何工作项。全量遍历兜底始终保留。

**与收敛判据的关系**：见证轮要求「零新发现 + 零修改」，冷启动子代理的「零发现」可能只是遗漏而非收敛。轮间摘要使前轮修复与遗留问题注入下一轮，把「零发现」从概率事件变为可追溯的因果结论；同时摘要提供「前轮全部修复清单」，见证轮候选须逐项复核该清单。

### 13.2 摘要格式

```markdown
## 轮间摘要 (Round {N-1} 完成后)

### 已发现问题 (已修复)
- [FP-001] 接口返回值类型不匹配 → 已修复 (Round 2)
- [FP-003] 缺少错误处理 → 已修复 (Round 3)

### 未解决问题
- [FP-005] 边界条件处理待确认 → 升级用户决策

### 覆盖率变化
- traceability.md 编码列: Round 1: 40% → Round {N-1}: 95%

### 累积未复核修复清单
- [FP-001] 接口返回值类型不匹配 (Round 2 修复) → 未复核
- [FP-003] 缺少错误处理 (Round 3 修复) → 未复核

### 本轮建议关注
- FP-005 待用户决策后处理
- 已修复项的回归检查
```

**「累积未复核修复清单」字段**：列出自审循环开始以来**全部尚未通过独立复核**的修复，而非仅上一轮的修复。清单为空时写「（空）」。该字段是终止判定（§14.5 第一步）与复检轮（§14.5.1）的唯一输入，SHALL NOT 省略。

### 13.3 摘要提取规则

| 提取来源 | 提取内容 | 提取时机 |
|---------|---------|---------|
| 子代理自审报告 | 已发现问题列表、已修复项列表 | 每轮子代理返回后 |
| 产物差异（.status.md / traceability.md） | 覆盖率变化（本轮 vs 上一轮） | 每轮子代理返回后 |
| 主 Agent 验收记录 | 未解决问题列表、升级用户决策项 | 每轮子代理返回后 |

**提取时机**：主 Agent 在每轮子代理返回后、构建下一轮子代理 prompt 前提取摘要。第 1 轮无摘要（无前轮信息），第 2 轮起注入。

**摘要写入位置**：主 Agent 将摘要暂存于内存（不写入文件），仅在构建下一轮子代理 prompt 时注入。

### 13.4 摘要注入方式

主 Agent 在构建第 2 轮及后续轮次的子代理 prompt 时，SHALL 在 prompt 开头的「重复制遍历指令」之后、「每轮工作内容定义」之前插入轮间摘要章节。格式：

```
## 轮间摘要 (Round {N-1} 完成后)
{摘要内容}

### 摘要使用说明
- 已修复项：仅做快速回归确认（检查修复是否引入新问题），不重新完整检查
- 未解决项：重点分析，优先处理
- 未涉及项：全量检查（兜底），不得跳过
- 见证轮候选：须逐项复核本摘要「累积未复核修复清单」中的全部修复，任一项复核不通过即不得判定为见证轮
- 复检轮：须逐项复核本摘要「累积未复核修复清单」中的全部条目，并给出每条目的复核结果
- 摘要仅用于优化注意力分配，不跳过任何工作项
```

### 13.5 跳过条件（注意力优化规则）

子代理收到轮间摘要后，按以下规则优化注意力分配：

| 工作项类别 | 处理方式 | 说明 |
|-----------|---------|------|
| 已修复项 | 快速回归确认 | 检查修复是否引入新问题，不重新执行完整检查流程 |
| 未解决项 | 重点分析 | 投入更多注意力深入分析，优先处理 |
| 未涉及项 | 全量检查（兜底） | 执行完整检查流程，不得因摘要跳过任何项 |

**见证轮复核要求**：当本轮同时零新发现且零修改（即见证轮候选）时，子代理 SHALL 逐项验证摘要「**累积未复核修复清单**」中的**全部条目**（不限于上一轮的修复）；任一项复核不通过（修复失效或引入新问题）时，该轮 SHALL NOT 被判定为见证轮。

**复检轮复核要求**：复检轮 SHALL 逐项验证「累积未复核修复清单」中的全部条目，SHALL NOT 仅复核最后一轮产生的修复；已在前序轮次中通过独立复核的修复 SHALL NOT 被重复纳入。

**禁止项**：
- 禁止因摘要中显示「已修复」而完全跳过该工作项
- 禁止因摘要中无「未解决」而减少全量检查的范围
- 摘要仅影响注意力分配的优先级，不影响工作项的覆盖范围

### 13.6 首轮与末轮特殊处理

| 轮次 | 摘要处理 |
|------|---------|
| 第 1 轮 | 不注入摘要（无前轮信息） |
| 第 2 轮起（收敛或达上限前的各轮） | 正常注入前轮摘要 |
| 收敛轮（见证轮） | 正常注入前轮摘要，并按 §13.5 逐项复核「累积未复核修复清单」内全部条目 |
| 复检轮（终止点追加轮） | 正常注入前轮摘要，且清单 SHALL 完整（含自审循环开始以来全部未复核修复），并按 §13.5 逐项复核清单内全部条目 |

> 轮次上限不再是固定值，故不再区分「末轮」；终止轮次由收敛或上限决定（§14.5）。

### 13.7 累积未复核修复清单的维护

**维护责任**：清单 SHALL 由**主 Agent** 维护，SHALL NOT 下放给子代理。理由：见证轮判定（§14.5）以产物文件差异为准，清单是该判定的输入，须与判定同源——子代理自述与产物事实冲突时才可裁决。

**增量规则**（每轮结束时由主 Agent 计算并写入摘要）：

```
清单(第 N 轮结束) = 清单(第 N-1 轮结束)
                  + 第 N 轮新增的修复
                  - 第 N 轮实际复核通过的修复
```

**消费方**：

| 消费方 | 用途 |
|--------|------|
| 终止判定（§14.5 第一步） | 判定到达终止点后是否须追加复检轮 |
| 复检轮（§14.5.1） | 作为该轮逐项复核的输入清单 |
| 见证轮候选（§13.5） | 逐项复核清单内全部条目，任一项不通过即不得判定为见证轮 |

**与「已发现问题（已修复）」字段的关系**：后者是**本轮视角**的修复记录，清单是**全循环视角**的未复核修复集合。两者 SHALL NOT 互相替代——清单 SHALL NOT 仅包含上一轮的修复。

## 14. 档位驱动轮次上限决策

### 14.1 概述

重复制的**轮次上限**由**变更档位**决定，不再使用与变更规模无关的固定轮次下限，也不再存在「必须完成的目标轮次」概念。轮次下限全局统一为 **1 轮（无例外）**：执行轮次 SHALL 不少于 1 轮。轮次不再取决于该阶段此前是否执行过，而只取决于变更规模与是否有回退。回退重执行时在档位上限上取影响范围分数映射的较大者，确保返工验证不因低档而放松。

**语义翻转**：变更档位表示**轮次上限**（最多做几轮），SHALL NOT 表示必须完成的固定轮次数。达成见证轮收敛时 SHALL 提前终止。

### 14.2 决策规则

**档位轮次上限**：

| 变更档位 | 轮次上限 |
|---------|---------|
| 轻量 | 1 |
| 标准 | 3 |
| 完整 | 5 |

> **plan 阶段例外**：kflow-plan 阶段的迭代循环为**产物自审**（每轮对 tasks.md 执行 4 维度审查），其轮次上限取设计自审口径 —— 轻量 1 / 标准 2 / 完整 5，SHALL NOT 取上表的 1/3/5。该口径定义于 `plan-self-review` 与 `tier-driven-repetition`（「设计自审轮次上限按档位决定」的 plan 例外）。本文件其余机制（子代理强制、轮间摘要、验证门控、回退叠加）对 plan 同样适用。

**统一轮次映射**（仅用于回退重执行时的叠加，唯一定义于 `tier-driven-repetition` 能力）：

| 影响范围分数 | 映射轮次 |
|-------------|---------|
| ≤ 3 | 1 |
| 4 ~ 15 | 3 |
| > 15 | 5 |

| 场景 | 轮次上限 |
|------|---------|
| 阶段本轮执行（无回退） | 档位上限（plan 阶段取其自审口径 1 / 2 / 5） |
| 回退重执行（有影响范围分数） | `max(档位上限, 影响范围分数映射)` |
| 回退重执行（无影响范围分数） | 档位上限 |

> 示例：轻量档变更因缺陷回退，影响范围分数 8 → 轮次上限 = `max(1, 3)` = 3 轮（被影响范围抬高，不因低档放松返工验证，其 1 轮的档位上限不会把返工卡死）。完整档变更回退，分数 1 → `max(5, 1)` = 5 轮。

**档位读取**：读取变更级 `.status.md` 基本信息的「变更档位」字段；字段缺失时按 `完整` 档处理。

### 14.3 判定流程

```
CHECK_HISTORY 步骤:
1. 读取变更级 .status.md 基本信息「变更档位」字段
   └── 缺失 → 按「完整」档处理
2. 取该档位的轮次上限作为初值
3. 读取 .status.md「阶段执行历史」表，查找当前阶段的执行记录
   └── 有记录（回退重执行）:
       ├── 读取 .status.md「最近修订信息」中的影响范围分数
       ├── 无分数 → 轮次上限 = 档位上限
       └── 有分数 → 轮次上限 = max(档位上限, 影响范围分数映射)
4. 将轮次上限写入 .status.md「执行轮次」字段（如 1/3、1/5、2/3）
```

### 14.4 子代理 prompt 适配

轮次上限确定后，子代理 prompt 中的重复制遍历指令 SHALL 使用实际的轮次上限（取值由变更档位确定，SHALL NOT 硬编码为 10），并采用收敛驱动表述。示例：轮次上限为 3 时，指令为「执行轮次 SHALL 不少于 1 轮且不超过 3 轮；当某轮零新发现且零修改、且报告证明全部工作项已完成全量遍历时，该轮构成见证轮，SHALL 提前返回验收报告。达成收敛或达到轮次上限之前 SHALL NOT 无理由返回」。

### 14.5 终止条件与终止原因

**终止判定分两步执行**：

**第一步**：主 Agent 判定**累积未复核修复清单**（定义与增量规则见 §13）是否为空。

**第二步**：按清单状态分支：

| 清单状态 | 终止点情形 | 处理 |
|---------|-----------|------|
| 非空 | 无论最近一轮是否为见证轮、`执行轮次` 是否等于轮次上限 | **追加 1 轮复检轮**（§14.5.1），SHALL NOT 在此时终止，SHALL NOT 消耗档位轮次预算 |
| 为空 | `执行轮次` >= 1 **且**最近一轮为**见证轮** | 终止，终止原因 `收敛` |
| 为空 | `执行轮次` = 轮次上限 | 终止，终止原因 `达上限` → 非收敛分支（§14.6） |

**复检轮的终止**：复检轮构成见证轮（零新发现 + 零修改 + 报告证明全维全量遍历 + 清单内全部修复逐项复核通过）→ 终止，终止原因 `收敛（复检轮）`；未构成 → 终止，终止原因 `达上限` → 非收敛分支（§14.6）。复检轮 SHALL NOT 再追加第二轮。

**见证轮的三项条件**：

| 条件 | 判定口径 |
|------|---------|
| (a) 零新发现问题 | 本轮的「新发现问题清单」为空 |
| (b) 零修改 | 本轮未对任何产物作出修复性修改。**判定依据**（优先级从高到低）：产物文件差异（`.status.md` / `traceability.md` / 阶段产物在本轮前后的实际变更）、子代理自述的「本轮修复内容」为空。两者冲突时以**产物文件差异**为准 |
| (c) 报告证明全维全量遍历 | 审查报告显式证明全部审查维度与全部工作项已完成遍历（防止空转轮被误判为见证轮） |

**终止原因写入**：阶段终止时，系统 SHALL 在 `.status.md` 写入**终止原因**字段，取值 `收敛`、`收敛（复检轮）` 或 `达上限`，使审计可判读「为何停在第 N 轮」以及是否使用了追加预算。终止原因 SHALL 与该阶段实际的终止路径一致。

**判读链**（门控与审计据此工作，无需新增字段）：

```
   终止原因              报告份数            推导结论
   ------------------    ----------------    ---------------------------
   收敛                  <= 档位上限         预算内收敛（末轮为见证轮）
   收敛（复检轮）         = 档位上限 + 1      复检轮已执行且通过
   达上限                 = 档位上限 + 1      复检轮已执行且未通过
   达上限                <= 档位上限         复检轮未触发（清单为空）
```

`执行轮次` 字段格式 SHALL 保持 `{N} / {上限}` 且仅记录审查轮，复检轮 SHALL NOT 改写该字段（分母与分子均不变）；复检轮的存在由终止原因蕴含。

### 14.5.1 复检轮（终止点追加轮）

**定义**：多轮审查循环到达终止点时，若累积未复核修复清单非空，系统追加的 1 轮**验证性**审查。复检轮只做验证——不重新发现、不重新修复、不新增审查强度。

| 维度 | 规则 |
|------|------|
| 触发 | 到达终止点（最近一轮为见证轮，或 `执行轮次` = 轮次上限）**且**累积未复核修复清单非空；触发判定在全部档位上一致适用，SHALL NOT 依档位分支 |
| 预算 | SHALL NOT 消耗档位轮次预算；单个阶段最多追加 1 轮；未通过时 SHALL NOT 追加第二轮 |
| 复核范围 | 逐项复核自审循环开始以来**全部**尚未通过独立复核的修复，SHALL NOT 仅复核最后一轮产生的修复；已通过独立复核的修复 SHALL NOT 被重复纳入 |
| 通过判据 | **构成见证轮**（零新发现 + 零修改 + 报告证明全维全量遍历 + 清单内全部条目逐项复核通过）；任一条件不满足即未通过。SHALL NOT 发明第二套判据，也 SHALL NOT 为空转轮 |
| 报告 | 产出 1 份独立报告，命名与存放遵循该阶段既有审查报告规则，报告内 SHALL 明确标注其为复检轮 |
| 状态写入 | 通过 → 终止原因 `收敛（复检轮）`；未通过 → 终止原因 `达上限` 并进入非收敛分支 |
| 清单维护 | 累积未复核修复清单由**主 Agent** 维护，载体为轮间摘要的固定字段（§13）；维护责任 SHALL NOT 下放给子代理 |

**清单增量规则**（每轮结束时由主 Agent 计算）：

```
清单(第 N 轮结束) = 清单(第 N-1 轮结束)
                  + 第 N 轮新增的修复
                  - 第 N 轮实际复核通过的修复
```

**反空转**：复检轮 SHALL 证明全量遍历已完成，并逐项给出清单内每条修复的复核结果；未证明全量遍历的复检轮 SHALL NOT 被判定为通过。

> 复检轮机制的**权威定义**见 `recheck-round` 能力；本节为其在执行类重复制文件中的落地表述，其他文件 SHALL 引用而不另行定义。

### 14.6 非收敛分支

达到轮次上限、**且不存在通过的复检轮**、且无任何一轮为见证轮时（即上限耗尽而未见收敛，或复检轮未通过），系统 SHALL 进入**非收敛分支**：

1. 记录到 `docs/skill-suggestion.md`（包含阶段、当前轮次 / 轮次上限、终止原因 `达上限`、覆盖缺口详情、复检轮的复核失败详情（如已执行复检轮）、改进建议）
2. 使用 AskUserQuestion 询问用户：「验收不通过，是否重新启动 Agent 迭代子代理？」
   - 用户选「是」→ 调整 prompt 后重新启动 Agent 子代理
   - 用户选「否」→ 标记 .status.md 为 ⚠️ 需修订，**阻塞当前阶段**
3. 系统 MAY 将该阶段标记为 ⚠️ 阻塞

该分支与 §9 类型 B 一致，不新增范式；与 §14.5 的终止原因 `达上限` 配对使用。

### 14.7 轻量档与产物门控

轻量档轮次上限为 1，即 SELFREV / 重复制 SHALL 至少执行 1 轮，**SHALL NOT 存在 0 轮豁免路径**。轻量档下验证门控（§15）仍按「执行轮次 < 轮次上限」判定——当第 1 轮即为见证轮而终止时（`执行轮次` = 1 = 轮次上限），不触发 §15 的额外门控；当回退叠加把上限抬至 3 而在第 1 轮收敛时（`执行轮次` = 1 < 3），SHALL 满足 §15 验证门控。

**轻量档与复检轮**：轻量档第 1 轮产生修复时，累积未复核修复清单必然非空，系统 SHALL 追加 1 轮复检轮（§14.5.1）——SHALL NOT 因 `执行轮次` 已达档位上限 1 而跳过复检轮、直接以 `达上限` 滑入非收敛分支。轻量档因此实际执行 1~2 轮：复检轮通过 → `收敛（复检轮）`；复检轮未通过 → `达上限` + 非收敛分支。

## 15. 验证门控（执行轮次 < 轮次上限，或使用复检轮时）

当 `执行轮次` < 轮次上限（即因收敛提前终止，未跑满上限）时，除标准验收项外，SHALL 额外满足以下三项验证门控：

### 15.1 受影响项 100% 覆盖验证

- 从 .status.md「最近修订信息」中读取受影响项清单
- 每个受影响项 SHALL 接受完整的阶段专属验证（不可缩写）
- 验证结果 SHALL 记录在阶段产物中

### 15.2 全量至少 1 轮兜底

- 至少 1 轮 SHALL 为完整的全量遍历（覆盖所有工作项）
- 该轮不得因影响范围评估而跳过任何工作项
- 确保不会遗漏关联影响

### 15.3 产物完整性

- 所有阶段定义的输出产物 SHALL 存在且格式合规
- 与标准重复制的产物要求一致

### 15.4 复检轮场景的门控判定

当终止原因为 `收敛（复检轮）` 时（`执行轮次` = 轮次上限，复检轮不计入该字段），三项验证门控 SHALL 同样适用：

| 门控项 | 复检轮场景下的判定 |
|--------|------------------|
| 受影响项 100% 覆盖 | 仍须满足；复检轮不替代受影响项的完整阶段专属验证 |
| 全量至少 1 轮兜底 | **由复检轮的全量遍历证明满足**——复检轮须证明全部工作项已完成遍历，且逐项复核清单内全部修复 |
| 产物完整性 | 仍须满足；复检轮报告 SHALL 作为该阶段的附加产物存在且格式合规 |

复检轮未通过时终止原因为 `达上限`，按非收敛分支（§14.6）处理，SHALL NOT 以门控通过与否作为是否进入非收敛分支的判据。

### 15.5 门控判定

三项验证全部通过 → 验收通过。任一未通过 → 按验收不通过流程处理（§9）。

## 16. 阶段执行历史追踪

### 16.1 阶段执行历史表

`.status.md` SHALL 包含「阶段执行历史」表，格式如下：

| Phase | Execution Count | Last Type | Rounds | Score | Notes |
|-------|----------------|-----------|--------|-------|-------|
| plan | 1st | First Execution | 2/2 | — | — |
| code | 1st | First Execution | 3/3 | — | — |
| code | 2nd | Rollback Re-execution | 3/3 | 4 | BUG-003 triage → L3 design revision |

**字段说明**：
- **Phase**：阶段名称
- **Execution Count**：第几次执行（1st, 2nd, ...）
- **Last Type**：执行类型（First Execution / REVISION / Rollback Re-execution）
- **Rounds**：最终执行轮次 / 轮次上限（如 2/2, 3/3, 3/5）——分子为实际终止轮次，可能小于上限（收敛提前终止）
- **Score**：影响范围分数（本阶段无执行记录时标 —）
- **Notes**：备注（如回退原因、终止原因）

### 16.2 更新时机

- 阶段完成时 SHALL 追加一行记录
- 回退时 SHALL 在「最近修订信息」节记录修订详情

### 16.3 最近修订信息节

`.status.md` SHALL 包含「最近修订信息」节，格式如下：

```markdown
## Recent Revision Info

- **Revision Trigger**: BUG-003 triage diagnosis
- **Source Phase**: L3 Detailed Design
- **Timestamp**: 2026-06-17T14:30:00
- **Summary**: 接口返回值类型定义错误，需修正 2 个接口定义
- **Affected Functional Points**: FP-003, FP-007
- **Affected Interfaces**: /api/orders/export, /api/orders/detail
- **Data Model Changes**: none
- **Impact Scope Score**: 5 (2×1 + 2×1.5 + 0×2)
- **Recommended Rounds**: 3
```

## 17. 影响范围分数读取机制

### 17.1 读取时机

执行阶段启动时（CHECK_HISTORY 步骤），主 Agent SHALL：

1. 读取 .status.md「最近修订信息」节
2. 提取 `Impact Scope Score` 值
3. 按 §14.2 统一映射取得映射轮次，与档位上限取 `max` 作为轮次上限
4. 提取 `Affected Functional Points` + `Affected Interfaces` 用于验证门控

### 17.2 分数计算公式

由 `kflow-bug-triage` 影响范围评估产出（参见 triage-impact-assessment capability）：

```
影响范围分数 = 功能点数 × 1 + 接口数 × 1.5 + 数据模型变更 × 2
```

- 功能点数：受影响的功能点数量
- 接口数：受影响的 API 端点数量
- 数据模型变更：存在数据模型修改时为 1，否则为 0

### 17.3 无分数时的处理

当 .status.md 中无「最近修订信息」节或分数为空时，轮次上限 SHALL 取变更档位上限（轻量 1 / 标准 3 / 完整 5）；变更档位字段亦缺失时按 `完整` 档处理。
