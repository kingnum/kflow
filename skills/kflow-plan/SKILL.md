# 角色

计划执行器（子变更级）。将变更级详细设计转化为可执行任务清单，为每个功能点编写 4 维 DoD 验收标准，确定任务执行顺序，区分后端SC/前端SC输入源。

> ⚠ **子代理强制规则**（参见 skills/kflow-plan/references/repetition.md §3、§12）:
> 1. 计划主工作 MUST 通过 **Agent 子代理**执行（任务拆分 / DoD 编写 / 子变更类型标注 / 输出 tasks.md），主 Agent 仅负责调度和验收，SHALL NOT 直接执行计划主工作
> 2. 本阶段另有 SELFREV 环节的 **1 个**独立验证子代理，串行且仅一轮
> 3. 子代理异常（意外停止 / 报错 / 返回不完整结果）时，主 Agent MUST 重新创建新子代理，SHALL NOT 接管其未完成的工作；最多重试 3 次，全部失败标记 ⚠️ 阻塞
> 4. 子代理 SHOULD 前台运行（推荐 `run_in_background=false`），后台模式仅在权限已预配置时使用
> 5. 后台子代理权限失败时 SHALL 创建新的前台子代理重新执行，主 Agent SHALL NOT 直接接管（参见 §12.7）

# 任务

门控检查 → 读取变更级 detailed-design.md 相关章节和测试用例 → 为每个子变更拆分任务到原子级 → 编写 DoD 验收标准（4 维 WHEN/THEN）→ 确定任务执行顺序 → 标注子变更类型 → 输出 tasks.md → 验证任务覆盖 → 更新状态文件。

进入计划阶段前检查：

| 详细设计状态 | = ✅ 完成 | [全部] |
| 变更级 `detailed-design.md` 或 `detailed-design/index.md` | 文件/目录索引存在（不再检查子变更级） | [全部] |
| `CONTEXT.md` | 存在 | [全部] |
| `functional-designs/index.md` | 存在 | [全部] |
| `api-tests/index.md` | 存在 或 已裁剪（轻量档适用性声明判 `接口单元测试` 为 `⏭️ 不适用` 且有判定依据） | [全部] |
| `e2e-tests/index.md` | 存在（条件：前端SC + 前后端项目） | [前端子变更] |
| 设计审查产物 | 按变更档位分支：轻量档 → `cross-reviews/{timestamp}/synthesis.md` 存在且标记审查通过；标准档 → 两份视角报告（business-technical-review.md、security-quality-review.md）+ `synthesis.md` 存在且标记审查通过。档位字段缺失或为历史遗留的 `完整` 取值时按标准档分支判读，SHALL NOT 要求四份视角报告存在 | [全部] |

| 子变更 HITL 标记 | 所有子变更 SHALL NOT 含 HITL 标记（HITL = 设计不完整，禁止进入 plan） | [全部] |

## 状态双写规则

阶段完成、回退与重执行时，主 Agent SHALL 同时执行两处写入：

1. **追加历史**：向 `docs/changes/{change}/status-log.md` 追加本次事件——阶段名、轮次、完成时间、耗时、终止结果；回退时另记回退原因与目标阶段
2. **刷新当前**：刷新变更级 `.status.md` 的当前状态字段——当前阶段、阶段状态表对应行、执行轮次、终止结果、未决事项

`.status.md` SHALL 保持在 100 行以内，超出部分改为写入 `status-log.md`。变更目录中不存在 `status-log.md`（历史变更未分层）时按既有单文件口径处理，SHALL NOT 强制回填。

> 读取边界：常规阶段推进与门控判定 SHALL 仅读取 `.status.md`；`status-log.md` 仅在中断恢复与审计场景读取。权威定义见 `status-file-layering` 能力。

# 执行流程

```
计划阶段流程:

┌───────────────────────────────────────────────────────────────────────┐
│                         PLAN WORKFLOW                                  │
├───────────────────────────────────────────────────────────────────────┤
│  1. PRE_HOOK  → 引用 skills/kflow-plan/references/hooks.md plan 阶段 PRE_HOOK   │
│  2. CHECK     → 门控检查                                               │
│  3. READ      → 读取变更级 detailed-design.md + FP 类型前置校验      │
│  │   3a. 读取 functional-designs/index.md FP 清单「类型」列            │
│  │   3b. 筛选本子变更包含的 FP，检查类型一致性                           │
│  │   3c. 后端子变更含前端FP → 🟡 警告 / 前端子变更含后端FP → 🟡 警告   │
│  │   3d. 警告不阻塞 tasks.md 生成，但记录到子变更信息段                  │
│  4. SPLIT     → 为每个子变更拆分任务到原子级（2-5 分钟粒度）           │
│  5. DOD       → 为每功能点编写 4 维 DoD 验收标准（WHEN/THEN 格式）     │
│  6. ORDER     → 确定任务执行顺序（考虑功能点依赖）                     │
│  7. ANNOTATE + OUTPUT → 标注子变更类型并为每个子变更输出 tasks.md      │
│  8. VERIFY    → 验证任务覆盖所有功能点和验收标准                       │
│  8.5 SELFREV  → 单轮验证自审（轮数恒为 1，无 0 轮豁免路径）            │
│  │   主 Agent 签署自证（零子代理）: 4 维度填「维度/自证结论/证据锚点」 │
│  │   1 轮独立子代理验证: 先独立遍历全部子变更 tasks.md 形成自身结论     │
│  │   （此阶段不读签署清单）→ 再逐项对照签署清单打假 → 只报告不修改     │
│  │   主 Agent 统一修复 + 生成「本阶段修复清单」，不追加确认轮           │
│  │   报告路径: self-reviews/plan/report.md（固定，不按轮次编号）        │
│  │   终止结果: 验证通过 / 验证发现问题({N})                             │
│  9. COMPLETE  → 更新状态文件 → 阶段衔接决策                            │
│ 10. POST_HOOK → 引用 skills/kflow-plan/references/hooks.md plan 阶段 POST_HOOK  │
└───────────────────────────────────────────────────────────────────────┘
```

## 步骤 1：PRE_HOOK — 阶段前置钩子

引用 `skills/kflow-plan/references/hooks.md` plan 阶段 PRE_HOOK（❌ 不需要服务：CHECK_STATE + RELOAD）。

## 步骤 2：CHECK — 门控检查

验证详细设计完成、设计审查通过、NFR 章节完整。不满足条件时 ❌ 阻塞，提示先完成设计阶段。

## 步骤 3：READ — 读取设计文档

**读取策略**（适配两种文档形态）：

```
1. 检查文档形态:
   ├── detailed-design/index.md 存在 → 拆分模式（FP > 20）
   │   ├── 读取 index.md 获取全局视图和文档导航
   │   ├── 按子变更定位对应的 domains/{domain-name}.md 文件
   │   ├── 读取 nfr.md（NFR 章节）
   │   ├── 读取 config-and-errors.md（配置项和错误处理）
   │   └── 读取 subchange-division.md（子变更划分）
   └── detailed-design.md 存在 → 单文件模式（FP ≤ 20）
       └── 读取 detailed-design.md 中属于当前子变更的章节
```

读取属于当前子变更的设计内容：
- 数据模型设计（涉及当前子变更的部分）
- 接口设计（涉及当前子变更的接口）
- 功能点设计表（当前子变更的功能点列表）
- API 测试用例（`api-tests/`）和 E2E 测试用例（`e2e-tests/`，仅前后端项目）；轻量档下两者按阶段适用性声明条件适用，判为 `⏭️ 不适用` 时对应目录不存在，跳过该输入的读取，SHALL NOT 因此判为缺项

### FP 类型校验（步骤 3 完成后执行）

读取 `functional-designs/index.md` FP 清单「类型」列，校验本子变更 FP 类型一致性：

```
1. 获取本子变更包含的 FP 列表（从 detailed-design.md 子变更划分章节）
2. 读取 functional-designs/index.md 中各 FP 的「类型」列
3. 校验:
   ├── 后端子变更 含「前端」FP → 🟡 警告，记录到 tasks.md 子变更信息段
   ├── 前端子变更 含「后端」FP → 🟡 警告，记录到 tasks.md 子变更信息段
   └── 全部一致 → ✅ 通过
4. 警告不阻塞，但 SHALL 显示在生成结果中
```

## 步骤 4：SPLIT — 拆分任务到原子级

### 任务粒度标准

| 粒度 | 判断标准 | 示例 |
|------|---------|------|
| 过粗 | 包含多个独立操作 | "实现用户服务" ❌ |
| 合适 | 2-5 分钟可完成 | "编写注册接口测试" ✅ |
| 过细 | 实现细节级别 | "添加一行代码" ❌ |

### 后端 FP / 前端 FP 区分

根据子变更类型区分功能点模板：

| FP 类型 | 子变更类型 | 任务模板 | 验证方式 |
|--------|-----------|---------|---------|
| 后端 FP | 后端子变更 | TDD 模板（Red → Green → Refactor） | 单元测试 + 接口测试 |
| 前端 FP | 前端子变更 | 原型转译模板（输入源 + 5 步实现） | 视觉对账 + Playwright 交互验证 |

### 功能点级全展开形式（后端 FP）

每个后端功能点拆分为 TDD 循环步骤：

```
功能点级全展开结构:

功能点 N: {描述}
  ├── DoD 验收标准（4 维 WHEN/THEN）
  ├── Step 1: 编写测试用例代码
  ├── Step 2: 运行测试，确认失败 (RED)
  ├── (HITL 决策点，如适用)
  ├── Step 3: 实现最小代码
  ├── Step 4: 运行测试，确认通过 (GREEN)
  ├── Step 5: 检查代码质量
  ├── Step 6: 执行必要重构（可选）
  └── Step 7: 确认重构后测试仍通过
```

### 功能点级全展开形式（前端 FP）

每个前端功能点使用「原型转译」模板：

```
前端功能点结构:

前端功能点 N: {页面/组件描述}
  ├── 输入源: 从 docs/designs/prototypes/manifest.md 获取页面文件路径、设计令牌路径、元素覆盖树路径
  ├── API 契约: detailed-design.md §{api-section}
  ├── Step 1: 实现组件骨架（结构+样式，对齐原型）
  ├── Step 2: 注入设计令牌（替换硬编码为 var(--xxx)）
  ├── Step 3: 实现交互状态（hover/active/focus/disabled/loading/empty/error）
  ├── Step 4: 对接 API（mock 数据 → 真实接口）
  └── Step 5: 按原型验证一致性（手动对照 docs/designs/prototypes/screens/{page}.html）
```

## 步骤 5：DOD — 编写 DoD 验收标准

### 四维验收

| 维度 | 最小数量 | 说明 | 示例场景 |
|------|---------|------|---------|
| Happy Path | ≥ 1 | 正常业务流程验收 | 用户输入有效信息，操作成功 |
| Error Path | ≥ 2 | 异常和错误处理验收 | 输入已注册邮箱 → 提示已存在；密码不足 8 位 → 提示格式错误 |
| Edge Case | ≥ 1 | 边界条件验收 | 邮箱长度超 100 字符 → 提示过长 |
| Quality | ≥ 1 | 质量属性验收 | 注册接口 P95 响应时间 < 500ms |

### 验收标准格式（WHEN/THEN）

每条验收标准使用 WHEN/THEN 格式：

```markdown
- Happy Path: WHEN 用户输入有效用户名和密码 THEN 系统返回 JWT token 且用户状态为已激活
- Error Path: WHEN 用户输入已被注册的邮箱 THEN 系统返回 409 Conflict 且提示"邮箱已注册"
- Error Path: WHEN 用户密码长度 < 8 位 THEN 系统返回 400 Bad Request 且提示"密码长度至少8位"
- Edge Case: WHEN 用户邮箱长度 = 255 字符 THEN 系统正常处理（边界值测试）
- Quality: WHEN 并发 100 个注册请求 THEN 无数据损坏且所有请求正确处理
```

## 步骤 6：ORDER — 确定任务执行顺序

考虑因素：
- 功能点依赖关系（基础功能先于扩展功能）
- 测试先行原则（测试编写先于实现）
- 数据模型优先（涉及数据模型变更的功能点优先）
- 接口依赖（提供方接口先于消费方接口）

## 步骤 8：VERIFY — 验证覆盖

### 任务覆盖标准

| 检查项 | 要求 |
|--------|------|
| 功能点覆盖 | 所有设计文档中的功能点都有对应任务（覆盖率 = 100%） |
| 测试先行 | 每功能点包含测试编写和测试执行步骤 |
| TDD 循环 | 包含 Red → Green → Refactor 完整流程（Step 1-7） |
| DoD 覆盖 | 每功能点包含 Happy Path(≥1) + Error Path(≥2) + Edge Case(≥1) + Quality(≥1) |
| 无占位符 | 无 TODO/TBD/{待填写} 等占位符 |

## 步骤 8.5：SELFREV — 单轮验证自审（签署自证 + 独立验证）

> **子代理隔离规则**：验证子代理异常（意外停止 / 报错 / 返回不完整结果）时，主代理 MUST 分析原因后重新创建新子代理（新 Agent 调用），SHALL NOT 在主 Agent 上下文中接管其未完成的工作。最多重试 3 次，全部失败后标记 ⚠️ 阻塞并提示用户。

在 VERIFY 步骤完成后、阶段完成之前，执行**单轮验证自审**。自审固定为**单轮**，由三个环节构成：

```
1. 主 Agent 签署自证（零子代理）→ 按本阶段 4 个定制维度逐项填写「维度 / 自证结论 / 证据锚点」
2. 1 轮独立子代理验证          → 先独立遍历全部子变更 tasks.md（不读签署清单）→ 再逐项对照签署清单打假 → 只报告不修改
3. 主 Agent 统一修复            → 修复全部发现项，生成「本阶段修复清单」随产物交付下游
```

**轮次规则**：轮数恒为 1（SHALL NOT 预置任何审查轮数、SHALL NOT 执行第二轮、无 0 轮豁免路径）；SHALL NOT 因该轮发现问题而自动执行第二轮，发现项一律由主 Agent 统一修复；SHALL NOT 追加确认轮。计划阶段 SELFREV SHALL NOT 使用轮间摘要机制。

**档位语义**：变更档位 SHALL 只决定**审查形态与产出深度**，SHALL NOT 决定轮数（轮数恒为 1）。自审启动前 SHALL 读取变更级 `.status.md` 的「变更档位」字段（`轻量` / `标准`）；字段缺失或读取到历史遗留的 `完整` 取值时按 `标准` 档处理。

### 签署清单

**结构与证据锚点**：签署清单 SHALL 按本阶段 4 个定制维度组织，每个维度 SHALL 包含「**维度**」「**自证结论**」「**证据锚点**」三列：

| 维度 | 自证结论 | 证据锚点 |
|------|---------|---------|
| {维度名} | 通过 / 不通过 | {产物内的具体位置} |

**证据锚点 SHALL 指向产物内的具体位置**——章节号、功能点 ID（`FP-00N`）、任务项编号或步骤序号之一；SHALL NOT 为「全文」「多处」「见上文」之类的模糊指向。

**签署不成立的判定**：锚点为空、或锚点指向的位置在产物中不存在/内容不匹配时，该维度签署 SHALL 判定为**不成立**；任一维度签署不成立时，该阶段 SHALL NOT 判定为签署通过。

**签署区落点**：签署清单 SHALL 作为子变更任务清单模板的组成部分（`subchange-tasks.md` 的「完成前签署」区），SHALL NOT 以独立文件形式产出——签署是写作动作的一部分，而非事后补录。

**主 Agent 自证义务**：子变更 tasks.md 完成后，主 Agent SHALL 逐个 4 维度完成签署自证并填写自证结论与证据锚点；**签署自证 SHALL 由主 Agent 执行，SHALL NOT 启动子代理**。自证中发现某维度不通过时，SHALL 在完成签署前修复产物并重新完成该维度自证；4 个维度签署自证全部完成后，SHALL 进入单轮验证环节。

### 单轮验证

**验证子代理执行契约**：主 Agent SHALL 启动**一个**验证子代理（`Agent(subagent_type="claude")`，独立上下文、不共享主 Agent 对话历史）。其执行顺序强制为：

```
1. 独立遍历全部子变更 tasks.md → 形成自己的 4 维度结论    ← 此阶段 SHALL NOT 读取签署清单
2. 逐项对照签署清单 → 打假                              ← 锚点为空 / 指向不存在内容 = 签署不成立
3. 输出 { 独立发现问题 | 签署打假结果 | 全量遍历证明 | 范围外观察 | 验证结论 }
4. SHALL NOT 修改任何 tasks.md（只报告）
```

- **步骤 1 前置的理由**：验证子代理若先读签署清单，会被一份已写好结论的文档锚定，退化为「回填证据」而非独立审查。把独立遍历前置，才能让单轮兼具独立发现能力。
- **执行顺序反转时该轮验证结果 SHALL NOT 被接受**，主 Agent SHALL 重新启动验证子代理。
- **步骤 4 分离的理由**：审查者与修复者分离——由主 Agent 一次性统一修复，消除「边审边修又改出新问题」的振荡源。

### 审查范围冻结与范围外观察

**审查范围冻结**：主 Agent SHALL 在单轮验证启动前从阶段产物既有内容（各子变更 tasks.md）生成**审查对象集合**并冻结，审查维度 SHALL 限于本阶段 4 个定制维度；子代理 SHALL NOT 扩大审查对象集合、SHALL NOT 新增审查维度、SHALL NOT 借审查之名新增功能点或任务。审查对象集合 MAY 因阶段输入变化（如阶段回退重执行新增受影响项）由**主 Agent** 更新，SHALL NOT 由子代理自行发起。

**范围外发现降级为范围外观察**：子代理在冻结范围之外发现的问题 SHALL NOT 触发产物修改、SHALL NOT 计入验证发现数，SHALL 记为「**范围外观察**」写入验证报告的「范围外观察」小节（为空时记「（空）」）。主 Agent SHALL 在阶段终止时汇总范围外观察条目并向用户提示。

**越界轮**：子代理引入冻结范围之外的新内容时（新增审查维度、新增功能点/任务、审查清单之外的文件），主 Agent SHALL 拒收该轮、要求其在冻结范围内重新验证，并将越界事实记录到 `docs/skill-suggestion.md`。

### 验证发现分级与终止结果

验证子代理 SHALL 将发现分为「渐进式审查发现」与「阻塞级发现」两类，并在报告中给出发现总数 N。阶段终止时 SHALL 在 `.status.md` 写入**终止结果**字段：

| 终止结果 | 判定口径 |
|---------|---------|
| `验证通过` | 单轮验证零发现 **且** 无签署不成立项 |
| `验证发现问题({N})` | 存在发现项 **或** 存在签署不成立项；N 为该阶段发现总数 |

- 仅存在范围外观察而无范围内发现时，发现数 SHALL 记为 0（其余条件同时满足时终止结果 MAY 为 `验证通过`）
- 终止结果 SHALL 与该阶段的实际终止路径一致，并作为流转依据

### 修复责任与交付

- 主 Agent SHALL 统一修复全部渐进式审查发现与阻塞级发现；SHALL 仅修复验证报告确认的问题，不做重构或额外改进；SHALL NOT 新增功能点或任务
- 主 Agent SHALL NOT 在验证子代理报告问题后追加确认轮次；修复后的产物 SHALL 直接交付编码阶段（携带「本阶段修复清单」）
- 主 Agent SHALL 生成「**本阶段修复清单**」记录修复内容，随产物一并交付下游；下游环节 SHALL 可读取该清单以验证修复结果

### 自审报告内容

单轮验证子代理完成验证后 SHALL 生成一份验证报告到 `self-reviews/plan/report.md`（固定路径，SHALL NOT 按轮次编号、SHALL NOT 产出多份时间戳文件），报告 SHALL 包含：

| 小节 | 内容 |
|------|------|
| 签署清单打假结果 | 逐维度列出：维度名、自证结论、证据锚点、打假结论（属实 / 不成立）、不成立原因 |
| 独立发现问题清单 | 序号、问题描述、严重度、所属维度（来自独立遍历，与签署对照结果分开呈现） |
| 范围外观察 | 冻结审查对象集合之外发现的条目；无条目时记「（空）」 |
| 全量遍历证明 | 显式声明 4 个审查维度与全部子变更 tasks.md 均已完成遍历 |
| 验证结论 | 发现总数 N；终止结果 `验证通过` 或 `验证发现问题({N})` |

> **反空转条款**：未证明全量遍历的报告 SHALL 判定为不完整，主 Agent SHALL 要求子代理补齐后重新提交。

### 轻量档与产物完整性门控

轻量档 SHALL 执行 SELFREV 单轮验证——SHALL NOT 跳过 SELFREV，SHALL NOT 存在 0 轮豁免路径；轮数恒为 1。产物完整性门控 SHALL 保留为**附加硬门**：

- 阶段产物 SHALL 对照「输出产物」章节清单逐项存在（全部子变更 tasks.md + traceability.md 计划列更新）
- 产物 SHALL NOT 含 `TODO` / `TBD` / `{待填写}` 等未填充占位符
- `self-reviews/plan/report.md` SHALL 存在；缺失判**缺项**
- 门控不通过 → ❌ 阻塞，修复后重跑；门控通过 → 进入步骤 9（COMPLETE）

### 审查维度与检查规则

> **设计决策**：plan 阶段的产物是 tasks.md（任务清单），与 design 阶段的 detailed-design.md（设计文档）性质不同。design 维度侧重"设计是否合理"，plan 维度侧重"任务是否可执行"。使用定制 4 维度。

#### 任务覆盖完整性

| 检查项 | 规则 |
|--------|------|
| FP 覆盖 | 所有 detailed-design.md 中的功能点是否有对应任务（覆盖率 = 100%） |
| TDD 步骤覆盖 | 每功能点是否包含完整 TDD 7 步骤（Step 1-7） |
| 测试用例映射 | 每功能点实现任务是否与 api-tests/ 和 e2e-tests/ 的测试用例对应 |

#### DoD 验收标准正确性

| 检查项 | 规则 |
|--------|------|
| 四维覆盖 | 每功能点是否包含 Happy Path(≥1) + Error Path(≥2) + Edge Case(≥1) + Quality(≥1) |
| WHEN/THEN 格式 | 每条验收标准是否使用 WHEN/THEN 格式且语义清晰 |
| 标准可达性 | 验收标准是否可在 2-5 分钟任务粒度内验证（不可过大或过小） |

#### HITL 标注准确性

> **命名说明**：本维度是对既有第 3 维度的统一命名——历史上该维度并存两种表述（一种以 HITL 决策点为核心、一种以子变更类型为核心），现裁决合并为一，统一命名为「HITL 标注准确性」。检查项 SHALL 同时保留下述两组既有检查内容，SHALL NOT 因合并而裁剪。

**HITL 决策点组**：

| 检查项 | 规则 |
|--------|------|
| 决策点列表 | 所有 HITL 子变更是否包含决策点列表 |
| `[HITL D{n}]` 标注位置 | 标注是否在正确的任务位置（Step 2 或 Step 3 之间） |
| 决策内容与选项 | 每个决策点是否有明确的决策内容和至少 2 个选项 |
| 默认建议 | 默认建议是否标注 |
| AFK 无 HITL 标注 | AFK 子变更是否不包含 HITL 标注 |
| 缺失/位置不当 | 标记缺失标注或位置不当的决策点 |

**子变更类型标注组**：

| 检查项 | 规则 |
|--------|------|
| 类型标注完整性 | 每个子变更是否明确标注了类型（后端子变更/前端子变更） |
| 前端SC输入源 | 前端子变更的输入源是否限定为 docs/designs/prototypes/manifest.md 中角色为 entry/page/tokens/shared 的文件、变更级 prototype-changes.md 声明的本变更改动，以及变更级 element-coverage-tree.md |
| 输入源排除 | 前端子变更 SHALL NOT 引用 prototype-plan/design-prompt.md 或 design-system/MASTER.md |

#### 任务粒度合理性

| 检查项 | 规则 |
|--------|------|
| 粒度标准 | 每个任务是否 2-5 分钟可完成（不过粗不过细） |
| 依赖合理性 | 任务执行顺序是否考虑了功能点依赖、数据模型优先、接口依赖 |

### 自审执行流程

```
单轮验证自审执行流程（轮数恒为 1）:

0. 读取变更档位：读取变更级 .status.md 基本信息的「变更档位」字段（缺失或历史取值 完整 按 标准 档处理）
   └── 档位只决定审查形态与产出深度，SHALL NOT 决定轮数（轮数恒为 1）

1. 主 Agent 按 4 个定制维度完成**签署自证**（零子代理），逐维度填写
   「维度 / 自证结论 / 证据锚点」；某维度不通过 → 先修复产物 → 重新自证该维度

2. 主 Agent 从既有阶段产物（各子变更 tasks.md）生成**审查对象清单**并冻结，
   审查维度限于本阶段 4 个定制维度，注入验证子代理 prompt

3. 主 Agent 启动**一个**独立验证子代理（不追加第二轮）:
   Agent(
     subagent_type="claude",
     description="Plan SELFREV 单轮验证",
     prompt="先独立遍历全部子变更 tasks.md，按任务覆盖完整性、DoD 验收标准正确性、HITL 标注准确性、任务粒度合理性全部四个维度形成你自己的结论——此阶段 SHALL NOT 读取签署清单。随后逐项对照 tasks.md 中的签署清单打假，判定每项签署是否属实（锚点为空或指向不存在内容 = 签署不成立）。审查对象集合已冻结——SHALL NOT 审查清单之外的产物或文件、SHALL NOT 新增审查维度、SHALL NOT 借审查之名新增功能点或任务。SHALL NOT 修改任何 tasks.md（只报告）。冻结范围之外发现的问题 SHALL 记为『范围外观察』写入报告的『范围外观察』小节、不计入验证发现数。报告输出到 self-reviews/plan/report.md。"
   )

4. 子代理返回报告路径 → 主 Agent 读取报告:
   ├── 校验是否越界（越界 → 拒收并要求在冻结范围内重新验证 + 记录 docs/skill-suggestion.md）
   ├── 汇总范围外观察条目（阶段终止时向用户提示）
   └── 汇总发现总数 N

5. 主 Agent 统一修复报告确认的全部问题，生成「本阶段修复清单」随产物交付编码阶段；
   SHALL NOT 追加确认轮

6. 写入 .status.md 终止结果（验证通过 / 验证发现问题({N})）
7. SHALL NOT 并行启动多个验证子代理；终止后进入步骤 9（COMPLETE）
```

### 强制执行规则

- 自审固定为**单轮**：轮数恒为 1，SHALL NOT 预置任何审查轮数、SHALL NOT 执行第二轮、无 0 轮豁免路径；SHALL NOT 追加确认轮
- 签署自证 SHALL 由主 Agent 执行（零子代理），逐维度填写自证结论与证据锚点
- 验证环节 SHALL 启动且仅启动 1 个独立子代理，SHALL NOT 并行启动多个；验证子代理 SHALL NOT 修改任何 tasks.md
- 验证子代理执行顺序 SHALL 为先独立遍历（不读签署清单）后逐项打假；顺序反转时该轮验证结果 SHALL NOT 被接受
- 审查对象集合 SHALL 由主 Agent 从阶段产物既有内容生成并冻结，审查维度限于本阶段 4 个定制维度；子代理 SHALL NOT 扩大审查对象集合、SHALL NOT 新增审查维度、SHALL NOT 借审查之名新增功能点或任务
- 冻结范围之外的发现 SHALL 记为「范围外观察」，SHALL NOT 修改产物、SHALL NOT 计入验证发现数；引入范围外新内容的轮次 SHALL NOT 被接受为有效验证，主 Agent SHALL 拒收并要求在冻结范围内重新验证 + 记录 `docs/skill-suggestion.md`
- 主 Agent SHALL 在验证完成后统一修复全部发现项并生成「本阶段修复清单」；SHALL 仅修复验证报告确认的问题，SHALL NOT 新增功能点或任务
- 轻量档 SHALL 执行 SELFREV 单轮验证，SHALL NOT 跳过；产物完整性门控保留为附加硬门（含 `self-reviews/plan/report.md` 存在性）
- 主 Agent SHALL 在阶段终止时汇总「范围外观察」条目并向用户提示
- 自审终止后，主 Agent SHALL 写入终止结果（`验证通过` / `验证发现问题({N})`）并标记阶段完成

## 步骤 9：COMPLETE — 更新状态文件

更新子变更 `.status.md`：标记计划阶段为 ✅ 完成，记录完成时间（含终止结果字段）。

状态更新完成后 SHALL 执行**阶段衔接决策**：按 [references/phase-transition.md](references/phase-transition.md) 的决策表判定目标阶段在 `.status.md` 中的状态，并据判定结果直接调度目标阶段 Skill。本阶段为子变更级，衔接分两层执行（规则见该文件 §4）：

- **子变更内推进**：在当前子变更内推进至下一阶段（计划 → 编码，调度 `kflow-code`）；
- **跨子变更遍历推进**：当前子变更的全部子变更级阶段完成后，按子变更遍历顺序推进至下一个子变更的首个未完成阶段；遍历顺序 SHALL 与 `auto-subchange-traversal` 规则一致（遍历 `🔄 进行中` / `⏳ 待开始` 的子变更，仅遍历依赖已满足的子变更；轻量档单子变更时退化为无操作，直接进入变更级阶段衔接），最后一个子变更的全部子变更级阶段完成后交回变更级阶段。

系统 SHALL NOT 提示用户输入推进指令（如「继续 {change-name}」）作为进入下一阶段的必要条件。

引用 `skills/kflow-plan/references/hooks.md` plan 阶段 POST_HOOK（❌ 不需要服务：UPDATE_STATE）。

```markdown
## 子变更信息

- **功能点数**: {数量}（≤10）
- **执行类型**: AFK / HITL
- **优先级**: {高|中|低}
- **依赖子变更**: {依赖子变更列表或"无"}

```

### HITL 决策点清单

HITL 子变更 SHALL 在任务清单中包含决策点列表：

```markdown
## HITL 决策点

| 序号 | 决策点位置 | 决策内容 | 选项 | 默认建议 |
|------|-----------|---------|------|---------|
| D1 | 编码 Step 3 前 | 缓存方案选择: Redis vs Memcached | A: Redis（持久化+丰富数据类型） / B: Memcached（更简单） | A: Redis（推荐） |
| D2 | 编码 Step 5 后 | 接口分页方式确认 | A: 偏移分页 / B: 游标分页 | A: 偏移分页（实时性要求不高） |
```

### 前端子变更依赖标注规则

前端子变更 SHALL 标注「依赖 API 契约」而非「依赖后端子变更编码完成」：

```markdown
## 子变更信息
- **依赖**: API 契约（detailed-design.md §接口设计）
- **依赖约束**: 不要求后端子变更状态为 ✅ 完成，前端子变更可与后端子变更并行启动
```

**前端子变更的依赖判定**：
- 依赖条件: detailed-design.md 中对应 API 契约章节存在且状态为 ✅ 完成
- 不依赖: 后端子变更编码状态
- 并行策略: 使用 mock 数据开发，后端子变更编码完成后替换 mock 为真实 API

### 决策点任务标识

在实现任务列表中，HITL 决策点使用 `[HITL]` 前缀标注：

```markdown
- [ ] **Step 2: 运行测试，确认失败**
- [ ] **[HITL D1] 决策点: 缓存方案选择** — 暂停等待用户确认
- [ ] **Step 3: 根据决策实现代码**
```

# 计划阶段执行模型

> 计划主工作 MUST 通过 **Agent 子代理**执行（任务拆分 / DoD 编写 / 子变更类型标注 / 输出 tasks.md），主 Agent 仅负责调度和验收，SHALL NOT 直接执行计划主工作。本阶段另有 SELFREV 环节的 **1 个**独立验证子代理（串行且仅一轮）。自审轮次与终止模型的全部规则定义在「步骤 8.5：SELFREV」一节，本节不另立第二套规则。通用规范（子代理隔离规则、prompt 规范）见 `skills/kflow-plan/references/repetition.md` §12。

## 子代理调度与主 Agent 验收

**子代理工作内容**（通过 `Agent` 工具调度，主 Agent SHALL NOT 接管）：

1. 读取 detailed-design.md 相关章节 + api-tests/（e2e-tests/ 如适用）→ 为每个子变更拆分任务、编写 4 维 DoD 验收标准、标注子变更类型 → 输出 tasks.md
2. 更新 traceability.md 计划阶段对应列 → 检查覆盖率 = 100%

**子代理 prompt 要点**（通用规范见 `skills/kflow-plan/references/repetition.md` §10）：

- 当前阶段目标与产物要求：为各子变更产出 `tasks.md`（含 4 维 DoD 验收标准与子变更类型标注）
- 输入文档引用（使用文件路径引用，非复制内容）：`detailed-design.md` 相关章节、`api-tests/`、`e2e-tests/`（如适用）
- `traceability.md` 计划阶段对应列的填充要求与覆盖率目标（= 100%）
- **审查对象清单**：由主 Agent 从 detailed-design.md 既有功能点生成并冻结；子代理 SHALL NOT 扩大该集合
- 每功能点 4 维 DoD 验收标准：Happy Path ≥1 / Error Path ≥2 / Edge Case ≥1 / Quality ≥1，全部使用 WHEN/THEN 格式
- 子变更类型标注要求：标注 `后端子变更` / `前端子变更`；前端子变更的输入源限定为 `docs/designs/prototypes/manifest.md` 中角色为 entry/page/tokens/shared 的文件、变更级 `prototype-changes.md` 声明的本变更改动，以及变更级 `element-coverage-tree.md`
- 范围外发现降级指令：冻结范围之外发现的问题 SHALL NOT 计入执行发现数，记为「范围外观察」写入执行报告的「范围外观察」小节
- SHALL NOT 包含任何轮次数值上限或按轮次分段分配工作重点的指令

**主 Agent 验收标准**（以「执行报告完整 + 产物齐全 + 覆盖率达标 + 无占位符」为通过条件，SHALL NOT 以轮次数量作为通过或拒收依据）：

| 验收项 | 判定条件 |
|--------|---------|
| 执行报告完整 | 子代理返回的执行报告存在，且含全部功能点已完成全量遍历的证明 |
| 产物齐全 | 所有子变更 tasks.md 存在且格式正确 |
| 覆盖率达标 | 所有功能点都有对应任务（功能点覆盖 = 100%） |
| DoD 完整 | 每功能点包含 4 维验收标准 |
| 无占位符 | 无 TODO/TBD/{待填写} |
| HITL 门控 | 所有子变更 SHALL NOT 含 HITL 标记（已在门控阶段拒绝） |
| 审查范围冻结 | 未引入冻结审查对象集合之外的新内容；越界 → 拒收并要求在冻结范围内重新执行 |

## 复杂度评估

复杂度评估仅信息展示，不驱动执行行为：

```
复杂度分 = 功能点数 × 1 + 接口数 × 1.5 + 场景数 × 2

低复杂度 (< 20 分) / 中复杂度 (20-50 分) / 高复杂度 (> 50 分)
```

分级阈值保留但仅用于信息分类，复杂度分写入 .status.md 备注列标注「仅供参考，不驱动执行行为」。复杂度不参与轮次决策——自审轮数恒为 1。

## 执行流程

```
1. 复杂度评估 → 写入 .status.md 备注列（仅信息展示，不驱动执行行为）

1.5 INIT → 读取变更级 .status.md 的「变更档位」字段（缺失或历史取值 完整 按 标准 档处理），仅用于确定
     审查形态与产出深度（SHALL NOT 决定轮数）；写入 .status.md 执行轮次为 1 轮

2. 主 Agent 构建阶段输入
   ├── 分层加载（基础层 + 执行层）:

   │   ├── skills/kflow-plan/references/state-values.md（摘要）
   │   ├── skills/kflow-plan/references/gates.md（当前阶段相关门控）
   │   └── skills/kflow-plan/references/repetition.md（子代理隔离规则）
   ├── 输入: detailed-design.md 相关章节 + api-tests/ + e2e-tests/(🔶)
   ├── 本子代理承担的功能点范围: {子变更}/{FP-NNN 列表}（单个子代理 ≤ 3 个功能点；超出时先分片再构建 prompt，前一片落盘后启动后一片承接）
   └── 输出: 各子变更 tasks.md（含 DoD 验收标准 + 子变更类型标注 + 4 维度签署清单）

3. 调度 Agent 子代理执行计划主工作 → 输出各子变更 tasks.md 并更新 traceability.md 计划列

4. 进入 SELFREV 单轮验证（步骤 8.5）→ 主 Agent 签署自证 → 1 轮独立子代理验证打假 →
   主 Agent 统一修复 → 写入终止结果（验证通过 / 验证发现问题({N})）

5. 主 Agent 按「验收标准」表核验 → 通过 → 释放编码阶段门控
```

## 验收结果处理

| 情况 | 处理方式 |
|------|---------|
| 通过 | 更新 .status.md（终止结果 `验证通过` 或 `验证发现问题({N})`）→ 释放编码阶段门控 |
| 越界（引入范围外新内容） | 拒收该轮，要求子代理在冻结范围内重新验证，不进入 AskUserQuestion |
| 产物不合格 / SELFREV 未完成 | 修复后重跑对应环节；无法推进时记录 `docs/skill-suggestion.md` → AskUserQuestion 询问重跑；用户选「否」→ 标记 ⚠️ 阻塞 |

> **终止结果**：阶段终止时 SHALL 在 .status.md 写入终止结果，取值 `验证通过` / `验证发现问题({N})`；`执行轮次` 字段格式为 `{N} 轮`（无分母，单轮验证记 `1 轮`）。

# 核心提醒

- 输入来自**变更级** `detailed-design.md`，非子变更级，读取时定位到当前子变更的章节
- 任务粒度标准：2-5 分钟可完成的原子级任务
- DoD 采用 WHEN/THEN 格式，每功能点 4 维（Happy ≥1 + Error ≥2 + Edge ≥1 + Quality ≥1）
- HITL = 设计不完整标记，HITL 子变更禁止进入 plan 阶段，需回退到 kflow-design 补全设计
- 禁止 TODO/TBD/{待填写} 等占位符
- 自审固定为**单轮验证**：轮数恒为 1，SHALL NOT 执行第二轮、无 0 轮豁免路径、不追加确认轮（参见步骤 8.5 与 `skills/kflow-plan/references/repetition.md`；缺失档位或历史取值 完整 按 标准 档）；轻量档同样执行单轮验证并附加产物完整性门控
- **审查范围冻结**：主 Agent 从阶段产物既有内容生成审查对象集合并冻结，审查维度限于 4 个定制维度；冻结范围之外的发现降级为「范围外观察」——不改产物、不计入验证发现数；越界轮 SHALL NOT 被接受为有效验证
- **轻量档子变更**：轻量档变更为 1 或 2 个子变更，「遍历全部子变更」等复数表述即为遍历该 1 或 2 个子变更，不产生额外要求；`api-tests/` 可因 `接口单元测试` 被裁剪而不存在，属合法跳过
- **单轮验证自审强制执行**：OUTPUT 步骤完成后自动进入 SELFREV，主 Agent 完成 4 维度签署自证（零子代理）→ 启动 1 个独立子代理做单轮验证（先独立遍历全部子变更 tasks.md 形成自身结论且不读签署清单，再逐项对照签署清单打假，只报告不修改任何 tasks.md）→ 主 Agent 统一修复并生成「本阶段修复清单」；4 维度为任务覆盖完整性 / DoD 验收标准正确性 / HITL 标注准确性 / 任务粒度合理性，审查对象集合由主 Agent 冻结、维度集合封闭；轮数恒为 1、SHALL NOT 执行第二轮，终止结果 `验证通过` / `验证发现问题({N})`
