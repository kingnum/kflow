> **适用范围**: 所有阶段的正向门控检查和回退门控
> **加载层级**: 基础层

>
> **v1.1.0**: 门控按变更档位分支——进入计划门控（Gate 2）按三档检查审查产物，代码审查门控新增轻量档单 Agent 判定，自审记录份数检查改为按档位目标轮次。新增「变更档位」字段的透传与校验要求。

## 1. 门控规则标注约定

每条门控规则显式标注适用性标签，用于门控执行时判断是否应用该规则。

| 标注 | 含义 |
|------|------|
| `[全部]` | 所有子变更类型和项目类型均适用 |
| `[后端子变更]` | 仅适用于后端子变更 |
| `[前端子变更]` | 仅适用于前端子变更 |
| `[前端项目]` | 仅适用于前后端项目 |
| `[纯后端项目]` | 仅适用于纯后端项目 |
| `[轻量档]` | 仅适用于变更档位 = 轻量 |
| `[标准档]` | 仅适用于变更档位 = 标准 |
| `[完整档]` | 仅适用于变更档位 = 完整 |

### 1.1 变更档位字段的透传与校验

变更档位（`轻量` / `标准` / `完整`）是门控分支的依据，持久化在变更级 `.status.md` 基本信息：

| 规则 | 说明 |
|------|------|
| 读取时机 | 每个阶段入口门控 SHALL 读取变更级 `.status.md` 的「变更档位」字段 |
| 缺省回退 | 字段缺失（如历史变更）时按 `完整` 档处理，等价于历史行为 |
| 透传 | 阶段执行与子代理 prompt 构建 SHALL 透传该字段；SHALL NOT 在门控中绕过读取并假定默认值 |
| 校验 | 字段值不在 `{轻量, 标准, 完整}` 枚举内时 SHALL 按 `完整` 档处理并记录到 `docs/skill-suggestion.md` |

> 未按档位分支而一律套用完整档检查项的门控，会造成轻量档误报阻塞（如要求 10 份自审报告、四份视角报告）。

### 1.2 阶段适用性声明与四态判定

**适用范围**: 阶段裁剪 SHALL 仅适用于 `变更档位 = 轻量` 的变更，且仅覆盖 `接口单元测试`、`E2E测试`、`集成测试` 三个阶段。`标准` 与 `完整` 档 SHALL NOT 应用本节规则；纯后端项目跳过 E2E测试的既有规则不受影响。

**声明读取**:

| 规则 | 说明 |
|------|------|
| 读取位置 | 变更级 `.status.md` 的「阶段适用性声明」区 |
| 读取时机 | 接口单元测试、E2E测试、集成测试、审计、归档各阶段的入口门控 |
| 缺省处理 | 声明区缺失（非轻量档、历史变更、升档后失效）时，三个阶段 SHALL 全部按 `✅ 适用` 处理 |
| 依据校验 | 判定 `⏭️ 不适用` 是否合法时，MUST 校验声明区中存在对应的判定依据条目 |

**四态判定矩阵**（门控检查涉及阶段产物时 SHALL 按「声明 × 产物」组合判定）:

| 声明 | 产物 | 判定 | 输出 |
|------|------|------|------|
| `⏭️ 不适用` | 不存在 | 合法跳过，通过 | — |
| `⏭️ 不适用` | 存在 | 不一致，阻塞 | 提示声明与产物矛盾，要求清理产物或恢复声明 |
| `✅ 适用` | 存在 | 通过 | — |
| `✅ 适用` | 不存在 | 阻塞 | 缺失产物清单 |

**无声明依据的跳过**:

- 某阶段被标记 `⏭️` 但 `.status.md` 中无对应的适用性声明依据 → SHALL 阻塞，提示缺失裁剪依据
- 判定依据 SHALL NOT 由产物存在性或缺省值推断得出（缺省只产生 `✅ 适用`，不产生 `⏭️`）
- 无依据的 `⏭️` 在阶段门控、审计轻量自检、归档门控、产物诊断中 SHALL 一律阻塞，不因标记来源或标记者而豁免
- **按项目类型的跳过不受本规则约束**: 由项目类型产生的 `⏭️`（如纯后端项目的 E2E测试阶段与 `traceability.md` 的 E2E测试列）依据项目类型判定、与变更档位无关，SHALL NOT 要求适用性声明依据。本规则仅约束声称由变更档位裁剪产生的 `⏭️`。两种依据并存时按项目类型的跳过优先判定，按变更档位的跳过仅在项目类型判定为适用时进一步判定

**裁剪可裁阶段的产物落点**:

| 阶段 | 产物 | 裁剪后 |
|------|------|--------|
| 接口单元测试 | `api-tests/` | SHALL NOT 产出；进入计划门控（Gate 2）的存在性检查与覆盖率列的检查均视为满足 |
| E2E测试 | `e2e-tests/` | SHALL NOT 产出；进入计划门控（Gate 2）的存在性检查与进入集成测试的前置覆盖检查均视为满足 |
| 集成测试 | `test-reports/integration/` | SHALL NOT 产出；归档门控视为满足，直接进入审计 |

> **轻量档下的步骤顺序约束**: 阶段适用性判定的输入是 `detailed-design.md`（接口设计章节、跨子变更接口契约章节），判定结果决定 `api-tests/`、`e2e-tests/` 是否产出。因此 `轻量` 档下 kflow-design SHALL 按下述顺序执行：**编写 detailed-design.md → DIVIDE → 判定适用性并写入声明 → 编写 `api-tests/` 与 `e2e-tests/`（仅限判定为 `✅ 适用` 者）→ 设计审查**。SHALL NOT 在判定之前产出这两个目录，否则会落入「声明不适用但产物存在」的阻塞态。
>
> `标准` 与 `完整` 档不生成适用性声明，步骤顺序维持既有规则不变。

> **四态判定的「产物」口径**: 以各阶段门控实际检查的路径为准——接口单元测试 → `api-tests/`，E2E测试 → `e2e-tests/`，集成测试 → `test-reports/integration/`。同属该阶段但未被门控检查的产物（如 `integration-tests/` 用例文档）在判定为 `⏭️ 不适用` 时 SHALL NOT 产出，其缺失不触发不一致判定。

> 接口单元测试与 E2E测试均被裁剪时，子变更在代码审查完成后 SHALL 直接进入变更级同步点，SHALL NOT 进入 `⏸️ 等待同步` 状态。

```

     └── 无声明依据的 ⏭️ → ❌ 阻塞，提示缺失裁剪依据
   - 检查: (当前子变更为前端SC 或 项目类型为前后端) e2e-tests/index.md 文件存在 [前端SC + 前后端项目]

     └── 无声明依据的 ⏭️ → ❌ 阻塞，提示缺失裁剪依据
   - 检查: (当前子变更为后端子变更) 跳过 e2e-tests/index.md 检查 [后端子变更]
   - 失败: 提示先完成详细设计和审查

2.5 ADR 门控规则:
   - ADR 三条件过滤: 仅当 1) 难以逆转 2) 缺上下文会奇怪 3) 真正做了权衡 — 三项同时满足时创建 ADR

   - 检查: 当前子变更的依赖子变更已完成编码和接口单元测试 [全部]
     └── 轻量档例外 [轻量档]: 依赖子变更的接口单元测试被判定为 ⏭️ 不适用 且有判定依据时，该项视为满足

   - 检查: (当前子变更为前端SC) 变更级 prototype-changes.md 存在 [前端子变更]

     ├── 声明 = ⏭️ 但无判定依据 → ❌ 阻塞，提示缺失裁剪依据
     └── 声明 = ✅ 适用 或 声明区缺失 → 继续以下检查
   - 检查: 编码状态 = ✅ 完成 [全部]
   - 检查: 代码审查状态 = ✅ 完成（kflow-code-review 通过）[全部]
   - 检查: 子变更代码审查报告存在(test-reports/review/code-review.md) [全部]
   - 检查: 所有接口单元测试代码已编写 [全部]
   - 失败: 提示先完成编码和代码审查

   **Step 0: 变更级服务刷新同步点**（每轮测试前强制执行，由变更级 agent 执行）:
   
   ```
   门控触发: 进入新的接口单元测试轮次、E2E 测试轮次或集成测试轮次（含首轮）
       │
       ▼
   变更级 agent 执行每轮编译重启标准步骤（详见 skills/kflow-code-review/references/hooks.md）:
   1. 停止当前服务
   2. 编译后端
   3. 编译前端（前后端项目）
   4. 执行未执行迁移（跳过 migration-log.md 已标记的迁移）
   5. 启动后端服务
   6. 启动前端服务（前后端项目）
   7. 健康检查 (/health + /db-health)
       │
       ├── 失败 → ❌ 阻塞 (障碍自解循环)
       └── 通过 → 释放门控 → 通知子变更 agent「服务就绪，开始 Round N」
   ```
   
   > 此同步点每轮测试前执行，不再是一次性门控。Round 1 首轮刷新与后续轮次流程一致。

     ├── 声明 = ⏭️ 不适用 但 `e2e-tests/` 存在 → ❌ 阻塞，提示声明与产物不一致
     ├── 声明 = ⏭️ 但无判定依据 → ❌ 阻塞，提示缺失裁剪依据
     └── 声明 = ✅ 适用 或 声明区缺失 → 继续以下检查
   - 检查: 接口单元测试状态 = ✅ 完成 或 ⏭️ 不适用（仅轻量档裁剪，且有声明依据）[全部]
   - 检查: 项目类型 = 前后端项目（纯后端跳过）[前后端项目]
   - 检查: traceability.md「接口测试」列覆盖率 = 100%（该列因轻量档裁剪标记 ⏭️ 不适用 时 SHALL NOT 检查）[全部]
   - 检查: element-coverage-tree.md 存在（有原型时在变更根目录，无原型时在 e2e-tests/ 目录下）[前端项目]
     └── 轻量档例外 [轻量档]: E2E测试被判定为 ⏭️ 不适用 且有判定依据时，该产物 SHALL NOT 产出，SHALL NOT 检查此项
   - 检查: (纯后端项目) 跳过 element-coverage-tree.md 检查 [纯后端项目]
   - 失败: 提示先完成接口单元测试

6. 进入集成测试阶段（执行入口: `kflow-integration-test` Skill）:
   - 检查: 阶段适用性声明按四态判定 [轻量档]:
     ├── 声明 = ⏭️ 不适用 且 `test-reports/integration/` 不存在 → 合法跳过：SHALL NOT 启动
     │     `kflow-integration-test`，SHALL 直接进入审计阶段，阶段状态标记为 ⏭️ 不适用
     ├── 声明 = ⏭️ 不适用 但 `test-reports/integration/` 存在 → ❌ 阻塞，提示声明与产物不一致
     ├── 声明 = ⏭️ 但无判定依据 → ❌ 阻塞，提示缺失裁剪依据
     └── 声明 = ✅ 适用 或 声明区缺失 → 继续以下检查
   - 检查: 所有子变更 E2E测试(前后端)或接口单元测试(纯后端) = ✅ 完成 或 ⏭️ 不适用（仅轻量档裁剪，且有声明依据）
   - 检查: 所有子变更 tasks.md 中所有 checkbox 已勾选
   - 检查: 变更级服务刷新已完成并通过
   - 检查: integration-tests/index.md 存在
   - 检查: traceability.md「编码实现」列覆盖率 = 100%
   - 检查: (前后端项目) traceability.md「E2E测试」列覆盖率 = 100%（该列因轻量档裁剪标记 ⏭️ 不适用 时 SHALL NOT 检查；纯后端项目该列的既有权跳过规则不变）
   - 检查: 因轻量档裁剪标记 ⏭️ 不适用 的列 SHALL NOT 参与上述覆盖率检查
   - 检查: functional-designs/index.md 存在且非空 [全部]
   - 检查: detailed-design.md 存在且非空 [全部]
   - 检查: (前后端项目 且 原型设计状态 ≠ ⏭️ 跳过) docs/designs/prototypes/manifest.md 与变更级 prototype-changes.md 存在 [前后端项目+原型未跳过]
   - 失败: 提示先完成所有子变更和服务刷新

7. 进入归档阶段:
   - 检查: 集成测试状态 = ✅ 完成 或 ⏭️ 不适用（仅轻量档裁剪，且有阶段适用性声明依据）
   - 检查: 无声明依据的 `⏭️` 阶段 → ❌ 阻塞，提示缺失裁剪依据
   - 检查: 所有子变更各阶段（计划、编码、代码审查、接口单元测试、E2E测试）完成 或 已按轻量档适用性声明裁剪
   - 检查: test-reports/integration/summary.md 存在且标记"集成测试通过"；集成测试阶段被合法裁剪时 SHALL NOT 要求该产物存在
   - 检查: traceability.md 所有适用列覆盖率 = 100%（仅轻量档裁剪产生的、具有声明依据的 ⏭️ 不适用 列 SHALL 视为满足，SHALL NOT 参与判定）
   - 检查: (前后端项目) traceability.md「E2E测试」列覆盖率 = 100%（该列因轻量档裁剪标记 ⏭️ 不适用 时 SHALL NOT 检查；纯后端项目该列的既有权跳过规则不变）
   - 检查: 用户验收确认状态 = ✅ 已确认 或 ⏭️ 用户跳过
   - 失败: 提示先完成集成测试和用户验收确认

8. 用户验收确认门控（归档前置）:
   - 检查: .status.md 中「用户验收确认」状态
   - 状态 = ✅ 已确认 或 ⏭️ 用户跳过 → 门控放行
   - 状态 = ⏳ 待确认 或未设置 → 门控失败，启动服务 + AskUserQuestion 发起用户验收
   - 用户验收不通过 → 路由到 kflow-bug-fix，修复后重新执行测试→审计→用户验收循环

9. 中断恢复产物完整性验证门控（kflow-resume GATE 步骤）:
   - 对 .status.md 中标记为「✅ 完成」的每个阶段执行产物验证:
     - 编码: 执行轮次=N/N（N 由弹性轮次决策确定）+ traceability 编码列=100% + 无占位符
     - 代码审查: code-review.md 存在 + 审查通过标记
     - 接口测试: api/summary.md 存在 + 健康评分达标
     - E2E 测试: e2e/summary.md 存在
     - 集成测试: integration/summary.md 存在
     - 详细设计: detailed-design.md + self-reviews/design 份数 = 自审目标轮次（首次 10 / 非首次弹性）+ cross-reviews ≥1 批次 + traceability 设计列=100%
     - 原型设计: docs/designs/prototypes/manifest.md 与变更级 prototype-changes.md 存在 + 用户评审=✅已确认 或 ⏭️跳过 + BUILD 报告存在（self-reviews/prototype/cdn-crossref-check/report.md）
   - 验证不通过 → 拒绝认定该阶段完成，标记为「⚠️ 需修订」，调度回退重新执行
   - 仅验证「✅ 完成」阶段，不检查「⏳ 待开始」或「🔄 进行中」阶段
```

## 3. 阶段回退门控规则

```
阶段回退门控规则:

触发回退时:
1. 当前阶段状态: 🔄 → ❌ 阻塞
2. 目标回退阶段状态: ✅ → ⚠️ 需修订
3. 目标阶段之后的所有阶段状态: 重置为 ⏳ 待开始
4. 受影响产物的状态: 标记为"待修订"（不删除，保留参考价值）

回退触发来源（6 种）:
├── 缺陷修复发现设计错误 → 回退到设计阶段
├── 代码审查发现结构性问题 → 回退到设计阶段
├── 用户需求变更 → 回退到设计探索阶段
├── 审计发现 (kflow-audit) → 按问题归属阶段回退
├── 编码发现原型交互/视觉/状态问题 → 回退到 prototype-design 阶段（REVISION 模式）
└── 编码发现功能点/业务规则需调整 → 回退到 explore（功能性）或 design（技术性）

回退到 prototype-design 的场景:
1. 编码时发现原型交互流程不合理（如按钮位置导致误操作、流程步骤跳跃）
2. 编码时发现视觉设计问题（如颜色对比度不足、元素被遮挡）
3. 编码时发现状态覆盖缺失（原型缺少错误态/加载态/空态定义）
4. 进入 prototype-design REVISION 模式（加载已有原型 + 用户修订需求 → 修订 → 验证 → 用户确认）

依赖子变更联动:
├── 仅当前子变更受影响 → 单独回退
├── 接口契约变更 → 依赖该接口的子变更联动回退
├── 架构级变更 → 所有子变更联动回退
├── 审计发现 → 按审计问题归属阶段确定回退范围和联动子变更
└── 原型回退 → 当前子变更回退到 prototype-design，不联动其他子变更（原型修订完成后需重新走 design→plan→code）

回退完成时:
1. 修订阶段重新执行完毕: ⚠️ 需修订 → ✅ 完成
2. 后续阶段逐个重新执行
3. 原型修订后: prototype-design REVISION 完成 → 回到 design 继续后续流程 → plan（仅影响原型变更的子变更）→ code

functional-designs/ 修订规则:

| 修订时机 | 允许 | 修订范围 | 影响 |
|---------|------|---------|------|
| 详细设计阶段 | ✅ | 功能点拆分、技术方案 | 更新版本号+修订记录 |
| 第一个子变更编码 | ✅ (走需求变更流程) | 该子变更相关功能点 | 回退设计阶段 |
| 后续子变更编码 | ⚠️ 有限 | 仅该子变更 | 不影响其他 |
| 集成测试阶段 | ❌ | - | 必须创建新变更 |
```

## 4. 代码审查门控规则

审查形态与门控条件按变更档位分支；档位读取自变更级 `.status.md`「变更档位」字段，缺失按 `完整` 档处理。

| 变更档位 | 审查形态 | 门控规则 |
|---------|---------|---------|
| 轻量 | 单 Agent 单轮，串行覆盖安全+规范与质量+性能两视角全部检查项 | 高严重度 = 0 且 中严重度 < 3 → ✅ 通过；否则 ❌ 阻塞。SHALL NOT 要求多份视角报告 |
| 标准 | 两视角并行（Agent 1 安全+规范 / Agent 2 质量+性能） | Agent 1 高严重度 = 0 且 Agent 2 高严重度 = 0 且 Agent 2 中严重度 < 3 → ✅ 通过；否则 ❌ 阻塞 |
| 完整 | 两视角并行（同上） | 同标准档 |

**视角检查项**（轻量档单 Agent 与标准/完整档两视角 SHALL 覆盖同一套检查项，不得因合并而裁剪）：

| Agent | 审查内容 | 门控规则 |
|-------|---------|---------|
| Agent 1 (安全+规范) | SQL注入/XSS/CSRF、敏感信息泄露、编码规范、依赖安全漏洞 | 高严重度 ≥1 → ❌ 阻塞 |
| Agent 2 (质量+性能) | N+1查询、内存泄漏、错误处理完整性、代码复杂度 | 高严重度 ≥1 或 中 ≥3 → ❌ 阻塞 |

## 5. 审查闭环验证规则

问题修复后的验证方式按变更档位分支。

**轻量档**：SHALL 执行**单轮复检**——由单 Agent 复核全部已修复问题，SHALL NOT 执行按高/中/低严重度分级的差异化重审。

**标准档与完整档**：

| 严重度 | 验证方式 | 执行者 |
|--------|---------|--------|
| 高 | 重新审查（原视角 + 安全视角交叉检查） | Agent |
| 中 | 重新审查（原视角） | Agent |
| 低 | 抽查（随机 30%） | Agent |

## 6. 子变更依赖规则

- 子变更按依赖顺序依次完成
- 当前子变更编码前，其依赖的子变更必须编码完成
- 编码启动前检查活跃变更文件重叠（跨变更冲突检测）
- 子变更接口单元测试和E2E测试独立进行，但集成测试需所有子变更完成

## 7. HITL 阻塞 plan 入口规则

```
HITL 阻塞 plan 入口:

  子变更标记为 HITL:
    │
    └── plan 入口门控 SHALL 检测到 HITL 标记 → ❌ 阻塞
         └── 提示: "子变更 {name} 存在未决设计决策，请先在 design 或 prototype-design 阶段完成决策"
  
  解决方案:
    1. 在设计阶段完成未决决策（创建 ADR、用户评审确认、接口契约批准）
    2. 将子变更标记从 HITL 转为 AFK
    3. 更新 detailed-design.md 子变更划分表中的执行类型
    4. plan 入口门控释放
```

## 8. 编码阶段上游问题决策流程

当编码阶段发现上游产物存在问题时，SHALL 执行标准化决策流程而非自动回退：

```
编码阶段发现上游问题:
    │
    ├── 步骤 1: 判定根因归属
    │   ├── 原型交互/视觉/状态问题 → 回退目标: prototype-design（REVISION 模式）
    │   ├── 功能点/业务规则问题 → 回退目标: explore（功能性）或 design（技术性）
    │   └── 纯实现层面可修复 → 不触发回退（继续编码）
    │
    ├── 步骤 2: 记录到 skill-suggestion.md
    │   └── 记录根因判定结果和影响范围
    │
    ├── 步骤 3: AskUserQuestion 确认决策
    │   ├── "确认回退到 [目标阶段]" → 执行回退流程
    │   ├── "暂缓此功能点（标记 ⏸️）" → 标记该 FP 为 ⏸️ 暂缓，继续其他 FP
    │   └── "记录为已知问题继续" → 记录不阻止继续
    │
    └── 步骤 4: 回退执行（如用户确认）
        ├── 原型回退 → 进入 prototype-design REVISION 模式（加载已有原型 + 用户修订需求 → 修订 → 验证 → 用户确认 → 回退到 design 继续）
        ├── 功能设计回退 → 回退到 explore 修订功能点设计
        └── 技术设计回退 → 回退到 design 修订技术方案
```
