# 执行类阶段执行模型规范

> **版本**: 3.0.0
> **来源**: core-mechanisms/07-agent-model.md §15
> **适用范围**: 所有执行类阶段（计划/编码/代码审查/接口单元测试/E2E测试/集成测试/缺陷修复）
> **加载层级**: 执行层
> **适用阶段**: plan/code/code-review/api-test/e2e-test/integration-test/bug-fix
>
> **v3.0.0**: 执行类阶段执行模型按阶段类型**二分**（**BREAKING**）——**单轮类阶段**（接口单元测试 / E2E 测试 / 集成测试）改为**单轮全面执行 + 定向重验**（仅重跑失败用例，属有界重试），删除多轮循环判据与轮间摘要注入；**重复制类阶段**（编码 / 代码审查 / 缺陷修复）沿用重复制循环，每轮全量遍历全部工作项，删除收敛判据与跨轮修复清单，连续 3 轮无实质进展时停滞升级。终止结果取值改为 `执行完成` / `定向重验失败` / `停滞`。kflow-plan 阶段的产物自审由 `plan-self-review` 承载，不适用本文件的执行模型。**执行类阶段的权威定义见 `agent-iteration-execution` 能力；轮间摘要见 `inter-round-summary` 能力。**
>
> **历史版本**（v1.1.0 轮间摘要机制、v1.2.0 §12 强化、v1.3.0 弹性重复制、v1.4.0 权限预配置与后台回退、v1.5.0 ~ v2.0.0 档位驱动轮次与收敛终止模型）中与本版本冲突的机制描述已删除——这些版本描述的机制本身已不存在，其变更记录保留在 `openspec/changes/archive/` 下的对应变更中。

## 1. 概述

> **分层加载说明**：本文件属于「执行层」，仅在执行类阶段（plan/code/code-review/api-test/e2e-test/integration-test/bug-fix）的子代理 prompt 中加载。设计类与归档类阶段不加载本文件。详见 `07-agent-model.md` §17。

执行类阶段按**执行模型**分为两类，划分标准是「该阶段的工作是否存在真实的逐轮增量」：

| 执行模型 | 阶段 | 模型要点 |
|---------|------|---------|
| **单轮类** | 接口单元测试、E2E测试、集成测试 | 一轮内遍历全部工作项执行完整流程；发现失败项时走**定向重验**——仅重跑失败用例，不重跑全量 |
| **重复制类** | 编码、代码审查、缺陷修复 | 每轮遍历全部工作项独立执行完整流程，禁止按轮次分段分配工作重点；轮次由实际执行的循环决定 |

> **为什么按增量真实性切分**：测试阶段的多轮通常只是在重复执行已覆盖的用例（成本真实、增量不真实）；编码阶段每轮确实在推进新工作项（增量真实）。

**kflow-plan 的适用性**：kflow-plan 阶段的产物自审（SELFREV）由 `plan-self-review` 能力承载，不适用本文件的单轮类 / 重复制类执行模型；其主工作 MUST 通过子代理执行（主 Agent SHALL NOT 执行计划主工作），本文件 §12（子代理隔离规则）对 kflow-plan 中调度子代理的环节仍然适用。

**设计类阶段的自审（SELFREV）** 由各阶段 Skill 自身的 `references/self-review.md` 承载，不适用本文件。

## 2. 执行模型核心特征

**单轮类阶段**：

- **单轮全量执行**：在一轮内遍历全部工作项执行完整流程，SHALL NOT 执行第二轮全量审查
- **定向重验**：发现失败项时 SHALL 仅重跑失败用例，不重跑全量；属**有界重试**，SHALL NOT 使用轮次循环判据
- **命名区分**：定向重验触发于测试失败后的修复动作，与已移除的 `recheck-round`（审查循环到达终止点后追加的复核轮）语义不同，SHALL NOT 混用命名
- **审查范围冻结**：审查对象集合由主 Agent 从阶段产物既有内容生成并冻结，审查维度限于该阶段固定枚举；冻结范围之外的发现降级为「范围外观察」

**重复制类阶段**：

- **每轮全量遍历**：每轮遍历全部工作项（全部功能点/全部代码变更/全部子变更任务），不跳过已通过项
- **独立完整流程**：每轮对每个工作项独立执行完整流程（TDD/审查/修复），不跨轮分工
- **子变更自动遍历**：编码和代码审查阶段采用双层遍历——外层遍历全部未完成编码/待审查的子变更，内层对每个子变更遍历其全部功能点/代码变更。禁止仅处理单个子变更后等待用户确认
- **禁止节奏指引**：禁止「前 N 轮重点执行/中间 N 轮细节优化/后 N 轮验证」等分段分配指令
- **自然终止**：某轮无新发现且无可执行工作时返回执行报告（须证明全部工作项已完成全量遍历），SHALL NOT 为凑轮次而执行无增量价值的轮次
- **停滞升级**：连续 3 轮无实质进展（同一问题项反复出现）时返回执行报告并标注停滞缘由，升级用户
- **审查范围冻结**：审查对象集合由主 Agent 从阶段产物既有内容生成并冻结，审查维度限于该阶段固定枚举；冻结范围之外的发现降级为「范围外观察」
- **轮间摘要**：第 2 轮起注入前轮摘要以优化注意力分配（§13），仅重复制类阶段适用
- **保留强制子代理 + 主 Agent 验收闭环**

## 3. 阶段分类

| 类别 | 阶段 | 执行模式 | 说明 |
|------|------|---------|------|
| 单轮类执行阶段 | 接口单元测试、E2E测试、集成测试 | 单轮全面执行 + 定向重验 | 任务明确可量化，一轮内遍历全部工作项执行完整流程；失败项按定向重验处理 |
| 重复制类执行阶段 | 编码、代码审查、缺陷修复 | 重复制循环 | 每轮全量遍历全部工作项，独立执行完整流程；轮次由实际执行的循环决定 |
| 创造性阶段 | 设计探索、原型设计、详细设计、归档、审计 | 主 Agent 直连（自审环节除外） | 需要创造性思维和深度上下文理解，主要流程由主 Agent 执行；自审（SELFREV）由各阶段自身的 `references/self-review.md` 承载 |
| 计划阶段 | 计划 | 主工作由子代理执行 + 单轮验证自审 | 主工作 MUST 通过子代理执行（主 Agent SHALL NOT 执行计划主工作）；产物自审（SELFREV）由 `plan-self-review` 能力承载，采用单轮验证模型；不适用本文件的单轮类 / 重复制类执行模型 |

## 4. 执行流程

```
单轮类阶段执行流程（接口单元测试 / E2E测试 / 集成测试）:

┌─────────────────────────────────────────────────────────────┐
│              SINGLE-ROUND WORKFLOW                            │
├─────────────────────────────────────────────────────────────┤
│  1. ASSESS     → 复杂度评估（仅信息展示，写入 .status.md）    │
│  1.5 CHECK_HISTORY → 读取阶段执行历史与最近修订信息           │
│  │   └── 回退重执行 → 读取「最近修订信息」中的受影响项清单     │
│  │       （供 §15 验证门控使用）                              │
│  1.6 INIT      → 主 Agent 写入 .status.md 执行轮次为 1 轮      │
│  2. PROMPT     → 构建阶段专属 prompt（含单轮执行指令、         │
│  │               审查范围冻结指令、范围外发现降级指令）        │
│  3. DISPATCH   → 启动 Agent 子代理                            │
│  4. EXECUTE    → 子代理在一轮内遍历全部工作项执行完整流程      │
│  │              发现失败项 → 返回执行报告（含失败用例清单）     │
│  5. FIX        → 主 Agent 汇总失败项 → 调度修复                │
│  6. RECHECK    → 定向重验：仅重跑失败用例（不重跑全量）        │
│  │   ├── 全部通过 → 进入验收                                  │
│  │   ├── 仍有失败 → 再次定向重验，`执行轮次` 递增              │
│  │   └── 连续 3 次定向重验未通过 → 终止结果 `定向重验失败`     │
│  7. ACCEPT     → 主 Agent 验收（§8）                          │
│  8. RESULT     → 通过 → 终止结果 `执行完成` → 释放门控         │
└─────────────────────────────────────────────────────────────┘
```

```

┌─────────────────────────────────────────────────────────────┐
│              REPETITION MODE WORKFLOW                         │
├─────────────────────────────────────────────────────────────┤
│  1. ASSESS     → 复杂度评估（仅信息展示，写入 .status.md）    │
│  1.5 CHECK_HISTORY → 读取阶段执行历史与最近修订信息           │
│  │   └── 回退重执行 → 读取「最近修订信息」中的受影响项清单     │
│  │       （供 §15 验证门控使用）                              │
│  1.6 INIT      → 主 Agent 写入 .status.md 执行轮次为 1 轮      │
│  2. PROMPT     → 构建阶段专属 prompt（含重复制遍历指令、      │
│  │               审查范围冻结指令、范围外发现降级指令）        │
│  3. DISPATCH   → 启动 Agent 迭代子代理                       │
│  4. ITERATE    → 子代理每轮遍历全部工作项独立执行完整流程      │
│  │              每轮递增计数器，直至全部工作项完成全量遍历      │
│  5. ACCEPT     → 主 Agent 验收（§8）:                        │
│  │   ├── 执行轮次 >= 1                                        │
│  │   ├── 未引入冻结审查对象集合之外的新内容                    │
│  │   ├── 产物文件是否齐全                                    │
│  │   ├── traceability.md 对应列覆盖率 = 100%                  │
│  │   ├── 无 TODO/TBD 占位符                                  │
│  │   └── 验证门控（§15）                                     │
│  6. RESULT     → 验收结果处理:                                │
│  │   ├── 通过 → 写入终止结果 `执行完成` → 更新状态 → 释放门控 │
│  │   ├── 引入范围外新内容 → 拒收该轮 → 要求在冻结范围内重新执行│
│  │   └── 停滞（连续 3 轮无实质进展）或产物不合格 → 升级分支   │
│  │       ├── 用户选「是」→ 调整 prompt → 重新启动 Agent 子代理 │
│  │       └── 用户选「否」→ 标记 ⚠️ 需修订 → 阻塞当前阶段     │

```

## 5. 复杂度评估机制

基于可量化指标计算复杂度，**仅作为信息展示**写入 .status.md 备注列，不驱动子代理执行行为：

```
复杂度分 = 功能点数 × 1 + 接口数 × 1.5 + 场景数 × 2
```

| 复杂度 | 分数范围 | 说明 |
|--------|---------|------|
| 低 | < 20 分 | 简单任务，少量功能点/接口 |
| 中 | 20-50 分 | 常规任务，适中复杂度 |
| 高 | > 50 分 | 复杂任务，多接口/多场景 |

**权重说明**：场景数权重最高（E2E/集成测试场景复杂度高于单接口），接口数次之，功能点基准权重为 1。

**用途说明**：复杂度评估结果计算后写入 .status.md 备注列，标注为「仅供参考，不驱动执行行为」。**禁止**将分级转化为节奏指引（前 N 轮重点执行/中间 N 轮细节优化/后 N 轮验证等）传递给子代理。复杂度不参与轮次决策——单轮类阶段的执行轮数恒为 1（定向重验次数另计），重复制类阶段的轮次由其实际执行的循环决定（§14）。

## 6. Agent 提前返回处理

当 Agent 子代理返回但主 Agent 验收发现产物不完整时：

1. 主 Agent 记录当前进度到 skill-suggestion.md
2. 使用 AskUserQuestion 询问用户是否调整 prompt 重新执行

## 7. Agent 完成判断

**单轮类阶段**（接口单元测试 / E2E测试 / 集成测试）：

- 子代理 SHALL 在一轮内完成全部工作项的完整流程后返回执行报告
- 执行报告 SHALL 证明全部工作项已完成全量遍历
- 发现失败项时 SHALL 在报告中列出失败用例清单，交由定向重验处理（§14.2）
- SHALL NOT 为凑轮次而执行无增量价值的轮次

**重复制类阶段**（编码 / 代码审查 / 缺陷修复）：

- 子代理 SHALL 在**全部工作项完成全量遍历且当前轮无新发现、无可执行工作**后返回执行报告
- 执行报告 SHALL 证明全部工作项与全部审查对象已完成全量遍历（反空转条款：未证明全量遍历的报告 SHALL NOT 被采信）
- 连续 3 轮无实质进展（同一问题项反复出现）时 SHALL 返回执行报告并标注**停滞**缘由
- SHALL NOT 为凑轮次而执行无增量价值的轮次
- **范围外发现降级**：子代理在冻结审查对象集合之外发现的问题 SHALL 记为「范围外观察」，SHALL NOT 在本轮修复、SHALL NOT 计入本轮新发现数；主 Agent 在阶段终止时汇总并向用户提示
- Agent 的 prompt 中内嵌重复制遍历指令与审查范围冻结、范围外发现降级指令；SHALL NOT 包含任何轮数上限数值

## 8. 主 Agent 验收标准

验收 SHALL 以「执行报告完整 + 阶段产物齐全 + 覆盖率达标 + 无占位符」为通过条件；单轮类阶段另须「定向重验全部通过」。系统 SHALL NOT 存在以轮次数量作为通过或拒收依据的路径。

| 验收项 | 检查方式 | 判定条件 |
|--------|---------|---------|
| 执行报告完整 | 检查执行报告是否存在且内容完整 | 报告存在，且含全部工作项已完成全量遍历的证明 |
| 定向重验通过（单轮类） | 检查定向重验结果 | 定向重验全部通过；连续 3 次未通过时终止结果记 `定向重验失败` |
| 审查范围冻结 | 检查最近一轮执行报告与产物差异 | 未引入冻结审查对象集合之外的新内容（范围外文件、新增审查维度、新增功能点/字段/章节/分支）；越界 → 拒收并要求在冻结范围内重新执行（§9 类型 A′） |
| 产物文件齐全 | 检查阶段定义的所有输出产物是否存在 | 全部存在则通过 |
| 覆盖率达标 | 检查 traceability.md 对应列覆盖率 | 覆盖率 = 100% |
| 无占位符 | 搜索 TODO/TBD/{待填写}/... | 无匹配项 |
| 验证门控 | 按 §15 检查 | 受影响项 100% 覆盖 + 产物完整性 |
| 终止结果 | 检查 .status.md 中 `终止结果` 字段 | 取值 `执行完成` / `定向重验失败` / `停滞`，与实际终止路径一致；后两者须有对应的升级记录 |

## 9. 验收失败记录与处理

验收不通过时按失败类型分流：

**类型 A —— 执行报告不完整或无理由提前返回**：

1. 记录到 `docs/skill-suggestion.md`（触发场景标注：执行报告不完整）
2. **直接重新启动 Agent 子代理执行剩余工作，不询问用户**

**类型 A′ —— 引入范围外新内容**（越界）：

1. 记录到 `docs/skill-suggestion.md`（触发场景标注：引入范围外新内容，附越界详情：范围外文件 / 新增审查维度 / 新增功能点、字段、章节、分支）
2. **SHALL 拒收并要求子代理在冻结审查对象集合范围内重新执行，不询问用户**

**类型 B —— 停滞（重复制类）／定向重验连续失败（单轮类）／产物条件不满足**（升级分支）：

1. 记录到 `docs/skill-suggestion.md`，包含以下字段：
   - 发现时间、发现阶段（Agent 验收）、触发场景
   - 覆盖缺口详情（缺失的功能点清单）
   - 轮次信息（当前轮数）
   - 执行结果（`执行完成` / `定向重验失败` / `停滞`）
   - 复杂度信息
   - 改进建议
   - 状态（待重跑）、优先级

2. 使用 AskUserQuestion 询问用户：「验收不通过，是否重新启动 Agent 迭代子代理？」
   - 用户选「是」→ 调整 prompt 后重新启动 Agent 子代理
   - 用户选「否」→ 标记 .status.md 为 ⚠️ 需修订，阻塞当前阶段

## 10. 子代理 prompt 规范

构建执行类阶段子代理 prompt 时 MUST 包含：

| 内容 | 说明 |
|------|------|
| 当前阶段目标与产物要求 | 明确子代理需要产出什么 |
| 输入文档引用 | functional-designs/、detailed-design.md 等（使用文件路径引用，非复制内容） |
| traceability.md 中待填充的列和覆盖率目标 | 告知子代理需要达到的覆盖标准 |
| **审查对象清单** | 由主 Agent 从阶段产物既有内容生成的审查范围（冻结）；子代理 SHALL NOT 扩大该集合 |
| **单轮类阶段的单轮执行指令** | 「在一轮内遍历全部工作项执行完整流程，完成后返回执行报告。发现失败项时按定向重验处理——仅重跑失败用例，不重跑全量。审查对象集合已冻结，SHALL NOT 审查清单之外的文件或内容、SHALL NOT 新增审查维度、SHALL NOT 借审查之名新增功能点/字段/章节/分支。」 |
| **重复制类阶段的重复制遍历指令** | 「每轮遍历全部工作项独立执行完整流程。更新 .status.md 中执行轮次计数器为当前轮次号。禁止按轮次分段分配工作重点——每轮均须对全部工作项执行完整检查。审查对象集合已冻结，SHALL NOT 审查清单之外的文件或内容、SHALL NOT 新增审查维度。」 |
| **范围外发现降级指令** | 「在冻结范围之外发现的问题 SHALL NOT 计入执行发现数；SHALL 记为『范围外观察』写入执行报告的『范围外观察』小节。」 |
| 轮间摘要（**仅重复制类阶段**自第 2 轮起注入） | 前轮摘要（已修复问题/未解决问题/覆盖率变化/范围外观察/本轮建议关注）；第 1 轮不注入 |
| 每轮工作内容定义 | 明确本阶段每轮全量执行的具体工作项、流程和产物 |
| 复杂度评估（仅信息展示） | 可出现在 prompt 中但必须附带标注「仅供参考，不驱动执行行为」，标注后不得跟随任何按轮次分配工作的指令 |

**禁止项**：prompt SHALL NOT 包含：

- 任何轮数上限数值（含「不超过 N 轮」类表述）
- 「前 N 轮重点执行/中间 N 轮细节优化/后 N 轮验证」等分段分配指令
- 「这部分留给后面轮次」等暗示
- 任何按轮次分段分配工作重点的节奏指引
- 强制走满轮次的指令（例如要求做满全部目标轮次才允许返回）
- 允许子代理自行扩大审查对象集合或新增审查维度的表述

## 11. skill-suggestion.md 触发条件扩展

原有 skill-suggestion.md 触发条件（用户指出指引方向错误、纠正意图识别结果、执行结果与预期不符）基础上新增：

- 子代理返回但主 Agent 验收不通过
- 复杂度评估不准确（首轮实践后反馈调整，仅影响信息展示的准确性）
- 子代理产物覆盖率不达标（traceability.md 对应列覆盖率 < 100%）
- 停滞（重复制类阶段连续 3 轮无实质进展，§14.3）
- 定向重验连续 3 次未通过（单轮类阶段，§14.2）
- 子代理引入范围外新内容（越界，§9 类型 A′）

## 12. 子代理隔离规则

### 12.1 主 Agent 职责边界硬线声明

执行类阶段中，主 Agent 职责严格限定为**调度**（构建 prompt、启动子代理）和**验收**（检查产物、决定通过/拒收）。主 Agent **SHALL NOT** 直接执行任何阶段主工作（编码/修复/测试/审查/计划等），**无例外**——即使子代理多次失败，主 Agent 也不得接管执行。

允许的主 Agent 工作：构建子代理 prompt、启动 Agent 子代理、读取产物文件检查验收标准、更新 .status.md 状态、使用 AskUserQuestion 与用户交互。

### 12.2 强制规则

| 规则 | 说明 |
|------|------|
| **子代理异常时 MUST 重新创建** | 子代理意外停止、报错、返回不完整结果或要求重做时，主代理 MUST 重新创建子代理（新 Agent 调用），SHALL NOT 接管子代理的执行工作 |
| **主 Agent SHALL NOT 接管** | 主代理不得在子代理失败后自行完成子代理的产出（如直接编写代码、设计文档、测试报告等），此规则无例外 |
| **重试粒度为轮次级** | 某轮子代理崩溃时，主 Agent 新建 Agent 重跑**该轮**（从当前轮次号继续，而非重启整个阶段）；新子代理的 prompt 包含前 N-1 轮的轮间摘要（仅重复制类阶段适用，如有） |
| **轮次级重试上限** | 同一轮次最多重试 3 次（即最多创建 4 个子代理：1 次初始 + 3 次重试）；3 次重试均失败后，主代理 MUST 标记该阶段为 ⚠️ 阻塞并提示用户 |
| **重新创建非恢复** | 重新创建的子代理是全新 Agent，不依赖前一个子代理的上下文或状态 |

### 12.3 适用阶段清单

| 阶段 | 使用子代理的步骤 | 隔离规则 | 子代理强制规则 |
|------|-----------------|---------|--------------|
| explore | SELFREV（单轮验证） | ✅ 子代理异常时 MUST 重新创建 | — |
| prototype-design | DESIGN（子代理委托，按有效工具链 execution_order 执行）；「子代理自动审查验证」路径下 VERIFY（单轮合并验证）与 SELFREV（单轮验证，人工审查方式下完全跳过） | ✅ 子代理异常时 MUST 重新创建 | — |
| design | SELFREV（单轮验证）、REVIEW（按变更档位：轻量单 Agent / 标准两视角 / 完整四视角） | ✅ 子代理异常时 MUST 重新创建 | — |
| plan | 主工作（任务拆分与 tasks.md 产出，子代理执行）；SELFREV（单轮验证，规范见 kflow-plan 的 SKILL.md） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行计划主工作 |
| code | 重复制（TDD 编码） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行编码主工作 |
| code-review | 重复制（代码审查） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行审查主工作 |
| api-test | 单轮执行 + 定向重验（接口测试） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行测试主工作 |
| e2e-test | 单轮执行 + 定向重验（E2E 测试） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行测试主工作 |
| integration-test | 单轮执行 + 定向重验（集成测试） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行测试主工作 |
| bug-fix | 重复制（缺陷修复） | ✅ 子代理异常时 MUST 重新创建 | ✅ 主 Agent SHALL NOT 执行修复主工作 |

### 12.4 执行模式推荐

| 模式 | 适用场景 | 说明 |
|------|---------|------|
| 前台模式（推荐） | 默认 | `run_in_background=false`，主 Agent 可实时验收、提取轮间摘要 |
| 后台模式 | 权限已预配置 | `run_in_background=true`，适用于长时间执行且无需轮间交互的场景 |

**无后台模式硬限制**：后台运行本身不是问题根源，权限未配置才是。项目 `.claude/settings.json` SHALL 由 kflow-init 根据 `skills/kflow-init/references/permission-model.md` 自动配置权限（参见 §12.5），确保子代理不会因权限不足而降级执行。即使权限未完美配置，§12.7 后台权限失败回退前台子代理机制提供韧性保障。

### 12.5 权限预配置

项目 `.claude/settings.json` 中的权限声明由 kflow-init 根据 `skills/kflow-init/references/permission-model.md` 自动配置（参见 `kflow-permission-model` capability）。kflow-init SHALL 在目标项目中读取 `skills/kflow-init/references/permission-model.md` §1 全局必需权限清单，通过幂等合并策略配置 `.claude/settings.json`，确保子代理执行过程中无权限请求中断。

子代理 SHALL 继承 settings.json 中的预配置权限。

### 12.6 设计理由

- **独立性保障**：子代理独立上下文是其核心价值（避免"作者盲点"），主代理接管会丧失这一优势
- **职责清晰**：主代理的职责是编排（orchestrate），子代理的职责是执行（execute），两者不可混淆
- **质量保证**：主代理通常已在该阶段投入大量上下文（撰写产物、分析需求），接管执行会有"完成偏差"——倾向于走捷径或忽略细节
- **Token 成本换正确性**：重新创建子代理的 Token 成本高于主代理接管，但正确性和独立性更重要

### 12.7 后台权限失败回退前台子代理机制

即使 kflow-init 正确配置了权限，仍可能出现后台子代理因权限问题失败的情况（用户手动修改 settings.json、工具版本差异、新增未覆盖的工具调用）。本节定义韧性机制，确保后台失败时自动回退前台子代理重新执行。

#### 12.7.1 权限错误模式检测

主 Agent 从后台子代理（run_in_background=true）错误输出中匹配以下权限相关错误模式：

- "permission denied" / "权限不足"
- "not allowed" / "不允许"
- "requires approval" / "需要批准"
- "blocked" / "被阻止"
- 错误信息包含工具名 + 拒绝语义（如 "Bash command blocked"）

匹配至少一种模式即判定为权限问题，非权限错误按原有轮次级重试机制处理（参见 §12.2）。

#### 12.7.2 回退执行规则

检测到后台子代理因权限问题失败后：

1. 主 Agent 输出提示："检测到子代理因权限问题失败，创建前台子代理重新执行"
2. 构建与原后台子代理相同的 prompt（相同任务内容、轮次上下文）
3. 调用 Agent 工具：`run_in_background=false`
4. 前台子代理成功 → 正常继续，更新 .status.md 记录回退事件
5. 前台子代理也失败 → 标记 ⚠️ 阻塞，输出提示："子代理前台/后台均失败，请检查权限配置或手动处理"

#### 12.7.3 主 Agent 禁止接管硬线

主 Agent SHALL NOT 在任何情况下直接接管执行——即使后台子代理和前台子代理均失败，主 Agent 也不得在主 Agent 上下文中执行阶段主工作。此规则与 §12.1 主 Agent 职责边界硬线一致，无例外。

#### 12.7.4 不计入重试上限

后台权限失败回退前台子代理的执行 SHALL NOT 计入 §12.2 定义的轮次级重试 3 次上限——因为是不同执行模式的切换（后台 → 前台），而非同一模式的重试。回退后的前台子代理执行失败时标记阻塞，后续恢复操作（如用户触发恢复）从轮次级重试计数器的当前值继续。

## 13. 轮间摘要传递机制

> **版本**: 2.6.0 新增（变更 token-opt-inter-round-summary）
> **适用范围**: **仅重复制类阶段**——编码（kflow-code）、代码审查（kflow-code-review）与缺陷修复（kflow-bug-fix）。设计类阶段自审（SELFREV）、kflow-plan 自审与单轮类测试阶段（接口单元测试 / E2E 测试 / 集成测试）SHALL NOT 使用本机制。

### 13.1 概述

重复制模式下，每轮子代理完全独立启动，零上下文继承。轮间摘要机制在每轮子代理返回后，由主 Agent 从执行报告/产物差异中提取摘要，注入到下一轮子代理 prompt 中，使后期轮次可以优化注意力分配——已修复项快速回归、未解决项重点分析、未涉及项全量检查（兜底）。

**核心原则**：摘要仅用于优化注意力分配，不跳过任何工作项。全量遍历兜底始终保留。

**与执行报告的关系**：摘要 SHALL NOT 承载跨轮累积的修复清单——修复由该阶段自身的执行报告追踪。

### 13.2 摘要格式

```markdown
## 轮间摘要 (Round {N-1} 完成后)

### 已修复问题
- [FP-001] 接口返回值类型不匹配 → 已修复 (Round 2)
- [FP-003] 缺少错误处理 → 已修复 (Round 3)

### 未解决问题
- [FP-005] 边界条件处理待确认 → 升级用户决策
- （无未解决问题时记「（空）」）

### 覆盖率变化
- traceability.md 编码列: Round 1: 40% → Round {N-1}: 95%

### 范围外观察
- [模块 X / 文件 Y] 冻结审查范围之外发现的缺陷或改进点（不改产物、不计入发现数）
- （无范围外发现时记「（空）」）

### 本轮建议关注
- FP-005 待用户决策后处理
- 已修复项的回归检查
```

**「已修复问题」字段**：本轮视角的修复记录，供子代理对已修复项做快速回归确认。

**「范围外观察」字段**：列出冻结审查对象集合之外发现的问题（子代理在轮内记入执行报告的「范围外观察」小节，主 Agent 提取到摘要中）。该字段使后续轮次不会重复发现同一范围外内容。无范围外发现时写「（空）」。该字段 SHALL NOT 计入本轮新发现数。

### 13.3 摘要提取规则

| 提取来源 | 提取内容 | 提取时机 |
|---------|---------|---------|
| 子代理执行报告 | 已修复问题列表、未解决问题列表、**范围外观察条目** | 每轮子代理返回后 |
| 产物差异（.status.md / traceability.md） | 覆盖率变化（本轮 vs 上一轮） | 每轮子代理返回后 |
| 主 Agent 验收记录 | 未解决问题列表、升级用户决策项 | 每轮子代理返回后 |

**提取时机**：主 Agent 在每轮子代理返回后、构建下一轮子代理 prompt 前提取摘要。第 1 轮无摘要（无前轮信息），第 2 轮起注入。

**摘要写入位置**：主 Agent 将摘要暂存于内存（不写入文件），仅在构建下一轮子代理 prompt 时注入。

### 13.4 摘要注入方式

主 Agent 在构建第 2 轮及后续轮次的子代理 prompt 时，SHALL 在 prompt 开头的「重复制遍历指令」之后、「每轮工作内容定义」之前插入轮间摘要章节。格式：

```
## 轮间摘要 (Round {N-1} 完成后)
{摘要内容}

### 摘要使用说明
- 已修复项：仅做快速回归确认（检查修复是否引入新问题），不重新完整检查
- 未解决项：重点分析，优先处理
- 未涉及项：全量检查（兜底），不得跳过
- 范围外观察：不重复发现，不纳入本轮审查对象或修复范围
- 摘要仅用于优化注意力分配，不跳过任何工作项
```

### 13.5 注意力优化规则

子代理收到轮间摘要后，按以下规则优化注意力分配：

| 工作项类别 | 处理方式 | 说明 |
|-----------|---------|------|
| 已修复项 | 快速回归确认 | 检查修复是否引入新问题，不重新执行完整检查流程 |
| 未解决项 | 重点分析 | 投入更多注意力深入分析，优先处理 |
| 未涉及项 | 全量检查（兜底） | 执行完整检查流程，不得因摘要跳过任何项 |

**禁止项**：

- 禁止因摘要中显示「已修复」而完全跳过该工作项
- 禁止因摘要中无「未解决」而减少全量检查的范围
- 摘要仅影响注意力分配的优先级，不影响工作项的覆盖范围

### 13.6 轮次与摘要处理

| 轮次 | 摘要处理 |
|------|---------|
| 第 1 轮 | 不注入摘要（无前轮信息） |
| 第 2 轮起 | 正常注入前轮摘要 |

## 14. 终止模型

### 14.1 概述

**单轮类阶段**（接口单元测试 / E2E测试 / 集成测试）：执行轮数恒为 1——一轮内遍历全部工作项执行完整流程，SHALL NOT 执行第二轮全量审查。发现失败项时走**定向重验**（§14.2）。

**重复制类阶段**（编码 / 代码审查 / 缺陷修复）：每轮遍历全部工作项独立执行完整流程；当前轮无新发现且无可执行工作时返回执行报告并终止。轮次由实际执行的循环决定，下限为 1 轮。

**档位语义**：变更档位只决定**审查形态**（`轻量` 单 Agent 串行覆盖全部视角检查项 / `标准` 两视角并行 / `完整` 四视角并行）与产出深度，SHALL NOT 决定执行轮数。档位读取自变更级 `.status.md` 基本信息「变更档位」字段；字段缺失时按 `完整` 档确定审查形态与产出深度。

### 14.2 单轮类阶段：定向重验

**定向重验**指测试阶段修复失败项后**仅重跑失败用例**，不重跑全量。它与已移除的 `recheck-round` 语义不同：`recheck-round` 指审查循环到达终止点后追加的复核轮（因依赖已废除的轮数上限而被移除），定向重验触发于测试失败后的修复动作。

```
单轮类阶段终止路径:

   单轮全面执行（执行轮数 = 1）
       │
       ├── 零失败项 → 终止，终止结果 `执行完成`
       │
       └── 存在失败项 → 修复 → 定向重验（仅重跑失败用例）
              ├── 全部通过 → 终止，终止结果 `执行完成`
              ├── 仍有失败 → 再次修复 → 再次定向重验（`执行轮次` 递增）
              └── 连续 3 次定向重验未通过
                     → 终止，终止结果 `定向重验失败` → 升级用户
```

- 定向重验属**有界重试**，SHALL NOT 使用轮次循环判据
- 每次定向重验时 SHALL 更新 `.status.md` 中 `执行轮次` 字段为当前轮次号
- 连续 3 次定向重验仍未通过时，系统 SHALL 记录到 `docs/skill-suggestion.md`（含失败用例清单与轮次），并使用 AskUserQuestion 询问用户：「定向重验连续失败，是否调整修复方案后重试？」；用户选择「否」时 MAY 标记 .status.md 为 ⚠️ 阻塞并终止当前阶段

### 14.3 重复制类阶段：循环终止

```
重复制类阶段终止路径:

   重复制循环（下限 1 轮）
       │
       ├── 当前轮无新发现且无可执行工作
       │       且报告证明全部工作项已完成全量遍历
       │       → 终止，终止结果 `执行完成`
       │
       ├── 连续 3 轮无实质进展（同一问题项反复出现）
       │       → 终止，终止结果 `停滞` → 升级用户
       │       （记录 `docs/skill-suggestion.md` + AskUserQuestion + 可标记 ⚠️ 阻塞）
       │
       └── 其余情形 → 递增 `执行轮次`，进入下一轮
```

**停滞升级流程**：

1. 记录到 `docs/skill-suggestion.md`（含阶段、当前轮数、停滞缘由、覆盖缺口详情、改进建议）
2. 使用 AskUserQuestion 询问用户：「验收不通过，是否重新启动 Agent 迭代子代理？」
   - 用户选「是」→ 调整 prompt 后重新启动 Agent 子代理
   - 用户选「否」→ 标记 .status.md 为 ⚠️ 需修订，**阻塞当前阶段**
3. 系统 MAY 将该阶段标记为 ⚠️ 阻塞

该分支与 §9 类型 B 一致，不新增范式。

**范围外发现不影响终止**：子代理在冻结审查对象集合之外发现的问题降级为「范围外观察」（§7），不计入本轮新发现数。

### 14.4 终止结果写入

阶段终止时，系统 SHALL 在 `.status.md` 写入**终止结果**字段：

| 取值 | 适用阶段 | 判定口径 |
|------|---------|---------|
| `执行完成` | 单轮类与重复制类 | 全部工作项完成全量遍历；单轮类另须定向重验全部通过 |
| `定向重验失败` | 单轮类 | 定向重验连续 3 次仍未通过（须有对应升级记录） |
| `停滞` | 重复制类 | 连续 3 轮无实质进展（须有对应升级记录） |

**读取兼容**：历史变更遗留的 `收敛` 是旧模型中「成功终止」的统一取值（不区分阶段类型）。读取侧 SHALL 将其归并为 `验证通过`，其余历史取值（`未收敛` 等）SHALL 归并为 `验证发现问题`；SHALL NOT 要求迁移历史 `.status.md`。归并后的取值仍须满足 §8 验收项与 §15 门控要求。

`执行轮次` 字段格式为 `{N} 轮`（无分母，见 §16.1）；读取侧遇到历史 `{N} / {上限}` 形式时取分子并忽略分母（见 `round-counter` 能力）。

### 14.5 完整档评分的报告深度

变更档位为 `完整` 时，代码审查与测试类阶段的执行报告 SHALL 输出各维度评分（0–10 量纲）与评分不达标时的具体问题项清单，作为**报告输出深度**要求。评分 SHALL NOT 参与终止判定。标准档与轻量档不适用评分底线（评分可记录但不作判定）。

### 14.6 回退重执行不预置轮数

阶段回退重执行时，系统 SHALL NOT 预置或提高轮数。回退带来的「最近修订信息」中的受影响项清单 SHALL 用于 §15 验证门控的「受影响项 100% 覆盖」，SHALL NOT 用于推算轮次。

**轻量档与产物门控**：轻量档 SHALL 执行完整执行模型，SHALL NOT 存在跳过路径。产物完整性门控（§15.2）作为附加硬门保留，不受档位影响。

## 15. 验证门控

阶段终止时，除 §8 标准验收项外，SHALL 满足以下门控项。

### 15.1 受影响项 100% 覆盖验证（回退重执行场景）

- 从 `.status.md`「最近修订信息」中读取受影响项清单（`Affected Functional Points` + `Affected Interfaces`）
- 每个受影响项 SHALL 接受完整的阶段专属验证（不可缩写）
- 验证结果 SHALL 记录在阶段产物中
- 该门控 SHALL 仅在阶段处于回退重执行且存在受影响项清单时适用；受影响项清单为空或不存在时该项视为满足

### 15.2 产物完整性

- 所有阶段定义的输出产物 SHALL 存在且格式合规
- 该项为**硬门**，不受变更档位影响

### 15.3 门控判定

两项验证全部通过 → 验收通过。任一未通过 → 按验收不通过流程处理（§9）。

> 原「全量至少 1 轮兜底」门控项已删除——其立法目的（防止跳过全量遍历）被 §8「执行报告完整（含全量遍历证明）」验收项吞并，不再需要独立门控项。

## 16. 阶段执行历史追踪

### 16.1 阶段执行历史表

`.status.md` SHALL 包含「阶段执行历史」表，格式如下：

| Phase | Execution Count | Last Type | Rounds | Score | Notes |
|-------|----------------|-----------|--------|-------|-------|
| plan | 1st | First Execution | — | — | — |
| code | 1st | First Execution | 3 轮 | — | — |
| api-test | 1st | First Execution | 2 轮 | — | 定向重验 1 次 |
| code | 2nd | Rollback Re-execution | 2 轮 | 4 | BUG-003 triage → L3 design revision |

**字段说明**：

- **Phase**：阶段名称
- **Execution Count**：第几次执行（1st, 2nd, ...）
- **Last Type**：执行类型（First Execution / REVISION / Rollback Re-execution）
- **Rounds**：最终执行轮次（如 `1 轮`、`2 轮`）——单轮类阶段含定向重验的累计轮次；重复制类阶段为实际执行轮次；主 Agent 直接执行的阶段标 `—`
- **Score**：影响范围分数（本阶段无执行记录时标 —）
- **Notes**：备注（如回退原因、终止结果、定向重验次数）

### 16.2 更新时机

- 阶段完成时 SHALL 追加一行记录
- 回退时 SHALL 在「最近修订信息」节记录修订详情

### 16.3 最近修订信息节

`.status.md` SHALL 包含「最近修订信息」节，格式如下：

```markdown
## Recent Revision Info

- **Revision Trigger**: BUG-003 triage diagnosis
- **Source Phase**: L3 Detailed Design
- **Timestamp**: 2026-06-17T14:30:00
- **Summary**: 接口返回值类型定义错误，需修正 2 个接口定义
- **Affected Functional Points**: FP-003, FP-007
- **Affected Interfaces**: /api/orders/export, /api/orders/detail
- **Data Model Changes**: none
- **Impact Scope Score**: 5 (2×1 + 2×1.5 + 0×2)
```

> 该节 SHALL NOT 含任何「建议轮次」字段——轮数由执行模型决定，影响范围分数只用于 §15.1 的受影响项清单与回退判定。

## 17. 影响范围分数读取机制

### 17.1 读取时机

执行阶段启动时（CHECK_HISTORY 步骤），主 Agent SHALL：

1. 读取 `.status.md`「最近修订信息」节
2. 提取 `Affected Functional Points` + `Affected Interfaces`，构成受影响项清单，供 §15.1 验证门控使用
3. 提取 `Impact Scope Score` 值，作为回退影响范围的记录性信息

**分数 SHALL NOT 用于推算执行轮次。**

### 17.2 分数计算公式

由 `kflow-bug-triage` 影响范围评估产出（参见 `triage-impact-assessment` capability）：

```
影响范围分数 = 功能点数 × 1 + 接口数 × 1.5 + 数据模型变更 × 2
```

- 功能点数：受影响的功能点数量
- 接口数：受影响的 API 端点数量
- 数据模型变更：存在数据模型修改时为 1，否则为 0

### 17.3 无分数时的处理

当 `.status.md` 中无「最近修订信息」节或分数为空时，§15.1 受影响项门控视为满足（非回退重执行场景），执行轮次不受影响。
