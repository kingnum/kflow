# 角色

KFlow 流程入口。不做阶段执行，只做意图识别和路由分发。将用户的自然语言输入映射到正确的阶段 Skill，并检测项目上下文（类型、活跃变更、冲突）。正则解析优先（「恢复/resume + 变更名」-> RESUME 路由到 `kflow-resume`；「继续 + 变更名」-> 轻量推进，直接调度目标阶段 Skill），关键词意图识别映射，活跃变更检测，项目类型读取（继承项目级记录，SHALL NOT 重新扫描判定），定向指引，指引错误记录到 skill-suggestion.md。新变更的创建前指引、变更类型分类与变更名称建议由 `kflow-explore` 承担，本 Skill SHALL NOT 重复提供。

# 任务

接收用户输入 -> 变更名正则解析（优先级最高）-> 关键词意图识别 -> 活跃变更检测 -> 项目类型读取（继承项目级记录）-> 路由分发（RESUME 路由 / 轻量推进 / DESIGN_REVISION 路由 / 定向指引 / 流程概览）-> 指引错误记录（按需）。

# 门控检查

此阶段为独立指引阶段，无前置门控要求。不产生持久化文件（除 skill-suggestion.md 错误日志外）。用于帮助用户确定当前应该使用的 Skill。

| 产物 | 图例 | 说明 |

| 项目上下文 | 🔶 条件 | 由本 Skill 自动检测，无需用户提供 |

在对话中输出流程指引信息，不产生持久化文件。

| 产物 | 说明 | 图例 |
|------|------|------|

| 定向指引 | 对话中输出特定变更的定向状态信息 | 🔶 条件 |
| 阶段调度 | 变更名模式命中时调度目标阶段 Skill（轻量推进）或 `kflow-resume`（中断恢复） | 🔶 条件 |
| skill-suggestion.md | 指引错误时追加错误记录 | 🔶 条件 |

# 执行流程

## 总流程

```
INPUT -> PARSE(变更名正则/设计修订解析) -> ROUTE(变更名模式直接路由)
    -> INTENT(关键词映射) -> CHANGES(活跃变更) -> TYPEREAD(项目类型读取)
    -> GUIDE(输出流程概览) -> ERRORLOG(按需)
```

变更名模式（PARSE 命中）时短路后续步骤，直接进入对应路由；未命中时按 INTENT → CHANGES → TYPEREAD → GUIDE 顺次执行。

```
┌─────────────────────────────────────────────────────────────────┐
│                        GUIDE WORKFLOW                            │
├─────────────────────────────────────────────────────────────────┤
│  1. INPUT      接收用户输入                                       │
│  2. PARSE      变更名正则/设计修订解析（优先级最高）              │
│     ├── /(?:恢复|resume)\s+([a-z0-9-]+)/ -> RESUME 路由 → resume │
│     ├── /继续\s+([a-z0-9-]+)/ -> 轻量推进 → 直接调度阶段 Skill   │
│     ├── /指引|引导|guide\s+([a-z0-9-]+)/  -> 定向指引            │
│     ├── 设计修订触发词 -> DESIGN_REVISION 路由                   │
│     └── 无匹配 -> 进入 INTENT 步骤                               │
│  3. INTENT     意图识别（关键词映射）                             │
│     ├── 识别成功 -> 确定目标 Skill                                │
│     └── 无法识别 -> 显示全套流程概览                              │
│  4. CHANGES    活跃变更检测（不阻断修复意图）                     │
│     ├── 修复意图 -> 直接路由到 kflow-bug-triage（无论活跃变更数） │
│     ├── 无活跃变更（非修复意图）-> 引导使用 kflow-explore 创建     │
│     ├── 单个活跃变更 -> 自动选择该变更                            │
│     └── 多个活跃变更 -> 列出供用户选择                            │
│  5. TYPEREAD   项目类型读取（读取项目级记录，确定基础阶段集合）   │
│     ├── 读取优先级 1) CLAUDE.md 项目画像 -> 2) toolchain.md 头部 │
│     ├── 前两级均不可用 -> 就地扫描检测（仅展示，不写文件）        │
│     ├── 前后端项目 -> 前后端阶段集合（9 阶段）                    │
│     └── 纯后端项目 -> 纯后端阶段集合（7 阶段）                    │
│  6. GUIDE      输出流程概览和下一步建议                           │
│     └── 按变更档位裁剪：轻量档按适用性声明标注 ⏭️ 不适用          │
│  7. ERRORLOG   (如有错误) 记录到 skill-suggestion.md              │
└─────────────────────────────────────────────────────────────────┘
```

## 步骤 1：INPUT — 接收用户输入

接收用户的自然语言输入，不做任何预处理，原样传递给后续步骤。

## 步骤 2：PARSE — 变更名正则解析（优先级最高）

> **Plan Mode 绕过**：正则匹配变更名模式（「恢复/resume + 变更名」或「继续 + 变更名」）时，SHALL NOT 进入 Plan Mode，直接进入 Skill 路由链。此规则优先级高于 Claude Code Plan Mode 自动触发。详见 CLAUDE.md 强制规则。

在意图识别之前，先用正则从用户输入中提取变更标识名称（kebab-case）：

| 正则模式 | 匹配示例 | 路由分支 |
|---------|---------|---------|
| `/(?:恢复\|resume)\s+([a-z0-9-]+)/` | "恢复 add-user-auth"、"resume add-user-auth" | RESUME 路由 -> 调用 `kflow-resume`（§2a） |
| `/继续\s+([a-z0-9-]+)/` | "继续 add-user-auth" | 轻量推进 -> 读 `.status.md` 后直接调度阶段 Skill（§2b） |
| `/指引\|引导\|guide\s+([a-z0-9-]+)/` | "指引 add-user-auth" | 定向指引分支（步骤 6） |
| `/(设计需调整\|功能设计需调整\|原型.*调整\|详细设计.*调整\|接口设计.*改\|修改.*设计\|调整.*设计)/` | "功能设计需调整"、"原型需调整"、"详细设计需调整" | DESIGN_REVISION 路由（§2c） |
| 无变更名的 "恢复/resume" 或 "继续" | "恢复"、"继续" | 按活跃变更数处理（步骤 4） |

**变更名提取规则**：
- 变更名为 kebab-case 格式（小写字母+数字+连字符）
- 提取后验证：检查 `docs/changes/{change-name}/` 目录是否存在
- 变更名不存在时 -> 提示变更不存在并列出活跃变更

> **两条变更名分支互斥**：`恢复`/`resume` 与 `继续` 是两条独立分支，各自的路由目标不同，SHALL NOT 合并为一条正则。二者同为优先级最高，正则命中时 SHALL NOT 再进入关键词映射流程。

### 2a. RESUME 路由（「恢复/resume + 变更名」命中时）

```
RESUME 路由流程:

1. 提取变更名: 正则捕获组 ([a-z0-9-]+)
2. 调用 Skill 工具: Skill(skill="kflow-resume", args="<change-name>")
3. 不额外处理: resume 负责 VERIFY -> STATE -> LOCATE -> GATE -> SUMMARIZE -> DISPATCH
```

### 2b. 轻量推进（「继续 + 变更名」命中时）

```
轻量推进流程:

1. 提取变更名: 正则捕获组 ([a-z0-9-]+)
2. 读取 docs/changes/{change-name}/.status.md，取「当前阶段」与阶段状态表
3. 按阶段衔接决策直接调度目标阶段 Skill:
   ├── ✅ 完成 -> 递归推进至第一个非完成阶段
   ├── 🔄 进行中 / ⏳ 待开始 -> 调度该阶段 Skill
   ├── ⚠️ 需修订 -> 调度该阶段标注的回退目标阶段 Skill
   ├── ❌ 阻塞 -> 输出阻碍信息，不调度
   └── ⏭️ 跳过 -> 视为已通过，对下一阶段重新执行决策
4. 调度方式: Skill(skill="{target-skill}", args="{change-name}")
```

- 阶段衔接决策的权威定义见各阶段 Skill 的 `references/phase-transition.md`（同一份共享规则的副本），本 Skill SHALL NOT 复制该文件的完整决策表
- 轻量推进 SHALL NOT 调用 `kflow-resume`，SHALL NOT 执行产物完整性二次校验、五问题摘要与服务恢复检测
- 其安全性由目标阶段 Skill 自有的入口门控兜底

### 2c. DESIGN_REVISION 路由（设计修订正则命中时）

```
DESIGN_REVISION 路由流程:

1. 解析用户输入，关键词→目标设计产物载体映射:
   ├── 含"功能"/"需求" → 变更级 functional-designs
   ├── 含"原型"/"UI"/"交互" → 产品级 docs/designs/prototypes/
   └── 含"详细"/"接口"/"架构" → 变更级 detailed-design

2. ROUTE 分流到目标设计 Skill（REVISION 模式）:
   ├── 变更级 functional-designs → Skill(skill="kflow-explore", args="REVISION")
   ├── 产品级 docs/designs/prototypes/ → Skill(skill="kflow-prototype-design", args="REVISION")
   └── 变更级 detailed-design → Skill(skill="kflow-design", args="REVISION")

3. 目标 Skill 完成后 → 进入「设计修订后处理流程」（§设计修订后处理）
```

### 修复类关键词上下文判断

当用户输入命中修复类关键词（修复、Bug、缺陷）时：

- 活跃变更数量 SHALL NOT 成为路由前置条件，SHALL NOT 作为是否创建变更的判定依据
- 存在活跃 bug-fix 子阶段 → 路由到 `kflow-bug-fix`（继续已有修复）
- 不存在活跃 bug-fix → 路由到 `kflow-bug-triage`（新问题诊断），无活跃变更时同样路由到 `kflow-bug-triage`
- SHALL NOT 将修复意图引导到 `kflow-explore` 创建新变更
- 存在活跃变更时，缺陷归属（项目级 / 变更级）由 `kflow-bug-triage` 判定；本 Skill SHALL NOT 因存在活跃变更而预先创建变更
- 无法判断 → 使用 AskUserQuestion 询问用户意图

### 意图识别优先级规则

```
优先级判定规则:

0. 正则解析优先（最高优先级）:
   ├── 输入匹配「恢复/resume + 变更名」-> RESUME 路由到 kflow-resume
   ├── 输入匹配「继续 + 变更名」-> 轻量推进（读 .status.md -> 按阶段衔接决策调度）
   ├── 输入匹配「指引/引导/guide + 变更名」-> 定向指引分支
   └── 正则未命中 -> 进入关键词匹配（下表）

1. 按上表中各匹配关键词的最高优先级值选择
2. 同优先级时:
   ├── 检查活跃变更当前阶段，优先选择符合当前流程方向的关键词
   ├── 无法从上下文判断时，使用 AskUserQuestion 确认
   └── 用户未明确纠正的记录到 skill-suggestion.md

3. 特殊排除规则:
   ├── 关键词"测试"在有活跃变更且当前阶段为编码/代码审查时 -> 不触发
   ├── 关键词"修复/Bug/缺陷"在有活跃变更且当前阶段为集成测试时 -> 引导到 kflow-integration-test
   ├── 关键词"修复/Bug/缺陷"-> 执行上下文判断（有活跃 bug-fix -> bug-fix，否则 -> triage）
   └── 关键词"归档"在有活跃变更且未全部完成时 -> 提示先完成前置阶段

4. 歧义处理:
   ├── 用户明确指代某 Skill 名称时直接触发该 Skill
   └── 上下文无法确定时 -> 显示匹配的选项供用户选择（最多3项）

5. 无变更名处理（正则未命中「变更名模式」时）:
   ├── 裸「恢复」/「resume」:
   │   ├── 0 个活跃变更 -> 提示没有可恢复的变更，引导使用 kflow-explore 创建变更
   │   ├── 1 个活跃变更 -> 自动选择该变更，调用 kflow-resume
   │   └── >1 个活跃变更 -> 列出所有活跃变更供用户选择，选择后调用 kflow-resume
   └── 裸「继续」:
       ├── 0 个活跃变更 -> 提示没有可推进的变更，引导使用 kflow-explore 创建变更
       ├── 1 个活跃变更 -> 自动选择该变更，执行轻量推进（不调用 kflow-resume）
       └── >1 个活跃变更 -> 列出所有活跃变更供用户选择，选择后执行轻量推进
```

> **正则优先于关键词映射**：变更名模式（「恢复/resume + 变更名」「继续 + 变更名」）命中时 SHALL 在关键词优先级裁决之前完成路由，SHALL NOT 再按关键词映射裁决一次。

## 步骤 4：CHANGES — 活跃变更检测

```
活跃变更检测:

┌─────────────────────────────────────────────────────────────────┐
│  1. SCAN     扫描 docs/changes/ 目录                             │
│  2. FILTER   过滤未归档变更                                       │
│     └── 排除 docs/changes/archive/ 目录下的变更                          │
│  3. READ     读取各变更的 .status.md                              │
│  4. COUNT    统计活跃变更数量（修复意图不以此为前提）             │
│     ├── 修复意图 -> 不引导创建变更，路由到 kflow-bug-triage       │
│     ├── 0 个（非修复意图）-> 引导使用 kflow-explore 创建          │
│     ├── 1 个 -> 自动选择该变更                                   │
│     └── > 1 个 -> 列出变更供用户选择                             │
└─────────────────────────────────────────────────────────────────┘
```

> 活跃变更数为 0 时，本 Skill SHALL NOT 输出创建前指引、变更类型分类或变更名称建议——新变更由 `kflow-explore` 承接，本 Skill 仅提示入口。**修复意图除外**：命中修复类关键词时 SHALL 直接路由到 `kflow-bug-triage`，SHALL NOT 因无活跃变更而引导创建变更。

## 步骤 5：TYPEREAD — 项目类型读取

**读取项目级项目类型记录**并据此确定基础阶段集合，再叠加变更档位裁剪。SHALL NOT 在流程指引中重新扫描判定项目类型。读取优先级与降级规则由 `project-type-detection` 能力定义（`docs/designs/core-mechanisms/01-project-types.md` §1.4），本 Skill SHALL NOT 重复定义：

| 优先级 | 读取源 |
|--------|--------|
| 1 | CLAUDE.md「## 项目画像」表的「项目类型」行 |
| 2 | `docs/toolchain.md` 头部的「项目类型」字段 |
| 3 | 前两级均不可用（项目从未 init）→ 就地扫描检测，仅用于指引展示，见下 |

第 3 级（就地扫描）的检测标识：

| 检测标识 | 判断为 |
|---------|--------|
| package.json 前端框架依赖（react, vue, angular, next, nuxt, svelte） | 前后端项目 |
| 前端源文件（.vue, .tsx, .jsx, .svelte） | 前后端项目 |
| 前端构建配置（vite.config, webpack.config） | 前后端项目 |
| 以上均不存在 | 纯后端项目 |

| 项目类型 | 基础阶段集合 | 可选/跳过阶段 |
|---------|-------------|--------------|

## 步骤 7：GUIDE — 流程概览输出

流程概览的阶段集合由「项目类型 + 变更档位」叠加决定，按下表选择展示形态：

| 变更档位 | 项目类型 | 显示形态 |
|---------|---------|---------|
| `标准` | 前后端项目 | 完整阶段集合（9 阶段），标注原型设计为可选阶段 |
| `标准` | 纯后端项目 | 完整阶段集合（7 阶段），标注跳过原型设计与 E2E 测试 |
| `轻量` + 已生成阶段适用性声明 | 任一项目类型 | 将声明为 `⏭️ 不适用` 的阶段标注为 `⏭️ 不适用`，显示实际执行的阶段集合 |
| `轻量` + 尚未生成阶段适用性声明 | 任一项目类型 | 显示完整阶段集合，标注「接口单元测试与 E2E 测试将在详细设计后按适用性判定」 |

**档位分支规则**：

- `标准` 档：SHALL 按项目类型显示完整阶段集合，SHALL NOT 标注档位裁剪。字段缺失或读取到历史遗留的 `完整` 取值时按 `标准` 档判读。
- `轻量` 档且已生成阶段适用性声明：SHALL 将声明为 `⏭️ 不适用` 的阶段标注为 `⏭️ 不适用`；SHALL 显示实际执行的阶段集合；SHALL NOT 将不适用阶段计入实际阶段数量。
- `轻量` 档且尚未生成阶段适用性声明：SHALL 显示完整阶段集合，并标注「接口单元测试与 E2E 测试将在详细设计后按适用性判定」。
- 阶段适用性声明读取自变更级 `.status.md` 的「阶段适用性声明」区；该区缺失时 SHALL 按「全部阶段适用」处理。
- 实际阶段数量的折算口径：`轻量` 档实际阶段数 = 项目类型基础阶段集合 − 阶段适用性声明判定为 `⏭️ 不适用` 的阶段数；`标准` 档按项目类型基础阶段集合计数。
- 无活跃变更时的全套流程概览 SHALL 按项目类型显示完整阶段集合，SHALL NOT 应用档位裁剪。

```markdown

### 变更档位: {轻量|标准}（`.status.md` 不含该字段或含历史遗留的 `完整` 取值时按 `标准` 档展示）

### 缺陷修复快车道（独立路径，不计入变更阶段集合）

```

    ├── L4 且满足快车道条件 -> kflow-bug-fix 快车道模式 -> 定向验证 -> 快速收口（不创建变更）

# 与其他 Skill 的关系

- **独立阶段**：可随时调用，不依赖其他阶段
- **引导进入**：根据意图识别结果引导进入对应 Skill
- **路由到 `kflow-resume`**：识别 RESUME 模式（「恢复/resume + 变更名」）后直接调用 `kflow-resume` 进行中断恢复
- **轻量推进 -> 目标阶段 Skill**：识别「继续 + 变更名」模式时读取 `.status.md`，按阶段衔接决策直接调度目标阶段 Skill，SHALL NOT 调用 `kflow-resume`
- **路由到 `kflow-bug-triage`**：用户反馈关键词（反馈/报告问题/报bug/提bug/问题）或修复类关键词（修复/Bug/缺陷）匹配时路由到 triage；修复意图无需变更名，且 SHALL NOT 以活跃变更数量作为前置条件
- **路由到 `kflow-bug-fix`**：修复类关键词 + 存在活跃 bug-fix 子阶段时路由继续已有修复
- **缺陷修复快车道**：L4 简单缺陷经 triage 判定后进入快车道（分诊 → 修复 → 定向验证 → 快速收口），无需创建变更；流程概览 SHALL 将其作为独立于变更阶段的路径展示
- **新变更 -> `kflow-explore`**：无活跃变更或用户表达新变更意图时，提示用户使用 `kflow-explore` 开始设计探索；本 Skill SHALL NOT 输出创建前指引、变更类型分类或变更名称建议
- **定向指引**：识别「指引/引导/guide + 变更名」模式时输出定向状态信息
- **无前置阶段**：无需门控检查
- **不创建文件**：仅输出指引信息（除 skill-suggestion.md 错误记录）

# 核心提醒

- 正则解析优先级最高，在关键词匹配之前执行；变更名模式命中时 SHALL NOT 再按关键词映射裁决一次
- 变更名模式有两条独立分支：「恢复/resume + 变更名」-> `kflow-resume`；「继续 + 变更名」-> 轻量推进（直接调度阶段 Skill）
- 意图识别按优先级值选择，同优先级结合活跃变更上下文判断
- 修复意图 SHALL NOT 以活跃变更数量为前置条件：无活跃变更时直接路由到 `kflow-bug-triage`，SHALL NOT 引导到 `kflow-explore` 创建变更；L4 简单缺陷进入缺陷修复快车道，无需变更名
- 流程概览 SHALL 将「缺陷修复快车道」作为独立于变更阶段集合的路径展示，并说明简单缺陷无需创建变更
- 无变更名时：「恢复/resume」按活跃变更数决定是否调用 `kflow-resume`（0 活跃->提示无可恢复变更，1 活跃->自动 resume，>1 活跃->列出供选择）；「继续」执行轻量推进，SHALL NOT 调用 `kflow-resume`
- 指引错误必须记录到 skill-suggestion.md，便于后续优化关键词映射
- 本 Skill 不创建变更目录和文件，变更初始化在 kflow-explore 阶段完成；创建前指引、变更类型分类、变更名称建议均由 `kflow-explore` 承担，本 Skill SHALL NOT 重复提供
- 项目类型 SHALL 读取项目级记录（CLAUDE.md 项目画像 → `docs/toolchain.md` 头部），SHALL NOT 重新扫描判定；前两级均不可用时才就地扫描检测，且仅在指引中展示（标注待 explore 确认与补写），不创建或修改任何文件
- 输出时根据项目类型显示对应流程（前后端 9 阶段 / 纯后端 7 阶段）；当前活跃变更为 `轻量` 档时，按阶段适用性声明标注 `⏭️ 不适用` 阶段并折算实际阶段数量（`标准` 档不裁剪）
