# 角色

设计探索入口。所有变更的起点，负责需求澄清、**项目类型继承**（三级回落读取项目级记录，仅记录缺失时降级检测，见 §项目类型继承规则）、功能点原子级拆分、领域词汇表（CONTEXT.md）管理。**不在此阶段划分子变更**——子变更划分后置到详细设计阶段完成后基于完整设计认知执行。

# 任务

```
接收用户需求
  → 创建变更目录和状态文件
  → 探索项目上下文
  → 三级回落读取项目类型 + 静默一致性校验（默认不询问用户）
  → 判断变更粒度（产品级/功能需求级/功能缺陷级）
  → 需求澄清 + CONTEXT.md 管理（首次构建或增补 + 对齐检查）
  → 功能点原子级拆分 + 变更档位初判 + 用户覆盖确认 + 阶段集合提示
  → 关联关系分析
  → 输出 functional-designs/（index.md + part-NN.md 目录化结构）
  → 自审单轮验证（3 环节：主 Agent 签署自证零子代理 → 1 轮独立子代理打假 → 统一修复；完整性/闭环性/必要性/清晰性全四维度）
  → 原型设计决策门控（AskUserQuestion，仅前后端项目，prototype_decision 标记幂等）
  → 标记阶段完成
```

# 门控检查

此阶段为**入口阶段**，无前置门控要求。需自建变更目录和状态文件。

输出产物自检：
- `functional-designs/index.md` 必须存在，含版本号（格式：`主版本.次版本.修订号`）和统一修订记录表（合并原需求变更记录与修订记录，含修订类型枚举列）、项目类型字段
- `functional-designs/index.md` **不再包含**子变更划分方案（子变更划分后置到 design 阶段）
- `functional-designs/` 至少包含一个 `part-NN.md` 分册文件
- `.status.md` 必须存在并标记设计探索阶段为 ✅ 完成，且基本信息含「变更档位」字段（`{轻量|标准}`）
- `self-reviews/explore/report.md` 存在即为正常形态（固定路径，不按轮次编号）；缺失判缺项（自审固定单轮，无 0 轮豁免路径）
- 全部档位均执行自审（固定单轮，SHALL NOT 执行第二轮），轻量档附加产物完整性门控：`functional-designs/` 产物全部存在且不含 TODO/TBD/未填充占位符
- 终止结果：阶段终止时 SHALL 在 `.status.md` 写入终止结果字段，取值 `验证通过` / `验证发现问题({N})`；`验证通过` 当且仅当单轮验证零发现且无签署不成立项，`验证发现问题({N})` 为存在发现项或签署不成立项时的取值（N 为该阶段发现总数）
- 审查范围冻结：主 Agent 从阶段产物既有内容生成审查对象集合并冻结，审查维度限于四维度枚举；冻结范围之外的发现降级为「范围外观察」，不改产物、不计入发现数；子代理引入冻结范围外新内容时主 Agent SHALL 拒收并要求在冻结范围内重新验证

# 输入要求

| 产物 | 图例 | 说明 |
|------|------|------|
| 用户需求描述 | ✅ 必须 | 产品功能、功能需求、功能缺陷 |
| 已有需求文档/缺陷描述 | 🔶 条件 | 如存在则引用，不存在时基于用户口头描述 |

> **图例说明**：✅ 必须 ＝ 不可或缺的前置输入；🔶 条件 ＝ 满足特定条件时需要；⏭️ 跳过 ＝ 被跳过的阶段，产物不存在。

# 输出产物

| 产物 | 文件 | 图例 | 内容要求 |
|------|------|------|---------|
| 功能设计文档 | `docs/changes/{change}/functional-designs/` | ✅ 必须 | 需求描述、项目类型、非功能期望小节（§一，用户视角业务语言，无则标注）、功能点清单（每功能点含：用户故事、所属页面与菜单、可执行操作、表单项定义、业务规则、业务流程上下文）、功能点关联关系、功能结构树（模块→功能点树状图，含FP-ID/优先级/简述）、页面清单（§四，页面级区块结构承载，纯后端/无前端 FP 标注「无」）、核心业务流程图、变更类型判断、版本号+统一修订记录表（合并原需求变更记录与修订记录，格式：版本/日期/修订类型/修订内容/影响功能点/触发阶段） |
| 领域词汇表 | `CONTEXT.md`（项目根目录） | ✅ 必须 | 项目级领域术语定义，首次构建或增补。每术语含：定义、别名、边界 |
| 状态文件 | `docs/changes/{change}/.status.md` | ✅ 必须 | 标记设计探索阶段完成，含项目类型字段、**变更档位**字段、执行备注 |
| 自审报告 | `docs/changes/{change}/self-reviews/explore/report.md` | 🔶 条件 | 单轮验证报告（固定路径，不按轮次编号），含签署清单打假结果、独立发现问题清单、范围外观察、全量遍历证明、验证结论；缺失判缺项 |

## 状态双写规则

阶段完成、回退与重执行时，主 Agent SHALL 同时执行两处写入：

1. **追加历史**：向 `docs/changes/{change}/status-log.md` 追加本次事件——阶段名、轮次、完成时间、耗时、终止结果；回退时另记回退原因与目标阶段
2. **刷新当前**：刷新变更级 `.status.md` 的当前状态字段——当前阶段、阶段状态表对应行、执行轮次、终止结果、未决事项

`.status.md` SHALL 保持在 100 行以内，超出部分改为写入 `status-log.md`。变更目录中不存在 `status-log.md`（历史变更未分层）时按既有单文件口径处理，SHALL NOT 强制回填。

> 读取边界：常规阶段推进与门控判定 SHALL 仅读取 `.status.md`；`status-log.md` 仅在中断恢复与审计场景读取。权威定义见 `status-file-layering` 能力。

# 执行流程

## 总流程

```
设计探索阶段流程:

┌──────────────────────────────────────────────────────────────────┐
│                      EXPLORE WORKFLOW                             │
├──────────────────────────────────────────────────────────────────┤
│  1. INIT      → 创建变更目录和状态文件                             │
│  2. CONTEXT   → 探索项目上下文（文件、文档、提交记录）              │
│  3. TYPEDET   → 三级回落读取项目类型（继承优先）                  │
│  │   ├── 1) CLAUDE.md「## 项目画像」表的项目类型行               │
│  │   ├── 2) docs/toolchain.md 头部的项目类型字段                 │
│  │   ├── 3) 就地扫描检测（仅前两级均不可用）                      │
│  │   └── 标注来源 → 项目级记录继承 / 降级检测                     │
│  4. CONFIRM   → 静默一致性校验（默认不询问用户）                  │
│  │   ├── 校验一致 → 静默继承，输出「项目类型: X（继承项目级记录）」│
│  │   ├── 校验冲突 → AskUserQuestion 复核（可更新项目级记录）      │
│  │   └── 校验失败 → 沿用记录值继续，不阻塞                        │
│  5. CLASSIFY  → 判断变更粒度（产品级/功能需求级/功能缺陷级）       │
│  6. CLARIFY   → 澄清需求 + 收集用户意图 + CONTEXT.md 管理        │
│  │   ├── 检测 CONTEXT.md 是否存在                                │
│  │   ├── 不存在 → 首次构建（从需求描述提炼领域术语）             │
│  │   ├── 已存在 → 增补检查（新术语/模糊术语对齐）                │
│  │   ├── 对齐检查（功能点术语 vs CONTEXT.md 定义）               │
│  │   └── 收敛门: 清单为空或已降级（进入 SPLIT 前置条件）         │
│  7. SPLIT     → 拆分功能点到原子级                                │
│  8. TIER      → 变更档位初判 + 用户覆盖确认                       │
│  │   ├── 按「变更类型 + 功能点数」映射初判档位                    │
│  │   ├── AskUserQuestion 展示初判结果，用户可上调/下调            │
│  │   ├── 写入变更级 .status.md「变更档位」字段                    │
│  │   └── 输出该档位对应的阶段集合提示（信息性输出，不阻塞）        │
│  9. RELATE    → 分析功能点关联关系                                │
│  10. OUTPUT   → 输出功能设计文档（含版本号+修订记录区+功能结构树）│
│  │   轻量档: 产出压缩为单页（功能点清单+影响分析+修复/实现范围  │
│  │   +非功能期望（一行，无则标注）+页面清单（简表或「无」标注））│
│  11. SELFREV  → 按变更档位自审（签署清单 + 单轮验证）           │
│  │   主 Agent 签署自证（零子代理，3 列签署清单）                 │
│  │   启动 1 个独立 Agent(subagent) 验证子代理                    │
│  │   先独立遍历产物形成自身 4 维度结论（不读签署清单）           │
│  │   再逐项对照签署清单打假；只报告，不修改产物                 │
│  │   主 Agent 统一修复 + 生成「本阶段修复清单」                  │
│  │   报告路径: self-reviews/explore/report.md                    │
│  │   轮数恒为 1，SHALL NOT 执行第二轮，无 0 轮豁免路径           │
│  12. PROTO_GATE → 原型设计决策门控（仅前后端项目）             │
│  │   ├── 轻量档 → 不主动询问，跳过本门控（用户显式要求时仍可执行）│
│  │   ├── 检查 .status.md 中是否存在 prototype_decision 标记     │
│  │   ├── 不存在 → AskUserQuestion: "检测到 {n} 个 UI 功能点，   │
│  │   │   是否进入原型设计阶段？"                                │
│  │   │   ├── 确认创建原型 → prototype_decision=已选择原型设计    │
│  │   │   └── 跳过原型设计 → prototype_decision=已跳过           │
│  │   └── 已存在 → 跳过询问，直接进入下一阶段                    │
│  13. COMPLETE → 更新状态文件，标记阶段完成                        │
└──────────────────────────────────────────────────────────────────┘
```

## 步骤 1：INIT — 创建变更目录和状态文件

```
1. 确定变更名称（kebab-case 格式）:
   ├── 功能需求: add-{feature-name}
   ├── 功能缺陷: fix-{issue-name}
   └── 产品需求: {platform-name}
2. 创建目录 docs/changes/{change}/:
   └── functional-designs/ 目录
   ⚠️ 不在此创建 self-reviews/explore/ —— 该目录在 SELFREV 步骤（步骤 11）执行时创建（全部档位均执行自审，固定单轮）
3. 创建 docs/changes/{change}/.status.md（变更级状态文件）:
   └── 填写基本信息: 创建时间、变更类型（初始标记）、变更档位（待 TIER 判定）、
       项目类型（待 TYPEDET 写入：继承项目级记录 / 降级检测，并标注来源）、变更描述、当前阶段=设计探索
```

## 步骤 2：CONTEXT — 探索项目上下文

使用 Glob/Grep/Read 快速了解项目概况：

```
1. 项目结构和关键目录
2. package.json 中的框架依赖
3. 已有文档（docs/designs/prototypes/、CONTEXT.md 的存在性）
4. 活跃变更情况（docs/changes/ 下的现有变更）
```

## 步骤 3：TYPEDET — 三级回落读取项目类型

按优先级读取**项目级项目类型记录**，命中即止；SHALL NOT 在项目级记录可用时重新扫描判定项目类型。规则权威定义见 `docs/designs/core-mechanisms/01-project-types.md` §1.4。

| 优先级 | 读取源 | 判定 |
|--------|--------|------|
| 1 | CLAUDE.md「## 项目画像」表的「项目类型」行 | CLAUDE.md 存在、含「## 项目画像」marker、且该行有值 → 读取该值，SHALL NOT 再读 `docs/toolchain.md` |
| 2 | `docs/toolchain.md` 头部的「项目类型」字段 | 优先级 1 不可用（CLAUDE.md 不存在 / 无 marker / 该行缺失）时读取 |
| 3 | 就地扫描检测 | 仅前两级均不可用（项目从未 init）时执行 |

第 3 级（就地扫描）的检测标识：

| 检测标识 | 存在时判断为 |
|---------|------------|
| package.json 前端框架依赖（react, vue, angular, next, nuxt, svelte） | 前后端项目 |
| 前端源文件（.vue, .tsx, .jsx, .svelte, .angular） | 前后端项目 |
| 前端构建配置（vite.config.*, webpack.config.*, tsconfig.json） | 前后端项目 |
| 以上均不存在 | 纯后端项目 |

**来源标注**：TYPEDET 结束后 SHALL 记录取值来源，取值 `项目级记录继承`（优先级 1、2）或 `降级检测`（优先级 3），供步骤 4 与产物写入使用。

## 步骤 4：CONFIRM — 静默一致性校验

本步骤**默认路径 SHALL NOT 使用 AskUserQuestion**。校验内容：扫描项目根目录的前端工程标识，与项目级记录读取值比对。

| 校验结果 | 处理 |
|---------|------|
| 一致 | 静默继承记录值并输出「项目类型: {值}（继承项目级记录）」，SHALL NOT 询问用户 |
| 冲突（如纯后端记录的项目新增了前端工程标识） | AskUserQuestion 展示冲突项（扫描结果 vs 记录值），用户可沿用记录值或修正为扫描值；选择修正时更新项目级记录 |
| 校验失败（项目根目录不可读等） | 沿用记录值继续，**校验失败不阻塞**变更创建 |

> 校验是安全阀而非门禁：冲突只触发复核请求，SHALL NOT 自动改写记录。

### 记录缺失时的降级路径（未 init 项目）

前两级记录均不可用时，SHALL 检测并确认**一次**，补写 `docs/toolchain.md` 头部：

- AskUserQuestion 展示检测结果，用户可确认或手动修正
- 结果写入 `docs/toolchain.md` 头部的项目类型字段（文件不存在时创建仅含头部与该字段的最小文件）
- SHALL NOT 写入 CLAUDE.md「## 项目画像」区块——该区块由 `kflow-init` 整体扫描填充，单项补写会产生残缺区块并与受管 marker 的替换逻辑冲突
- 此后该项目的所有变更均静默继承，不再询问

### 用户显式覆盖

用户在需求描述中显式声明的项目类型（或指出记录有误）优先于项目级记录与扫描结果：采用声明值、更新项目级记录、本次变更的变更级快照写入声明值。这是初始误判（扫描信号与错误记录一致，校验比对不出冲突）的唯一纠正通道。

### 变更级快照

读取或降级检测的结果 SHALL 写入变更级快照（`functional-designs/index.md` 与变更级 `.status.md` 的项目类型字段）并标注来源。变更进入执行阶段后快照值冻结，SHALL NOT 随项目级记录变化而变更。

### 项目类型对后续阶段的影响

| 项目类型 | 原型设计阶段 | E2E 测试阶段 | 集成测试阶段 |
|---------|------------|------------|------------|
| 前后端项目 | 可选 | 必须 | 必须 |
| 纯后端项目 | ⏭️ 跳过 | ⏭️ 跳过 | 必须 |

## 步骤 5：CLASSIFY — 判断变更粒度

根据用户输入关键词自动判断，并按粒度调整流程深度：

| 粒度 | 关键词特征 | 流程深度 | 产出要求 |
|------|-----------|---------|---------|
| **产品级** | "搭建/创建平台/系统/完整/产品" | 完整流程 | 需求描述 + 项目类型 + 功能点清单 + 技术方案建议 |
| **功能需求级** | "添加/新增/实现/做/增加" | 标准流程 | 需求描述 + 项目类型 + 功能点清单 + 关联关系 |
| **功能缺陷级** | "修复/Bug/问题/报错/异常" | 简化流程 | 缺陷描述 + 项目类型 + 影响分析 + 修复范围 |

## 步骤 6：CLARIFY — 需求澄清 + CONTEXT.md 管理

### 6a. 领域词汇表管理

`CONTEXT.md` 是项目级领域词汇表，作为所有后续阶段术语引用的**唯一真实来源**。

```
1. 检测 CONTEXT.md 是否存在
2. 不存在 → 首次构建:
   ├── 从用户需求描述中提取关键领域概念
   ├── 为每个概念编写: 定义、别名、边界
   ├── 按字母顺序排列术语
   └── 写入 CONTEXT.md（含版本号和修订记录）
3. 已存在 → 增补检查:
   ├── 检查新出现的术语是否已在词汇表中
   ├── 新术语 → 按首次构建规则添加到 CONTEXT.md
   ├── 用户使用模糊/过载术语 → 提议精确术语并写入
   └── 更新版本号（次版本 +1）和修订记录
4. 对齐检查（SHALL 执行）:
   ├── 检查功能点描述中使用的术语是否与 CONTEXT.md 定义一致
   ├── 功能设计文档中的实体名称 SHALL 使用 CONTEXT.md 中的术语
   └── 发现不一致时 → 更新功能设计文档或更新 CONTEXT.md 定义
```

#### CONTEXT.md 文件格式

`CONTEXT.md` 的格式 SHALL 以 [references/context-template.md](references/context-template.md) 为准——该文件是 CONTEXT.md 格式的**唯一权威来源**，含文件格式模板（项目名标题、术语列表〔定义/别名/边界〕、修订记录三要素）、术语提炼规则（定义精确性/别名必查/边界明确/过载术语处理/禁止实现耦合）与消费链。系统 SHALL NOT 将 CONTEXT.md 的格式定义委托给任何外部技能的格式文件。

### 6b. 需求澄清

使用 AskUserQuestion 澄清模糊需求。输出功能设计时覆盖以下域内内容：

- **页面结构/菜单层级**：用户可见的页面导航结构
- **可执行操作**：每个页面的具体操作、触发方式、可见条件
- **表单项定义**：字段名、字段类型、校验规则、默认值
- **业务规则**：前置条件、校验规则、触发条件、后置结果
- **业务流程**：用户视角的完整业务流程闭环（从触发点到最终结果）
- **非功能期望**：用户视角的性能/安全/可用性/兼容期望（业务语言，不含技术目标值）

### 6c. 收敛门（进入 SPLIT 的前置条件）

CLARIFY SHALL 维护「未决问题清单」，并在进入 SPLIT 之前要求清单为**空**；清单中每一项须被**消解**，或被**显式降级**为 `待补充` 并记录降级理由与责任阶段。存在未处理项时 SHALL NOT 进入 SPLIT。要点：

- **候选来源**：由页面结构/菜单、可执行操作、表单项、业务规则、业务流程、非功能期望**六个内容域逐域遍历**产生候选；清单为空时 SHALL 说明六域均已遍历且未发现歧义
- **消歧路径限定**：仅可经 (a) 澄清提问、(b) 精确化 CONTEXT.md 术语定义、(c) 代码库/事实查库解析；SHALL NOT 以扩增功能设计内容（新增功能点、字段、章节或分支）的方式消歧
- **非必要不增加**：SHALL NOT 为假想分支或将来需求预留功能点、字段与章节；歧义须**收敛为一个确定答案**，SHALL NOT 铺开为多个可能
- **提问纪律**：事实项自动查证（不占用用户注意力），仅决策项提交用户，且一次只提交一项；提问遵循依赖序遍历
- **落点**：清单与降级项写入变更级 `.status.md`，不新增独立产物文件

详见 [references/clarify-convergence.md](references/clarify-convergence.md) — 收敛硬门、候选清单生成规则、消歧路径限定、内容克制、提问纪律，以及降级标记 `待补充`（须含降级理由与责任阶段）与 TODO/TBD 占位符的区分。

## 步骤 7：SPLIT — 拆分功能点到原子级 + 标记 FP 类型

### 7.0 前置条件：收敛门已通过（硬门）

进入本步骤前 SHALL 确认步骤 6c 的**未决问题清单**为空，或清单中每一项均已消解、已显式降级为 `待补充`（含降级理由与责任阶段）。存在未处理项时 SHALL NOT 进入 SPLIT，须返回 6c 逐项消解或降级后再继续。规则依据见 [references/clarify-convergence.md](references/clarify-convergence.md)。

### 7a. 原子级判定标准

| 粒度 | 判断标准 | 示例 |
|------|---------|------|
| 过粗 | 包含多个独立行为 | "用户管理功能" ❌ |
| 合适 | 单一明确行为 | "用户注册"、"用户登录" ✅ |
| 过细 | 实现细节级别 | "添加注册按钮" ❌ |
| 无法归类（跨层） | 同时涉及后端和前端判定标准 | "实现注册功能（含 API + 页面）" ❌ → 必须拆分 |

### 7b. FP 类型判定

每个功能点在拆分完成后 SHALL 标记为「后端」或「前端」：

| 类型 | 判定标准 | 示例 |
|------|---------|------|
| **后端** | API 实现、服务逻辑、数据模型、数据库操作、业务规则引擎、外部服务集成 | "实现注册 API"、"实现用户表迁移" |
| **前端** | 页面组件、UI 组件、路由配置、状态管理、样式实现、CSS 变量注入 | "实现注册表单页面"、"实现导航守卫" |

### 7c. 无法归类则强制拆分

| 步骤 | 操作 |
|------|------|
| 检测 | 当 FP 同时涉及后端和前端判定标准 |
| 判定 | 粒度过粗，MUST 继续拆分 |
| 拆分 | 拆为独立后端 FP + 前端 FP |
| 禁止 | SHALL NOT 以混合形式写入 functional-designs/ |

### 7d. 拆分后关联标注

跨层拆分后的后端 FP 和前端 FP SHALL 在「关联功能点」列相互引用，前端 FP 描述中标注「关联后端 FP: {FP-ID}」。

### 功能点数量与后续处理

> **重要**：子变更划分不在本阶段执行——在详细设计阶段完成后基于完整设计认知划分。

| 条件 | 处理方式 |
|------|---------|
| 功能点 ≤ 10 | 详细设计阶段确认后，创建 1 或 2 个子变更（FP 类型混合时为后端子变更 + 前端子变更） |
| 功能点 > 10 且 ≤ 20 | 详细设计阶段完成后拆分为多个子变更 |
| 功能点总数 > 20 | 提示用户拆分为多个变更 |

## 步骤 8：TIER — 变更档位初判 + 用户覆盖确认

SPLIT 完成后执行变更档位初判，结果写入变更级 `.status.md` 的「变更档位」字段。档位是贯穿全流程的单一分级依据，驱动后续阶段的审查形态与产出深度——SHALL NOT 决定执行轮次。

**初判仅使用本阶段可得的信息**（变更类型 + 功能点数）。接口契约变更数与数据模型变更数属于本阶段域外内容（见「阶段边界约束」），SHALL NOT 为凑齐复核公式而在 explore 阶段定义接口或数据模型；完整复核由 kflow-design 在 DIVIDE 之后按设计面口径执行（新增/修改的接口契约数与 schema/migration 数；受影响但未改契约的接口不计入）。初判映射表与本节说明 SHALL NOT 引入接口或数据模型的计量定义。

### 8a. 初判映射规则

| 变更类型 | 功能点数 | 初判档位 |
|---------|---------|---------|
| 功能缺陷 | FP ≤ 3 | 轻量 |
| 功能缺陷 | FP > 3 | 标准 |
| 功能需求 | FP ≤ 2 | 轻量 |
| 功能需求 | FP > 2 | 标准 |
| 产品需求 | 按功能点数比照功能需求规则 | 与功能需求同规则分档 |

> 阈值保守取值：功能需求需 FP ≤ 2 才判轻量，避免初判偏低导致 design 阶段频繁升档。
>
> `产品需求` SHALL 按功能点数比照 `功能需求` 的分档规则判定（如 FP = 5 → `标准`），SHALL NOT 设独立于该规则的档位下限。
> SHALL NOT 无条件判定为 `标准` 之外的档位；初判结果 SHALL 标注为「初判」，由 kflow-design 的复核环节用设计面分数公式校正；SHALL NOT 存在任何独立于该映射规则的变更类型档位分支。枚举为 `{轻量, 标准}` 二值，SHALL NOT 存在按功能点数上探的第三档取值。
>
> 升档分硬升档（数据迁移、破坏性契约变更、跨变更契约影响；不可拒绝）与软升档（默认保持轻量，仅在新增下游测试阶段时提示，拒绝后记录理由）。

### 8b. 用户覆盖确认

通过 AskUserQuestion 向用户展示初判档位及判定依据（变更类型 + 功能点数），用户可上调或下调。用户覆盖结果优先于初判结果用于后续阶段。

### 8c. 写入状态文件

将最终档位（初判结果或用户覆盖结果）写入变更级 `.status.md` 基本信息：

```
- **变更档位**: {轻量|标准}
```

### 8d. 按档位的阶段集合提示

档位确定（含用户覆盖）后 SHALL 向用户输出该档位对应的阶段集合提示。提示为**信息性输出**，SHALL NOT 作为新的用户确认点或阻塞点；用户在 8b 覆盖档位时，SHALL 按覆盖后的档位重新输出提示，不保留初判档位的提示内容。

| 档位 | 阶段集合提示内容 |
|------|----------------|
| 轻量 | 计划 → 编码 → 代码审查 为**恒执行**；接口单元测试、E2E测试、集成测试为**条件适用**，将在详细设计后由「阶段适用性声明」判定；审计由单一子代理按统一形态执行 |
| 标准 | 全阶段执行，无裁剪 |

提示文案要求：

- SHALL 显式区分「恒执行阶段」与「条件适用阶段」，SHALL NOT 将条件适用阶段表述为已跳过
- SHALL 说明条件适用阶段的判定责任在 `kflow-design`（DIVIDE 之后生成阶段适用性声明），本步骤 SHALL NOT 给出适用性结论
- SHALL 说明 `标准` 档全阶段执行、无裁剪
- SHALL 说明不适用阶段在 `traceability.md` 中整列标记 `⏭️` 且不计入覆盖率分母

> **轻量档不改动探索流程**：轻量档 SHALL NOT 改变本阶段的流程——不新增或跳过任何步骤（本提示为唯一新增输出）、不改变产出物路径与结构、SHALL NOT 在功能点上预判「是否涉及接口」或「是否涉及 UI」（该判定依据详细设计的客观信号，属 `kflow-design` 职责）。

### 8e. 档位对 explore 自身的影响

| 档位 | explore 自身影响 |
|------|----------------|
| 轻量 | OUTPUT 产出压缩为单页（功能点清单 + 影响分析 + 修复/实现范围 + 非功能期望（一行，无则标注） + 页面清单（简表或「无」标注）），仍写入既有产物路径；SELFREV 固定单轮（产物完整性门控为附加硬门）；PROTO_GATE 不主动询问 |

## 步骤 11：SELFREV — 按变更档位自审（签署清单 + 单轮验证）

### 子代理上下文文件加载（基础层 + 创意层）

自审验证子代理 prompt 中 SHALL 包含以下分层加载文件（基础层 + 创意层）：

- skills/kflow-explore/references/state-values.md（摘要）
- skills/kflow-explore/references/gates.md（当前阶段相关门控）
- skills/kflow-explore/references/self-review.md
- skills/kflow-explore/references/clarify-convergence.md（创意层，explore 专属：CLARIFY 收敛门规则）

> **子代理隔离规则**：验证子代理异常时 MUST 重新创建（新 Agent 调用），主代理 SHALL NOT 接管验证执行。同一任务最多重试 3 次（1 次初始 + 3 次重试），全部失败后标记 ⚠️ 阻塞并提示用户。重新创建的子代理是全新 Agent，不依赖前上下文。

### 自审模型：签署自证 → 单轮独立验证 → 统一修复

> **v3.0.0 变更（BREAKING）**：自审终止模型由「多轮收敛循环」改为**固定单轮**——删除多轮收敛判据、失败终止判定、跨轮摘要注入与跨轮修复清单。验证子代理改为**只报告不修改产物**（审查者与修复者分离，消除「边审边修又改出新问题」的振荡源）。自审由三个环节构成：

```
1. 主 Agent 签署自证（零子代理）→ 写作时按 4 维度逐项填写「维度 / 自证结论 / 证据锚点」
2. 单轮独立子代理验证         → 先独立遍历产物（不读签署清单）→ 再逐项打假 → 只报告不修改
3. 主 Agent 统一修复          → 修复全部发现项，产出「本阶段修复清单」随产物交付下游
```

系统 SHALL NOT 预置任何审查轮数、SHALL NOT 执行第二轮、SHALL NOT 存在 0 轮豁免路径。终止结果 SHALL 为 `验证通过` 或 `验证发现问题({N})`，写入变更级 `.status.md`。

> **档位语义**：变更档位只决定**审查形态与产出深度**，SHALL NOT 决定自审轮数（轮数恒为 1）。自审启动前 SHALL 读取变更级 `.status.md` 基本信息的「变更档位」字段；字段缺失或读取到历史遗留的 `完整` 取值时按 `标准` 档处理。

> **独立验证的归属**：本机制只承担「写作质量控制 + 单轮打假」。**真正的独立验证留给交叉审查（REVIEW）环节**——主 Agent 统一修复后生成的「本阶段修复清单」随产物一并交给交叉审查，使下游验证者掌握已知修复清单。

### 签署清单

签署清单 SHALL 按本阶段专属的 4 个维度（完整性 / 闭环性 / 必要性 / 清晰性）组织，每个维度 SHALL 包含「维度」「自证结论」「证据锚点」三列：

| 维度 | 自证结论 | 证据锚点 |
|------|---------|---------|
| {维度名} | 通过 / 不通过 | {产物内的具体位置} |

- **证据锚点 SHALL 指向产物内的具体位置**——章节号、功能点 ID（`FP-00N`）、接口 ID、用例 ID 或表名之一；SHALL NOT 为「全文」「多处」「见上文」之类的模糊指向
- **签署不成立判定**：锚点为空，或锚点指向的位置在产物中不存在、内容不匹配 → 该维度签署判定为**不成立**；任一维度签署不成立时该阶段 SHALL NOT 判定为签署通过
- 签署区 SHALL 作为阶段产物模板的组成部分存在于产物中（`functional-designs/part-NN.md`），SHALL NOT 以独立文件形式产出
- 产物初稿完成后主 Agent SHALL 逐个 4 维度完成签署自证，**SHALL NOT 启动子代理**；自证中发现某维度不通过时 SHALL 先修复该产物并重新完成该维度自证

### 单轮验证

主 Agent SHALL 启动**一个**验证子代理（`Agent(subagent_type="claude")`，独立上下文、不共享主 Agent 对话历史），其执行顺序强制为：

```
1. 独立遍历产物 → 形成自己的 4 维度结论      ← 此阶段 SHALL NOT 读取签署清单
2. 逐项对照签署清单 → 打假                   ← 锚点为空 / 指向不存在内容 = 签署不成立
3. 输出 { 独立发现问题 | 签署打假结果 | 全量遍历证明 | 范围外观察 | 验证结论 }
4. SHALL NOT 修改任何产物（只报告）
```

- **步骤 1 前置的理由**：验证子代理若先读签署清单，会被一份已写好结论的文档锚定，退化为「回填证据」而非独立审查；把独立遍历前置，单轮才能兼具独立发现能力。执行顺序反转时该轮验证结果 SHALL NOT 被接受，主 Agent SHALL 重新启动验证子代理
- **子代理异常处置**：意外停止、报错退出或返回不完整结果时，主代理 MUST 分析原因后重新创建新的子代理，SHALL NOT 在主 Agent 上下文中接管其未完成的工作；最多重试 3 次，全部失败后标记 ⚠️ 阻塞并提示用户

**审查范围冻结与范围外观察**：主 Agent SHALL 在单轮验证启动前从阶段产物**既有内容**生成**审查对象集合**并冻结，审查维度 SHALL 限于本阶段固定 4 个维度枚举；子代理 SHALL NOT 扩大审查对象集合、SHALL NOT 新增审查维度、SHALL NOT 借审查之名新增功能点/字段/章节/分支。冻结范围之外的发现降级为「范围外观察」——不改产物、不计入发现数，写入报告的「范围外观察」小节（为空时记「（空）」）。子代理引入冻结范围外新内容时主 Agent SHALL 拒收并要求在冻结范围内重新验证，越界事实记录到 `docs/skill-suggestion.md`。主 Agent SHALL 在阶段终止时汇总范围外观察条目并向用户提示。

**验证发现分级与终止结果**：

| 终止结果 | 判定口径 |
|---------|---------|
| `验证通过` | 单轮验证零发现 **且** 无签署不成立项 |
| `验证发现问题({N})` | 存在发现项 **或** 存在签署不成立项；N 为该阶段发现总数 |

- 仅存在范围外观察而无范围内发现时，发现数记为 0（其余条件同时满足时终止结果 MAY 为 `验证通过`）
- 读取兼容：读取侧遇到历史变更遗留的 `收敛` 取值 SHALL 归并为 `验证通过`，其余历史取值 SHALL 归并为 `验证发现问题`；SHALL NOT 要求迁移历史 `.status.md`

### 审查维度与检查规则

详见 [references/self-review-dimensions.md](references/self-review-dimensions.md) — 四维度检查规则（完整性/闭环性/必要性/清晰性）及子代理执行说明。

### 轻量档产物完整性门控

轻量档 SHALL 执行单轮自审，SHALL NOT 跳过自审。产物完整性门控保留为附加硬门：`functional-designs/` 产物全部存在且不含 TODO/TBD/未填充占位符，`self-reviews/explore/report.md` SHALL 存在；门控不通过 → 标记 ⚠️ 阻塞并修复后重跑。

### 验证报告内容

单轮验证子代理 SHALL 生成一份验证报告到 `self-reviews/explore/report.md`（固定路径，SHALL NOT 按轮次编号、SHALL NOT 产出多份时间戳文件），且 SHALL 足以判定验证结果与签署是否属实。报告 SHALL 包含：

| 小节 | 内容 |
|------|------|
| 签署清单打假结果 | 逐维度列出：维度名、自证结论、证据锚点、打假结论（属实 / 不成立）、不成立原因 |
| 独立发现问题清单 | 序号、问题描述、严重度、所属维度（此清单 SHALL 来自独立遍历，与签署清单对照结果分开呈现） |
| 范围外观察 | 冻结审查对象集合之外发现的条目；无条目时记「（空）」 |
| 全量遍历证明 | 显式声明全部 4 个审查维度与全部审查对象均已完成遍历 |
| 验证结论 | 发现总数 N；终止结果 `验证通过` 或 `验证发现问题({N})` |

> **反空转条款**：未证明全量遍历的报告 SHALL 判定为不完整，主 Agent SHALL 要求子代理补齐后重新提交。

### 统一修复与流转

验证完成后，主 Agent SHALL 统一修复全部发现项：SHALL 仅修复验证报告确认的问题，不做重构或额外改进；SHALL NOT 新增冻结审查对象集合之外的产物内容（功能点、字段、章节、分支）。主 Agent SHALL NOT 追加确认轮，SHALL 生成「本阶段修复清单」随产物交付下游。修复完成后 SHALL 将终止结果写入 `.status.md` 并标记阶段完成，释放 prototype 或 design 阶段门控。

### 强制执行规则

- 全部档位 SHALL 执行单轮自审，SHALL NOT 存在 0 轮豁免路径；轮数恒为 1，SHALL NOT 执行第二轮
- 签署自证 SHALL 由主 Agent 执行（零子代理），逐维度填写自证结论与证据锚点；锚点 SHALL 指向产物内具体位置，锚点为空或指向不存在内容判该维度签署不成立
- 验证 SHALL 由 1 个独立子代理执行，先独立遍历（不读签署清单）后逐项打假；子代理 SHALL NOT 修改任何产物，全部修复由主 Agent 统一执行
- 审查对象集合 SHALL 由主 Agent 从阶段产物既有内容生成并冻结，审查维度限于完整性/闭环性/必要性/清晰性四维枚举；子代理 SHALL NOT 扩大审查对象集合、SHALL NOT 新增审查维度
- 冻结范围之外的发现 SHALL 记为「范围外观察」，SHALL NOT 修改产物、SHALL NOT 计入发现数；引入范围外新内容的验证 SHALL 被拒收并要求在冻结范围内重新验证，越界事实记录 `docs/skill-suggestion.md`
- 统一修复 SHALL 仅修复报告确认的问题，SHALL NOT 追加确认轮；「本阶段修复清单」SHALL 随产物交付下游交叉审查
- 验证报告 SHALL NOT 输出各维度 0–10 评分与不达标项清单（该评分要求原为第三档专属的报告输出深度，已随该取值一并废除）
- 终止结果 SHALL 写入 `.status.md`，取值 `验证通过` / `验证发现问题({N})`
- 子代理异常时 MUST 重新创建（新 Agent 调用），主代理 SHALL NOT 接管验证执行；最多重试 3 次，全部失败后标记 ⚠️ 阻塞并提示用户
- 主 Agent SHALL 在阶段终止时汇总「范围外观察」条目并向用户提示

## 步骤 12：PROTO_GATE — 原型设计决策门控（仅前后端项目）

> **来源**: refine-skill-execution-rules 变更。探索完成后必须询问是否需要原型设计，避免原型设计被无意跳过。使用 `.status.md` 中的 `prototype_decision` 标记控制幂等，避免重复询问。

### 触发条件

| 条件 | 处理 |
|------|------|
| 项目类型 = 纯后端 | ⏭️ 跳过此步骤 |
| 变更档位 = 轻量 | ⏭️ 不主动询问，跳过本门控（用户显式要求原型设计时仍可执行） |
| `.status.md` 中已有 `prototype_decision` 标记 | ⏭️ 跳过询问（幂等） |
| 前后端项目且无 `prototype_decision` 标记 | 执行 AskUserQuestion |

> **轻量档不主动询问的语义**：仅取消主动提示，不是禁止原型设计。用户显式要求时仍可执行本阶段的 AskUserQuestion 流程并进入 kflow-prototype-design。

### AskUserQuestion 流程

```
Question: "检测到 {n} 个 UI 功能点。是否进入原型设计阶段？"
Options:
  - "确认创建原型"（推荐）→ 写入 prototype_decision=已选择原型设计 → 后续阶段进入 kflow-prototype-design
  - "跳过原型设计" → 写入 prototype_decision=已跳过 → 后续阶段直接进入 kflow-design
```

### 标记写入

在 `.status.md` 中写入：
```markdown
prototype_decision: 已选择原型设计 | 已跳过
```

此标记在整个变更生命周期内有效，后续阶段（如 kflow-guide、kflow-design）读取此标记决定流程走向。

## 步骤 13：COMPLETE — 更新状态文件

更新 `docs/changes/{change}/.status.md`：
1. 标记设计探索阶段为 `✅ 完成`
2. 记录完成时间和执行备注
3. 设置当前阶段为下一阶段（原型设计或详细设计）

### 阶段衔接决策

状态文件更新完成后 SHALL 执行阶段衔接决策，规则见 [references/phase-transition.md](references/phase-transition.md)（决策表与调度映射表的单一真源；本步骤只引用，SHALL NOT 内联决策表或调度映射表）。

- **门控先于衔接**：步骤 12 的原型设计决策门控 SHALL 在衔接决策之前完成；门控未通过时按该步骤既有规则处理，不进入衔接决策
- **按 `prototype_decision` 确定目标阶段**：衔接决策按 `.status.md` 中 `prototype_decision` 标记确定的阶段顺序推进——标记为 `已选择原型设计` → 调动 `kflow-prototype-design`；标记为 `已跳过` → 调动 `kflow-design`
- **调度方式**：按决策表判定目标阶段状态后直接调度目标阶段 Skill（`Skill(skill="{target-skill}", args="{change-name}")`）
- **SHALL NOT 提示推进指令**：系统 SHALL NOT 将「提示用户输入推进指令（如「继续 {change-name}」）」作为进入下一阶段的必要条件
- **停止衔接时说明原因**：衔接决策停止（目标阶段 `❌ 阻塞` 等）时 SHALL 向用户说明停止原因与可执行的下一步操作

## 阶段边界约束

### 域内内容（explore 负责）

| 内容类别 | 说明 |
|---------|------|
| 页面结构/菜单层级 | 用户可见的页面导航结构 |
| 可执行操作 | 用户在每个页面可执行的具体操作 |
| 表单项定义 | 字段名、类型、校验规则、默认值 |
| 业务规则 | 前置条件、校验规则、触发条件、后置结果 |
| 业务流程 | 用户视角的完整业务流程闭环 |
| 非功能期望 | 用户视角的性能/安全/可用性/兼容期望（业务语言，不含技术目标值） |
| 页面清单 | 页面 × 菜单路径 × 类型 × 区块级结构描述 × 涉及功能点 |
| 功能结构树 | 以树状图展示模块→功能点层级，节点标注 FP-ID + 优先级 + 简述 |
| 功能点拆分 | 原子级功能点、依赖关系、优先级 |

### 域外内容（禁止）

| 内容类别 | 说明 | 应由哪个阶段处理 |
|---------|------|----------------|
| 技术架构选型 | 框架、组件库、中间件选择 | design |
| 数据模型设计 | 实体定义、表结构、索引设计 | design |
| 接口定义 | API 路径、方法、入参出参 | design |
| 代码实现 | 任何代码文件 | code |
| 子变更划分 | 执行单元划分 | design |
| UI 原型 | 视觉设计和交互原型 | prototype |

### 越界处理

当 explore 阶段发现信息不足以完成功能设计时：
1. 在当前阶段文档中标记"待补充"，并同步记录**降级理由**与**责任阶段**——该标记与步骤 6c 收敛门的显式降级为**同一语义**，须写入变更级 `.status.md` 的未决问题清单；缺降级理由或责任阶段即退化为被禁止的占位符（详见 [references/clarify-convergence.md](references/clarify-convergence.md) §六）
2. 记录到 `docs/skill-suggestion.md`
3. 禁止自创新文档来填补信息空缺
4. 禁止越界输出技术方案或接口定义

# 核心提醒

- **FP 类型标记**：每个功能点 SHALL 标记为「后端」或「前端」，无法归类的 FP 必须继续拆分，类型作为后续子变更划分类型校验的依据
- **项目类型继承**：三级回落读取项目级记录（CLAUDE.md 项目画像 → `docs/toolchain.md` 头部 → 就地检测），项目级记录可用时 SHALL NOT 重新扫描判定；静默一致性校验一致即静默继承（不询问用户），仅记录缺失或校验冲突时才 AskUserQuestion；校验失败不阻塞；降级补写落在 `docs/toolchain.md` 头部且 SHALL NOT 写入 CLAUDE.md 项目画像区块；变更级快照在变更生命周期内冻结
- **子变更划分不在此阶段执行**：后置到详细设计阶段完成后基于完整设计认知划分
- **自审强制执行（签署清单 + 单轮验证）**：固定单轮，SHALL NOT 执行第二轮、SHALL NOT 存在 0 轮豁免路径。三环节：主 Agent 签署自证（零子代理，`维度 / 自证结论 / 证据锚点` 三列，锚点 SHALL 指向产物内具体位置）→ 1 个独立子代理单轮验证（先独立遍历产物形成自身 4 维度结论且不读签署清单，再逐项对照签署清单打假，只报告不修改产物）→ 主 Agent 统一修复并生成「本阶段修复清单」随产物交付下游，不追加确认轮。审查对象集合由主 Agent 冻结、维度集合封闭为完整性/闭环性/必要性/清晰性四维，范围外发现降级为「范围外观察」；引入范围外新内容的验证 SHALL 被拒收。终止结果取值 `验证通过` / `验证发现问题({N})`，写入变更级 `.status.md`
- **两动作规则**：每 2 次外部信息收集操作后立即保存关键发现到 functional-designs/
- **CONTEXT.md**：项目级领域词汇表，首次构建后持续增补，后续阶段只引用不修改
- **functional-designs/ 结构**：index.md（含版本号、需求变更记录表、配置项影响矩阵）+ part-NN.md 目录化结构
- **functional-designs/index.md 版本号**：格式为 `主版本.次版本.修订号`，初始版本为 `1.0.0`
- **变更粒度**：产品级 → 完整流程；功能需求级 → 标准流程；功能缺陷级 → 简化流程
- **档位阶段集合提示**：档位初判（含用户覆盖）后 SHALL 向用户输出该档位的阶段集合——轻量档为「计划→编码→代码审查」恒执行，接口单元测试/E2E测试/集成测试为条件适用（由 `kflow-design` 的阶段适用性声明判定）；标准档全阶段执行、无裁剪。提示为信息性输出，不作为新的确认点；轻量档不改动探索流程本身
- **禁止越界**：不得输出技术方案、接口定义、数据模型、子变更划分方案
- **需求澄清收敛门**：CLARIFY SHALL 维护未决问题清单，清单为空或每项已消解/已显式降级（`待补充` + 降级理由 + 责任阶段）方可进入 SPLIT；候选须由六个内容域逐域遍历产生，SHALL NOT 以直接置空代替；SHALL NOT 以扩增功能设计内容的方式消歧；事实项自动查证、决策项一次一项
- **非功能期望业务语言边界**：index.md §一「非功能期望」小节 SHALL 使用用户视角业务语言并关联功能点，SHALL NOT 定义技术目标值（并发数、P95 等技术定义由 design 阶段 NFR 章节转译）；用户期望含技术性表述时记录用户原意并标注口径来源；无显式期望时整节标注「本变更无特殊非功能期望」
- **页面清单一致性**：index.md §四「页面清单」与各 FP「所属页面与菜单」的页面归属 SHALL 一致（无孤页、无漏页）；纯后端/无前端 FP 标注「本变更无涉及页面」；轻量档保留简表（结构描述可合并为一句）
- **变更名称**：使用 kebab-case 格式
- **原型设计决策门控**：探索完成后 SHALL 询问是否进入原型设计（前后端项目），写入 `prototype_decision` 标记控制幂等，避免重复询问
- **CONTEXT.md 对齐检查**：增补后必须执行术语对齐检查
