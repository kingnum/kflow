# KFlow Skills 核心运行机制

> **版本**: 参见仓库根目录 `VERSION` 文件
> **创建时间**: 2026-04-29
> **更新时间**: 2026-05-17

> **加载层级**: 基础层
> **适用阶段**: 全部

本文档定义 KFlow Skills 体系的核心运行机制，包括目录结构、状态文件、任务清单、阶段流转规则、回退机制和条件产物引用规范。

## 一、项目类型区分机制

### 1.1 项目类型定义

| 项目类型 | 定义 | 阶段数量 |
|---------|------|---------|
| **前后端项目** | 包含前端工程（存在前端框架依赖、.vue/.tsx/.jsx 文件、前端构建配置等） | 11 阶段（含审计门控） |
| **纯后端项目** | 不包含前端工程 | 9 阶段（含审计门控） |

### 1.2 检测规则

| 检测标识 | 判断依据 |
|---------|---------|
| package.json 前端框架依赖 | react, vue, angular, next, nuxt 等 |
| 前端源文件 | .vue, .tsx, .jsx, .svelte 等文件存在 |
| 前端构建配置 | vite.config.*, webpack.config.*, tsconfig.json 等 |

### 1.3 阶段差异

| 阶段 | 前后端项目 | 纯后端项目 |
|------|-----------|-----------|
| 设计探索 | ✓ 必须 | ✓ 必须 |
| 原型设计 | ✓ 可选（推荐） | ⏭️ 跳过 |
| 详细设计 | ✓ 必须（变更级） | ✓ 必须（变更级） |
| 计划 | ✓ 必须 | ✓ 必须 |
| 编码 | ✓ 必须 | ✓ 必须 |
| 代码审查 | ✓ 必须 | ✓ 必须 |
| 接口单元测试 | ✓ 必须 | ✓ 必须 |
| E2E 测试 | ✓ 必须 | ⏭️ 跳过 |
| 集成测试 | ✓ 必须（变更级） | ✓ 必须（变更级） |
| 审计 | ✓ 必须（归档门控） | ✓ 必须（归档门控） |
| 归档 | ✓ 必须 | ✓ 必须 |

### 1.4 项目类型记录与继承

> **版本**: 当前变更新增（能力 `project-type-detection`）

项目类型是**仓库级不变量**——在一个项目内稳定；但它同时决定每个变更的阶段集合，因此必须落到变更级并冻结。本节定义项目级记录的存放位置与读取顺序、确认时机、静默一致性校验与漂移处理、用户显式覆盖通道，以及变更级快照的冻结规则。

#### 1.4.1 项目级记录真源与三级读取优先级

项目级记录有两处落点，均由 `kflow-init` 在**同一轮扫描**中写入，值保持一致：

| 读取优先级 | 记录位置 | 性质 |
|-----------|---------|------|
| 1 | CLAUDE.md「## 项目画像」表的「项目类型」行 | **权威来源**：会话自动加载进上下文，零读取成本 |
| 2 | `docs/toolchain.md` 头部的「项目类型」字段 | **兜底来源**：init 的唯一必须产物，存在性有保证 |
| 3 | 就地扫描检测（仅前两级均不可用时） | 降级路径，见 1.4.1 末条与 1.4.2 |

读取规则：

- 第 1 级可用（CLAUDE.md 存在、含「## 项目画像」marker、且项目类型行有值）→ 直接采用，SHALL NOT 再读 `docs/toolchain.md`
- 第 1 级不可用（CLAUDE.md 不存在、无「## 项目画像」marker、或项目类型行缺失）→ 读取 `docs/toolchain.md` 头部的项目类型字段
- 前两级均不可用 → 就地扫描检测并向用户确认一次，确认结果写入 `docs/toolchain.md` 头部
- 降级补写 SHALL NOT 写入 CLAUDE.md「## 项目画像」区块——该区块是 `kflow-init` 整体扫描的产物（含技术栈、目录、入口文件、8 项产品文档状态），由变更创建链路单项补写会产生残缺区块，且与受管 marker 的「替换整个 section」逻辑冲突

变更创建链路（`kflow-guide`、`kflow-explore`）在项目级记录可用时 SHALL NOT 重新扫描判定项目类型。

#### 1.4.2 确认时机

AskUserQuestion 确认项目类型**只发生在以下情形**：

| 情形 | 触发条件 |
|------|---------|
| init 首次确定项目类型 | 项目级记录不存在 |
| re-init 扫描与记录冲突 | 重新扫描结果与项目级记录不一致 |
| 变更创建时的降级检测 | 前两级记录均不可用（等价于项目从未执行 init） |
| 变更创建时静默校验发现冲突 | 扫描结果与项目级记录冲突（漂移，见 1.4.3） |

其余情形 SHALL **静默复用**已记录的项目类型，SHALL NOT 发起确认：

- re-init 且扫描结果与记录一致 → 静默复用记录值，不询问
- 变更创建且静默一致性校验与记录一致 → 静默继承并输出「项目类型: {值}（继承项目级记录）」
- 项目级记录仅 `docs/toolchain.md` 一处有值（CLAUDE.md 画像缺失或被清理）→ 以该值静默复用并与扫描比对

确认动作的价值在于**校准一次**，而非每次重算：自动检测曾误判（前后端分离、前端在独立仓库的项目被判为纯后端，见 [examples/skill-suggestion.md](../examples/skill-suggestion.md) 记录 3）。把确认前移到 init 后，一个项目内的所有变更共享同一次确认结果。

#### 1.4.3 静默一致性校验与漂移处理

变更创建时执行**一次**静默一致性校验：扫描项目根目录的前端工程标识（按 1.2 节检测规则），与项目级记录比对。

| 校验结果 | 处理 |
|---------|------|
| 一致 | 静默继承记录值并继续变更创建流程，SHALL NOT 打扰用户 |
| 冲突（如纯后端记录的项目新增了前端工程标识） | AskUserQuestion 展示冲突项（扫描结果 vs 记录值），用户可沿用记录值或修正为扫描值；选择修正时更新项目级记录 |
| 校验无法完成（项目根目录不可读等） | 沿用项目级记录值继续流程，SHALL NOT 因校验失败阻塞变更创建 |

校验是**安全阀，不是门禁**：冲突只触发复核请求，SHALL NOT 自动改写记录。成本为一次 `package.json` 读取加至多一次 Glob。

**记录过期（漂移）**——项目会演进，纯后端项目后来新增前端工程——由本校验发现。**初始误判**（扫描信号与错误记录一致，比对不出冲突）由 1.4.4 的显式覆盖通道兜住。

#### 1.4.4 用户显式覆盖

用户在需求描述中显式声明的项目类型（或指出已记录的项目类型有误）**优先于项目级记录与扫描结果**：

- 采用声明值，SHALL NOT 因记录值不同而要求用户重新执行 init
- 更新项目级记录：写入两处落点中**已存在**的那一处；两处皆无时写入 `docs/toolchain.md` 头部
- 本次变更的变更级快照写入声明值

这是初始误判的唯一逃生舱：此类误判中扫描信号与错误记录一致，1.4.3 的一致性校验无法发现。

#### 1.4.5 变更级快照与生命周期冻结

`functional-designs/index.md` 与变更级 `.status.md` 的项目类型字段**继续保留**，取值来源由「重新检测」改为「继承项目级记录（或降级检测）」并标注来源。

变更进入执行阶段后，变更级 `.status.md` 的项目类型字段 SHALL NOT 随项目级记录变化而变更；该变更的所有阶段判定（含阶段适用性与阶段流转）以变更级快照为准。原因是阶段集合由项目类型决定——纯后端项目的 E2E 阶段标 `⏭️`、`traceability.md` 对应列整列填 `⏭️` 且不计入覆盖率分母，审计与归档门控据此放行；若项目类型在变更中途变化，已跳过的阶段会复活，列填充与门控判定将失去一致性依据。项目级记录的更新在下一个新变更生效。

**副产物**：消费侧 7 个 Skill（`kflow-design`、`kflow-prototype-design`、`kflow-api-test`、`kflow-e2e-test`、`kflow-verify`、`kflow-audit`、`kflow-archive`）只读变更级快照，快照依然有值，其判定逻辑与读取路径不需变更。
