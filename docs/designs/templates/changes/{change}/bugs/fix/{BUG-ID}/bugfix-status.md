# 缺陷修复状态：{BUG-ID}

> **关联变更**: {change-name}
> **产物路径**: `docs/changes/{change}/bugs/fix/{BUG-ID}/bugfix-status.md`
> **机制定义**: `bugfix-fast-lane` 能力；字段语义见 `core-mechanisms/03-status-and-tasks.md` §3.5

> **填写责任分配**:
>
> | 区 | 填写责任 | 时机 |
> |---|---------|------|
> | 一、基本信息 / 二、分诊结论 / 三、受影响项清单 | `kflow-bug-triage` | L4 结论时创建并填写 |
> | 四、修复记录 / 五、定向验证 | `kflow-bug-fix`（快车道模式） | 修复与验证过程中 |
> | 六、收口结论 | `kflow-bug-fix`（快车道模式） | 快速收口时 |
>
> **填写要求**: 六个区 SHALL NOT 省略。快速收口校验要求全部必填区已填写且无占位符（`TODO` / `TBD` / `{待填写}` / `...`）。
>
> **生命周期**: 本文件 SHALL NOT 随收口删除，保留为历史记录。同一变更下多个快车道缺陷各自持有独立的 `bugfix-status.md`，互不干扰。
>
> **隔离要求**: 本文件是快车道缺陷生命周期的唯一状态载体。快车道执行期间 SHALL NOT 读写变更级 `.status.md` 的阶段状态矩阵字段（阶段状态、执行轮次、终止结果、阶段耗时与轮次统计）。

| 字段 | 值 | 填写要求 |

| 四层判断摘要 | {L1/L2/L3 通过结论 + L4 判定依据} | 必填；承接 `bugs/bug-NNN-NNN.md` 的「诊断结果」节 |
| 影响范围评估 | {受影响功能点 / 接口 / 数据模型变更} | 必填；承接「影响范围评估」节 |

**四层溯源摘要**：

| 层级 | 结论 | 判断依据 |
|------|------|---------|
| L1 需求定义 | ✅ 通过 | {证据：功能点覆盖度与歧义检查结论} |

| L3 详细设计 | ✅ 通过 | {证据：接口定义 / 数据模型 / 状态流转一致性结论} |
| L4 实现执行 | ❌ 问题源头 | {证据：代码与 detailed-design.md 的一致性缺口} |

**用户确认记录**：

| 字段 | 值 | 填写要求 |
|------|---|---------|
| 用户是否覆盖诊断结论 | {否 / 是} | 必填 |
| 覆盖后指定的层级 | {无 / L1 / L2 / L3 / L4} | 选择「是」时必填 |
| 覆盖原因 | {原因描述 或「（无）」} | 选择「是」时必填 |

> **前置条件**: L1 / L2 / L3 三层 MUST 全部为 ✅ 通过。任一层为 ❌ 时问题源头不是 L4，SHALL NOT 进入快车道。

> **入口独占**: 快车道 SHALL 仅由 `kflow-bug-triage` 的四层溯源 L4 结论进入（含用户覆盖诊断结论为 L4 的情形），SHALL NOT 提供其他入口。

## 三、受影响项清单

**填写责任**: kflow-bug-triage（创建时）；**SHALL NOT 由修复者修改**

| 类别 | 清单 | 填写要求 |
|------|------|---------|
| 受影响功能点 | {FP-NNN, FP-NNN, ...} | 必填（无则为 `none`）；来源 `functional-designs/` |
| 受影响接口 | {/api/xxx, /api/yyy, ...} | 必填（无则为 `none`）；来源 `detailed-design.md` |
| 受影响测试用例 | {用例标识, ...} | 必填；来源 `api-tests/`、`e2e-tests/` |
| 数据模型变更 | {none / 变更描述} | 必填 |
| 影响范围分数 | {FP数×1 + 接口数×1.5 + 数据模型×2 = 计算值} | 必填；仅记录性信息，SHALL NOT 用于推算轮次 |

> **冻结规则**: 本清单是快车道模式的**冻结验证范围**——定向验证 SHALL 仅执行本清单覆盖的测试用例，SHALL NOT 重跑全量测试套件。修复者 SHALL NOT 扩大或缩小本清单。
>
> **分诊失效**: 修复过程中发现实际影响面超出本清单时 SHALL 判定为**分诊失效**，退回 `kflow-bug-triage` 重新评估影响范围。

## 五、定向验证

**填写责任**: `kflow-bug-fix`（快车道模式）；每次验证**追加**一条记录，SHALL NOT 覆盖之前的记录；追加顺序按验证时间排列

### 验证记录 1

| 字段 | 值 | 填写要求 |
|------|---|---------|
| 验证时间 | {YYYY-MM-DD HH:MM} | 必填 |
| 验证范围 | 受影响项清单覆盖的测试用例 | 固定；SHALL NOT 重跑全量测试套件 |
| 用例清单与结果 | {用例标识 → ✅ / ❌} | 必填；逐项列出 |
| 受影响项覆盖率 | {N%} | 必填；SHALL 达 100%，未达 100% 时本次验证判定为不通过 |
| 通过结果 | {通过 / 未通过} | 必填 |
| 失败用例 | {用例标识列表 或「（无）」} | 未通过时必填 |
| 失败原因 | {原因描述 或「（无）」} | 未通过时必填 |
| 报告路径 | `bugs/fix/{BUG-ID}/verify-report.md` | 通过时必填 |

<!-- 后续验证追加「### 验证记录 2」「### 验证记录 3」，按验证时间排列 -->

> **重试上限**: 定向验证未通过时复用「三次修复尝试上限」（第 1 次直接修复 / 第 2 次替代方案 / 第 3 次重新审视假设；同一用例在多次验证间的尝试次数累加）；达到上限时使用 AskUserQuestion 升级用户。SHALL NOT 引入新的轮次模型。
>
> **不做全量**: 定向验证 SHALL NOT 触发集成测试轮次，SHALL NOT 更新变更级 `执行轮次`。
>
> **未通过时的回写**: 定向验证未通过时 SHALL NOT 更新 `bugs/index.md` 状态，SHALL 在本区记录失败信息（验证时间、失败用例、失败原因）。

## 六、收口结论

**填写责任**: `kflow-bug-fix`（快车道模式，快速收口时）

| 校验项 | 结论 | 填写要求 |
|-------|------|---------|
| 受影响项清单 100% 覆盖且全部通过 | {✅ 满足 / ❌ 不满足} | 必填 |
| 定向验证报告存在 | {✅ 满足 / ❌ 不满足} | 必填 |
| 本文件全部必填区已填写且无占位符 | {✅ 满足 / ❌ 不满足} | 必填 |
| 收口时间 | {YYYY-MM-DD HH:MM} | 全部校验项满足时填写 |
| 缺陷最终状态 | {已解决 / 处理中} | 全部校验项满足 → `已解决`；任一不满足 → `处理中` |

> **收口动作**: 全部校验项满足时，SHALL 更新 `bugs/index.md` 对应行状态为「已解决」，并在问题详情文件 `bugs/bug-NNN-NNN.md` 的「修复记录」节追加修复摘要、标记快车道收口完成。任一校验项不满足时 SHALL NOT 标记为「已解决」，SHALL 在「定向验证」区记录未通过原因。
>
> **术语边界**: 本机制为「**快速收口**」而非「快速归档」——「归档」是变更级元工作流（`/opsx:archive` + 版本自增 + 打包），缺陷级闭环复用该词会造成歧义。
>
> **边界**: 快速收口 SHALL NOT 触发阶段回退、SHALL NOT 阻塞变更级阶段流转、SHALL NOT 修改变更级 `.status.md` 的任何阶段状态字段。
