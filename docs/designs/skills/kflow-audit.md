## 门控检查

> **机制说明**：审计门控规则定义在 [core-mechanisms/04-gates-and-transitions.md](../core-mechanisms/04-gates-and-transitions.md#63-归档条件)

审计触发方式：
- **归档前自动触发**：集成测试通过后进入归档流程时，自动执行审计作为归档门控
- **手动调用**：用户直接调用 kflow-audit，对指定变更或全部活跃变更执行审计

归档门控规则：
- 阻塞级问题（缺少必须产物、阶段门控未通过、阶段跳转、审查未闭环、裁剪无声明依据）→ 阻断归档，要求修复后重新审计
- 建议级问题（文档格式不规范、耗时数据缺失、效率异常）→ 不阻断归档，记录改进建议到 `docs/skill-suggestion.md`
- **裁剪豁免**：有阶段适用性声明依据的裁剪不判缺项，SHALL NOT 因合法裁剪的产物缺失阻断归档
- 审计 SHALL 保留阻塞级问题拦截权与归档门控地位，SHALL NOT 因降级为记账员而丧失门控能力

## 审计执行方式

审计 SHALL 由**单个**子代理执行，SHALL NOT 由主 Agent 直接执行，SHALL NOT 拆分为多个并行子代理。该约束适用于**全部变更档位**：系统 SHALL NOT 因变更档位而改变审计的执行方式、职责集合或报告形态——不存在按档位分化的简化审计路径。

审计子代理 SHALL 先完成全部四项记账职责的事实采集并逐项呈现判定依据，再输出检查项结论；SHALL NOT 在事实采集未完成时输出结论。

> **子代理隔离规则**（本 skill 内联声明，规则来源见 `subagent-isolation-rule` capability 的「隔离规则适用范围」需求）：审计子代理意外停止、报错退出或返回不完整结果时 MUST 重新创建新的子代理（新 Agent 调用），主 Agent SHALL NOT 接管审计执行。最多重试 3 次，全部失败后标记 ⚠️ 阻塞并提示用户。审计为单次执行、无轮次概念，SHALL NOT 适用轮次级重试粒度。

## 四项记账职责

审计 SHALL 以四项记账职责执行。系统 SHALL NOT 计算总分或任何维度得分，SHALL NOT 输出评分表，SHALL NOT 对阶段产物质量作独立评审——产物质量评审由签署清单自证、单轮验证与交叉审查承担。

| 职责 | 内容 | 不通过后果 |
|------|------|-----------|
| (a) 门控校验 | 读取变更级 `.status.md`，校验各阶段门控是否全部通过；检查是否存在跳阶段、可选阶段是否正确处理（跳过 vs 执行）、回退是否走正规流程（⚠️ 需修订 → 修订 → 完成）；校验各阶段终止结果取值是否合法（`验证通过` / `验证发现问题({N})` / `执行完成` / `定向重验失败` / `停滞`；历史取值 `收敛` / `未收敛` 按读取侧归并规则处理） | 不通过 = 阻塞 |
| (b) 覆盖率与产物存在性校验 | 校验 `traceability.md` 覆盖率是否达 100%；校验各阶段必须产物是否存在（.status.md、functional-designs/、detailed-design.md、tasks.md、traceability.md）、条件产物是否正确处理（🔶 / ⏭️ 图例）、产物内容非空且无占位符；校验自审报告 `self-reviews/{phase}/report.md` 是否存在（份数为 1 为正常形态） | 缺项 = 阻塞 |
| (c) 阶段耗时汇总 | 汇总各阶段耗时与子代理轮次数据（来自 `.status.md`「阶段耗时与轮次统计」区），输出效率摘要（含总耗时、各阶段耗时占比、最耗时阶段）；统计缺陷发现-修复周期；汇总各子变更 fix-report 的架构改进机会（见下方 Post-mortem 汇总） | 信息展示，SHALL NOT 参与门控判定 |
| (d) 阻塞级问题兜底 | 兜底扫出未被前序环节关闭的阻塞级问题（缺少必须产物、阶段门控未通过、阶段跳转、审查未闭环、裁剪无声明依据；缺陷根因分类未执行、修复未闭环、设计错误未触发回退），并记录问题的归属阶段以支持回退路由 | 有问题 = 阻塞 |

### 职责 (a)(b) 的裁剪豁免

- 有阶段适用性声明依据的 `⏭️ 不适用` 阶段，其产物（`api-tests/`、`e2e-tests/`、`test-reports/integration/`）缺失属**合法状态**，SHALL NOT 判为缺项；SHALL NOT 将该类 `⏭️` 判为跳阶段。无声明依据的 `⏭️` 判为**阻塞级问题**。
- 按项目类型产生的 `⏭️ 跳过`（纯后端项目的 E2E测试阶段与 E2E测试列）不按跳阶段判定。

### 职责 (b) 的审查报告校验

- SHALL NOT 因缺少超出该档位要求的视角报告而判为缺项。
- SHALL NOT 因自审报告仅 1 份而判为缺项或「轮次超标」（单轮验证下份数恒为 1 属正常形态）。

### 职责 (c) 的子项：Post-mortem 汇总

审计时 SHALL 读取所有子变更的 fix-report 文件，汇总架构改进建议：

```
1. 扫描所有子变更 fix-report 目录
   └── subchanges/*/test-reports/fix-reports/*.md
2. 提取每个 fix-report 的"关联建议"字段（架构改进建议、测试 seam 缺失报告）
3. 按类型归类：
   ├── 测试 seam 缺失 → 测试架构改进机会
   ├── 模块耦合 → 模块化改进机会
   ├── 接口契约 → 契约设计改进机会
   └── 其他 → 通用改进建议
4. 汇总到审计报告的改进建议章节
```

| 检查项 | 说明 |
|--------|------|
| Post-mortem 完成率 | 所有子变更 fix-report 是否包含 post-mortem 章节 |
| 架构改进识别 | 是否有被打捞出的架构级改进机会 |
| 建议质量 | 建议是否具体可执行（非"改进代码质量"等空泛建议） |
| 建议传递 | 汇总后的架构改进机会是否可传递给下一变更的设计阶段 |

## 执行流程

```
审计阶段流程:

┌─────────────────────────────────────────────────────────────┐
│                      AUDIT WORKFLOW                          │
├─────────────────────────────────────────────────────────────┤
│  1. PRE_HOOK  → 引用 `skills/kflow-audit/references/hooks.md` audit 阶段 PRE_HOOK (轻量) │
│  │   ├── CHECK_STATE → 验证前置阶段状态                       │
│  │   ├── RELOAD → 重读全量产物, cross-reviews/, test-reports/, .status.md │
│  │   └── 不需要服务                                            │
│  2. SCOPE     → 确定审计范围                                  │
│  │   ├── 指定变更 → 审计单个变更                               │
│  │   └── 全部活跃变更 → 审计所有未归档变更                      │
│  3. COLLECT   → 收集审计材料                                   │
│  │   ├── .status.md (阶段状态、耗时)                          │
│  │   ├── functional-designs/ (功能设计)                      │
│  │   ├── detailed-design.md (详细设计)                        │
│  │   ├── cross-reviews/* (审查报告)                          │
│  │   └── test-reports/*/summary.md (测试报告)                 │
│  4. EVALUATE  → 四项记账职责事实采集（全部档位同一路径，单子代理）│
│  │   ├── (a) 门控校验 → 读 .status.md 校验各阶段门控与终止结果    │
│  │   ├── (b) 覆盖率与产物存在性校验 → traceability + 产物树      │
│  │   ├── (c) 阶段耗时汇总（含 Post-mortem 汇总）                 │
│  │   └── (d) 阻塞级问题兜底 → 扫出未关闭的阻塞级问题              │
│  │   逐项呈现判定依据                                           │
│  5. VERDICT   → 事实采集完成后依问题清单严重度分级作出判定        │
│  │              （SHALL NOT 计算总分）                          │
│  6. CLASSIFY  → 问题分级（阻塞/建议）                          │
│  │   ├── 阻塞级 → 阻断归档，要求修复后重新审计                   │
│  │   └── 建议级 → 不阻断，记录到 skill-suggestion.md           │
│  7. ROUTE     → 审计回退路由                                   │
│  │   ├── 问题归属设计阶段 → 设计阶段 ⚠️ 需修订                  │
│  │   ├── 问题归属编码阶段 → 编码阶段 ⚠️ 需修订                  │
│  │   └── 问题归属测试阶段 → 测试阶段 ⚠️ 需修订                  │
│  8. REPORT    → 输出审计报告（记账记录形态，全档位同一形态）      │
│  9. POST_HOOK → 引用 `skills/kflow-audit/references/hooks.md` audit 阶段 POST_HOOK (轻量) │
│  │   └── UPDATE_STATE → 更新 .status.md                       │
│ 10. COMPLETE  → 审计通过（无阻塞级问题）或触发回退               │
└─────────────────────────────────────────────────────────────┘
```

## 审计回退路由

审计发现问题是第 4 种回退触发来源（与缺陷修复、代码审查、用户需求变更并列）：

```
审计回退流程:

1. 确定问题归属阶段:
   ├── 设计探索/详细设计问题 → 对应设计阶段 ⚠️ 需修订
   ├── 编码问题 → 编码阶段 ⚠️ 需修订
   └── 测试问题 → 对应测试阶段 ⚠️ 需修订

2. 重置后续阶段:
   - 目标阶段之后的所有阶段状态 → ⏳ 待开始
   - 受影响产物标记为"待修订"

3. 联动评估:
   ├── 仅当前变更受影响 → 单独回退
   ├── 接口契约变更 → 依赖该接口的子变更联动回退
   ├── 架构级变更 → 所有子变更联动回退
   └── 审计发现 → 按审计问题归属阶段确定回退范围和联动子变更

4. 修复后重新审计:
   - 修复完成 → 目标阶段 ⚠️ 需修订 → ✅ 完成
   - 后续阶段逐个重新执行
   - 重新进入归档流程时再次触发审计
```

## 一、四项记账职责检查结论

> 子代理 SHALL 先完成全部四项职责的事实采集并逐项呈现判定依据，再输出检查项结论。

| 职责 | 覆盖内容 | 结论 | 判定依据（事实采集结果） |
|------|---------|------|------------------------|
| (a) 门控校验 | 阶段门控是否全部通过、阶段跳转与回退、终止结果取值合法性 | {✅ 通过 / ❌ 不通过} | {读取 `.status.md` 阶段状态与终止结果的事实} |
| (b) 覆盖率与产物校验 | traceability 覆盖率、必须产物与条件产物存在性、自审报告存在性 | {✅ 通过 / ❌ 不通过} | {覆盖率与产物事实} |
| (c) 耗时汇总 | 各阶段耗时与子代理轮次汇总、效率摘要、post-mortem 改进机会归类 | {✅ 通过 / ❌ 不通过} | {耗时数据齐全性事实} |
| (d) 阻塞兜底 | 兜底扫出未被前序环节关闭的阻塞级问题、缺陷根因与修复闭环、设计错误回退 | {✅ 通过 / ❌ 不通过} | {未关闭阻塞级问题数、修复闭环事实} |

### 1. (a) 门控校验

| 检查项 | 结论 | 判定依据 |
|--------|------|---------|
| 各阶段门控是否全部通过 | {✅ 通过 / ❌ 不通过} | {阶段状态表摘要} |
| 是否存在跳阶段 | {✅ 通过 / ❌ 不通过} | {跳阶段检查结果；有适用性声明依据的 `⏭️` 不判跳阶段} |
| 可选阶段处理是否正确 | {✅ 通过 / ❌ 不通过} | {跳过 vs 执行} |
| 回退是否走正规流程 | {✅ 通过 / ❌ 不通过} | {⚠️ 需修订 → 修订 → 完成} |
| 各阶段终止结果取值是否合法 | {✅ 通过 / ❌ 不通过} | {`验证通过` / `验证发现问题({N})` / `执行完成` / `定向重验失败` / `停滞`；历史 `收敛` / `未收敛` 按归并规则处理} |
| 测试阶段门控与执行报告 | {✅ 通过 / ❌ 不通过 / ⏭️} | {测试阶段（适用时）门控通过，执行报告存在且定向重验结果通过} |

### 2. (b) 覆盖率与产物校验

| 检查项 | 结论 | 判定依据 |
|--------|------|---------|
| traceability.md 覆盖率是否达 100% | {✅ 通过 / ❌ 不通过} | {覆盖率数值} |
| 各阶段必须产物是否存在 | {✅ 通过 / ❌ 不通过} | {.status.md / functional-designs/ / detailed-design.md / tasks.md / traceability.md} |
| 条件产物是否正确处理 | {✅ 通过 / ❌ 不通过} | {🔶 / ⏭️ 图例处理} |
| 产物内容是否非空且无占位符 | {✅ 通过 / ❌ 不通过} | {含占位符的产物清单} |
| 自审报告是否存在（份数为 1 为正常形态） | {✅ 通过 / ❌ 不通过} | {self-reviews/{phase}/report.md} |
| 裁剪阶段不判缺项 | {✅ / ⏭️} | {合法裁剪的 api-tests/、e2e-tests/、test-reports/integration/ 缺失 SHALL NOT 判为缺项} |

### 3. (c) 耗时汇总

| 检查项 | 结论 | 判定依据 |
|--------|------|---------|
| 各阶段耗时与轮次数据齐全 | {✅ 通过 / ❌ 不通过} | {`.status.md`「阶段耗时与轮次统计」区行数 / 阶段总数} |
| 事件计时按阈值展开 | {✅ 通过 / ❌ 不通过 / ⏭️} | {命中阈值的阶段是否已展开「阶段内事件计时」} |
| 异常终止阶段有处理记录 | {✅ 通过 / ❌ 不通过 / ⏭️} | {终止结果为 `验证发现问题({N})` 或 `定向重验失败` 的阶段须核验存在对应的处理记录} |
| 缺陷发现-修复周期统计 | {✅ 通过 / ❌ 不通过} | {周期数据} |
| Post-mortem 建议归类 | {✅ 通过 / ❌ 不通过 / ⏭️} | {读取全部子变更 fix-report 的关联建议，按类型归类架构改进机会：测试 seam / 模块耦合 / 接口契约 / 其他；汇总到改进建议章节} |

> 本职责产出的汇总数据仅供信息展示与改进，SHALL NOT 参与门控判定；判定依据为问题清单的严重度分级。

### 4. (d) 阻塞兜底

| 检查项 | 结论 | 说明 |
|--------|------|------|

## 与其他 Skill 的关系

- **触发来源**：归档流程自动触发（集成测试通过后）、用户手动调用
- **执行者**：审计由单一子代理执行（全部档位同一路径），主 Agent 负责调度与验收，SHALL NOT 接管审计执行
- **回退路由**：按问题归属阶段回退到 `kflow-explore`、`kflow-design`、`kflow-code`、`kflow-api-test`、`kflow-e2e-test`
- **门控关系**：归档门控（`kflow-archive` 的前置条件）
- **输出给**：`kflow-archive`（审计通过后）
- **第 4 种回退来源**：与缺陷修复（`kflow-bug-fix`）、代码审查（`kflow-code-review`）、用户需求变更并列

## 核心提醒

- 审计是归档门控，未通过不能归档
- 审计由单一子代理执行：SHALL NOT 由主 Agent 直接执行，SHALL NOT 拆分为多个并行子代理；该约束适用于全部变更档位
- 审计 SHALL 以四项记账职责执行：`(a)` 门控校验 / `(b)` 覆盖率与产物存在性校验 / `(c)` 阶段耗时汇总 / `(d)` 阻塞级问题兜底。SHALL NOT 因变更档位而改变执行方式、职责集合或报告形态——不存在按档位分化的简化审计路径
- 记账员式审计 SHALL NOT 计算总分或任何维度得分，SHALL NOT 输出评分表，SHALL NOT 对阶段产物质量作独立评审——产物质量评审由签署清单自证、单轮验证与交叉审查承担
- 审计报告为记账记录形态：四项职责各自的检查结论、阶段耗时与效率摘要、按严重度分级的问题清单、改进建议
- 证据先于结论：先完成四项职责事实采集并逐项呈现判定依据，再输出检查项结论
- 审计子代理异常时 MUST 重新创建，主 Agent SHALL NOT 接管；最多重试 3 次，全部失败后标记 ⚠️ 阻塞并提示用户（审计为单次执行，不适用轮次级重试粒度）
- 阻塞级问题 SHALL 保留拦截权与归档门控地位，不因降级为记账员而丧失门控能力
- 合法裁剪不判缺项：`api-tests/`、`e2e-tests/`、`test-reports/integration/` 缺失且有阶段适用性声明依据时，SHALL NOT 判定为缺项；无声明依据的 `⏭️` 判为阻塞级问题
- 自审报告校验：`self-reviews/{phase}/report.md` 份数为 1 属正常形态，SHALL NOT 因仅 1 份而判缺项或「轮次超标」；SHALL NOT 因缺少超出该档位要求的视角报告而判缺项
- 阶段终止结果取值核验：`验证通过` / `验证发现问题({N})` / `执行完成` / `定向重验失败` / `停滞`；历史 `收敛` / `未收敛` 按读取侧归并规则处理；终止结果为 `验证发现问题({N})` 或 `定向重验失败` 的阶段须核验存在对应的处理记录（该摘要仅作信息展示，不参与门控判定）
- 阻塞级问题阻断归档，建议级不阻断
- 阻塞级：缺少必须产物、阶段门控未通过、阶段跳转、审查未闭环、裁剪无声明依据
- 建议级：文档格式不规范、耗时数据缺失、效率异常
- 审计回退按问题归属阶段确定回退范围和联动子变更
- Post-mortem 汇总需扫描所有子变更 fix-report 的关联建议，打捞架构级改进机会（计入职责 (c)）
- 支持指定变更或全部活跃变更审计
