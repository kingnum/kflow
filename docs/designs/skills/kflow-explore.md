> **状态双写**：阶段完成、回退与重执行时，主 Agent SHALL 向 `docs/changes/{change}/status-log.md` 追加事件记录，并刷新 `.status.md` 的当前状态字段；`.status.md` SHALL 保持在 100 行以内。常规阶段推进与门控判定 SHALL 仅读取 `.status.md`，`status-log.md` 仅在中断恢复与审计场景读取。权威定义见 `status-file-layering` 能力。

## 执行流程

```
设计探索阶段流程:

┌─────────────────────────────────────────────────────────────┐
│                    EXPLORE WORKFLOW                          │
├─────────────────────────────────────────────────────────────┤
│  1. INIT      → 创建变更目录和状态文件                       │
│  2. CONTEXT   → 探索项目上下文（文件、文档、提交记录）         │
│  3. TYPEDET   → 三级回落读取项目类型（继承优先）              │
│  │   ├── 1) CLAUDE.md「## 项目画像」表的项目类型行           │
│  │   ├── 2) docs/toolchain.md 头部的项目类型字段             │
│  │   ├── 3) 就地扫描检测（仅前两级均不可用）                  │
│  │   └── 标注来源 → 项目级记录继承 / 降级检测                 │
│  4. CONFIRM   → 静默一致性校验（默认不询问用户）              │
│  │   ├── 校验一致 → 静默继承并输出「项目类型: X（继承项目级记录）」│
│  │   ├── 校验冲突 → AskUserQuestion 复核（可更新项目级记录）  │
│  │   └── 校验失败 → 沿用记录值继续，不阻塞                    │
│  5. CLASSIFY  → 判断变更粒度（产品级/功能级/缺陷级）          │
│  6. CLARIFY   → 澄清需求，收集用户意图                        │
│  │   ├── 检测 CONTEXT.md 是否存在                              │
│  │   ├── 不存在 → 首次构建 CONTEXT.md                           │
│  │   │   └── 从用户需求描述中提炼初始领域术语                   │
│  │   │       └── 每个术语含: 定义、别名、边界                   │
│  │   ├── 已存在 → 增补检查                                     │
│  │   │   └── 检查是否有新术语需要添加                          │
│  │   │   └── 用户使用模糊/过载术语 → 提议精确术语并写入         │
│  │   │   └── 增补完成后更新修订记录                            │
│  │   ├── 术语提炼完成后继续需求澄清                            │
│  │   └── 收敛门: 未决问题清单为空或已降级（SPLIT 前置条件）     │
│  7. SPLIT     → 拆分功能点到原子级 + 标记类型（后端/前端）    │
│  │   子步骤:                                                    │
│  │   7a. 原子级拆分 — 按单一明确行为标准拆分                     │
│  │   7b. 类型判定 — 对每个 FP 按后端/前端标准判定               │
│  │   7c. 混合检测 — 无法归类(跨层)的 FP 强制继续拆分            │
│  │   7d. 关联标注 — 拆分产生的跨层 FP 对相互引用                │
│  8. TIER      → 变更档位初判 + 用户覆盖确认                    │
│  │   8a. 初判 — 按功能点数映射档位                             │
│  │       功能缺陷 FP<=3 → 轻量；FP>3 → 标准                   │
│  │       功能需求/产品需求 FP<=2 → 轻量；FP>2 → 标准          │
│  │       产品需求比照功能需求分档规则判定；无第三档取值       │
│  │   8b. 用户覆盖 — AskUserQuestion 展示初判档位与理由         │
│  │       用户可上调或下调；结果优先于初判结果                 │
│  │   8c. 写入变更级 .status.md 基本信息「变更档位」字段        │
│  │   8d. 提示 — 输出该档位对应的阶段集合                       │
│  9. RELATE    → 分析功能点关联关系                            │
│  10. OUTPUT   → 输出功能设计文档（含版本号+修订记录区+功能结构树）│
│  │   轻量档：产出压缩为单页（功能点清单+影响分析+修复/实现范围）│
│  11. SELFREV  → 单轮验证（签署自证 + 1 轮独立子代理验证）      │
│  │   1) 主 Agent 按 完整性/闭环性/必要性/清晰性 逐项签署自证    │
│  │      （零子代理，含证据锚点）                               │
│  │   2) 1 轮子代理验证：先独立遍历后打假，只报告不修改          │
│  │   3) 主 Agent 统一修复，生成「本阶段修复清单」随产物交付     │
│  │   报告路径: self-reviews/explore/report.md（固定一份）      │
│  │   终止结果: 验证通过 / 验证发现问题({N})                     │
│  12. PROTO_GATE → 原型设计决策门控（仅前后端项目）           │
│  │   ├── 轻量档 → 不主动询问，跳过本门控（用户显式要求时仍可执行）│
│  │   ├── 检查 .status.md 中是否存在 prototype_decision 标记   │
│  │   ├── 不存在 → AskUserQuestion: "检测到 {n} 个 UI 功能点，│
│  │   │   是否进入原型设计阶段？"                              │
│  │   │   ├── 确认创建原型 → prototype_decision=已选择原型设计 │
│  │   │   └── 跳过原型设计 → prototype_decision=已跳过         │
│  │   └── 已存在 → 跳过询问，直接进入下一阶段                  │
│  13. COMPLETE → 更新状态文件，标记阶段完成                    │
└─────────────────────────────────────────────────────────────┘
```

**注意**：设计探索阶段不再划分子变更。子变更划分后置到详细设计阶段完成后执行。

### COMPLETE 步骤（步骤 13）与阶段衔接决策

更新 `.status.md` 标记设计探索阶段为 `✅ 完成`、记录完成时间与执行备注、设置当前阶段为下一阶段后，本阶段 SHALL 执行**阶段衔接决策**，规则权威定义见 `skills/kflow-explore/references/phase-transition.md`（决策表与调度映射表的单一真源，本文件 SHALL NOT 内联）。

| 要点 | 说明 |
|------|------|
| 门控先于衔接 | 步骤 12 的原型设计决策门控 SHALL 先于衔接决策完成；门控未通过时按该步骤既有规则处理，不进入衔接决策 |
| 目标阶段确定 | 按 `.status.md` 中的 `prototype_decision` 标记确定阶段顺序：`已选择原型设计` → 调度 `kflow-prototype-design`；`已跳过` → 调度 `kflow-design` |
| 调度方式 | 按决策表判定目标阶段状态后直接调度目标阶段 Skill（`Skill(skill="{target-skill}", args="{change-name}")`） |
| 免除范围 | 自动衔接免除的**仅为**「提示用户输入推进指令」一步——系统 SHALL NOT 将「提示用户输入推进指令（如「继续 {change-name}」）」作为进入下一阶段的必要条件；本阶段自有的人工门控照常执行 |
| 停止衔接 | 衔接决策停止（目标阶段 `❌ 阻塞` 等）时 SHALL 向用户说明停止原因与可执行的下一步操作 |

## 两动作规则

探索阶段 SHALL 遵循「两动作规则」行为准则，防止信息收集操作的结果在上下文轮转后不可恢复。

### 行为准则

每执行 **2 次**信息收集操作后，SHALL 将收集到的关键发现写入当前阶段的产出文件（`functional-designs/`）。

### 适用范围（计数触发）

以下操作计入两动作计数：

| 操作类型 | 说明 |
|---------|------|
| WebFetch | 获取外部网页内容 |
| WebSearch | 搜索外部信息 |
| Read（外部资源） | 读取项目外的文档、配置文件等 |
| Read（图片） | 查看图片/截图内容 |
| Read（PDF） | 阅读 PDF 文件内容 |

### 不适用范围（不计数）

以下操作不计入两动作计数：

| 操作类型 | 说明 | 原因 |
|---------|------|------|
| Read（项目内源代码） | 读取项目内的源代码文件 | 代码内容可通过文件系统随时重新获取 |
| Glob | 搜索项目文件 | 文件系统操作，非信息收集 |
| Grep | 搜索项目内容 | 文件系统操作，非信息收集 |
| Bash | 查看项目状态 | 本地操作，非外部信息收集 |

### 保存内容规范

写入产出文件的内容 SHALL 包含：

| 字段 | 说明 |
|------|------|
| 信息来源 | 操作类型 + URL/路径（便于追溯） |
| 关键要点 | 从信息收集结果中提炼的核心发现 |
| 影响分析 | 该发现对功能设计的影响或建议 |

### 执行时机

| 场景 | 行为 |
|------|------|
| 正常探索 | 每 2 次信息收集操作后立即保存 |
| 连续信息收集 | 每批相关信息收集完成后保存（不严格按计数） |
| 阶段结束前 | 强制检查并保存所有未写入的发现 |
| 会话中断前 | 立即保存所有中间发现 |

> **原则**："2 次"为启发式指导值，核心原则是"频繁保存中间发现"，防止非文本操作结果在上下文轮转后丢失。

## 项目类型继承规则（TYPEDET + CONFIRM）

> **版本**: 当前变更改写。项目类型是仓库级不变量，其确认动作已在 `kflow-init` 一次完成；本阶段改为**继承**——不再重新扫描判定，也不再默认询问用户。规则权威定义见 [core-mechanisms/01-project-types.md](../core-mechanisms/01-project-types.md#14-项目类型记录与继承)。

### 三级回落读取（TYPEDET）

按优先级读取项目级项目类型记录，命中即止：

| 优先级 | 读取源 | 判定 |
|--------|--------|------|
| 1 | CLAUDE.md「## 项目画像」表的「项目类型」行 | CLAUDE.md 存在、含「## 项目画像」marker、且该行有值 → 读取该值，SHALL NOT 再读 `docs/toolchain.md` |
| 2 | `docs/toolchain.md` 头部的「项目类型」字段 | 优先级 1 不可用（CLAUDE.md 不存在 / 无 marker / 该行缺失）时读取 |
| 3 | 就地扫描检测 | 仅前两级均不可用（项目从未 init）时执行 |

第 3 级的扫描检测标识：

| 检测标识 | 存在时判断 |
|---------|-----------|
| package.json 前端框架依赖（react, vue, angular, next, nuxt, svelte 等） | 前后端项目 |
| 前端源文件（.vue, .tsx, .jsx, .svelte, .angular 等） | 前后端项目 |
| 前端构建配置（vite.config.*, webpack.config.*, tsconfig.json 等） | 前后端项目 |
| 以上均不存在 | 纯后端项目 |

**来源标注**：TYPEDET 结束后 SHALL 记录本次取值的来源，取值 `项目级记录继承`（第 1、2 级）或 `降级检测`（第 3 级），供 CONFIRM 与产物写入使用。

### 静默一致性校验（CONFIRM）

本步骤**默认路径 SHALL NOT 使用 AskUserQuestion**。校验内容：扫描项目根目录的前端工程标识，与项目级记录读取值比对。

| 校验结果 | 处理 |
|---------|------|
| 一致 | 静默继承记录值并输出「项目类型: {值}（继承项目级记录）」，SHALL NOT 询问用户 |
| 冲突（如纯后端记录的项目新增了前端工程标识） | AskUserQuestion 展示冲突项（扫描结果 vs 记录值），用户可沿用记录值或修正为扫描值；选择修正时更新项目级记录 |
| 校验失败（项目根目录不可读等） | 沿用记录值继续，**校验失败不阻塞**变更创建 |

> 校验是安全阀而非门禁：冲突只触发复核请求，SHALL NOT 自动改写记录。

### 记录缺失时的降级路径（未 init 项目）

前两级记录均不可用时，本阶段 SHALL 检测并确认**一次**，补写 `docs/toolchain.md` 头部：

- AskUserQuestion 展示检测结果，用户可确认或手动修正
- 结果写入 `docs/toolchain.md` 头部的项目类型字段（文件不存在时创建仅含头部与该字段的最小文件）
- SHALL NOT 写入 CLAUDE.md「## 项目画像」区块——该区块由 `kflow-init` 整体扫描填充，单项补写会产生残缺区块并与受管 marker 的替换逻辑冲突
- 此后该项目的所有变更均静默继承，不再询问

### 用户显式覆盖

用户在需求描述中显式声明的项目类型（或指出记录有误）优先于项目级记录与扫描结果：采用声明值、更新项目级记录、本次变更的变更级快照写入声明值。这是初始误判（扫描信号与错误记录一致，一致性校验比对不出冲突）的唯一纠正通道。

### 变更级快照

读取或降级检测的结果 SHALL 写入变更级快照（`functional-designs/index.md` 与变更级 `.status.md` 的项目类型字段）并标注来源。变更进入执行阶段后快照值冻结，SHALL NOT 随项目级记录变化而变更。

### 项目类型影响

| 项目类型 | 后续阶段影响 |
|---------|-------------|
| 前后端项目 | 原型设计阶段可选，E2E测试阶段必须，集成测试必须 |
| 纯后端项目 | 跳过原型设计阶段，跳过E2E测试阶段，集成测试必须 |

## 功能点拆分规则

### 原子级功能点定义

| 粒度 | 判断标准 | 示例 |
|------|---------|------|
| 过粗 | 包含多个独立行为 | "用户管理功能" ❌ |
| 合适 | 单一明确行为 | "用户注册"、"用户登录" ✅ |
| 过细 | 实现细节级别 | "添加注册按钮" ❌ |
| 无法归类（跨层） | 包含跨层行为，同时涉及后端和前端判定标准 | "实现注册功能（含 API + 页面）" ❌ — MUST 拆分为独立后端 FP 和前端 FP |

### FP 类型判定规则

> **版本**: 当前变更新增

每个功能点在拆分 SHALL 标记为「后端」或「前端」，类型作为后续子变更划分类型校验、任务模板选择、输入源检查的依据。

#### 后端 FP 判定标准

功能点涉及以下任一内容时，SHALL 标记为「后端」：

| 判定标准 | 说明 |
|---------|------|
| API 实现 | REST 接口 / GraphQL / gRPC |
| 服务逻辑 | 业务规则处理 / 工作流编排 |
| 数据模型定义 | ORM 实体 / 数据库表结构 |
| 数据库操作 | CRUD / 查询 / 事务 |
| 业务规则引擎 | 规则校验 / 计算逻辑 |
| 外部服务集成 | 第三方 API 调用 / 消息队列 |

#### 前端 FP 判定标准

功能点涉及以下任一内容时，SHALL 标记为「前端」：

| 判定标准 | 说明 |
|---------|------|
| 页面组件 | 页面布局 / 模板结构 |
| UI 组件 | 按钮 / 表单 / 表格 / 弹窗等可复用组件 |
| 路由配置 | 页面路径 / 导航守卫 |
| 状态管理 | store / context / reactive state |
| 样式实现 | CSS / SCSS / CSS-in-JS / Tailwind |
| CSS 变量注入 | design-tokens 应用 |

#### 无法归类则强制拆分

| 场景 | 处理方式 |
|------|---------|
| 一个 FP 同时涉及后端和前端判定标准 | 判定为粒度过粗，MUST 继续拆分 |
| 拆分结果 | 一个后端 FP + 一个前端 FP |
| 拆分后关联标注 | 两个新 FP SHALL 在「关联功能点」列相互引用，前端 FP SHALL 描述中标注「关联后端 FP: {FP-ID}」 |
| 禁止做法 | SHALL NOT 以混合形式写入 functional-designs/ |

**示例**：
- 「实现注册 API」→ 后端
- 「实现注册表单页面」→ 前端
- 「实现用户注册功能」→ ❌ 过粗，MUST 拆分为上述两个独立 FP
- 拆分后 FP-001(后端)「注册 API」+ FP-002(前端)「注册页面」→ 在「关联功能点」列相互引用 #FP-002 / #FP-001

### 功能点数量与子变更划分

> **重要变更**：子变更划分不再在设计探索阶段执行，而是在详细设计阶段完成后基于完整设计认知划分。

| 条件 | 处理方式 |
|------|---------|
| 功能点 ≤ 10 | 详细设计阶段确认后，创建 1 或 2 个子变更（FP 类型混合时为后端子变更 + 前端子变更） |
| 功能点 > 10 且 ≤ 20 | 详细设计阶段完成后拆分为多个子变更 |
| 功能点总数 > 20 | 提示拆分为多个变更 |

### 功能点关联关系类型

| 关系类型 | 定义 | 标注格式 |
|----------|------|---------|
| 前置依赖 | A 必须在 B 前完成 | `A -> B` |
| 后置依赖 | B 完成后才可执行 A | `B <- A` |
| 并行关系 | A 和 B 可同时实现 | `A \|\| B` |
| 包含关系 | A 是 B 的子功能 | `B ⊃ A` |

## 需求澄清收敛门（CLARIFY 步骤）

> **版本**: 新增变更 `explore-clarify-convergence`（能力 `requirement-clarification`）

### 概述

CLARIFY SHALL 维护「未决问题清单」，并在进入 SPLIT 之前要求该清单为**空**。这是需求探索出口条件的**可判定化**：出口不再是「看起来问完了」，而是「清单归零或每项已显式降级」。

清单项的状态只有三种：

| 状态 | 含义 | 是否阻塞进入 SPLIT |
|------|------|------------------|
| 未处理 | 既未消解也未降级 | ✅ 阻塞 |
| 已消解 | 已通过消歧路径收敛为单一确定答案 | ❌ 不阻塞 |
| 已降级 | 本阶段无法消解，显式标记 `待补充` 并记录降级理由与责任阶段 | ❌ 不阻塞 |

清单与降级项 SHALL 写入变更级 `.status.md`（作为 CLARIFY 的工作记录），**不新增**独立产物文件、**不新增**步骤编号。

### 候选清单生成规则

候选 SHALL 由**五个内容域逐域遍历**产生（页面结构/菜单、可执行操作、表单项、业务规则、业务流程），SHALL NOT 以直接置空代替逐域遍历。清单为空时 SHALL 说明五域均已遍历且未发现歧义——该说明是空清单的合法凭据。

### 消歧路径限定

消解一项歧义 SHALL 通过以下三条路径之一完成：(a) 向用户澄清提问；(b) 精确化 `CONTEXT.md` 中的术语定义；(c) 通过代码库或事实查库直接解析。系统 SHALL NOT 以**扩增功能设计内容**（新增功能点、字段、章节或分支）的方式消除歧义。

> **明确度与复杂度正交**：收敛门只管「歧义量是否归零」，不构成抬高「功能设计内容量」的许可。歧义「能否中途取消」须通过提问收敛为「可以/不可以」一个确定答案，而不是新增取消流程章节加字段把多种可能全覆盖。

### 需求内容非必要不增加

需求探索 SHALL NOT 为假想分支、将来需求或未确认的边界情况预留功能点、字段或章节。歧义 SHALL 收敛为一个确定答案，SHALL NOT 铺开为多个可能。

> **与「结构性章节不得省略」的边界**：本规则约束的是「不得**为消歧而新增**内容」，不影响结构性章节在无内容时按既有规则标注「无」。

### 提问纪律

系统 SHALL 区分**事实项**与**决策项**：事实项通过查库或代码探索自动解析，SHALL NOT 占用用户注意力；决策项 SHALL 提交用户，且**一次只提交一项**。提问顺序遵循**依赖序遍历**（先定前提需求，再问依赖它的细节），此为 CLARIFY 内部的顺序纪律，**不重排** CLARIFY → SPLIT → TIER → RELATE 的步骤骨架。

### 不分档

收敛门 SHALL NOT 按变更档位分级。门槛强度由真实歧义量自调节：歧义多则清单长；无歧义的简单需求清单为空、近乎零额外成本。按档位再造多套澄清深度属于非必要的设计。

## 领域词汇表管理 (CONTEXT.md)

### 概述

`CONTEXT.md` 是项目级领域词汇表，作为所有后续阶段术语引用的唯一真实来源。kflow-explore 在 CLARIFY 步骤中负责其首次构建和持续增补。

**格式权威**：`CONTEXT.md` 的格式 SHALL 以 `skills/kflow-explore/references/context-template.md`（开发布局）或 `.claude/skills/kflow-explore/references/context-template.md`（消费布局）为**唯一权威来源**，该文件随 KFlow Skill 一同安装并自包含。系统 SHALL NOT 将 `CONTEXT.md` 的格式定义委托给任何外部技能的格式文件。文件结构三要素为：项目名标题、领域术语列表（每项含定义/别名/边界）、修订记录。

### 文件格式

```markdown
# CONTEXT — {项目名} 领域词汇表

> **版本**: 1.0.0
> **创建时间**: {YYYY-MM-DD}
> **修订记录**:
> | 版本 | 日期 | 修订内容 | 触发阶段 |
> |------|------|---------|---------|
> | 1.0.0 | {YYYY-MM-DD} | 初始构建 | 设计探索 |

---

## {领域术语1}

- **定义**: 该概念在项目中的精确定义
- **别名**: （可选，代码中出现的变体名称或简称）
- **边界**: 明确什么不是这个概念（显式排除）

## {领域术语2}
...
```

### 术语提炼规则

| 规则 | 说明 |
|------|------|
| 定义精确性 | 定义 SHALL 使用领域专家能理解的描述，不耦合实现细节 |
| 别名必查 | 如果代码中已有变体名，SHALL 记录为别名以便对齐 |
| 边界明确 | 每个术语 SHALL 明确排除相近但不同的概念 |
| 过载术语处理 | 用户使用模糊/过载术语时，SHALL 提议精确术语并写入 |
| 禁止实现耦合 | 禁止将术语与代码实现细节绑定（如类名、表名） |

### 首次构建流程

```
1. 检查 CONTEXT.md 是否存在
2. 不存在时:
   ├── 从用户需求描述中提取关键领域概念
   ├── 为每个概念编写: 定义、别名、边界
   ├── 按字母顺序排列术语
   └── 写入 CONTEXT.md（含版本号和修订记录）
3. 完成构建后继续需求澄清
```

### 增补流程

```
1. CONTEXT.md 已存在时
2. 在需求澄清过程中:
   ├── 检查新出现的术语是否已在词汇表中
   ├── 新术语 → 按首次构建规则添加到 CONTEXT.md
   ├── 模糊术语 → 与用户确认精确含义后写入
   └── 更新版本号（次版本 +1）和修订记录
```

### 消费链

CONTEXT.md 构建后贯穿整个变更流程：

```
explore 构建 → design 引用审查 → plan 用于任务描述 → code 用于命名 → review 用于审查报告
```

### 对齐检查

增补完成后 SHALL 执行对齐检查：
- 检查功能点描述中使用的术语是否与 CONTEXT.md 定义一致
- 功能设计文档中的实体名称 SHALL 使用 CONTEXT.md 中的术语
- 发现不一致时：更新功能设计文档或更新 CONTEXT.md 定义

## 变更档位初判（TIER 步骤）

> **版本**: 新增变更 `add-change-tier`

### 概述

SPLIT 步骤完成后，本阶段 SHALL 执行变更档位初判，并将结果写入变更级 `.status.md` 的「变更档位」字段。档位是贯穿全流程的单一分级依据，驱动后续阶段的**审查形态与产出深度**（SHALL NOT 决定审查轮数——设计类自审固定单轮验证、测试三阶段单轮执行，轮数恒为 1）。

初判仅使用本阶段可得的信息（变更类型与功能点数）——接口契约变更数与数据模型变更数属于本阶段域外内容（见「阶段边界约束」），SHALL NOT 为凑齐复核公式而在 explore 阶段定义接口或数据模型。完整复核由 `kflow-design` 在 DIVIDE 之后按设计面口径执行（新增/修改的接口契约数与 schema/migration 数；受影响但未改契约的接口不计入）。初判映射表与本节说明 SHALL NOT 引入接口或数据模型的计量定义。

### 初判映射规则

| 变更类型 | 功能点数 | 初判档位 |
|---------|---------|---------|
| 功能缺陷 | FP ≤ 3 | 轻量 |
| 功能缺陷 | FP > 3 | 标准 |
| 功能需求 | FP ≤ 2 | 轻量 |
| 功能需求 | FP > 2 | 标准 |
| 产品需求 | 按功能点数比照功能需求规则 | 与功能需求同规则分档 |

> 枚举为 `{轻量, 标准}` 二值，SHALL NOT 存在按功能点数上探的第三档取值。

> **产品需求不分档特判**：`产品需求` SHALL NOT 无条件判定为 `标准` 之外的档位，而是按功能点数比照 `功能需求` 的分档规则判定——一个功能点数较小的产品需求小迭代得以按 `轻量` 档执行，避免审查强度被业务视角的变更类型绑架。
>
> 阈值保守取值：功能需求/产品需求需 FP ≤ 2 才判轻量，避免初判偏低导致 design 阶段频繁升档。
>
> 初判结果由 `kflow-design` 在 DIVIDE 之后使用设计面分数公式校正；升档分硬升档（不可拒绝）与软升档（默认保持轻量，仅在新增下游测试阶段时提示）。

### 用户覆盖规则

初判完成后 SHALL 通过 AskUserQuestion 向用户展示初判档位及其判定依据，用户可上调或下调。用户覆盖结果 SHALL 写入 `.status.md` 并优先于初判结果用于后续阶段。

### 按档位的阶段集合提示

初判档位确定后（含用户覆盖），本阶段 SHALL 向用户输出该档位对应的阶段集合提示。提示为**信息性输出**，SHALL NOT 作为新的用户确认点或阻塞点。

| 档位 | 阶段集合提示内容 |
|------|----------------|
| 轻量 | 计划 → 编码 → 代码审查 为**恒执行**；接口单元测试、E2E测试、集成测试为**条件适用**，将在详细设计后由「阶段适用性声明」判定；审计由单一子代理按统一形态执行 |
| 标准 | 全阶段执行，无裁剪 |

**触发时机**：在 8c 写入 `.status.md`「变更档位」字段后输出。用户在 8b 覆盖档位时，提示 SHALL 按覆盖后的档位重新输出，SHALL NOT 保留初判档位的提示内容。

**文案要求**：

| 要求 | 说明 |
|------|------|
| 区分恒执行与条件适用 | SHALL 显式区分「恒执行阶段」与「条件适用阶段」，SHALL NOT 将条件适用阶段表述为已跳过 |
| 明确判定责任 | SHALL 说明条件适用阶段的判定责任在 `kflow-design`（DIVIDE 之后生成「阶段适用性声明」），本阶段 SHALL NOT 给出适用性结论 |
| 明确档位边界 | SHALL 说明 `标准` 档全阶段执行、无裁剪，避免误读为档位会改变阶段集合 |
| 说明后续表示 | SHALL 说明不适用阶段在 `traceability.md` 中整列标记 `⏭️` 且不计入覆盖率分母 |

### 轻量档不改动探索流程

轻量档 SHALL NOT 改变本阶段的执行流程：

| 约束 | 说明 |
|------|------|
| 不新增或跳过步骤 | 阶段集合提示是唯一新增输出，步骤序列与执行顺序不变，其余行为与标准档一致 |
| 不改变产出物 | 产出物路径与结构不变，轻量档仅压缩 OUTPUT 的产出内容（单页） |
| 不在 FP 上预判适用性 | SHALL NOT 为判定「是否涉及接口」而在 explore 阶段预判或补充接口信息；适用性判定依据详细设计的客观信号，属 `kflow-design` 职责 |

### 档位影响

| 档位 | explore 自身影响 |
|------|----------------|
| 轻量 | 产出压缩为单页（功能点清单 + 影响分析 + 修复/实现范围），仍写入既有产物路径；PROTO_GATE 不主动询问 |
| 标准 | 标准产出 |

> SELFREV 恒为**单轮验证**，档位 SHALL NOT 决定自审轮数——上表仅描述产出深度与形态差异。
>
> 档位判定公式、阈值与单向升档安全阀的完整规范参见 `docs/designs/core-mechanisms/03-status-and-tasks.md` §3.1.1。

## 渐进式流程调整

根据变更粒度自动调整流程深度：

| 粒度 | 流程深度 | 产出要求 |
|------|---------|---------|
| **产品级** | 完整流程 | 需求描述 + 项目类型 + 功能点清单 + 技术方案建议 |

4. 禁止越界输出技术方案或接口定义

## 自审（SELFREV 单轮验证）

> **版本**: 1.8.0 新增；当前变更为单轮验证模型

### 概述

设计探索阶段在 OUTPUT 步骤之后、COMPLETE 步骤之前执行自审（SELFREV）。自审固定为**单轮**：SHALL NOT 预置轮数上限，SHALL NOT 执行第二轮，SHALL NOT 存在 0 轮豁免路径。变更档位只决定**审查形态与产出深度**，SHALL NOT 决定轮数。自审启动前 SHALL 读取变更级 `.status.md` 的「变更档位」字段（缺失或读取到历史遗留的 `完整` 取值时按 `标准` 档处理，仅决定报告输出深度）。

单轮由三个环节构成：

1. **主 Agent 签署自证（零子代理）**——主 Agent 在写作时按本阶段 4 个固定维度（完整性 / 闭环性 / 必要性 / 清晰性）逐项填写「维度 / 自证结论 / 证据锚点」。证据锚点 SHALL 指向产物内的具体位置（章节号、功能点 ID、接口 ID、用例 ID 或表名之一）；锚点为空、或指向产物中不存在的内容时，该维度签署 SHALL 判定为不成立。自证中发现某维度不通过时 SHALL 先行修复该产物并重新完成该维度自证。
2. **单轮独立子代理验证**——主 Agent 启动一个验证子代理（独立上下文）。执行契约强制为：**先独立遍历产物形成自身结论（此阶段 SHALL NOT 读取签署清单，防锚定）→ 再逐项对照签署清单打假 → 输出验证报告**。执行顺序反转时该轮结果 SHALL NOT 被接受。子代理 SHALL NOT 修改任何产物（只报告）。
3. **主 Agent 统一修复**——主 Agent 按验证结论统一修复全部发现项，生成「本阶段修复清单」随产物交付下游。SHALL NOT 追加确认轮；修复结果由下游的交叉审查或下游阶段验证。

**终止结果**：单轮验证零发现且无签署不成立项时写入 `验证通过`；存在发现项或签署不成立项时写入 `验证发现问题({N})`，N 为该阶段发现总数。终止结果 SHALL 写入变更级 `.status.md`。历史遗留的 `收敛` 取值读取侧归并为 `验证通过`，其余归并为 `验证发现问题`。

**审查范围冻结与范围外观察**：主 Agent 从阶段产物既有内容生成审查对象集合并冻结，审查维度集合封闭；子代理 SHALL NOT 扩大审查对象集合、SHALL NOT 新增审查维度、SHALL NOT 借审查之名新增功能点/字段/章节/分支。冻结范围之外的发现 SHALL 记为「范围外观察」——不改产物、不计入发现数，写入验证报告的「范围外观察」小节（为空时记「（空）」），由主 Agent 在阶段终止时汇总并向用户提示。子代理引入冻结范围之外的新内容时，主 Agent SHALL 拒收该轮并要求其在冻结范围内重新验证。

**评分语义**：验证报告 SHALL NOT 输出各维度 0–10 评分与不达标项清单——该评分要求原为第三档专属的报告输出深度，且不参与终止判定（单轮验证无论评分高低均在单轮结束时终止，发现项由主 Agent 统一修复），已随该取值一并废除。

**子代理异常**：验证子代理意外停止、报错退出或返回不完整结果时，主代理 MUST 分析原因后重新创建新的子代理，SHALL NOT 在主 Agent 上下文中接管其未完成的工作；最多重试 3 次，全部失败后标记 ⚠️ 阻塞并提示用户。

**产物完整性门控（附加硬门）**：功能设计产物 SHALL 全部存在且不含 TODO、TBD 或未填充占位符；任一产物缺失或含占位符时该阶段阻塞。审计 SHALL NOT 因自审报告仅 1 份而判定为缺项。

> 机制权威定义见 `07-agent-model.md` §16 与 `signed-checklist-verification` 能力，落地表述见 `skills/kflow-explore/references/self-review.md`。

### 审查维度与检查规则

#### 完整性

| 检查项 | 规则 |
|--------|------|
| 页面覆盖 | 是否所有用户可见页面均已覆盖 |
| 菜单覆盖 | 是否所有菜单路径均有对应功能点 |
| 操作覆盖 | 是否所有用户可执行操作均有对应功能点 |
| 表单项覆盖 | 是否所有涉及表单输入的功能点均有完整表单项定义 |

#### 闭环性

| 检查项 | 规则 |
|--------|------|
| 流程完整性 | 每个业务流程是否从触发点到最终结果形成完整路径 |
| 断点检测 | 检查是否存在"无处可去"的中间状态 |
| 异常路径 | 业务流程中的分支条件和异常路径是否已标注 |

#### 必要性

| 检查项 | 规则 |
|--------|------|
| 多余功能点 | 检查是否存在无明确用户价值的功能点 |
| 冗余功能点 | 检查是否存在功能重叠的功能点 |
| 价值验证 | 每个功能点是否有明确的用户价值描述 |

#### 清晰性

| 检查项 | 规则 |
|--------|------|
| 描述无歧义 | 每个功能点描述是否无歧义 |
| 边界明确 | 每个功能点的输入/输出边界是否清晰定义 |
| 术语一致 | 功能点描述中使用的术语是否与 CONTEXT.md 定义一致 |

### 自审模式：单轮验证

> **当前变更**: 由多轮重复制改为**单轮验证**——主 Agent 写作时按四个维度（完整性/闭环性/必要性/清晰性）逐项签署自证，随后 1 轮独立子代理验证打假，主 Agent 统一修复，不追加确认轮。

### 自审流程

```
自审执行流程（单轮验证）:

1. 读取变更级 .status.md 的「变更档位」字段（缺失或历史取值 完整 按 标准 档处理，仅决定报告输出深度）
2. 主 Agent 按 完整性、闭环性、必要性、清晰性 四个维度逐项签署自证（零子代理）
   ├── 逐维度填写「自证结论」与「证据锚点」
   └── 自证发现某维度不通过 → 先行修复并重新自证该维度
3. 记录开始时间（作为时间戳）
4. 启动 1 个验证子代理：
   ├── 先独立遍历产物形成自身 4 维度结论（此阶段 SHALL NOT 读签署清单）
   ├── 再逐项对照签署清单打假（锚点为空 / 指向不存在内容 = 签署不成立）
   ├── 只报告，SHALL NOT 修改产物
   └── 输出验证报告
5. 主 Agent 按验证结论统一修复全部发现项，生成「本阶段修复清单」
6. 在 .status.md 写入终止结果（验证通过 / 验证发现问题({N})），标记阶段完成
   └── SHALL NOT 追加确认轮
```

### 自审记录存储

- 报告路径固定为 `self-reviews/explore/report.md`（不按轮次编号）
- 报告份数恒为 1，SHALL NOT 产出多份时间戳文件；缺失判缺项（无 0 轮豁免路径）
- 报告模板参考：`docs/designs/templates/changes/{change}/self-reviews/review-round.md`

### 自审报告内容

- 签署自证表（维度 / 自证结论 / 证据锚点）
- 独立遍历发现清单（序号、问题描述、严重度、状态）
- 签署打假结果（逐项：属实 / 不成立）
- 范围外观察小节（无条目时记「（空）」）
- 全量遍历证明（显式声明全部 4 个维度与全部审查对象均已完成遍历，反空转）
- 验证结论（终止结果 `验证通过` / `验证发现问题({N})`）
- 本阶段修复清单（主 Agent 统一修复后填写）

### 强制执行规则

- 全部档位 SHALL 执行单轮验证，SHALL NOT 跳过 SELFREV、SHALL NOT 存在 0 轮豁免路径
- SHALL NOT 执行第二轮；SHALL NOT 在验证后追加确认轮
- 审查对象集合 SHALL 由主 Agent 从阶段产物既有内容生成并冻结，审查维度集合封闭；子代理 SHALL NOT 扩大审查对象集合、SHALL NOT 新增审查维度
- 冻结范围之外的发现 SHALL 记为「范围外观察」，SHALL NOT 在本轮修复、SHALL NOT 计入发现数
- 自审终止后 SHALL 在 `.status.md` 写入终止结果字段（`验证通过` / `验证发现问题({N})`），标记阶段完成，释放 prototype 或 design 阶段门控

## REVISION 模式

> **版本**: 当前变更新增

### 触发条件

当 kflow-guide 的 DESIGN_REVISION 路由检测到用户意图为功能设计修订（含"功能"/"需求"关键词）时，唤醒 kflow-explore 进入 REVISION 模式。

### REVISION 模式流程

```
REVISION 模式流程:

1. 加载 functional-designs/index.md 和 functional-designs/part-NN.md 现有内容
2. 加载 .status.md 获取当前阶段状态
3. AskUserQuestion 确认修订需求:
   - "功能设计修订模式。请描述需要调整的内容。"
4. 根据用户反馈修订 functional-designs/ 中的对应功能点
5. 更新 functional-designs/index.md 修订记录:
   ├── 版本号递增（semver）
   └── 追加修订记录行: 版本 | 日期 | 修订类型 | 修订内容 | 影响功能点 | 触发阶段
6. 返回 kflow-guide 进入设计修订后处理流程
```

### REVISION 模式约束

- REVISION 模式下不重新执行完整的 explore 流程（跳过 INIT/CONTEXT/TYPEDET/CLASSIFY）
- 仅修订用户指定的功能点，不重写整个 functional-designs/
- 修订完成后 SHALL 更新 index.md 的修订记录表
- 如修订涉及功能点新增/删除，同步更新功能结构树和分册
