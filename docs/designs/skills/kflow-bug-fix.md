## 门控检查

> **机制说明**：门控规则定义在 [core-mechanisms/03-status-and-tasks.md](../core-mechanisms/03-status-and-tasks.md#34-门控规则)

**入口模式判定**：

| 条件 | 模式 | 入口门控 |
|------|------|---------|
| 存在测试失败轮次报告，且当前阶段为接口单元测试或 E2E 测试 | 既有模式（子变更级） | 该测试轮次报告存在 |
| 存在测试失败轮次报告，且当前阶段为集成测试 | 既有模式（变更级） | 该集成测试失败轮次报告存在 |
| **无**触发测试阶段上下文，且调用来源为 `kflow-bug-triage` 的 L4 路由 | **快车道模式** | 缺陷级状态文件 `bugs/fix/{BUG-ID}/bugfix-status.md` 存在且「受影响项清单」区已填写 |
| 无触发测试阶段上下文，且调用来源**不是** L4 路由 | ❌ 阻塞 | 使用 AskUserQuestion 询问用户确认调用上下文；SHALL NOT 在未确认来源的情况下进入快车道模式 |

> **注意**：用户反馈统一由 `kflow-bug-triage` 处理（A路径），既有模式的入口仅限测试阶段自动发现（B路径）；快车道模式的入口仅由 `kflow-bug-triage` 的 L4 结论独占，SHALL NOT 提供其他入口。

缺陷修复完成后：
- 本地验证通过
- 输出缺陷修复报告（含根因分类）
- 既有模式：实现错误/测试错误 → 返回测试阶段
- 快车道模式：→ 进入定向验证，通过后完成快速收口

自动跳过规则：
- 测试阶段一轮通过 → 自动跳过缺陷修复阶段（快车道模式不适用本规则）

> **注意**：既有模式下本 Skill 处理子变更级缺陷修复。集成测试失败时使用 `kflow-integration-test` Skill 内置的四分法修复循环。快车道模式见「快车道模式」章节。

## 执行流程

**第一步：模式判定**

| 判定结果 | 后续流程 |
|---------|---------|
| 存在触发测试阶段上下文（接口单元测试 / E2E 测试 / 集成测试失败报告） | **既有模式** → 下方「子变更级缺陷修复流程」，轮次与门控不变，出口为返回测试阶段 |
| 无测试阶段上下文，且调用来源为 `kflow-bug-triage` 的 L4 路由 | **快车道模式** → 下方「快车道修复流程」，状态写入 `bugfix-status.md`，出口为进入定向验证 |
| 无测试阶段上下文，且调用来源不是 L4 路由 | ❌ 阻塞：使用 AskUserQuestion 确认调用上下文，SHALL NOT 直接进入快车道模式 |

## 根因分类（二分法）

### 分类标准

| 根因类型 | 判断依据 | 占比估计 | 处理路由 |
|---------|---------|---------|---------|
| 实现错误 | 代码实现与设计文档一致但逻辑有误、未处理边界条件、编码错误 | ~80% | 修复代码 |
| 测试错误 | 测试用例预期值与设计不符、测试数据准备错误、测试环境配置问题 | ~20% | 修正测试 |

> **变更说明**：原三分法中的"设计错误"分类已上移到 `kflow-bug-triage`。当三次尝试后升级用户且用户选择设计回退时，引导用户通过 kflow-bug-triage 进行正式诊断。

### 决策流程

```
根因分析 Agent 完成分析后:

1. 对比测试失败信息与 detailed-design.md 中的设计定义
2. 检查代码实现是否与设计一致:
   ├── 一致但仍有 Bug → 实现错误（默认分类）
   ├── 不一致 → 检查不一致的原因:
   │   └── 实现疏忽 → 实现错误
   └── 测试断言值与设计预期不符 → 测试错误
```

## 修复尝试上限

为防止子变更级缺陷修复无限自动循环，SHALL 遵循以下尝试上限规则：

### 递进策略

同一测试用例的三次尝试遵循递进策略：

| 尝试次数 | 策略 | 说明 |
|----------|------|------|
| 第 1 次 | 直接修复 | 按二分法根因分类采用针对性方案，快速定位并修复 |
| 第 2 次 | 替代方案 | 采用不同工具或方法，不得重复第 1 次尝试的相同方案 |
| 第 3 次 | 重新思考 | 重新审视问题假设，考虑更广泛的替代方案，不得重复前两次方案 |
| 超出上限 | 升级用户 | 使用 AskUserQuestion 升级用户，提供三个选项：保留当前状态（人工介入）/ 跳过该功能点（标记为已知问题）/ 通过 kflow-bug-triage 进行诊断 |

### 计数规则

| 规则 | 说明 |
|------|------|
| 独立计数 | 不同测试用例的尝试次数独立计算，一个用例达到上限不影响其他用例 |
| 根因变更重置 | 修复过程中根因分类发生变更时（如从实现错误变更为设计错误），重置尝试计数 |
| 跨轮次累加 | 同一测试用例在不同轮次中的尝试次数累加计算 |
| 上限兜底 | 无论根因类型，同一用例累计 3 次失败后 SHALL 升级用户 |

### 修复报告记录

每次修复尝试 SHALL 在缺陷修复报告中记录：
- 当前尝试次数（第 N/3 次）
- 采用的修复策略（直接修复 / 替代方案 / 重新思考）
- 与之前尝试的方案差异说明（第 2 次起必填）
- 失败原因分析（如适用）

## Feedback Loop 构建 (DISCOVER 1a)

### 概述

缺陷修复的第一步是构建一个快速、确定性、Agent 可运行的 pass/fail 信号，用于验证缺陷是否存在及修复是否有效。

### 10 种方法优先级排序

按优先级从高到低尝试，自动化优先：

| 优先级 | 方法 | 说明 | 适用场景 |
|--------|------|------|---------|
| 1 | 失败测试 at nearest seam | 运行最近接口的已有失败测试 | 接口单元测试框架可用 |
| 2 | Curl/HTTP 脚本 | 针对 dev server 运行 HTTP 请求脚本 | 后端 API 缺陷 |
| 3 | CLI 调用 with fixture | 输入 fixtured 数据 → diff snapshot 输出 | CLI 工具、数据处理 |
| 4 | Headless 浏览器脚本 | Playwright/Puppeteer 脚本 | 前端 UI 缺陷 |
| 5 | Replay captured trace | 回放捕获的 HAR/请求 trace | 有抓包 trace 可用 |
| 6 | Throwaway harness | 最小化子系统 harness | 复杂集成场景 |
| 7 | Property/Fuzz loop | 1000 随机输入 fuzz 循环 | 数据相关缺陷 |
| 8 | Bisection harness | git bisect run 自动化 | 回归缺陷 |
| 9 | Differential loop | 旧版本 vs 新版本 diff 对比 | 性能回归 |
| 10 | HITL bash script (last resort) | 人工操作的脚本 | 需要手动步骤的缺陷 |

### Loop 优化

构建成功后，尝试优化：

| 优化维度 | 目标 | 方法 |
|---------|------|------|
| 速度 | 2 秒确定性 loop 优于 30 秒不稳定 loop | 缓存 setup、跳过无关 init |
| 信号清晰度 | 断言具体症状，非模糊"不对劲" | 精确断言失败模式 |
| 确定性 | 每次运行结果一致 | 固定时间、随机种子、文件系统隔离 |

### 无法构建 Loop 时的处理

所有 10 种方法均失败时：

1. 停止并明确列出已尝试方法
2. 请求用户提供：
   - a) 可复现环境访问权限
   - b) 捕获的 artifact（HAR 文件、日志 dump、core dump、带时间戳的屏幕录制）
   - c) 添加临时生产 instrumentation 的授权
3. 禁止不通过 feedback loop 直接进入假设阶段

## 非确定性缺陷处理 (DISCOVER 1b)

### 复现率提升策略

对于不能 100% 复现的缺陷，不追求 100% 复现，而是提升复现率至可调试水平：

| 策略 | 说明 |
|------|------|
| Loop 触发 100× | 在循环中重复触发，统计数据 |
| 并行化 | 同时运行多个 loop 实例 |
| 增加压力 | 提高并发度、数据量 |
| 缩小时间窗口 | 聚焦最可能触发的关键路径 |
| 注入 sleeps | 在竞态条件怀疑点注入延时 |

### 复现率分级

| 复现率 | 分类 | 处理方式 |
|--------|------|---------|
| ≥ 50% | 可调试 | 进入正常 DEBUG → HYPOTHESISE 流程 |
| 1% - 50% | 边缘可调试 | 提升复现率后再进入假设阶段 |
| < 1% | 不可调试 | 转向"无法构建 loop"流程，请求用户协助 |

## 可证伪多假设生成 (DISCOVER 1c)

### 假设格式

每个假设 SHALL 使用可证伪格式：

```
如果 <X> 是原因，则 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重
```

### 生成规则

| 规则 | 说明 |
|------|------|
| 数量 | 生成 3-5 个假设 |
| 可证伪性 | 每个假设 SHALL 给出可证伪预测 |
| 不可证伪 → 丢弃 | 无法给出可证伪预测的假设视为"感觉"，丢弃或锐化 |
| 排序 | 按可能性排序后展示给用户 |
| 用户参与 | 用户可以基于领域知识重排序 |

### 单变量测试

| 规则 | 说明 |
|------|------|
| 每次仅改变一个变量 | 确保测试结果可归因 |
| 测试结果映射 | 将每次测试结果映射到对应假设的预测 |
| 反馈循环验证 | 最终验证假设时使用 Phase 1 构建的 loop |

## Regression Test at Correct Seam (步骤 3.5)

### Seam 正确性评估

修复方案确定后，在修复前评估测试 seam：

| 评估项 | 说明 |
|--------|------|
| seam 是否锻炼真实 bug 模式 | 测试能否复制触发 bug 的完整调用链 |
| 正确 seam | 先写回归测试确认失败 → 应用修复 → 确认通过 |
| seam 太浅 | single-caller 测试无法复制真实调用链 → 标记"无正确 seam" |

### 无正确 seam 时的处理

标记为发现并记录到 fix-report：

1. 记录为什么不存在正确 seam
2. 建议需要哪种架构改进（如模块拆分、接口重构）
3. 这些建议在 post-mortem 阶段传递给 kflow-audit

### 原始场景验证

修复完成后：
1. 重新运行 Phase 1 构建的 feedback loop
2. 确认原始（未最小化）场景不再复现缺陷

## Post-mortem 检查点 (步骤 7)

### 触发条件

修复已完成且本地验证通过后自动执行。

### 检查内容

| 检查项 | 内容 |
|--------|------|
| 复盘问题 | "什么可以防止此缺陷发生？"、"此缺陷的根本原因为何未被早期阶段捕获？" |
| 架构改进识别 | 是否存在架构改进可以防止同类缺陷（如缺少正确的测试 seam、模块耦合导致变更波及） |
| 假设记录 | 最终正确的假设及证明过程；备选假设被排除的原因 |
| 调试日志清理 | 所有调试 instrumentation 已清理；throwaway prototype 已删除或移动到标记位置；临时文件已清理 |

### 架构改进建议传递

| 来源 | 目标 | 内容 |
|------|------|------|
| fix-report "关联建议" 字段 | kflow-audit 审计评估 | 架构层面的改进机会 |
| Regression test seam 问题 | kflow-audit 审计评估 | 测试 seam 缺失报告 |
| 假设记录 | fix-report "最终正确的假设" 字段 | 供未来调试参考 |

### 无改进时的处理

post-mortem 未发现架构改进机会时，简要记录"无架构改进建议"，检查点仍标记完成。

## 重复制（执行类阶段）

> ⚠ **子代理强制规则**（参见 skills/kflow-bug-fix/references/repetition.md §12）：本阶段（缺陷修复）主工作 MUST 通过 Agent 子代理执行，主 Agent 仅负责调度和验收，SHALL NOT 直接执行缺陷修复主工作（缺陷诊断/根因分析/代码修复/测试修正等），无例外。子代理崩溃时轮次级重试（≤3 次），全部失败标记 ⚠️ 阻塞。

缺陷修复阶段属于执行类阶段中的**重复制类阶段**，沿用重复制子代理循环。子代理每轮遍历全部失败用例，每个独立分析+修复+验证，内层 3 次修复上限独立共存于外层重复制循环中。轮次由实际执行的循环决定（下限 1 轮），变更档位只决定**执行形态与产出深度**，SHALL NOT 决定轮数（参见 `skills/kflow-bug-fix/references/repetition.md` §14）：

- **档位来源**：读取变更级 `.status.md` 基本信息的「变更档位」字段；档位仅决定执行形态与产出深度。
- **轮数**：由实际执行的循环决定，全局下限 1 轮（无例外，SHALL NOT 存在跳过路径），SHALL NOT 预置或受限于任何数值。
- **回退重执行**：SHALL NOT 因回退而预置或提高轮数；`.status.md` 中无影响范围分数时同样由实际执行的循环决定轮次。
- **验证门控**：受影响项 100% 覆盖（回退重执行场景）+ 产物完整性（参见 `skills/kflow-bug-fix/references/repetition.md` §15）。原「全量至少 1 轮兜底」已被 §8 验收项「执行报告完整（含全量遍历证明）」吞并删除。
- **自然终止**：某轮无新发现且无可执行工作、且报告证明全部审查维度与全部失败用例已完成全量遍历时终止，终止结果 `执行完成`。
- **停滞终止**：连续 3 轮无实质进展（同一问题项反复出现）时返回报告并标注 `停滞`，进入升级分支并升级用户（记录 `docs/skill-suggestion.md` + AskUserQuestion + 可标记 ⚠️ 阻塞）。
- **审查范围冻结**：主 Agent 从阶段产物既有内容生成审查对象集合并冻结，审查维度限于本阶段固定枚举（缺陷诊断/根因分类/代码修复/测试修正等，依重复制遍历指令）。子代理 SHALL NOT 扩大审查对象集合、SHALL NOT 新增审查维度/检查项、SHALL NOT 借审查之名新增功能点/字段/章节。冻结范围之外的发现降级为「**范围外观察**」——不改产物、不计入发现数，写入该轮报告。
- **轮间摘要**：第 2 轮起注入前轮摘要（已修复问题/未解决问题/覆盖率变化/范围外观察/本轮建议关注），仅优化注意力分配，不跳过任何工作项。

> **权威定义**：执行模型与终止模型唯一定义于 `agent-iteration-execution` 能力，审查范围冻结定义于 `convergence-driven-repetition` 能力，本 Skill 仅引用，SHALL NOT 自行定义轮次数值。

### 每轮工作内容

**遍历项**：全部失败用例

**每轮流程**：
1. 遍历全部失败用例，每个独立执行完整修复流程：
   - Phase 1: BUILD LOOP（10 种方法优先级尝试，优化 loop）
   - Phase 2: REPRODUCE（确定性/非确定性缺陷策略）
   - Phase 3: HYPOTHESISE（3-5 个可证伪假设 → 单变量测试）
   - 二分法根因分类 → 修复 → 验证循环
   - Regression test at correct seam 评估
   - Post-mortem 检查点（复盘 + 架构建议 + 日志清理 + 假设记录）
2. 已修复的用例仍需验证无回归
3. 单用例 3 次修复上限独立共存于内层（不终止外层轮次）

**每轮产物**：fix-report 或 design-error-report

**轮次结束后**：更新 .status.md 执行轮次计数器

### 复杂度评估

复杂度评估仅信息展示，不驱动执行行为：

```
复杂度分 = 失败用例数 × 1.5 + 非确定性缺陷 × 2

低复杂度 (< 20 分) / 中复杂度 (20-50 分) / 高复杂度 (> 50 分)
```

分级阈值保留但仅用于信息分类，复杂度分写入 .status.md 备注列标注「仅供参考，不驱动执行行为」。无论复杂度高低，均须执行至全部失败用例完成全量遍历（由 `skills/kflow-bug-fix/references/repetition.md` §14.3 终止模型确定）；连续 3 轮无实质进展时 SHALL 标注 `停滞` 并进入升级分支。

### 重复制循环与3次修复上限的层级关系

缺陷修复阶段并行维护两个独立指标：

| 维度 | 重复制循环（外层，轮数由实际循环决定） | 3次修复上限（内层，单用例） |
|------|---------|-----------|
| 约束层级 | 外层循环（整体迭代轮次） | 内层循环（单用例修复尝试） |
| 方向 | 自然终止——轮次由实际执行的循环决定，下限 1 轮 | 上限（ceiling）——阻止无限重试 |
| 计数范围 | 每阶段统一计数 `{N} 轮`（N 为实际执行的轮次，SHALL NOT 受限于档位或任何数值） | 每用例独立计数 1-3，跨轮次累加 |
| 触发后果 | 当前轮无新发现且无可执行工作 → 终止（终止结果 `执行完成`）；连续 3 轮无实质进展 → 终止（终止结果 `停滞`）并进入升级分支 | 达到 3 次 → 升级用户决策 |
| 互动关系 | 外层在全部失败用例完成全量遍历后终止 | 上限触发不终止轮次 |

**场景**：第 2 轮某用例 3 次修复均失败 → 升级用户决策（3 次上限触发不终止轮次）→ Agent 继续处理当前轮次其他可修复问题。某轮所有用例均已触发 3 次上限且该轮零修改、报告证明全部用例已全量遍历时，该轮 SHALL 终止，SHALL NOT 为凑轮数而继续。

### 执行流程

```
1. 复杂度评估 → 写入 .status.md 备注列（仅信息展示，不驱动执行行为）

1.5 INIT → 主 Agent 初始化，写入 .status.md 执行轮次为 1 轮
    └── 判定流程: 读取变更级 .status.md「变更档位」字段（仅用于确定每轮执行形态与产出深度；字段缺失或历史取值 完整 按 标准 档处理）；轮数由收敛实际发生在第几轮决定，下限 1 轮，SHALL NOT 预置或受限于任何数值

2. 构建阶段专属提示词
   ├── 输入: 测试轮次报告 + detailed-design.md + functional-designs/
   ├── 执行要求:
   │   ├── Phase 1: BUILD LOOP（10 种方法优先级尝试，优化 loop）
   │   ├── Phase 2: REPRODUCE（确定性/非确定性缺陷策略）
   │   ├── Phase 3: HYPOTHESISE（3-5 个可证伪假设 → 单变量测试）
   │   ├── 二分法根因分类 → 修复 → 验证循环
   │   ├── 修复尝试上限: 每用例 3 次（上限），第 4 次升级用户
   │   ├── Regression test at correct seam 评估
   │   └── Post-mortem 检查点（复盘 + 架构建议 + 日志清理 + 假设记录）
   ├── 输出: fix-report（含 loop+假设+seam+post-mortem）
   ├── 重复制遍历指令: 「每轮遍历全部失败用例独立执行完整修复流程。更新 .status.md 中执行轮次计数器为当前轮次号。禁止按轮次分段分配工作重点——每轮均须对全部失败用例执行完整检查。执行轮次 SHALL 不少于 1 轮；当某轮无新发现且无可执行工作、且报告证明全部审查维度与全部失败用例已完成全量遍历时，SHALL 返回执行报告并终止，终止结果 `执行完成`。连续 3 轮无实质进展时 SHALL 返回执行报告并标注 `停滞`。审查对象集合已冻结，SHALL NOT 审查清单之外的文件或内容、SHALL NOT 新增审查维度。3次修复上限约束单用例修复尝试次数（内层），整体执行轮数由实际循环决定（外层），两者独立共存。」（SHALL NOT 预置或硬编码任何轮次数值）
   └── 完成承诺: COMPLETED

3. 启动 Agent 迭代子代理 (Agent(description, prompt, run_in_background))
   └── 子代理内维持现有多 Agent 并行分析 + 二分法根因分类

4. 主 Agent 验收
   ├── 轮次: .status.md 执行轮次 >= 1（SHALL NOT 以轮次数量作为通过或拒收依据）
   ├── 终止结果: .status.md 终止结果字段取值 `执行完成`（完成全量遍历）/ `停滞`（连续 3 轮无实质进展，须有升级记录），且与实际终止路径一致
   ├── 产物: fix-report 存在且完整
   ├── Feedback loop: Phase 1 构建的 loop 已记录
   ├── 假设记录: 3-5 个假设及验证结果已记录
   ├── 修复验证: 本地验证通过 + 原始场景验证通过
   ├── Seam 评估: Regression test seam 正确性已评估
   ├── Post-mortem: 复盘检查点已完成，日志已清理
   ├── 根因分类: 分类结论正确（实现错误/测试错误）
   └── 验证门控: 受影响项 100% 覆盖（回退重执行场景）+ 产物完整性
```

### 验收结果处理

- **通过** → 返回测试阶段重新执行（含 post-mortem 完成标记）
- **执行报告不完整或无理由提前返回** → 拒收，直接重新启动 Agent 子代理继续执行，不进入 AskUserQuestion
- **连续 3 轮无实质进展（停滞），或产物不合格** → 记录 skill-suggestion.md → AskUserQuestion 询问重跑（升级分支）

## 快车道模式

缺陷修复快车道承载 L4 实现层缺陷的独立闭环：**分诊 → 修复 → 定向验证 → 快速收口**。机制权威定义见 `bugfix-fast-lane` 能力，状态文件结构与隔离规则见 [core-mechanisms/03-status-and-tasks.md](../core-mechanisms/03-status-and-tasks.md#35-缺陷级状态文件格式-bugsfixbug-idbugfix-statusmd)，门控分支见各 skill 的 `references/gates.md` §9，钩子分支见 `references/hooks.md`。

### 入口条件

- 无触发测试阶段上下文（不存在待处理的接口单元测试 / E2E 测试 / 集成测试失败轮次报告）
- 调用来源为 `kflow-bug-triage` 的 L4 实现执行结论
- 缺陷级状态文件 `bugs/fix/{BUG-ID}/bugfix-status.md` 存在且「受影响项清单」区已填写

三项同时满足时进入快车道模式；任一不满足时按「门控检查」的入口模式判定分支处理。

### 状态写入位置

| 状态项 | 写入位置 | SHALL NOT 写入 |
|-------|---------|---------------|
| 修复阶段状态 / 耗时 / 轮次 / 根因分类 | `bugfix-status.md` 的「修复记录」区 | 变更级 `.status.md` 的 `执行轮次` 字段 |
| 定向验证结果 | `bugfix-status.md` 的「定向验证」区 + `verify-report.md` | — |
| 收口结论 | `bugfix-status.md` 的「收口结论」区 | — |
| 缺陷状态 | `bugs/index.md` 对应行 + 问题详情文件 | — |

### 与变更级状态的解耦

快车道执行期间 SHALL NOT 读取变更级 `.status.md` 的「变更档位」字段与阶段状态字段，SHALL NOT 读写其 `执行轮次`、`终止结果`、阶段状态矩阵、阶段耗时与轮次统计；SHALL NOT 要求任何变更级阶段的门控通过，SHALL NOT 阻塞变更级阶段流转，SHALL NOT 触发阶段回退。

> 快车道不进入变更级阶段集合，故变更档位（决定审查形态与产出深度的字段）对快车道无意义——快车道不执行阶段审查。轮次计数以缺陷为独立单位，写入缺陷级状态文件。

### 复用既有修复能力

快车道模式 SHALL 复用本 Skill 既有修复能力，SHALL NOT 定义第二套修复流程：根因二分法（实现错误 / 测试错误）、子代理强制与主 Agent 验收隔离（`references/repetition.md` §12）、三次修复尝试上限与递进策略、Regression Test at Correct Seam、Post-mortem 复盘检查点。

### 定向验证（流程出口）

- 验证范围 SHALL 严格限定为 `bugfix-status.md`「受影响项清单」区列出的测试用例
- SHALL NOT 重跑全量测试套件，SHALL NOT 触发集成测试轮次，SHALL NOT 使用收敛驱动循环
- 受影响项清单覆盖率 SHALL 达 100%，未达 100% 时定向验证判定为不通过
- 未通过时复用三次修复尝试上限处理（每用例独立计数、跨次累加），达到上限时使用 AskUserQuestion 升级用户；SHALL NOT 引入新的轮次模型
- 每次验证 SHALL 在「定向验证」区**追加**新的验证记录（不覆盖之前的记录），追加顺序按验证时间排列
- 定向验证未通过时 SHALL NOT 更新 `bugs/index.md` 状态，SHALL 记录失败信息（验证时间、失败用例、失败原因）

### 快速收口

定向验证通过且以下校验项全部满足后执行快速收口：

| 校验项 | 判定 |
|-------|------|
| 受影响项清单 100% 覆盖且全部通过 | 必须满足 |
| 定向验证报告存在 | 必须满足 |
| `bugfix-status.md` 全部必填区已填写且无占位符 | 必须满足 |

任一条件不满足时收口判定为不通过：缺陷状态保持「处理中」，记录未通过原因，SHALL NOT 标记为「已解决」。

收口完成动作：更新 `bugs/index.md` 对应行状态为「已解决」、写入 `bugfix-status.md`「收口结论」区、在问题详情文件中标记快车道收口完成。快速收口 SHALL NOT 触发阶段回退、SHALL NOT 阻塞变更级阶段流转。

> **术语边界**: 本机制命名为「**快速收口**」而非「快速归档」——仓库中的「归档」是变更级元工作流（`/opsx:archive` + 版本自增 + 打包），缺陷级闭环复用该词会造成歧义。「**定向验证**」亦与已移除的 `recheck-round` 语义不同：前者重跑受影响项用例，后者复核审查循环内的修复。

### 分诊失效与诊断层级错误的处理

| 情形 | 判定 | 处理 |
|------|------|------|
| 修复过程中发现实际影响面**超出**受影响项清单覆盖范围 | 分诊失效 | SHALL 退回 `kflow-bug-triage` 重新评估影响范围；SHALL NOT 由修复者擅自扩大或缩小验证范围 |
| 修复过程中发现必须修改 `detailed-design.md` 或更上游的设计产物才能正确修复 | 诊断层级错误 | SHALL 退回 `kflow-bug-triage` 重新执行四层溯源；SHALL NOT 在快车道内修改设计产物 |

### 产物边界

快车道 SHALL NOT 创建或修改 `functional-designs/`、`detailed-design/`、`api-tests/`、`e2e-tests/` 下的任何文件；允许修改的范围限于代码实现与测试代码。产出清单：`bugfix-status.md`、`verify-report.md`、代码与测试代码修改、`bugs/index.md` 与问题详情文件的更新。

### 与审计的边界

审计的**门控校验** SHALL NOT 覆盖快车道缺陷（不要求其经过阶段门控，不判定为「跳阶段」）；**覆盖率与产物存在性校验** SHALL 覆盖快车道状态文件的完整性（存在性 + 必填区完整），缺失或不完整时判定为阻塞。

## 与其他 Skill 的关系

- **输入来自**：`kflow-api-test`（接口单元测试失败）、`kflow-e2e-test`（E2E 测试失败）、`kflow-bug-triage`（L4 实现问题路由 → 快车道模式）
- **输出给**：既有模式 → 测试阶段（重新测试）；快车道模式 → 定向验证 → 快速收口
- **前置阶段**：测试（子变更级：接口单元测试或 E2E 测试），或 kflow-bug-triage 的 L4 路由（快车道模式，无测试阶段上下文）
- **后续阶段**：既有模式返回测试阶段（实现/测试错误）；快车道模式进入定向验证并在收口后终止，SHALL NOT 返回任何变更级测试阶段
- **关系说明**：既有模式下处理子变更级缺陷修复，变更级集成测试修复由 `kflow-integration-test` 内聚处理。用户反馈统一由 `kflow-bug-triage` 处理（A路径），既有模式入口仅限测试阶段自动发现（B路径）；快车道模式由 `kflow-bug-triage` 的 L4 结论独占入口
- **回写 bugs/ 目录**：A 路径修复完成后 SHALL 回写 `bugs/bug-NNN-NNN.md` 修复记录节并更新 `bugs/index.md` 状态；B 路径修复报告留在子变更目录，若对应 bug 已在 bugs/ 登记则同步追加摘要；快车道模式 SHALL 回写 `bugs/fix/{BUG-ID}/bugfix-status.md` 并在快速收口后更新 `bugs/index.md` 状态为「已解决」
- **执行模式**：既有模式为重复制循环（内嵌多 Agent 并行分析），终止模型为「当前轮无新发现且无可执行工作 → `执行完成`；连续 3 轮无实质进展 → `停滞`」（轮次下限 1 轮；档位仅决定执行形态与产出深度，权威定义见 `agent-iteration-execution` 能力），3次修复上限独立共存，轮间摘要保留，复杂度评估仅信息展示，主 Agent 验收闭环；快车道模式复用 3 次修复上限与子代理隔离，不使用收敛驱动循环，状态写入缺陷级 `bugfix-status.md`
