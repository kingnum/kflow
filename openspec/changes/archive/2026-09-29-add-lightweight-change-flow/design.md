# Design

## Context

参见 `proposal.md` 的 Why。以下现状与约束决定了实现方式：

**前置依赖**：本变更读取 `add-change-tier` 引入的 `变更档位` 字段与单向升档机制。该字段由 kflow-explore 写入变更级 `.status.md`，由 kflow-design 复核后更新。

**判定依据的可得位置**：轻量档在 kflow-design 的 DIVIDE 之后生成适用性声明，此时以下产物已存在且可读——`functional-designs/index.md` 的功能点清单与 FP 类型列（explore 产出）、`detailed-design.md` 的「设计域章节 → 接口设计」表与「跨子变更接口契约」子章节（design 产出）。

**追溯矩阵的列结构**：`traceability.md` 的覆盖总览表列固定为 功能点ID、功能设计(§)、详细设计(§)、接口测试(ID)、E2E测试(ID)、编码实现(SC)、集成测试(ID)。列是「格」的容器，裁剪必须以列为单位才能保证分母一致。

**门控的实现形态**：各阶段的进入门控写在各 skill 的 `references/gates.md`，`conditional-product-refs` 统一定义了三种产物状态的判定（跳过通过 / 完成有文件通过 / 待开始阻塞）。

**审计的两条路径**：审计既是归档门控（集成测试通过后自动触发），也可由用户随时手动调用。轻量档降级必须只影响轻量档，且不改变其门控地位。

**与 `add-change-tier` 的规格重叠**：`devflow-audit` 的能力被两个变更同时修改，见 `proposal.md` 的同名说明。

## Goals / Non-Goals

**Goals:**

- 使轻量档的执行阶段集合与该变更的实际验证需求匹配，同时保持「跳过的合法性」可被门控自动验证。
- 让裁剪的判定依据落在 design 阶段已产出的客观内容上，而不是新增一套主观的「是否涉及 X」问答。
- 使裁剪不破坏覆盖率门控的语义——覆盖率仍是有意义的分母，而非被整体豁免。
- 保持标准档与完整档的行为逐字不变。

**Non-Goals:**

- 不调整轮次、审查分级与自审规则（属 `add-change-tier`）。
- 不为轻量档引入新的阶段或新的产物文件路径。
- 不改变纯后端项目跳过 E2E 的既有规则。
- 不让裁剪判定依赖用户的主观输入（用户覆盖档位是唯一入口，判定本身不做询问）。

## Decisions

### 决策 1：判定依据取 design 产物而非 explore 产物

接口适用性读取 `detailed-design.md` 的接口设计表，集成测试适用性读取同文件的跨子变更接口契约章节，UI 适用性读取 `functional-designs/index.md` 的前端 FP 与页面/组件/路由信息。

**未采用**的方案是让 explore 在功能点清单上直接标注「是否涉及接口 / 是否涉及 UI」。理由：explore 的域外内容明确禁止接口定义与数据模型设计，让它在 FP 上预判「是否涉及接口」等于让它替 design 做技术判断，且预判与实际设计必然出现偏差。design 阶段已有接口设计表这一确定产物，直接读它比让 explore 猜更准。

UI 适用性用 functional-designs 的 FP 类型列是例外，因为页面/组件/路由信息本就是 explore 的域内内容（用户体验规格说明书的一部分）。

### 决策 2：判定不可读时保守回退为「适用」

任一判定依据的产物不存在、格式不符或字段缺失时，该阶段 SHALL 判定为「适用」。

理由：裁剪是优化，不是正确性要求。多跑一个阶段只消耗成本，漏跑一个阶段会产生未验证的变更。判定失败方向必须偏向执行。这条规则同时消除了「design 产物写得不规范导致静默跳过测试」的风险。

### 决策 3：声明与产物的一致性是四态判定，不是两态

在 `conditional-product-refs` 已有的三态（跳过通过 / 完成有文件通过 / 待开始阻塞）之上追加第四态：

| 声明 | 产物 | 判定 |
|------|------|------|
| 不适用 | 不存在 | 合法跳过，通过 |
| 不适用 | 存在 | 不一致，阻塞并提示 |
| 适用 | 存在 | 通过 |
| 适用 | 不存在 | 阻塞，输出缺失产物清单 |

**未采用**的方案是只检查声明（不检查产物）。理由：只信声明会让漏产出产物的情况静默通过；只信产物则无法区分「因不适用而未产出」与「漏产出」。两者交叉才能把「跳过」与「遗漏」分开。

「不适用但产物存在」判为不一致而非自动修正，因为产物存在意味着该阶段实际执行过，与声明矛盾——这通常说明声明生成有误或档位被中途改动，需要人工介入而不是自动取舍。

### 决策 4：裁剪以列为单位，覆盖率分母按列排除

`traceability.md` 中被裁剪的阶段，整列填充 `⏭️`，阶段覆盖统计表中该列标记 `N/A`，且该列的行数从分母移除。

**未采用**的方案是逐格填充 `⏭️`（允许同一列内部分格适用）。理由：适用性是阶段级的（一个阶段要么跑要么不跑），列内混合会产生「半列覆盖率」这种无法定义通过条件的中间状态。列级排除使覆盖率公式保持「已填充 / (总格数 - 不适用格数)」的简单形式，且与现有「纯后端项目 E2E测试列标记为 ⏭️」的处理方式一致——该既有规则正是列级排除。

### 决策 5：轻量档 FP 类型混合时升档而非阻塞

子变更类型严格二分为后端子变更或前端子变更，混合必须拆分为多个子变更，而轻量档恒为单一子变更。两个规则冲突时，选择升档。

**未采用**的方案是阻塞并提示用户手动拆分。理由：阻塞会把「系统本可自行处理的规模判断」变成用户的手工操作，与轻量档「快速进入开发」的目标相悖。升档动作复用 `add-change-tier` 已建立的单向升档机制（经用户确认、不回退 explore），不引入新机制。

升档需用户确认，因为档位变化会影响该变更剩余全部阶段的轮次与审查形态，这是用户应当知情的成本变化。

### 决策 6：轻量档审计降级但保留门控地位

轻量档审计由主 Agent 执行轻量自检，检查阶段完整性、产物存在性与无占位符、裁剪合法性三项，输出简化记录，不计算加权总分。

**未采用**的方案是完全跳过审计。理由：审计是归档前的最后一道检查，完全跳过会让轻量档变更成为唯一没有归档门控的路径；而七维度加权评分对 1-3 个功能点的变更确实是过度设计。降级而非删除，保留「有依据的跳过可放行、无依据的跳过被拦住」这一关键能力——这正是轻量档最容易出问题的点。

### 决策 7：无测试阶段时子变更跳过「等待同步」状态

轻量档若接口单元测试与 E2E测试均被裁剪，子变更在代码审查完成后直接进入变更级同步点，不进入 `⏸️ 等待同步`。

理由：`⏸️ 等待同步` 的语义是「等待变更级服务刷新后进入下一轮测试」。无测试阶段时不存在下一轮测试，保留该状态会让子变更无限等待一个不会到来的通知。

## Risks / Trade-offs

- **判定依据依赖 `detailed-design.md` 的章节写法，design 产物不规范会让判定大面积回退为「适用」**（即裁剪失效，退化为 `add-change-tier` 后的状态） → 决策 2 的保守回退使失败方向安全；`kflow-verify` 的产物诊断可检出章节缺失。
- **UI 变更判定过严会让含 UI 的轻量档跳过 E2E，产生未验证的界面回归** → 判定条件取宽（只要触及页面、组件或路由的新增或变更即判适用），宁多跑不漏跑。
- **覆盖率分母排除可能被当作绕过门控的手段**（人工把阶段标为 `⏭️`） → 排除仅在有适用性声明依据时生效；无依据的 `⏭️` 在归档门控与轻量自检中均判为阻塞。
- **「不适用但产物存在」判为阻塞可能误伤**（阶段先执行、后因档位下调改判不适用） → 档位下降在 `add-change-tier` 中已被禁止（复核只允许单向升档），该场景不会出现；若因用户覆盖档位下调产生，阻塞提示会要求清理产物或恢复声明。
- **`devflow-audit` 被两个变更同时修改，归档顺序错误会导致规格与实现不一致** → 本变更的 `devflow-audit` 增量写成 `add-change-tier` 编辑结果的超集（沿用同一需求名与全部原场景名），使两个归档顺序下的校验均可通过；顺序约束记录在 `proposal.md`。
- **轻量档裁剪后审计的「测试充分性」维度无数据可评** → 该维度改为「该阶段适用时」检查，合法裁剪不判缺项，与决策 6 的检查项一致。

## Migration Plan

依赖 `add-change-tier` 先落地（需要 `变更档位` 字段与升档机制）。

改动落地顺序：

1. `openspec/specs/` 下 1 个新能力与 7 个修改能力（本变更的 delta）。
2. `docs/designs/core-mechanisms/` 的 `03-status-and-tasks.md`（阶段状态表的不适用表示、适用性声明字段）、`04-gates-and-transitions.md`（门控分支）、`08-governance.md`（分级口径引用）。
3. `docs/designs/skills/` 的 `kflow-design.md`（适用性声明步骤、DIVIDE 简化、类型混合升档）、`kflow-explore.md`（阶段集合提示）、`kflow-api-test.md`、`kflow-e2e-test.md`、`kflow-integration-test.md`（适用性分支）、`kflow-audit.md`（轻量自检路径）、`kflow-archive.md`（归档门控）、`kflow-guide.md`（流程概览）、`kflow-verify.md`（诊断接受裁剪）。
4. `skills/` 下上述 skill 的 `SKILL.md`、`references/gates.md`、`references/state-values.md`、`references/hooks.md`。
5. `docs/designs/templates/changes/{change}/change-status.md`（适用性声明字段）、`traceability.md` 模板（`⏭️` 列）、`audit-report.md`（轻量自检形态）。
6. `README.md`。

向后兼容：阶段适用性声明为新增字段，历史变更缺失时按「全部阶段适用」处理，等价于现状。无需数据迁移。

回滚策略：删除适用性声明字段与 `⏭️` 列标记，恢复全阶段执行；`traceability.md` 中已填充的 `⏭️` 需清理为空格以避免成为无依据的跳过。
