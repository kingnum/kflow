# 集成验证记录

> 本文件承载 `tasks.md` 第 6 组（集成场景验证）的走查记录。本仓库以 Skill 规范与 references 为交付物，验证方式为按变更后的规则对构造场景做逐步骤走查（规则推演），并核对规则文本与产物字段。

## 验证基准

- 设计面分数：`功能点数 × 1 + 接口契约变更数 × 1.5 + 数据模型变更数 × 2`
- 接口契约变更数只计新增/修改的 API 契约；数据模型变更数只计新增/修改的 schema/migration
- 阈值：`≤ 3` → `轻量`；`> 3` → `标准`
- 升档分类：硬升档（数据迁移、破坏性契约变更、跨变更契约影响；不可拒绝）/ 软升档（默认保持轻量；仅在新增下游测试阶段时提示；拒绝后记录理由且不再重复提示）

规则来源：`skills/kflow-design/SKILL.md` 步骤 9 / 9.5、`skills/kflow-explore/SKILL.md` 步骤 8、`references-src/state-values.md` §4、`references-src/gates.md` §1.4。

## 场景 6.1：受影响的接口不计入设计面

**构造输入**：功能缺陷变更，1 个 FP；triage 影响面清单列出 3 个受影响接口；无接口契约修改、无 schema/migration。

| 验证点 | 规则推演 | 结果 |
|--------|---------|------|
| 设计面分数 | `1×1 + 0×1.5 + 0×2 = 1` | 1.0 |
| 档位映射 | 1 ≤ 3 | `轻量` |
| TIER_RECHECK | 复核档位 = 当前档位 = `轻量` | 维持轻量，不弹升档 |
| 影响面用途 | 3 个受影响接口进入影响面清单 | 定向验证覆盖 3 个接口；不参与档位计算 |

**结论**：设计面分数为 1，维持轻量且不触发升档提示；定向验证覆盖全部 3 个受影响接口。✓

**构造输入**：功能缺陷变更，1 个 FP；1 个接口契约新增/修改；无 schema/migration。

| 验证点 | 规则推演 | 结果 |
|--------|---------|------|
| 设计面分数 | `1×1 + 1×1.5 + 0×2 = 2.5` | 2.5 |
| 档位映射 | 2.5 ≤ 3 | `轻量` |

**结论**：设计面分数为 2.5，未超过阈值 3，维持轻量。✓

## 场景 6.3：schema/migration 变更触发硬升档

**构造输入**：功能缺陷变更，1 个 FP；1 个接口契约新增/修改；1 个 schema/migration（含数据迁移脚本）。

| 验证点 | 规则推演 | 结果 |
|--------|---------|------|
| 设计面分数 | `1×1 + 1×1.5 + 1×2 = 4.5` | 4.5 |
| 档位映射 | 4.5 > 3 | 复核档位 `标准` |
| 升档分类 | 含数据迁移/schema 变更 → 硬升档 | 硬升档 |
| 提示形态 | AskUserQuestion 说明原因，不提供保持轻量的选项 | 不可拒绝，升为 `标准` |

**结论**：设计面分数为 4.5，命中硬升档，用户无保持轻量选项。✓

## 场景 6.4：后端 + 前端 FP 的轻量变更拆为两个子变更

**构造输入**：轻量档变更，1 个后端 FP + 1 个前端 FP。

| 验证点 | 规则推演 | 结果 |
|--------|---------|------|
| DIVIDE 分支 | FP 类型混合 → 2 个子变更（1 后端 + 1 前端） | 不升档 |
| 最小划分表字段 | 子变更名称、类型、包含功能点、实现顺序、依赖说明 | 字段齐全 |
| 实现顺序与依赖 | 后端子变更在前；前端子变更标注「依赖后端 API 契约：{METHOD} {path}」 | 满足 |
| TIER_RECHECK | 设计面分数 `2×1 = 2` ≤ 3；复核 = 当前 = `轻量` | 维持轻量 |
| 类型一致性 | 每个子变更内 FP 类型全部一致 | 通过 |

**结论**：产出 2 个子变更、不升档，最小划分表字段齐全且前端子变更标注 API 契约依赖。✓

## 场景 6.5：后端子变更 FP 超限触发边界升档

**构造输入**：轻量档变更，DIVIDE 时后端子变更包含 11 个 FP（> 10）。

| 验证点 | 规则推演 | 结果 |
|--------|---------|------|
| DIVIDE 边界 | 单个子变更 FP > 10 | 命中轻量档边界升档 |
| 升档动作 | AskUserQuestion 说明原因；确认后覆写 `.status.md` 为 `标准` | 升为 `标准` |
| 后续划分 | 按标准档流程执行完整依赖关系分析与划分表 | 完整划分 |
| 阶段适用性声明 | 升档后 SHALL NOT 生成（已生成亦失效） | 按全阶段适用处理 |

**结论**：后端子变更 FP > 10 时升档为标准，并执行完整子变更划分。✓

## 场景 6.6：软升档被拒绝后记录且不重复提示

**构造输入**：轻量档变更，TIER_RECHECK 设计面分数为 4（非硬升档）；轻量档下 E2E测试将被判定为 `⏭️ 不适用`，升档为标准会新增该测试阶段。

| 验证点 | 规则推演 | 结果 |
|--------|---------|------|
| 升档分类 | 非硬升档且复核档位更高 | 软升档 |
| 必要性判定 | 升档会新增至少一个下游测试阶段 | 显示升档提示 |
| 用户选择 | 选择保持当前档位 | 保持 `轻量` |
| 状态记录 | 拒绝理由写入变更级 `.status.md` | 已记录 |
| 后续阶段 | 后续门控与阶段读取该记录 | SHALL NOT 重复提示升档 |

**结论**：软升档选择保持轻量后，理由写入 `.status.md`，后续阶段不再重复提示。✓
