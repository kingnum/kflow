# Design

## Context

`变更档位` 目前以三档枚举（`轻量` / `标准` / `完整`）贯穿全流程，透传至门控、子代理 prompt、状态文件、hooks、repetition 规则与审计。三次简化后其语义已收窄为「审查形态与产出深度」（见 `proposal.md` - Why），轮次维度不存在。现状的实现分布：

- `skills/` 下 64 个文件、756 处引用 `档位`，其中 49 个文件含 `完整档` / `完整模式` 字样
- `docs/designs/` 下 22 个文件 + `README.md` 含 `完整档` / `完整模式`
- `openspec/specs/` 下 11 个能力的 requirement 文本按三档分支

约束：

- **轻量档的裁剪链必须保留**（阶段适用性声明、测试三阶段条件适用、覆盖率分母口径、归档裁剪、跳过子变更划分）。该链的前置条件是「本变更属于轻量档」，因此二级化的档位信号是这条链的载体，不能取消。
- **检查项不得缩减**是既有硬约束（`design-review-tiering`、`convergence-driven-repetition`）：档位只改并行度与产物形态，不改审查内容。
- 历史变更的 `.status.md` 中已写入 `完整` 取值，不能要求用户手工迁移。
- delta spec 的 MODIFIED 块不允许删除或重命名既有 scenario，只允许改写其内容与追加新 scenario。

## Goals / Non-Goals

**Goals:**

- 档位枚举由三档收敛为二档（`轻量` / `标准`），消除贯穿全流程的第三分支
- 保留轻量档裁剪链的完整可用性，轻量档行为不变
- 非轻量档的审查形态唯一化，使门控、hooks、状态字段判读全部由三分支降为两分支
- 修复本次改写路径上的既有不一致（0.24.0 遗留的「产品需求 → 完整」映射残句、审计给分要求残句、档位化轮次表述残句）

**Non-Goals:**

- 不改阶段裁剪的判据与裁剪范围（仍以轻量档为前置条件，不改为无条件生成声明）
- 不改影响范围分数公式与两段式判定时机（explore 初判 / design 复核）
- 不改单向升档安全阀的机制，仅收窄其目标取值
- 不改编码 / 代码审查 / 缺陷修复的重复制循环模型
- 不迁移历史变更的 `.status.md` 文件

## Decisions

### D1: 合并方向取「向下合并」，标准档 = 两视角并行

**决策**：合并后 `标准` 档的设计交叉审查形态沿用现有的两视角并行（业务+技术 / 安全+质量），四视角并行模式废除。

**备选与理由**：

| 备选 | 结果 | 否决理由 |
|---|---|---|
| 向下合并（采用） | 全部非轻量变更跑两视角 | 与代码审查形态一致（代码审查在 `标准` 与 `完整` 下本就是同一形态）；与 0.23.0 以来「降本、贴近敏捷节奏」的方向一致；检查项覆盖不变 |
| 向上合并（四视角） | 全部非轻量变更跑四视角 | 中等规模变更（现 `标准` 档，占比最高）的审查成本翻倍，与 `streamline-design-flow` 的目标反向 |
| 保留四视角但改由非档位信号触发 | 需引入第二套分级信号 | 正是本次要消除的并列分支；且信号本身也没有比档位更客观的来源 |

**代价**：并行度下降带来的是**审查独立性**下降（2 个 Agent 各自覆盖两视角，替代 4 个 Agent 各覆盖一视角），非检查项覆盖下降。单轮验证模型下每个 Agent 的审查预算由阶段确定，此代价需由后续遥测数据评估（见 Risks）。

### D2: 保留档位概念本身，仅收窄枚举

**决策**：不取消 `变更档位` 字段，保留 `轻量` / `标准` 二值。

**理由**：轻量档是**阶段集合**差异的判据（可裁剪测试三阶段、跳过子变更划分、覆盖率分母口径、归档裁剪），不是审查强度差异。取消档位需要把裁剪判据改为「无条件按客观产物信号生成适用性声明」，那会改变裁剪的触发面（当前只有小变更进入裁剪），属于另一类变更；且会一并取消「用户可上调档位」这一唯一的人工加严入口。

**取值命名**：非轻量档沿用 `标准` 而非新造名称（如 `常规`），以最小化 `docs/designs/`、`README.md`、状态文件模板的措辞改动面；`标准` 在二值枚举中语义无歧义。

### D3: 缺省回退值改为 `标准`，历史 `完整` 按读取侧归并

**决策**：「变更档位」字段缺失或取值非法时按 `标准` 处理；历史遗留的 `完整` 取值在读取侧归并为 `标准`。

**理由**：

- 原设计的回退值 `完整` 之所以合理，是因为它「等价于历史行为」（三档引入前所有变更都跑四视角）。合并后非轻量档统一跑两视角，`标准` 即等价于合并后的历史行为，`完整` 不再对应任何可执行形态。
- 归并而非迁移：延续 0.24.0 对 `收敛` → `验证通过` 的读取侧归并先例，避免改写既有变更的状态文件（其中含审计与追溯依据）。

**影响**：读取侧需在档位读取的单一位置实现归并（`state-values.md` 的档位字段定义 + 各 `gates.md` 的档位校验分支），而非散落在各阶段。

### D4: 删除完整档专属的评分报告深度要求

**决策**：删除「`完整` 档下自审、代码审查与测试类阶段的执行报告 SHALL 输出各维度 0–10 评分与不达标项清单」的产出深度要求。

**理由**：该要求本就不参与终止判定（`repetition.md` §14.5 明确「评分 SHALL NOT 参与终止判定」），其触发条件（档位 = `完整`）在二档枚举下无对应取值；若改为对 `标准` 档无条件生效，则等于给全部变更加一层无条件评分产出，与 0.24.0「审计删除评分表」的方向相悖。

### D5: MODIFIED 块保留既有 scenario 名，名称漂移在本次接受

**决策**：含废弃语义的既有 scenario 不改名，仅在原名下改写内容并追加新 scenario。

**理由**：delta 格式与校验器要求 MODIFIED 块完整保留既有 scenario 名（校验失败即 `omits scenario(s) the current spec still has`），改名会被判为「删除」。仓库已有同类先例（0.24.0 的「产品需求强制完整档」scenario 在本体中已改写为 `标准`）。

**接受的残留**：合并后 main spec 中会出现名实不符的 scenario 名，例如「高分映射完整档」的本体为「> 15 判为 `标准`」、「完整档走完整模式」的本体为「历史 `完整` 取值走两视角」、「无档位字段按完整档处理」的本体为「按 `标准` 档处理」。

**缓解**：在每个受影响 requirement 的本体文本中显式写明二档语义与历史取值归并规则，使内容自洽可读；`main spec` 的 scenario 名统一留待后续大版本重写。

### D6: 一致性收口以全仓检索为判据

**决策**：实现完成后以「全仓检索 `完整档` / `完整模式` / `或变更类型为 产品需求` / `档位轮次` 零命中（`openspec/changes/archive/` 与历史变更记录除外）」作为收口判据，而非逐文件清单核对。

**理由**：引用面为 64 文件 756 处，逐项清单易漏；检索式判据可被机械验证且可复核。

## Risks / Trade-offs

- **审查独立性下降（2 个 Agent 覆盖 4 视角）** → 检查项覆盖由 spec 硬约束保证不缩减；`phase-time-telemetry` 的阶段耗时与轮次数据可持续观察；若后续数据显示非轻量变更的审查漏检率上升，可另开变更恢复四视角（需同时决定其触发信号）。
- **64 文件 756 处引用的同步遗漏** → D6 的全仓检索收口 + `scripts/sync-references.sh` 一致性校验共同兜底；本变更按「机制规范 → 实现 → 文档 → 检索收口」波次执行，每波以检索为门。
- **历史 `完整` 取值要求读取侧归并，遗漏任一读取点会造成门控误判** → 归并规则集中在 `state-values.md` 的字段定义与各 `gates.md` 的档位校验分支两处声明；检索「变更档位」的全部读取点作为核对清单。
- **scenario 名实不符残留**（见 D5）→ 本体文本显式写明二档语义；影响面限于可读性，不影响可执行行为。
- **门控产物校验面收窄**（不再要求四份视角报告）→ 历史变更的 `cross-reviews/` 若含四份报告，读取侧不因「多出的产物」判为不一致；该放宽仅作用于读取侧，不作为新产出要求。

## Migration Plan

1. **机制规范层**：`docs/designs/core-mechanisms/` 的档位判定与门控分支章节改写为二档；`overview.md`、`index.md` 的决策表同步。
2. **可运行 Skills 层**：按 `state-values.md` → `gates.md` → `hooks.md` → `repetition.md` → `SKILL.md` 的顺序同步（字段定义先于消费点）。
3. **设计规格与文档层**：`docs/designs/skills/kflow-*.md`、模板、示例、`README.md` 档位章节同步。
4. **一致性收口**：按 D6 执行全仓检索，并运行 `scripts/sync-references.sh` 与 `python scripts/validate-frontmatter.py`。
5. **main spec 的 Purpose 段**：`change-tier-classification`、`design-review-tiering`、`lightweight-flow-trimming` 三份 main spec 的 `## Purpose` 含三档表述，delta 不承载 Purpose，需在 `openspec/specs/<capability>/spec.md` 中直接改写。

**回滚策略**：本变更为规范的枚举收窄，回滚需成组恢复——档位枚举、四视角审查路径、门控三分支、`state-values.md` 之字段表同时回退，否则会出现枚举与审查形态不匹配；因此以单次 git 提交边界（而非子步骤）作为回滚单位。

**兼容性**：历史变更的状态文件不迁移；读取侧归并处理 `完整` 取值；历史四视角审查产物保留但不被要求。
