# Design

## Context

动机见 `proposal.md` — 本节只记录塑造方案的现状与约束。

**现状事实**（已核实）：

| 事实 | 出处 |
|------|------|
| 项目类型在 init 已检测并写入两处项目级记录：CLAUDE.md「项目画像」表的项目类型行、`docs/toolchain.md` 头部的项目类型字段 | `skills/kflow-init/SKILL.md` 步骤 1 DETECT、步骤 9 OUTPUT、步骤 11 INJECT |
| `docs/toolchain.md` 是 init 的「唯一必须输出文件」 | `skills/kflow-init/SKILL.md` 核心提醒 |
| CLAUDE.md 注入为条件产物：CLAUDE.md 不存在时跳过注入 | `init-claude-md-injection` spec「项目画像 section 注入」 |
| 变更创建链路重新扫描并要求用户确认 | `skills/kflow-explore/SKILL.md` 步骤 3 TYPEDET、步骤 4 CONFIRM；`skills/kflow-guide/SKILL.md` NEW CHANGE 指引步骤 2 DETECT |
| 消费侧 7 个 skill 一律读变更级快照，不问用户 | `kflow-design`、`kflow-prototype-design`、`kflow-api-test`、`kflow-e2e-test`、`kflow-verify`、`kflow-audit`、`kflow-archive` |
| 自动检测曾误判，由用户纠正 | `docs/designs/examples/skill-suggestion.md` 记录 3（前后端分离、前端在独立仓库 → 判为纯后端） |

**约束**：

- 变更生命周期长达十余个阶段，项目类型必须在该变更内冻结（阶段集合由项目类型决定）。
- CLAUDE.md「项目画像」区块由 init 的整体扫描填充（语言、框架、数据库、构建工具、关键目录、入口文件、产品文档状态），并受 marker 的「替换整个 section」逻辑管理。
- 本变更不改动消费侧读取逻辑与快照机制。

## Goals / Non-Goals

**Goals:**

- 项目类型的用户确认从"每次创建变更一次"降为"每个项目一次"。
- 为项目类型建立唯一真源与确定的读取优先级，消除"记录存在却无人读取"的状态。
- 为记录漂移与初始误判各提供一个安全阀，且都不增加常规路径的交互。
- 存量项目（已 init 与未 init）都无需人工迁移。

**Non-Goals:**

- 不改动 7 个消费侧 skill 的项目类型读取与判定逻辑。
- 不改动变更级快照机制与其「阶段适用性声明」区。
- 不改动 init 的前端工程扫描（L2.5）与老项目逆向分析链路。
- 不引入新的项目级文件类型。
- 不追求"项目类型可被检测得绝对准确"——本设计承认检测可能出错，用确认与覆盖通道兜住，而非靠增强检测规则解决。

## Decisions

### 决策 1：确认动作前移到 init，而非取消确认

init 是项目生命周期中唯一"必然要打断用户一次"的场合（已有的权限配置、工具链方案选择确认），且执行时正在做项目画像扫描，上下文最贴合。变更创建则是高频动作，不该在其中插入仓库级问题。

**备选与取舍**：
- *彻底取消确认、完全相信检测*：交互最少，但历史误判会使错误的阶段集合静默传导到整条流水线，缺少人工校准点。否决。
- *保留 explore 每次确认*：现状，即本次要消除的问题。否决。

### 决策 2：真源首选 CLAUDE.md「项目画像」，`docs/toolchain.md` 兜底

| 读取源 | 优势 | 劣势 |
|--------|------|------|
| CLAUDE.md 项目画像（首选） | 会话自动加载进上下文，零读取成本 | 条件产物：未注入或被用户清理时不存在 |
| `docs/toolchain.md` 头部（兜底） | init 唯一必须产物，存在性有保证 | 需一次显式 Read |

两者由 init 同一轮扫描写入，不存在天然分叉；优先级只解决"读到哪个"的效率问题，不引入语义分歧。

**备选与取舍**：
- *`docs/toolchain.md` 为唯一权威*：语义最清晰，但每次创建变更都多一次 Read，且要为"未 init 补写"定义 toolchain.md 的最小完整形态。否决。
- *新建独立真源文件*：读写权最干净，但项目类型会变成第三个落点（与项目画像、toolchain.md 并存），需额外收敛既有两处，代价高于收益。否决。

### 决策 3：未 init 项目的补写落在 `docs/toolchain.md`，不写 CLAUDE.md 项目画像

explore 只掌握项目类型一项信息，而项目画像区块是一个整体（含技术栈、目录、入口文件、8 项产品文档状态）。由 explore 写入会产生一个残缺的项目画像区块，且与 init 的「替换 `## 项目画像` 到下一个 `## ` 之间内容」逻辑耦合——下次 re-init 会整体覆盖，残缺状态在中间期误导读者。

写入 `docs/toolchain.md` 头部则只需维护一个字段（文件不存在时创建仅含头部与项目类型行的最小文件），init 后续执行时会重新扫描并同步两处，自然收敛。

### 决策 4：保留变更级快照，只把填充方式从"重检"改为"继承"

阶段集合由项目类型决定：纯后端项目的 E2E 阶段标 `⏭️`、`traceability.md` 对应列整列填 `⏭️`、不计入覆盖率分母，审计与归档门控据此放行。若项目类型在变更执行中途变化，已跳过的阶段会复活，`traceability.md` 的列填充与门控判定将失去一致性依据。

因此变更级 `.status.md` 与 `functional-designs/index.md` 的项目类型字段继续存在，值来自项目级记录（继承或降级检测），并在变更内冻结。**副产物：消费侧 7 个 skill 零改动**——它们读的快照依然有值。

### 决策 5：变更创建时执行一次静默一致性校验，冲突才复核

校验内容：扫描项目根目录的前端工程标识，与项目级记录比对。成本为一次 `package.json` 读取加至多一次 Glob，可忽略；结果一致时对用户完全静默。

这解决的是记录**过期**（纯后端项目后来新增前端工程）。校验失败（如根目录不可读）时沿用记录值继续，不作为阻塞项——校验是安全阀，不是门禁。

**备选与取舍**：
- *不校验，完全信任记录*：记录会僵化，只能靠用户主动 re-init 刷新。否决。
- *仅在记录缺失时检测*：省掉每次一次的 Glob，但放弃了漂移检测。否决。

### 决策 6：新增用户显式覆盖通道

一致性校验发现不了"初始就误判"的情形：扫描信号与错误记录一致（例如前端在独立仓库时，扫描同样认为无前端标识），比对无冲突可报。因此保留人工通道——用户在需求描述中显式声明项目类型（或指出记录有误）时，该声明优先于记录与扫描，并更新项目级记录。

### 决策 7：各 skill 的职责边界

| Skill | 改动 | 不改动 |
|-------|------|--------|
| `kflow-init` | DETECT 后新增 CONFIRM（仅记录缺失或扫描冲突时询问）；写入项目级记录 | 工具链匹配、权限配置、老项目逆向、L2.5 前端扫描、git 检测 |
| `kflow-explore` | 步骤 3 由重扫改为三级回落读取；步骤 4 由询问改为静默校验 + 冲突复核；快照写入来源标注 | 变更目录创建、需求澄清、CONTEXT.md 管理、功能点拆分、档位判定 |
| `kflow-guide` | NEW CHANGE 指引的 DETECT 改为读取记录 | 变更类型分类、名称建议、冲突预检、指引"不创建文件"原则 |
| 消费侧 7 个 skill | 无 | 全部逻辑与读取路径 |

`project-type-detection` 保持项目类型规则的唯一权威定义位置（与 `init-claude-md-injection` 对 marker 注入、`devflow-init` 对工具推荐矩阵的定位一致），`devflow-guide` 与 `init-claude-md-injection` 的 delta 仅做引用与契约声明，不重复定义检测/确认/继承规则。

## Risks / Trade-offs

- **[CLAUDE.md 被用户清理，首选读取源失效]** → 回退 `docs/toolchain.md`；两级皆无（从未 init）→ 降级检测并补写。三级路径覆盖全部情形。
- **[项目级记录与变更级快照不一致（用户在变更执行中途修正记录）]** → 快照在变更内冻结，变更内判定一律以快照为准；规则来源的更新在下一个新变更生效。这是有意为之：避免中途改变阶段集合。
- **[静默校验误报（如 monorepo 前端位于子目录、前端为独立仓库）]** → 校验冲突只触发复核请求，SHALL NOT 自动改写记录；用户可沿用记录值。校验是提示通道，不是自动决策。
- **[两处项目级记录不一致]** → 由同一轮扫描写入的机制保证；若用户手改其一，冲突时以扫描结果为准并请求裁决，收敛后两处重新一致。
- **[设计文档与 SKILL.md 措辞不同步，规则漂移]** → tasks 中列出"设计文档 → SKILL.md 同步"任务并附检索验证项；沿用既有 `scripts/validate-frontmatter.py`、`scripts/sync-references.sh` 校验链。
- **[存量已 init 项目的 `docs/toolchain.md` 存在但项目类型字段被用户删改]** → 属决策 2 的兜底路径范畴，最终由降级检测与用户确认兜住，不阻塞。

## Migration Plan

**运行方式**：三处 `SKILL.md` 的规则变更即刻生效（skill 以文件形式被消费方引用/安装）；`project-type-detection` 等 delta 在归档时合并入主 spec。

**存量项目**：

| 情形 | 行为 |
|------|------|
| 已 init 且 CLAUDE.md 含项目画像 | 首个变更创建即静默继承，无需任何操作 |
| 已 init 但 CLAUDE.md 被清理或未注入 | 回退读 `docs/toolchain.md` 头部，静默继承 |
| 从未 init（无任何项目级记录） | 首个变更创建时检测 + 确认一次 + 补写 `docs/toolchain.md`，此后静默 |
| 变更执行中途（`.status.md` 已存在） | 不受影响，快照字段与读取路径未变 |

**回滚**：还原三处 `SKILL.md` 与设计文档的相应段落即可。项目级记录中的项目类型字段为增量信息，即使回滚也无副作用（旧逻辑会重新扫描并覆盖）。

## Open Questions

- 项目级记录是否需要携带「判定依据」（如"前端在独立仓库"的说明），以便后续复核者理解记录成因。当前 spec 未要求该字段，可在实现时按需决定，不影响本设计的方法与任务划分。
