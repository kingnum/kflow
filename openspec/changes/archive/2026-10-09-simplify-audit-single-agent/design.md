# Design

## Context

动机见 `proposal.md` — Why；行为契约见本变更的 delta `specs/devflow-audit/spec.md` 与 `specs/subagent-isolation-rule/spec.md`。

影响本设计的既有状态：

- `skills/kflow-audit/SKILL.md` 现有的七维度评分表、按档位给分规则表、审计报告格式三处结构互为依据，任一维度改动都要三处同步，否则文档自相矛盾。
- front matter 的 `description` 字段内**写死了权重串**（`流程22%/产物23%/审查20%/测试15%/缺陷10%/效率5%/Post-mortem5%`）。该字段参与技能触发，改维度不同步会留下错误元数据且不报错。
- `openspec validate` 对 `MODIFIED` 块按**名称**匹配 scenario 集合：丢弃现有 scenario 会报 `omits scenario(s) the current spec still has`；scenario 级无 `RENAMED` 机制。本项目已有先例记录（`openspec/changes/archive/2026-09-29-sync-legacy-prototype-specs/design.md` D7/D8）。
- `subagent-isolation-rule` 的「隔离规则适用范围」清单未含 `kflow-audit`，但 `kflow-audit` 今天已在标准/完整档启动 4 个并行子代理——该缺口先于本变更存在。同时该 capability 未定义非执行类阶段的**重试上限**（3 次上限写在执行类子句内）。

## Goals / Non-Goals

**Goals:**

- 审计子代理数由 4 收敛为 1，且轻量档与标准/完整档共用同一个执行者模型
- 维度由 7 收敛为 4，合并切点落在证据源与判定性质的**边界**上
- 合并前后总分量纲（0-100）不变，保留总分层面的历史可比性
- 用可执行的约束替代多子代理并行的天然隔离，不使审计质量净下降
- 把 delta 机制无法表达的修改（scenario 标题、`## Purpose`）显式收口，避免夹带

**Non-Goals:**

- 不改变审计的触发方式（归档门控自动 + 手动调用）
- 不改变问题分级（阻塞 / 严重 / 建议）与判定链路
- 不改变轻量档的产物形态（3 项检查项、不评分）
- 不为 `kflow-audit` 新建 `references/repetition.md`（见 D5）
- 不修正 `subagent-isolation-rule` 中「各 Skill SKILL.md 中标注引用」与设计类 skill 实际做法（内联声明）之间的既存分歧（见 D5）

## Decisions

### D1 维度合并的切点：三条独立判据，7 → 4

维度按**证据源**与**判定性质**的边界合并，而非按权重或均衡原则合并：

| 新维度 | 权重 | 合并来源 | 合并判据 |
|--------|------|---------|---------|
| 流程与产物合规性 | 45% | 流程合规性 22% + 产物完整性 23% | 同一证据源的两个视角：同读一份 `.status.md` + 同一棵目录树 |
| 审查与缺陷闭环 | 30% | 审查质量 20% + 缺陷管理 10% | 同一判定性质的两个证据源：都判「问题 → 修复 → 闭环」，证据分别落在 `cross-reviews/` 与 `test-reports/fix-reports/` |
| 测试充分性 | 15% | 保留 | 独立证据源 + 独立的严重级判定来源，不与之重叠 |
| 效率与改进 | 10% | 效率指标 5% + Post-mortem 汇总 5% | 两个维度的门控价值均为零：从不产出阻塞/严重级问题，只喂报告「改进建议」章节 |

权重取合并来源之和（45 = 22 + 23、30 = 20 + 10、10 = 5 + 5），不重新分配。理由：重分配会引入一个无法从证据推导的新口径，而取和使合并前后的**总分**在同一量纲上可对照。

**结构性收益**：合并后的「流程与产物合规性」正好是轻量档三项检查项（阶段完整性 / 产物存在性与无占位符 / 裁剪合法性）的超集。原先审计内部同时存在「七维度」与「三项检查项」两套粒度，合并后两者成为同一维度的完整形态与简化形态，不再互相矛盾。

**备选**：7 → 5（保留「审查质量」与「缺陷管理」为两维，仅合并流程+产物、效率+Post-mortem）。否掉——两者查同一条闭环链，切分点落在链条半路，是三个方案中最不适定的。

### D2 保留加权总分

**选择**：标准/完整档继续输出 0-100 加权总分，定位为「变更健康度参考」，SHALL NOT 参与门控判定。

**理由**：权重只有在评分制存在时才有意义——取消总分会让 D1 的四个权重变成四个无落点的数字，两者不能同时成立。在此基础上保留总分是更稳的一侧：它只占评分表的一个合计行，对「简化」的边际贡献接近零；而取消会让新报告与既有归档报告在总分层面断裂。真正的简化量来自维度数与子代理数，这两项已经拿到。

**备选**：取消总分，仅输出各维度 ✅/⚠️/❌ 状态。否掉——需同时放弃 D1 的权重口径，且总分层面的历史可比性无替代。

### D3 用「证据先于评分」替代多子代理的天然隔离

**问题**：4 个并行子代理互相看不到对方结论，这是一种**未被设计声明、但客观存在**的隔离，使各维度评分不易被整体印象污染。收敛为 1 个子代理后该隔离消失。

**选择**：把约束写进规范而非留给实现自行把握——子代理 SHALL 先完成全部四个维度的事实采集、逐维度呈现判定证据，**再统一评分**，SHALL NOT 边采集边评分。已在 delta 的 ADDED 需求以 `证据先于评分` 场景固化。

**理由**：该约束可被主 Agent 在验收时直接检查（报告是否按「证据分节 → 评分表」组织、评分是否与证据一致），而抽象的「请保持客观」不可检查。它把隔离从「上下文层面的物理隔离」转为「输出结构层面的顺序隔离」，在单子代理下仍可成立。

**备选**：保留 2 个子代理（一个查流程+产物+测试，一个查审查+缺陷+效率）。否掉——未解决「维度切点」问题，且用户已明确选择单子代理。

### D4 轻量档统一由子代理执行

**选择**：轻量档由主 Agent 直连改为审计子代理执行；三项检查项、不评分、简化审计记录形态均不变。

**理由**：执行者模型统一（一套模型覆盖全部档位），且消除轻量档「主 Agent 既执行审计又判定审计」的角色重合，取得独立视角。该调整不违反 `subagent-isolation-rule` 的主 Agent 职责边界硬线——硬线只约束执行类阶段。

**代价**：轻量档多一次子代理冷启动 + RELOAD。可接受，因轻量档的 RELOAD 范围在全部档位中最小（只读 `.status.md` 与目录树，不涉及跨模块设计产物），增量模式（已验证标记）亦适用于该子代理。

### D5 隔离规则的落点：内联声明，不新建 references 文件

**选择**：`kflow-audit/SKILL.md` 在审计执行步骤内联「子代理隔离规则」简短声明（异常时新建子代理、禁止主 Agent 接管、重试上限 3 次），并同时把 `kflow-audit` 补入 `subagent-isolation-rule` 的适用范围清单。

**理由**：`kflow-design` 与 `kflow-explore` 两个同样使用子代理的**非执行类** skill 已是内联做法；为 `kflow-audit` 单独新建 `references/repetition.md` 会与这两个 skill 不一致，且该文件名绑定「重复制」语义，而审计是单次门控评估、无轮次概念。内联满足 CLAUDE.md 的自包含要求。

**已知分歧（本次不处理）**：`subagent-isolation-rule` 的「各 Skill SKILL.md 中标注引用」要求标注形式为指向该 skill 自身 `references/repetition.md` §12 的路径引用——设计类 skill 并无此文件，故该要求与设计类实践不一致。修正它会影响 `kflow-design`/`kflow-explore`，超出本变更范围。本变更只按内联形态实施 `kflow-audit`，不改该条 requirement。

**连带声明**：审计适用隔离规则与 3 次重试上限，**不适用**轮次级重试粒度（审计为单次执行，无轮次）。此点在 `subagent-isolation-rule` 的 delta 中以 `审计阶段的规则适用子集` 场景固化。

### D6 delta 无法表达的修改，收口为实施阶段显式任务

delta 机制带两处硬限制，均在本变更命中：

1. **scenario 标题不可改名**。`轻量档审计降级为轻量自检` 下的 `标准档与完整档维持七维度审计` 标题含旧口径「七维度」，正文已改为四维度。delta 内已附非规范性说明解释保留原因。
2. **既有 capability 的 `## Purpose` 只能直接编辑主规格**，delta 中的 Purpose 被忽略并告警。`devflow-audit` 主规格 Purpose 现写「六维度评估」，与新结构矛盾。

**选择**：两处残留合并为**一个实施阶段任务**，该任务同时修改主规格与 delta（保持 `openspec validate` 通过）。不拆散、不夹带在正文改写任务中。

**理由**：沿用项目先例（D8）。propose 阶段不应直写主规格；且两处修改都必须与 delta 配对才能维持校验通过，拆散会各自引入一次校验失败窗口。

### D7 被否方案

| 方案 | 否掉理由 |
|------|---------|
| 只收敛子代理数、维度不动 | 未解决维度切点问题；4 个 Agent 的分工表本身依赖七维度结构，只改执行者会留下 4 → 1 与七维度分工表的表达冲突 |
| 维度合并为 3 个（效率/Post-mortem 降为不计分的报告章节） | 总分只剩三档加权，健康度指标失去分辨力；且需同时放弃 D1 的权重口径 |
| 保留 4 个并行子代理，仅做维度合并 | 每个子代理冷启动重复 RELOAD 全量产物的开销是主要成本来源，不动它则简化量不足 |

## Risks / Trade-offs

- **[单子代理在大变更下的上下文压力]** → 完整档的大变更需单子代理读全量产物。缓解：既有 RELOAD 增量模式（已验证标记）继续适用；维度合并后报告结构更短，评分表的对比面由 7 行降为 4 行。
- **[光环效应污染分维度评分]** → 由 D3 的「证据先于评分」硬约束与报告的证据分节结构缓解；主 Agent 验收时按报告结构抽查维度得分与证据的一致性。
- **[总分历史可比性下降]** → 总分保留且量纲（0-100）不变，可比性在总分层面保留；维度层面不保留，已在 `proposal.md` 的兼容性段落显式声明。
- **[scenario 标题残留旧口径被误读为规范]** → delta 内附非规范性说明指明正文为准、标题更正收口于实施任务；D6 的实施任务以 `openspec validate` 通过为完成判据。
- **[权重串在 description 中写死，易漏改]** → 实施任务单列该项（`skills/kflow-audit/SKILL.md` 的 front matter），不并入「维度表改写」任务。
- **[维度与权重在十余处文档重复，改一处漏多处]** → 实施任务按「同一口径、分批同步」组织：`skills/kflow-audit/SKILL.md` 与镜像 `docs/designs/skills/kflow-audit.md` 为主，下游 `kflow-archive`（SKILL.md + references）、`kflow-guide`（SKILL.md + 设计文档）、`docs/designs/` 的索引与核心机制文档、模板与示例、`README.md` 为从。校验手段为全仓 `grep -rn "七维度\|六维度"` 扫描加 `scripts/validate-frontmatter.py`——`scripts/sync-references.sh` 只比对跨 skill 的同名 references 文件，不适用于本类口径同步，故不采用。
- **[审计子代理异常时无轮次可续]** → 重试语义按「整次重跑」而非「轮次续跑」，已在两个 delta 中同时声明，避免实施阶段自行发明。

## Migration Plan

1. **规格先行**：本变更 delta 已写入 `openspec/changes/simplify-audit-single-agent/specs/`，`openspec validate` 与 `--strict` 均通过。
2. **归档应用 delta**：归档时把 delta 应用到 `openspec/specs/`，主规格成为新权威。
3. **实现同步**：按 `tasks.md` 改写 `skills/kflow-audit/SKILL.md`（含 front matter 的 `description` 权重串）、`skills/kflow-archive/SKILL.md` 措辞、`docs/designs/` 下的镜像文档、模板与示例、`README.md`。
4. **残留收口**：执行 D6 的独立任务，同时修改 `openspec/specs/devflow-audit/spec.md` 的 Purpose 与 delta 中的 scenario 标题，逐次以 `openspec validate` 为判据。
5. **回滚策略**：本变更为规范与文档变更，无运行时数据迁移，回滚即 `git revert`。已归档变更的既有审计报告为七维度结构，不随本变更修改，作为历史产物保留。
