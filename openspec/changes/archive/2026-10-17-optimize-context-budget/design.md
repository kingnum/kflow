# Design

## Context

见 `proposal.md` — Why。以下仅记录塑造方案的现状事实与约束。

### 实测基线（`software-dev-agent`，100 个真实会话）

```
  主会话 cache_read        9.70 B        （15 个大会话占 60.5%）
  子代理 cache_read        8.58 B        （652 个子代理，平均 122 轮/个，最长 532 轮）
  输入侧合计              18.28 B
  output                  65.5 M        （输入 : 输出 = 292 : 1）
```

### 三处「设计要求未落实」的直接证据

| 设计要求 | 位置 | 实测偏离 |
|---------|------|---------|
| 主 Agent 职责边界硬线 | `07-agent-model.md` §15.3 / `subagent-isolation-rule` | 主 Agent 自写生产代码与测试、自跑 pytest；单会话 169~254 次 Bash、66~215 次 Edit |
| references 按阶段裁剪 | `skill-self-contained`「references content is phase-specific」 | 95 个技能文件中 600,010 字符（55.1%）为逐字节相同副本；10 份 `gates.md` 内容完全一致 |
| 仅提取当前阶段相关章节 | `phase-file-reload` | 主 Agent 全文读取 `detailed-design.md`（全库 468 次、7.35 MB 注入） |

### 约束

- **自包含强制规则**（`CLAUDE.md`）：每个 skill 的辅助规则存放在自身 `references/` 中，安装后零外部依赖。任何去重方案不得破坏这一安装期属性。
- **零用户负担**（用户裁决）：不引入 `/clear`、`/compact` 或任何需要用户记忆的新操作。
- **打包路径**：`scripts/package-skills.sh` 逐个 skill 复制 `references/`；消费者可由 `skills-lock.json` 从 `skills/` 目录直接同步。
- **主 Agent 无法自我清空上下文**：内置斜杠命令不是模型可调用的工具；子代理是唯一可编程、零用户干预的上下文隔离手段。

## Goals / Non-Goals

**Goals:**

- 把上述三处「已写明但未落实」的要求变成**可强制、可验证**的机制
- 补齐体系缺失的「上下文预算」维度：阈值、节流、度量
- 在**不增加任何用户操作**的前提下，将单变更消耗从 18.28 B 降至约 4.3 B（≈ 4.2x）
- 消除 55.1% 的逐字节副本，同时保持安装期自包含

**Non-Goals:**

- 任何形式的用户手动上下文重置
- `kflow-guide` / `kflow-resume` 的调用频次治理（属路由层问题，另案处理）
- 项目侧 `.orca` hook 造成的注入噪声治理（不在 Skill 体系范围内）
- 变更级门控矩阵本身的结构调整
- 历史变更 `.status.md` 的强制回填

## Decisions

### D-1：主 Agent 禁手采用 `PreToolUse` 工具级门控

**决定**：在目标项目 `.claude/settings.json` 注册 `PreToolUse` hook，由 hook 判定当前阶段并拒绝主 Agent 的越界调用。

**理由与备选**：

| 备选 | 评估 |
|------|------|
| SKILL.md 内的声明性约束 | ❌ **已证明无效**。该约束现行版本即为此形态，实测被明确违反 |
| `settings.json` 的 `permissions.deny` | ⚠️ **不能单独使用**。权限系统没有「按调用来源区分」的维度；即便 deny 约束子代理，它也无法实现「仅禁主 Agent、对子代理放行」。作为路径 B 的组件保留（见下） |
| 子代理 agent 定义的 `tools` / `disallowedTools` | ❌ **方向相反**。官方文档明确二者语义为**收窄**（从继承的工具集里再缩小），无法反向放开全局 deny |
| `PreToolUse` hook 拒绝 | ✅ **采用**。可读取阶段状态、拒绝结果对主 Agent 表现为可读的工具错误 |

**前提核实结论（已核实，2026-10-16）**：

原设想的前提——「`PreToolUse` 输入可区分主 Agent 与子代理」——**在官方文档层面不成立**：

- `PreToolUse` 的输入字段为 `session_id` / `transcript_path` / `cwd` / `hook_event_name` / `tool_name` / `tool_input`，**不含任何 agent 标识**；
- 仅 `SubagentStart` / `SubagentStop` 携带 `agent_id` / `agent_type`，而 `SubagentStart` **只能注入 context、不能阻断**，其注入内容也无法在 `PreToolUse` 中读回作判据；
- 官方仓库存在至少四个同类未关闭需求（#40140 / #26495 / #21481 / #36270），佐证该能力当前缺失。

**修订后的路径（按探针顺序）**：

| 路径 | 机制 | 文档状态 | 探针 |
|------|------|---------|------|
| **A** | `PreToolUse` stdin 中的 `agent_id` / `agent_type` 判别 | **未文档化**。有 issue 与第三方采用记录暗示近期版本的 tool-event stdin 可能带该字段，但不稳定、不受支持 | 探针 1：hook 原样转储 stdin，分别由主 Agent 与子代理各触发一次 `Edit` / `Bash`，比对原始 JSON |
| **B** | session 级 `permissions.deny`（禁主 Agent） + 子代理 agent 定义的 `permissionMode`（放开） | **未明确**。文档确认 `permissionMode` 存在且可按 agent 设置，但未说明它能否解除 `settings.json` 的硬性 `deny` | 探针 2：写入 `deny` 后由子代理尝试调用被禁工具，观察是否放行 |
| **C** | 仅以 `Task` / `Agent` 工具的 `PreToolUse` 拦截点管住「是否派发子代理」这一步，配合声明约束 | **文档明确支持**，但只能覆盖「启动子代理」这一个动作，管不住主 Agent 自行 `Edit` | 探针 3：验证拦截点的可达性与拒绝文案 |

**采用路径 A 时的附加要求**：因该字段未文档化，实现 SHALL 附带降级逻辑（字段缺失时按路径 B/C 或放行处理），并在实现中标注该依赖为未文档化行为、存在版本升级失效的风险。

**若 A / B / C 三条探针均不成立**：

1. 记录到 `docs/skill-suggestion.md` 并向用户报告该能力缺口（附官方 issue 编号供反馈）
2. 门控退为**不实现**，`subagent-isolation-rule` 的硬线维持声明形态，并在设计中登记为**待上游能力支持**
3. 该动作的预期收益从总量中扣除，其余动作（读取纪律、references 切片、子代理粒度、压缩阈值）不依赖本决策，照常落地

### D-2：门控的阶段判定来源为 `.status.md` 阶段字段

**决定**：hook 每次判定时读取变更级 `.status.md` 的阶段状态字段；无法判定（不在变更上下文 / 文件缺失 / 字段不可解析）时**放行**。

**理由**：阶段状态是既有单一权威源，无需新增状态。**放行为默认**——门控的目的是降低消耗，不是安全边界；误伤非变更场景（如 Skill 体系自身的维护工作）的代价高于漏放。

**备选**：由 SKILL.md 在进入阶段时写入一个标记文件 → 多一处状态同步，且与 `.status.md` 存在不一致风险，弃用。

### D-3：references 切片 + `sync-references.sh` 由校验升级为生成

**决定**：共享 references 文件按阶段切片后分发到各 skill；`scripts/sync-references.sh` 由「校验一致性」升级为「**从切片结果生成并校验**」。

**理由**：直接原因——`skill-self-contained` 已要求按阶段裁剪，实测未落实；落实后各 skill 副本自然分化，55.1% 的逐字节副本消失。

**自包含约束的满足方式**：

```
  开发期（源码仓库）                    安装期（消费者项目）
  ┌──────────────────────────┐         ┌──────────────────────────┐
  │ 各 skill 的 references/   │         │ .claude/skills/kflow-*/  │
  │ 均为「已切片的完整副本」   │  打包   │ references/*.md          │
  │ ← sync-references.sh 生成 │ ──────> │ ← 与各 skill 目录逐字节相同│
  └──────────────────────────┘         └──────────────────────────┘
         ↑ 权威源在此                    ↑ 零外部依赖，规则不变
```

生成的产物**就是**各 skill 目录下的真实文件，因此 `package-skills.sh` 无需改动，安装后仍是完整副本。

**备选**：新增 `kflow-shared/` 共享目录 → ❌ 直接违反 `skill-self-contained` 与 `layered-context-loading` 中「SHALL NOT 引用任何跨 skill 共享目录」的既有要求。

### D-4：子代理粒度以「工作量上限」表述，而非「轮数上限」

**决定**：约束表述为「单个子代理 SHALL NOT 承担超过 3 个功能点或 10 个 TDD 步骤」。

**理由**：`agent-iteration-execution` 与各 `repetition.md` §10 明确将「任何轮数上限数值」列为 prompt **禁止项**（原意图是禁止「为凑轮次而跑」）。**约束对象换成工作量**即可在不违反既有禁止项的前提下拿到同一效果——subagent 的成本 ≈ 轮次数 × 平均上下文，而工作量分片同时压缩这两个因子。

```
  单个子代理 T 轮、上下文峰值 Cmax：
    现有成本   ≈ T × Cmax/2
    拆为 k 片  ≈ T × (20k + (Cmax-20k)/k) / 2
    k=4, Cmax=440k  →  降幅约 3.5x
```

固定开销（每片子代理冷启动约 20k）远小于收益，不构成反例。

### D-5：阶段边界节流通过子代理承接实现，不引入 `/clear`

**决定**：阶段收尾时主 Agent 落盘交接摘要；下一阶段的主工作由子代理以独立上下文承接。

**理由**：

| 方案 | Token 收益 | 用户干预 | 结论 |
|------|-----------|---------|------|
| 每阶段手动 `/clear` + SessionStart hook 注入交接摘要 | ~6x（理论） | 12 次/变更 | ❌ 违反零用户负担；且依赖两处已知 bug（`SessionStart(compact)` 不注入 #28305、`/clear` 不触发 SessionStart #28692） |
| **子代理承接阶段（本方案）** | ~5x | 0 | ✅ 采用 |
| 仅调低 `autoCompactWindow` | ~1.5x | 0 | 保留为叠加项 |

实测分段测算支持该结论：把全流程会话按阶段切段、各段从 30k 起步，10 个大会话的平均降幅为 **4.2x**（最好 6.0x，最差 2.7x）。

**附带收益**：`/clear` 只能在阶段边界切分；子代理可在**任意粒度**隔离（实测已出现深度 2 的嵌套子代理 121 个）。

### D-6：`.status.md` 分层为「当前状态 + 历史日志」

**决定**：`.status.md` 仅承载当前有效状态（约束 100 行以内）；历史记录移入 `status-log.md`，仅在恢复与审计场景读取。

**理由**：`.status.md` 是状态机，每阶段每轮都要读；实测全库被读取 297 次、累计注入 3.49 MB。其当前位置同时承载当前状态与全量历史，随变更推进单调增长。

**兼容**：读取侧兼容未分层的既有 `.status.md`；不回填历史变更。

### D-7：`autoCompactWindow` 取 300000

**决定**：kflow-init 在 `.claude/settings.json` 写入 `autoCompactWindow: 300000`。

**理由**：实测会话在 900k~1,046k 才触发自动压缩，压缩后回落到 ~100k 又继续增长——**同一份工作被做了两遍**（`8d6480d8`: 894k→97k、`edcfff4b`: 797k→150k、`8d661a0f`: 788k→99k、`dbbc7cfb`: 744k→107k）。提前到 300k 可削减压缩前的高基数轮次。

**备选**：关闭自动压缩 → ❌ 无官方支持的关闭方式（issue #42817），且方向相反。

### D-8：无效引用条目直接移除

**决定**：从子代理 prompt 的引用加载清单中移除两条实测未执行的条目——子代理读自身 `SKILL.md`（点名 40 次、执行 **0** 次）、`tdd-checklist.md`（执行率 **50%**）。

**理由**：实测各 references 条目的执行率为 80~100%，唯独这两条显著偏离。要求一个子代理读取其自身阶段的 SKILL.md 在语义上冗余（其 prompt 已由主 Agent 按该 SKILL.md 构造）。

### D-9：门控脚本的实现约定

**决定**：门控脚本按以下约定实现，避免依赖已废弃写法与不稳定的工作目录。

| 项 | 约定 | 依据 |
|----|------|------|
| 拒绝输出 | `hookSpecificOutput.permissionDecision: "deny"` + `permissionDecisionReason`；`hookEventName` **必填** | 顶层 `decision: "block"` 已标记废弃；漏 `hookEventName` 会导致判定不被采纳 |
| 拒绝文案 | 写入 `permissionDecisionReason`——`deny` 的理由会回传给主 Agent，作为其改派子代理的指导；`allow` / `ask` 的理由仅对用户可见 | 官方文档 |
| 路径解析 | 以 `$CLAUDE_PROJECT_DIR` 或 stdin 的 `cwd` 字段解析项目根，SHALL NOT 依赖 hook 进程的工作目录 | hook 进程 cwd 的官方定义不明确 |
| 超时 | hook 项显式设置 `timeout`（单位：秒）；门控只做本地文件读取与模式匹配，取较小值即可 | 多数事件默认为 600 秒，`UserPromptSubmit` 为 30 秒 |
| 匹配范围 | 用 hook 项的 matcher 限定到 `Edit` / `Write` / `Bash`，避免每次工具调用都启动进程 | 官方文档 |

### D-10：`.status.md` 阶段字段缺失时的判定优先级

**决定**：门控判定按「`.status.md` 阶段字段 → 放行」的固定优先级，SHALL NOT 引入任何猜测性回退（如从目录名、从 `docs/changes/index.md` 推断阶段）。

**理由**：`docs/changes/index.md` 中的「当前阶段」列与实际 `.status.md` 存在不一致的历史记录（实测 `index.md` 的活跃表含手写阶段描述），以它为判据会引入误伤。放行的代价仅是漏掉一次门控，误伤的代价是打断正常流程。

### D-11：修订记录头部保留 3 条，历史按层级承载

**决定**：文档头部保留最近 **3 条**修订记录；超出部分按层级移入历史承载位置——变更级产物移入该变更目录下的 `revision-history.md`，产品级文档移入 `docs/designs/changelog.md`。

**理由：写侧与读侧的需求不匹配。**

```
  写侧（02-directory-structure.md:359）      读侧（09-phase-hooks.md:227）
  「修订记录强制：每次增补必须                「重读 functional-designs/
    更新版本号和修订记录」                      index.md 获取【最新】修订记录」
        │                                          │
        └──────── 全设计文档中无任何 ───────────────┘
                  留存边界规定
                       ↓
        实测：functional-designs/index.md 的修订记录占全文 54.6%
              CONTEXT.md 占 46.7% / docs/changes/index.md 占 42.4%
```

**3 条的取值依据**：读取侧的判定需求是「判断该文档在本阶段之前是否发生了修订」——当前版本号 + 最近两次修订已足以支撑该判定，且能覆盖常见的「上一次改了什么」追问。再多即属历史追溯，应由历史承载位置承担。

**备选**：
- 保留 1 条 → 无法回答「上上次改了什么」，在连续修订场景下会迫使读取历史文件，反而增加读取
- 保留 5~10 条 → 收益递减，实测多数文件的修订频率不支持这么长的窗口

**与 `status-file-layering` 的口径一致性**：D-6 处理状态文件的阶段记录，D-11 处理产物文档的修订记录，二者遵循同一原则——**当前有效信息留在头部，历史移入独立文件且不参与常规读取**。

### D-12：产品级文档按体积两档处理（30 KB 索引 / 80 KB 拆分）

**决定**：产品级文档（`CONTEXT.md`、`docs/designs/**`、`docs/open/**`）超过 **30 KB** 提供章节索引，超过 **80 KB** 拆分为目录化结构。

**理由**：

```
  实测产品级文档体积分布：
    软件开发数字人开放集成指南.md   182.0 KB  → 超 80 KB，拆分
    design-prompt.md              152.9 KB  → 超 80 KB，拆分
    nfr-baseline.md                88.1 KB  → 超 80 KB，拆分
    data-model.md                  81.4 KB  → 超 80 KB，拆分
    error-handling.md              72.7 KB  → 超 30 KB，建索引
    api-catalog.md                 65.1 KB  → 超 30 KB，建索引
    CONTEXT.md                     64.0 KB  → 术语表例外，建索引

  阈值取值参考：实测子代理加载 46 KB 的 references 时有约 85% 内容与本阶段无关，
  该量级已被判定为需要切分；故 30 KB 作为「需要索引定位」的门槛，
  80 KB 作为「单文件已不适合整体读取」的门槛。
```

**备选**：沿用既有 `large-doc-splitting` 的**条目数**触发（>30 条目）→ ❌ 产品级文档多为叙述性内容，无稳定条目计数；体积是唯一通用且可机器判定的维度。

**术语表例外**：`CONTEXT.md` 的读取模式是「按术语名随机查询」，拆分会破坏随机查询能力。保持单文件 + 按模块/首字母索引，读取侧按索引定位区间。

### D-13：存量优化入口采用独立 Skill，与自动机制三层分工

**决定**：新增 `kflow-doc-optimize`（独立维护 Skill，非流程阶段）作为**存量文档**的优化入口；新变更产生的文档由**归档合并步骤自动**遵守留存边界，不需要用户操作。

**三层分工**：

```
  ① 规范层   —— 定义「该写什么、保留多少」       写进 docs/designs/ 与各模板
                          ↓
  ② 自动层   —— 归档设计合并步骤执行裁剪、       archive-design-merge 能力
                索引维护与拆分触发                用户零操作（新文档不再膨胀）
                          ↓
  ③ 存量层   —— 对已生成的文档执行一次性优化     kflow-doc-optimize Skill
                扫描 → 清单 → 用户确认 → 执行      需要显式触发
                → 引用校验 → 报告
```

**为什么新增 Skill 而不是扩展 `kflow-verify`**：

| 维度 | `kflow-verify` | 本需求 |
|------|---------------|--------|
| 作用域 | **变更级**——读 `.status.md`、七维度针对该变更的产物 | **项目级**——`CONTEXT.md`、`docs/designs/**` 等产品级文档 |
| 修复目标 | 路由到对应阶段的 REVISION 模式 | 就地搬移与拆分，不触发阶段 |
| 触发前提 | 存在变更 | 可无活跃变更 |

**为什么沿用「独立 Skill（非流程阶段）」这一形态**：该形态已由 `kflow-verify` 与 `kflow-bug-triage` 建立，具备「可随时手动调用 + guide 关键词路由 + 不写入阶段状态」的既定模式，新增同类 Skill 是体系内既有模式的延续。

**关键约束**：该 Skill SHALL 仅搬移、拆分与建索引，SHALL NOT 改写文档实质内容；且执行前须经用户确认执行范围。

## Risks / Trade-offs

- **[`PreToolUse` 无法区分主 Agent 与子代理（已核实）] →** 已修订为路径 A/B/C 三选一，以三条实测探针定夺；三条均不成立时门控退为不实现，其余四个动作不依赖本决策，照常落地。
- **[门控误伤非变更场景] →** 无法判定当前阶段时一律放行；白名单覆盖状态文件与 skill-suggestion；主 Agent 保留 Read/Grep/只读 Bash。
- **[切片引入规则漂移] →** 生成脚本 + 校验作为阻断式门控（非零退出码），并由 `validate-injection-scope.sh` 一并在打包前拦截。
- **[切片边界争议：一条规则同时适用于多个阶段] →** 切片规则按「规则的作用对象阶段」归属；跨阶段通用规则（如门控标注约定）进入所有相关 skill 的切片。若某规则确实无法归属单一阶段，保留其全量形态并在设计中登记。
- **[子代理分片增加冷启动开销] →** 量化对比（见 D-4）显示收益约为开销的 10 倍以上；且分片后单片上下文的峰值显著低于未分片。
- **[`.status.md` 分层打断既有读取路径] →** 读取侧兼容单文件形态；新结构自新建变更起适用，不强制回填。
- **[`autoCompactWindow` 在第三方模型中转环境下行为未验证] →** 该项作为独立可回滚的配置先落地，单独验证后再推进其他项。
- **[修订记录移出导致追溯不便] →** 历史承载位置保留全部字段且可按版本检索；此项为**搬移**而非删除，可随时查阅。若某项目确有高频版本追溯需求，保留条数可就地调高（规则允许项目级覆盖）。
- **[产品级文档拆分打断既有引用] →** 拆分动作内 MUST 同步更新全部引用（项目文档 / Skill 规则 / 脚本），校验未通过时停止而非静默通过；拆分前先产出受影响引用清单，随优化清单一同提交用户确认。
- **[拆分 `CONTEXT.md` 破坏术语随机查询] →** 已例外处理（D-12）——保持单文件，改为提供按模块/首字母的术语索引。
- **[`kflow-doc-optimize` 误改文档实质内容] →** 该 Skill 的能力约束明确限定为「仅搬移、拆分与建索引」；执行后以体积变化与引用校验作为可观测证据，正文改写不在允许动作内。
- **[存量优化一次性动作被反复触发] →** 该 Skill 在扫描阶段识别「已符合边界」的文档并排除，重复执行时清单为空即报告「无需优化」，不产生副作用。

## Migration Plan

实现顺序按「低风险可独立验证」到「高风险跨文件」推进：

```
  ① 配置项（D-7）              独立、可回滚，先落地并单独验证
  ② 脚本（D-3）                sync-references.sh 升级；此时尚无切片，行为等价
  ③ 规范层（写侧）              docs/designs/ 机制文档 + 全部产出文档模板的留存边界说明
  ④ references 切片（D-3）      按阶段逐个 skill 切片，一次一个阶段
  ⑤ 读取纪律（D-6 + D-11 + 按需分片）  规范 + skill 同步
  ⑥ 子代理粒度（D-4）           规范 + 各 repetition.md 同步
  ⑦ 自动机制（D-11）           archive-design-merge 的合并步骤补入裁剪、索引维护与拆分触发
  ⑧ 存量入口（D-13）           新建 kflow-doc-optimize Skill + kflow-guide 路由
  ⑨ 门控（D-1/D-2）            前提核实后实施，最后落地
  ⑩ 存量文档优化（D-13）        在 software-dev-agent 上执行一次，产出优化报告
  ⑪ 端到端验证                 跑一个真实变更做前后对比
```

**①②③④⑤⑥⑦⑧** 为体系侧改动，可独立验证；**⑩** 是对实战项目存量文档的一次性迁移，须在体系侧全部落地后执行（否则优化完又会被旧规则写回）；**⑨** 与其余动作无依赖，可并行。

**回滚**：①移除 `settings.json` 中的 `autoCompactWindow` 与 hook 注册即可；②③④⑤⑥⑦⑧⑨为文档与文本改动，按 git 回退；④ 的切片可整体还原为原副本；**⑩ 的存量优化不可自动回滚**，故其执行前须产出受影响引用清单并留档，必要时按该清单反向还原。
