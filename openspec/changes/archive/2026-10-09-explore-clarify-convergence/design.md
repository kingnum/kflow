# Design

## Context

动机见 `proposal.md - Why`。影响本方案的约束：

- **自包含**：`skill-self-contained` 要求安装后零外部依赖，跨技能引用仅限 KFlow 自有脚本或 KFlow 自有单属主规则文件。因此本方案的所有规则须落在 `kflow-explore/references/` 内，且 SHALL NOT 引入任何外部技能引用。
- **既有结构**：kflow-explore 的 CLARIFY 已有五个内容域（页面结构/菜单、可执行操作、表单项、业务规则、业务流程）与 `CONTEXT.md` 管理流程；越界处理规则已允许以「待补充」标记继续流转。
- **既有自审**：explore 自审检查产物的完整性/闭环性/必要性/清晰性，**不检查歧义是否已被消解**——本方案补的正是这一层。
- **内容克制的既有先例**：`self-review-dimensions.md` 已有「SHALL NOT 新增功能（非必要不增加新功能）」；本方案把它从产物自审延伸到需求探索。
- **结构性章节的既有约束**：`functional-design-content` 规定「无关联配置项时 SHALL NOT 省略该章节」。新规则必须与之显式划清边界。

## Goals / Non-Goals

**Goals：**

- 让「需求是否已澄清充分」成为**可判定**的命题（清单为空或已显式降级）
- 限定消歧手段，阻止「用内容堆砌冒充澄清」
- 把已存在的 `CONTEXT.md` 格式权威收回 KFlow 自有 references

**Non-Goals：**

- 不改 explore 的五个内容域清单本身，不改自审维度
- 不按变更档位分级门槛（理由见 D2）
- 不重排 CLARIFY → SPLIT → TIER → RELATE 的步骤顺序
- 不修 ADR 一侧的外部依赖（属 `kflow-design`/归档，另立变更）
- 不新增独立产物文件，不新增步骤编号

## Decisions

### D1 硬门 + 客观门槛（未决问题清单 = ∅），而非用户口头确认

出口条件是「清单为空或每项已显式降级」，是一个**可判定的状态**，而不是「用户说理解一致了」。

- **替代方案 A（软警告 + 仅记录）**：保留 AFK，但收敛无强制力，与目标「需求探索更加明确」相背。否决。
- **替代方案 B（硬门 + 要求用户显式确认）**：语义最强，但 explore 变成每次都必须等用户回应，AFK 能力丧失。否决。
- **选定**：门槛客观化——事实项自动解析、决策项才需用户答，交互量由**真实歧义**决定。

### D2 不做档位分级

门槛强度由歧义自调节：歧义多则清单长、耗时长；无歧义的简单需求清单短、近乎零成本。按档位再造多套澄清深度属于「非必要的设计」，故不引入。**这一决策直接消掉了原先规划中的「按档位分级」选项。**

### D3 消歧路径限定 + 反堆砌：明确度与复杂度正交

```
  明确度 = 歧义量                复杂度 = 内容量
  ────────────────              ────────────────
  未决清单长度 → 门槛管这里      功能设计内容 → 门槛不管,但设上限
  → 必须归零                     → 不得为消歧而扩增
```

界线规则：**不得以扩增功能设计内容（新增功能点、字段、章节、分支）来消歧**。歧义「能否中途取消」应通过提问收敛为「可以/不可以」一个确定答案，而不是新增取消流程章节 + 3 个字段把三种可能都覆盖——后者同时违反「明确」（仍留多可能）与「不过度复杂化」（抬高内容量）。

### D4 提问纪律：事实项与决策项分流

可查证的事实项（代码库、配置、既有文档）自动解析，不占用用户注意力；仅决策项提交用户，且一次一项。这是 D1「门槛客观化」得以不牺牲明确度的前提。

### D5 未决清单的落点 = 变更级 `.status.md`

不新增独立文件、不新增步骤编号——清单作为 CLARIFY 的工作记录写入 `.status.md`，降级项同样留痕于此。符合「非必要的设计不要有」。

### D6 依赖序遍历不重排步骤

不把 RELATE 前移，仅落为 **CLARIFY 内部的提问顺序纪律**：先定前提需求，再问依赖它的细节。拿到依赖序遍历的收益（避免前置未定导致返工），不动流程骨架。

### D7 CONTEXT.md 格式权威内部化

`domain-glossary` 的格式权威改为 `kflow-explore/references/context-template.md`（该文件已存在）。同时全变更**零外部技能引用**——机制原生实现，依据 `skill-self-contained`。

## Risks / Trade-offs

- **[空清单造假：直接置空即通过]** → 规格已要求清单候选**必须由五个内容域逐域遍历产生**，清单为空时须说明五域均已遍历且未发现歧义；实现层在 references 中给出候选生成规则。
- **[降级滥用：把难项一律降级为 `待补充`]** → 降级须记录理由与责任阶段并留痕于 `.status.md`，审计维度可核查；降级语义**复用既有「待补充」标记**，不引入第二套标记，避免双重语义。
- **[与 CLAUDE.md「文档禁止占位符」的张力]** → `待补充` 属显式降级标记（有理由、有责任阶段），不同于无理由的 TODO/TBD 占位符；实现层须在 references 中写明二者区别。
- **[与「结构性章节不得省略」冲突]** → 规格文本已显式排除：新规则约束的是「不得为消歧而新增内容」，不影响结构性章节在无内容时按既有规则标注「无」。
- **[硬门增加交互次数]** → 交互量由真实歧义驱动；无歧义需求近乎零成本。
- **[ADR 一侧的外部依赖未修]** → 本变更只修 `domain-glossary` 一侧；`adr-records` 的同类依赖须另立变更，否则自包含原则仍被违反。已在 proposal 中记录。

## Migration Plan

1. **规格层**：本变更 delta（新增 `requirement-clarification`，修改 `domain-glossary`），归档时应用。
2. **规则层**：在 `skills/kflow-explore/references/` 新增承载收敛门的规则文件；`context-template.md` 明确为 CONTEXT.md 格式唯一权威。
3. **实现层**：同步 `skills/kflow-explore/SKILL.md` 步骤 6 / 步骤 7 前置条件 / 越界处理表述。
4. **文档层**：同步 `docs/designs/skills/kflow-explore.md`。
5. **核验层**：全仓校验零外部技能引用、格式权威路径可解析。
6. **回滚策略**：纯文档/规格级变更，无运行时状态；回滚 = 还原上述文件。

## Open Questions

- 未决问题清单在 `.status.md` 中的具体呈现形态（表格 vs 列表 vs 子章节）留待实现层决定——不影响规格语义、方案或任务拆分。实现层选定为「变更级 `.status.md` 中 CLARIFY 工作记录区」，呈现形态不限。

### 6.2 样例一：有歧义需求 —— 收敛门在 SPLIT 之前阻塞

**构造需求**：「在订单列表页增加批量导出功能」（功能需求级）

**五个内容域逐域遍历产生的候选**：

| 内容域 | 候选 | 类别 | 初始状态 |
|--------|------|------|---------|
| 页面结构/菜单 | 导出入口放置位置（工具栏 / 行内 / 更多菜单） | 决策项 | 未处理 |
| 可执行操作 | 触发方式 | 事实项 | 未处理 |
| 表单项 | 无表单 | — | 无候选 |
| 业务规则 | 导出范围（当前页选中行 / 全部筛选结果 / 全部订单） | 决策项 | 未处理 |
| 业务流程 | 导出完成后的反馈方式 | 事实项 | 未处理 |

**走查结论**：

1. 两个决策项（入口位置、导出范围）未处理 → 按 SKILL.md 步骤 7 前置条件，SHALL NOT 进入 SPLIT。**门在 SPLIT 之前阻塞，符合规格 Scenario「清单非空时阻塞」。**
2. 两个事实项经路径 (c) 自行查证消解——触发方式与既有批量操作一致、导出反馈与既有导出流程一致，**未占用用户注意力**，符合「提问纪律」。
3. 两个决策项按「一次只提交一项」逐个提问，先问入口位置（前提），再问导出范围（依赖前者的细节），符合「依赖序遍历」。每次取得单一确定答案后该项标记为已消解。
4. 两项消解后清单为空 → 放行进入 SPLIT。
5. **反例校验**：若改用「新增导出配置页 + 3 个字段把三种范围全覆盖」来规避提问，则命中「消歧路径限定」——该手段 SHALL NOT 被视为有效消解。

### 6.3 样例二：无歧义需求 —— 清单为空、近乎零额外交互

**构造需求**：「修复订单列表分页在第 2 页点击后跳回第 1 页的缺陷」（功能缺陷级，轻量档）

**五个内容域逐域遍历结果**：

| 内容域 | 遍历结论 | 是否产生候选 |
|--------|---------|------------|
| 页面结构/菜单 | 不涉及页面与菜单变更 | 否 |
| 可执行操作 | 点击页码后保持当前页码，行为唯一确定 | 否 |
| 表单项 | 不涉及表单 | 否 |
| 业务规则 | 分页保持当前页码、数据按页返回，规则唯一确定 | 否 |
| 业务流程 | 「翻页 → 保持页码」闭环唯一确定 | 否 |

**走查结论**：

1. 清单为空，且已附「五个内容域均已遍历且未发现歧义」说明——该说明是空清单的合法凭据，符合规格 Scenario「清单候选来源覆盖澄清内容域」的反造假要求。
2. 未触发任何决策项提问，额外交互次数为 **0**，验证「门槛强度由真实歧义量自调节、无歧义需求近乎零成本」。
3. 直接放行进入 SPLIT，验证收敛门**未**给简单需求增加负担。

### 6.4 样例三：降级路径 —— `待补充` + 理由 + 责任阶段后放行

**构造需求**：「用户中心增加第三方登录」（功能需求级）

**歧义项**：是否支持微信登录

**走查结论**：

1. 该项经五域遍历产生候选，判定为决策项，但**本阶段无法消解**——微信开放平台资质与 AppID 归属需业务方对外协调，explore 阶段无从取得答案。
2. 按步骤 6c 作显式降级，写入变更级 `.status.md` 的 CLARIFY 未决问题清单：

   | 项 | 状态 | 降级理由 | 责任阶段 |
   |----|------|---------|---------|
   | 是否支持微信登录 | `待补充` | 微信开放平台资质与 AppID 归属未确定，需业务方对外协调后方可决策 | 详细设计（`kflow-design`）——接口定义前须确认 |

3. 降级项**不阻塞**进入 SPLIT，符合规格 Scenario「显式降级放行」。
4. 记录落在 `.status.md` 且可被后续阶段读取，符合规格 Scenario「降级项留痕」。
5. 同一表述与「越界处理」段落对齐：产物中的 `待补充` 与本降级记录为同一语义，且均附降级理由与责任阶段——**未退化为 TODO/TBD 占位符**，与 CLAUDE.md「文档禁止占位符」不冲突。
