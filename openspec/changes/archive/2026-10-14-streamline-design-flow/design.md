# Design

## Context

参见 `proposal.md` — Why。

设计前需要交代三项现状约束，它们决定了本次方案的边界：

**约束 1：上个变更刚刚反转了终止模型。** `2026-10-14` 归档的 `converge-review-termination` 把「收敛为唯一成功终止条件、删除轮数上限」设为权威模型，并据此移除了三项能力：`tier-driven-repetition`（档位→轮次映射）与 `recheck-round`（终止前复检轮）被 retire，`convergence-driven-repetition` 被全量重写。本次变更**直接反转该方向**，需要一并处理这批遗留的「禁止项」表述（例如 `execution-repetition-mode` 与 `flexible-repetition-mode` 中「SHALL NOT append a recheck round」的条款）。

**约束 2：`recheck-round` 与本次的「定向重验」是不同语义，不得混用命名。** `recheck-round` 指审查循环到达终止点后追加的复核轮（因依赖已废除的轮数上限而被移除）；本次的「定向重验」指测试阶段修复后仅重跑失败用例。二者在触发时机、输入、输出上均不同，但名称近似，规范中必须显式区分。

**约束 3：自审与交叉审查的职责边界已在既有设计中确立。** 现行 `skills/kflow-design/references/self-review.md` §6 明确写着「真正的独立验证留给四视角交叉审查」——即 SELFREV 本就只承担「自我完善」，独立验证由 REVIEW 承担。本次把 SELFREV 降为单轮，并不削弱独立验证能力，只是让它回到设计意图。这是方案成立的**前提性事实**，不是新增假设。

## Goals / Non-Goals

**Goals:**

- 把设计链路（explore / prototype / design / plan）与测试三阶段（api / e2e / integration）的审查轮次从「无界、由产物质量偶然决定」变为「固定、可预算」，同时**不减少任何设计文档产出**
- 把质量保证从「审查阶段发现问题」前移到「写作阶段保证质量」，通过签署清单把抽象维度落为可核对的具体锚点
- 使审计从「第三遍审查」回到「封账 + 兜底」，消除与自审/交叉审查的语义重叠
- 建立可支撑后续优化的阶段耗时数据源与跨变更趋势回流

**Non-Goals:**

- 不删除或压缩任何设计产出（functional-designs、detailed-design、原型、api-tests、e2e-tests、traceability 全部保留）
- 不削弱交叉审查（design 阶段四视角 / 两视角 / 单 Agent 的档位映射不变）
- 不改动编码与代码审查的重复制循环
- 不改动代码审查的闭环重审机制（留待计时数据积累后评估）
- 不引入缺陷修复快车道（后续独立变更）
- 不改动阶段集合、阶段门控、子变更划分、回退机制等流程骨架

## Decisions

### D1：自审终止模型——单轮验证取代收敛循环

**选择**：设计类与计划阶段的自审固定为「主 Agent 签署自证（零子代理）→ 1 轮独立子代理验证 → 主 Agent 统一修复」。删除见证轮四判据、不收敛判定、轮间摘要注入、累积未复核修复清单。

**为什么**：问题根因不是自审慢，是**自审没有终点**。在「全量遍历 4 维度、主动找问题」的审查语义下，见证轮条件 (a)「零新发现」结构性倾向于永不满足——审查者只要找到一个改进点，循环就继续。删掉轮数上限把这个风险从「有界浪费」放大为「无界」。单轮化把轮次从「不可预测」变成「固定 1 轮」，同时把质量责任前移到写作。

**备选方案**：

| 方案 | 否决理由 |
|------|---------|
| 保留收敛循环 + 加轮数上限（轻量 1 / 标准 2 / 完整 3） | 回到 v1.3.0 之前模型，改动面最小，但「上限即止」意味着产物可能带着已知问题交付；且上限仍是「试出来的数」，不同阶段最优上限不同，无法一次定准 |
| 完全取消 SELFREV，只留交叉审查 | 改动最大但收益未必最高——交叉审查本身也要给所有产物配视角 agent，去掉 SELFREV 后交叉审查变成「首审」，其成本会反向膨胀；且轻量档交叉审查仅单 Agent，失去全部前置过滤 |
| **单轮验证 + 签署清单（选中）** | 成本固定且最低；质量通过签署清单前移；与既有「独立验证交给交叉审查」的设计意图一致 |

### D2：签署清单——证据锚点是硬性要求

**选择**：每个 4 维度签署项必须具备「维度 / 自证结论 / 证据锚点」三列，锚点必须指向产物内的具体位置（章节号、条目 ID、用例 ID）。锚点为空或指向不存在内容时，该维度签署**不成立**。

**为什么**：维度是抽象的（「闭环性 ✓」毫无约束力）。不给锚点要求，签署清单会在第一次使用时就退化成打勾游戏，单轮验证随即失去价值。锚点要求把「高质量产出」从口号变成写作时必须填出的可核对内容——**清单本身成为写作质量的驱动力**，这是把质量前移的落地机制。

**清单落点**：写在各阶段产物模板中（而非独立文件），使签署成为写作动作的一部分。这同时满足「设计产出不减少」——签署区是模板的增量，不是新增文档。

### D3：验证子代理执行契约——先独立遍历，后打假

**选择**：验证子代理的执行顺序强制为：

```
1. 独立遍历产物 → 形成自己的 4 维度结论      ← 此阶段 SHALL NOT 读签署清单
2. 逐项对照签署清单 → 打假                   ← 锚点为空 / 指向不存在内容 = 签署不成立
3. 输出 { 独立发现 | 签署打假结果 | 全量遍历证明 }
4. SHALL NOT 修改产物（只报告）
```

**为什么（步骤 1 的顺序）**：验证子代理若先读签署清单，会被一份已写好结论的文档锚定，退化为「回填证据」而非独立审查。把独立遍历前置，才能让「单轮」兼具独立发现能力。

**为什么（步骤 4 的分离）**：现行机制是「边审边修」，这会造成修复与审查在同一轮内交织，进而产生「修复引入新问题」的振荡——而振荡正是 v2.0.0 必须引入「不收敛判定」的原因。单轮下改为**审查者与修复者分离**，主 Agent 一次性统一修复，振荡源从机制上消失。

### D4：单轮验证后不再追加确认轮，修复产物直接交付下游

**选择**：验证子代理报告问题 → 主 Agent 统一修复 → 生成「本阶段修复清单」→ 随产物交付交叉审查（设计类）或下游阶段。**不追加确认轮。**

**为什么**：追加确认轮会让无界风险复现。且自上而下的验证本就在交叉审查——**让交叉审查拿着「已知修复清单」去验，比让自审自己盖章更有信息量**。这与约束 3（独立验证归交叉审查）一致。

**L4 测试阶段的对应形态**：测试三阶段单轮执行后若发现失败项，走「定向重验」（仅重跑失败用例，有界），不重跑全量。注意与已移除的 `recheck-round` 区分（见约束 2）。

### D5：审计降级为记账员——保留阻塞兜底

**选择**：删除四维度加权评分，改为四项职责：

```
1. 校验各阶段门控是否全部通过（读 .status.md）   → 不通过 = 阻塞
2. 校验 traceability 覆盖率与产物存在性          → 缺项 = 阻塞
3. 汇总各阶段耗时数据 → 输出效率摘要              → 信息
4. 兜底：扫出未被前序环节关闭的阻塞级问题          → 有问题 = 阻塞
```

**为什么**：审计四维度中，「流程与产物合规性」（45%）与各阶段产物完整性门控重复，「审查与缺陷闭环」（30%）与 SELFREV + REVIEW 的闭环验证重复，「测试充分性」（15%）与 traceability 覆盖率门控重复。只有「效率与改进」（10%）是真新增。审计本质是**第三次读同一批产物**。

**为什么保留职责 4**：审计失去质量评审权后，必须回答「最后谁为质量兜底」。完整性链为：签署清单（写作）→ 单轮验证（打假）→ 交叉审查（独立审查）→ 编码/审查/测试循环（实现层）→ 审计阻塞兜底。审计不再评分，但保留对阻塞级问题的拦截权，作为最后一道哨兵。

### D6：变更档位统一按影响范围分数——让轻量档真的敏捷

**选择**：删除「产品需求 → 完整档」硬映射，产品需求与功能需求、功能缺陷统一走影响范围分数映射。

**为什么**：「产品需求」是**业务视角的分类**，不该直接决定**审查强度**。一个 5 个功能点的产品需求小迭代，当前被迫享受四视角审查 + 每维度评分 > 8 的完整档待遇。这正是「任务耗费时间比 openspec 长很多」在档位层面的来源。

**安全阀保留**：kflow-design 的 DIVIDE 之后仍可复核升档（仅升不降）。设计阶段能看到完整影响范围，若分数确实高，仍会升到完整档——**不会漏审**。

### D7：测试三阶段单轮化，编码与代码审查保留重复制

**选择**：接口单元测试 / E2E 测试 / 集成测试改为单轮全面执行 + 定向重验；编码与代码审查的重复制循环不动。

**为什么（区分标准）**：判断「某阶段该不该多轮」的标准是**该阶段的工作是否存在真实的逐轮增量**。测试阶段的多轮通常只是在重复执行已覆盖的用例（成本真实、增量不真实）；编码阶段每轮确实在推进新工作项（增量真实）。按此标准切分，而不是按「设计类 / 执行类」的现有分类切分。

### D8：耗时遥测——两区结构 + 自动标注 + 趋势回流

**选择**：

- `.status.md` 新增「阶段耗时与轮次统计」区（阶段 × 开始 / 结束 / 耗时 / 子代理轮次 / 执行方式）
- 新增「阶段内事件计时」区，仅在触发阈值时展开（某阶段耗时占比 > 40% 或子代理轮次超阈值）
- 归档时将计时摘要回流至 `docs/skill-suggestion.md`

**为什么需要「自动标注」**：只记录不标注，数据仍需人工分析，无法支撑持续优化。触发阈值让数据自己浮现瓶颈。

**为什么需要「回流」**：单次变更的耗时数据说明不了趋势。跨变更回流后积累 5~10 条，才能回答「哪个阶段在恶化、本次改造是否见效」。这是让体系自我优化的飞轮——**先测量，再优化**，也正是本次不贸然改动代码审查闭环重审的原因。

### D9：历史兼容——读取侧归并，不做迁移

**选择**：

- 终止结果字段：历史 `.status.md` 中的 `收敛` 读作 `验证通过`，其余读作 `验证发现问题`
- 自审报告：历史多份时间戳报告不做迁移，读取侧按「目录下至少一份报告存在」判定
- 档位字段缺失时按 `完整` 档处理的既有规则不变

**为什么**：历史变更多已完成归档，迁移成本高于收益，且迁移过程本身可能引入不一致。

## Risks / Trade-offs

**风险 1：签署清单退化为打勾游戏。** → 缓解：证据锚点为硬性要求（D2）；验证子代理先独立遍历后打假（D3 步骤 1）；锚点为空或指向不存在内容时该维度签署不成立。三重约束叠加。

**风险 2：单轮验证削弱「作者盲点」覆盖。** → 缓解：约束 3 已确立——独立验证本就由交叉审查承担，本次未削弱该环节；签署清单的证据锚点强制提供了可核对的具体位置。残余风险由交叉审查吸收。

**风险 3：审计降级后质量兜底变弱。** → 缓解：保留阻塞级兜底（D5 职责 4）；交叉审查环节不动；单轮验证的打假能力保证签署不被虚报。**若后续计时数据显示质量事故上升，第一条回滚项即恢复审计四维度评分。**

**风险 4：质量问题被推迟到后段暴露，回退成本上升。** → 缓解：自审的「独立发现」能力保留（D3 步骤 1 前置独立遍历）；交叉审查仍是设计阶段的完整质量关口；测试阶段保留定向重验。**验收信号：耗时遥测中「回退次数」不应较改造前上升。**

**风险 5：一次性改动 13 个既有能力 + 2 个新能力，审查易失效。** → 缓解：拆两个变更交付（本次为变更 1，缺陷快车道为变更 2），本次内部再分 4 波落地（见 Migration Plan），每波可独立验证。

**风险 6：命名混淆——「定向重验」被误读为已移除的 `recheck-round`。** → 缓解：约束 2 已在 design 与 specs 中显式区分；同时需要清理 `execution-repetition-mode`、`flexible-repetition-mode`、`inter-round-summary` 中悬空的「SHALL NOT append a recheck round」表述（其指向的能力已不存在）。

## Migration Plan

```

  ├─ convergence-driven-repetition  全量重写为单轮验证模型
  ├─ signed-checklist-verification  新能力
  └─ phase-time-telemetry           新能力

波次 2  Skill 层（实现层，引用波次 1）
  ├─ kflow-explore / kflow-design / kflow-prototype-design / kflow-plan

  ├─ kflow-{api-test,e2e-test,integration-test}/references/repetition.md
  ├─ kflow-audit/SKILL.md + references/
  └─ kflow-{explore,design}/SKILL.md 档位判定步骤

波次 3  模板层（签署清单与计时区的载体）
  ├─ functional-designs/part-NN.md、detailed-design.md、
  │    api-tests/part-NN.md、e2e-tests/part-NN.md、subchange-tasks.md
  ├─ change-status.md（耗时统计区 + 事件计时区）

波次 4  设计文档与示例同步
  ├─ docs/designs/core-mechanisms/03-status-and-tasks.md、07-agent-model.md
```

> 按 CLAUDE.md「提案创建要求」，`.claude/skills/` 中对应 SKILL.md 的同步任务须列入 tasks.md，标注「设计文档 → SKILL.md 同步」。

### 回滚策略

各波次可独立回滚。回滚优先级（若出现质量事故，按此顺序恢复）：

1. **恢复审计四维度评分**（`devflow-audit` 单能力回滚）——影响面最小，直接恢复质量把关
2. **恢复自审轮数上限**（如轻量 1 / 标准 2 / 完整 3）而非完整恢复收敛循环——保留单轮化的多数收益，同时恢复「发现即再审」能力
3. **完整回滚至 `converge-review-termination` 后的状态**——恢复收敛驱动模型

### 部署顺序约束

- 波次 1 必须先于波次 2 完成：技能层引用机制层的权威定义
- 波次 3 必须先于波次 4：模板是签署清单的载体，示例需与模板一致
- `scripts/sync-version.sh`、`scripts/sync-references.sh`、`scripts/validate-frontmatter.py` 在校验环节执行

## Open Questions

- 验证子代理的独立遍历阶段是否需要显式给出「审查对象清单」，还是由子代理自行确定范围？前者可复现性更强，后者更贴近交叉审查的独立语义。**可在实现时按首轮实测效果调整，不影响 specs 与任务拆分**（specs 已把「全量遍历证明」列为报告必填项，两种实现都能满足）。
- 「阶段内事件计时」的展开阈值（耗时占比 40% / 子代理轮次阈值）的具体数值，**可在收集前 3~5 个变更的真实数据后校准**，不影响 specs 的字段结构定义。
